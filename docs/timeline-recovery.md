# 기존 연표 찾기와 연결 재시도

2026-10-09 KST · `codex/timeline-recovery-entry` · 기준 main `d22ed42`

## 해결 범위

개편 뒤 연표는 로그인 계정별 localStorage와 `haedo_documents`에서 읽는다. 예전 `caeyeon_life_registry`, `caeyeon_life_doc_*`, `caeyeon_life_v2` 및 예전 서버 `charts`는 자동 귀속하지 않는다. 자료 화면의 IndexedDB 백업은 연표 백업과 다르다.

이번 변경은 기존 연표 연결을 찾기 쉽게 하고, 사본 생성 뒤 서버 저장 실패를 복구한다. **실제 채연 연표를 찾았거나 복원했다고 보고하는 작업이 아니다.** Cloud에서 사용자 기기의 저장소를 읽을 수 없고, 원본 기기·브라우저·주소는 아직 확인되지 않았다. 이전 공개 접근의 조회 결과가 비어 있었어도 권한 뒤의 자료가 없거나 삭제됐다는 뜻은 아니다.

## 화면과 동작

- `workspace.html`에서 현재 목록이 비었거나, 미연결 기기 연표·미완료 업로드·그대로 읽지 못한 원본이 있으면 목록 위에 복구 안내를 표시한다. 기존 연표 연결과 연표 JSON 백업 가져오기를 바로 열 수 있다.
- 해당 브라우저에서 원본을 찾지 못하면 연결 버튼은 숨기고 백업 가져오기와 다른 기기·주소·로그인 확인 안내를 남긴다. 원격 목록만 정상적으로 있으면 새 복구 안내를 숨기며 기존 백업 관리 메뉴는 유지한다.
- 기존 연결 모달의 원본 백업 다운로드와 본인 자료 확인 뒤 새 계정 사본을 만드는 절차를 유지한다. `legacySource`로 이미 만든 사본을 구분한다.
- 사본 생성 후 서버 저장이 실패하면 재시도는 같은 사본 ID 중 저장 미완료인 것만 업로드한다. 성공한 사본은 건너뛰고 원본을 덮어쓰거나 중복 사본을 만들지 않는다. 서버가 이미 저장했으나 응답만 유실된 경우에는 기존 충돌 검사를 유지하며 강제 덮어쓰지 않는다.
- 연결 중 중복 실행을 막고, 모달을 연 계정의 세대를 확인해 계정 전환·A→B→A 이후 이전 작업이 저장이나 성공 표시를 이어가지 않게 한다.

기존 HTML·CSS·네이티브 details·데이터 모듈을 재사용했다. 새 라이브러리·저장 형식·SQL·원격 `charts` 자동 읽기를 추가하지 않는다. 연표 값·계산·SVG·지도와 원문 자료 저장은 변경하지 않는다. 서비스워커 캐시는 v90이다.

## 검증

검증에는 익명 연표와 격리된 브라우저, 모의 인증/HTTP 및 실제 플랫폼 저장 모듈을 사용한다. 운영 데이터나 실제 Google 세션은 사용하지 않는다. [QA와 전후 화면](design-review/evidence/timeline-recovery/qa.md), [원본 결과](design-review/evidence/timeline-recovery/combined-report.json)에 최초 결함 재현과 수정 후 결과를 구분했다. 이전 재현은 연표 1개, 수정 후 실패 검사는 2개 중 부분 성공하는 경우로 강화했으므로 같은 자료 개수의 시각 비교라고 주장하지 않는다.

- `npm run check`: HTML 18·JavaScript 59·참조 271·PWA 통과. `npm test`: 398/398 통과.
- `platform-import-browser.cjs`: 파일 읽기 중 A→B/A→B→A 계정 전환과 다른 백업 형식 거절 3/3 통과.
- 새 `platform-recovery-browser.cjs`: 6/6 통과. 390·820·1440px 복구 진입, 실제 파일 선택/복원, 원격 목록 보존, 업로드 중 계정 전환을 확인했다. 두 연표 중 첫 사본 성공·둘째 실패 뒤 둘째 ID만 재시도하며 사본 2개·POST 총 3회였고 원본 바이트는 유지됐다.
- 독립 코드 검토에서 원본 보존·계정 전환·중복 사본의 중대한 결함을 발견하지 못했다. 기능 검증과 별도로 실제 3폭 화면 및 오류 모달을 검토했다. 콘솔·페이지 오류·예상하지 않은 외부 요청은 0이며 운영 쓰기는 수행하지 않았다.

화면 크기 모사는 실제 Apple 기기·IME·Files·Google 인증 검증이 아니다. 같은 브라우저의 `legacySource` 메타데이터로 재시도 중복을 막는 범위이며, 다른 기기에서 별도로 가져온 같은 원본을 전역 중복 제거하는 기능은 아니다. 기존 모델의 로컬 저장 용량 오류 뒤 미등록 사본 복구 범위도 변경하지 않는다.

## Local의 실제 자료 복구 순서

1. 마지막으로 채연 연표가 표시됐던 기기·브라우저·사이트 주소 및 로그인 계정을 확인한다. 사이트 데이터 삭제·초기화·샘플 덮어쓰기는 하지 않는다.
2. 같은 주소에서 기존 연표 연결 또는 연표 JSON 내보내기로 원본 사본을 먼저 보관한다. 공유 기기의 다른 사람 자료는 함께 가져오지 않는다. 여러 자료가 섞여 있으면 대상 연표만 담은 백업을 준비한다.
3. 기기 원본이 없고 예전 서버를 사용했다면 Local의 승인된 관리자 연결로 정확한 프로젝트와 대상 연표를 확인한다. 기존 `charts`의 구조·권한·소유자를 일괄 변경하지 말고 대상만 안전하게 백업한다. 키·비밀번호·개인 내용은 채팅·로그·저장소에 남기지 않는다.
4. 현재 본인 계정에서 해당 연표 JSON을 새 사본으로 가져온다. 사건·기간·생각·곡선 값·레이어·날짜·지도 자료와 사용자 확장 필드를 원본과 대조하고, 새로고침·동일 계정의 다른 기기에서 재확인한다. 원본은 확인 뒤에도 보존한다.
5. 앱 수정의 병합·배포는 Local에서 진행한다. 선행 통합 이후 캐시 번호가 겹쳤다면 통합 시 새 번호로 갱신한다. 이 작업에 운영 SQL 재설치는 필요 없다.
