# 기능별 작업 계약

`AGENTS.md`에서 옮긴 기능별 규칙이다(2026-11-02 이동). 수정할 기능의 항목만 읽는다.
`AGENTS.md`의 운영 체계·작업 방식·2026-11-01 소유자 지시·공통 안전 원칙이 이 문서보다 우선하며, 공통 안전 원칙(공개 홈의 서버 계정 검증, 저장 실패 때 입력 보존, 비공개 미리보기와 공개 구분, 색 검증, 없는 검사기 보고 금지)은 여기에 다시 적지 않는다. 2026-11-01 소유자 지시(모든 데이터 계정 자동 연동)가 이전의 '로컬 전용·명시 연결·초안 미전송·브라우저 보관' 조항을 대체한다. 2026-11-04 정리에서 그런 조항을 현재 동기화 경로([영역별 표](../design-review/account-sync-everywhere.md#영역별-동기화-경로))로 고쳤고, 정확 원문 버전·CAS·영수증·실패 복구 조항은 유지했다.

## 화면 흐름·자료·블로그

- 2026-10-24 자료 시작 속도: 서버 계정을 새로 확인한 뒤 같은 소유자·정확한 원격 연결·서버 ACK가 있는 자료 캐시를 먼저 연다. 최초 기기에서는 선택 공간의 원문·정확 구성을 준비한 뒤 화면을 열고 나머지 공간은 이어 받는다. 캐시 표시는 최신 동기화 완료가 아니며 서버를 원본으로 유지한다. 계정 전환·복구 공간 선택·미저장 입력·한글 조합·검색 초점·읽던 정확 판을 늦은 응답으로 바꾸지 않는다. Auth는 같은 계정/토큰/세대의 진행 중 검증을 공유한다. 2026-11-02 소유자 승인(W4)으로 끝난 검증은 한 작업 범위(`HaedoAuth.verificationScope()`, 현재 sync 엔진 한 작업) 안에서만 다시 쓴다. 조건은 모두 맞아야 한다: 같은 epoch, 그 뒤 Auth 이벤트·취소·pagehide/pageshow·다른 탭 세션 변경 없음, 저장 세션의 사용자와 access token이 같음, 로그아웃 표시 없음, bfcache에 머문 상태가 아님. 범위가 끝나면 버린다. 시간 기준 재사용은 없다. 서버 쪽 세션 철회(다른 기기 전체 로그아웃·계정 삭제 등)는 작업 단위로 감지한다. 한 작업 안의 읽기는 철회 뒤에도 그 작업이 끝날 때까지 이어질 수 있다. 서버 스냅샷 덮어쓰기(`life_sync_put`)·충돌 선택(`resolve`)·공개·삭제는 호출마다 서버에서 확인한다. 2026-11-03 첫 화면 지연 작업: 페이지 열기(shell 계정 확인 → 계정 자료 우선 초기화 → 첫 mount, `HaedoAuth.beginStartup()`)도 한 작업 범위로 본다. 그 안에서 끝난 확인을 다시 쓰는 곳은 shell 확인, AccountLibrary의 작업 시작 확인(우선 초기화와 범위 안에 시작한 `reconcile`), 빌린 클라이언트의 `getStartupUser()`(자료실 기능·카탈로그·메타 읽기, 구성 읽기, 원문 계정 읽기), W4 범위의 첫 확인뿐이다. 조건은 W4와 같고, 예외는 문서의 첫 `pageshow`(bfcache 복귀가 아님)뿐이다. 같은 epoch·세대에서 시작한 진행 중 확인은 함께 기다려 그 답을 쓴다. 쓰기, `life_library_open`, BlogSync 주기, `fresh` 확인은 계속 서버에서 확인한다. 화면을 보이거나 열기에 실패하면 범위를 끝내고, 10초(`STARTUP_LIMIT_MS`)가 지나면 다시 쓰지 않는다. 10초 상한은 열기 범위 자체에만 걸린다. 열기 안에서 시작한 W4 범위가 첫 확인으로 열기의 답을 받았다면, 그 W4 범위는 자기 작업이 끝날 때까지 W4 조건으로 그 답을 계속 쓴다. 2026-11-04 지연 추가 단축: 구성·자료 메타 엔진의 동기화 한 번(`run`, enable에서 이어진 경우 포함)은 원문 head를 한 번 확인한다. 같은 동기화의 뒤 확인은 저장된 원문 상태가 `synced`이고 필요한 `source_revision` 이상이면 서버를 다시 부르지 않는다. 아니면 이전처럼 head를 확인한다. 저장된 상태가 늦어 storage가 `composition_source_pending`으로 거절하면 head를 한 번 더 확인하고 다시 시도한다. compare·resolve 자체의 확인은 매번 서버에 묻는다. 계정 자료실의 배경 수신은 자료공간을 2개까지 동시에 받고 동기화한다. 첫 실패 뒤에는 새 공간을 시작하지 않고, 시작한 공간이 끝난 뒤 실패를 낸다. 오프라인 셸 설치는 화면 준비 뒤 시작한다. [속도·보존·측정 계약](../design-review/startup-performance.md)을 따른다.

아래 두 항목(10-26·10-24)의 메뉴 이름은 2026-11-02 개편 전 기준이다. 현재 위치는 '탐색·자료실·검색·연표'의 탐색 항목이 우선한다(홈·계획·도구 → 일정, 자료실 → 자료).

- 2026-10-26 목적별 동선 통합은 [구현·검수 계약](../design-review/purpose-workflow-implementation.md)을 따른다. 자료실 모아 보기와 전문 기능은 자료 메뉴, 글 공개·보관은 홈 메뉴와 정확 글 더보기, 뉴스 설정은 관심/언어/추천/출처·갱신/기록 관리, 파일은 자료·글 및 계획·연표로 배치한다. 정확 글 진입은 ID/revision을 전달하고 변경된 판은 자동 대체하지 않는다. 표시 이름 계획과 기존 tools 주소를 함께 보존한다.

- 2026-10-24 기능 흐름 통합: 홈의 블로그 메뉴는 글 관리·공개 표지·공개 페이지(2026-11-02부터 일정 목록의 블로그 메뉴는 글 관리만, 공개 표지·공개 페이지는 설정), 자료 메뉴는 다시 찾기·회고·책·네이버/Obsidian·원본 첨부·휴지통, 뉴스 설정은 관심/언어/추천을 담당한다. 도구에는 연간 계획·목표·습관과 상호 이동을 두고 공통 설정은 자료공간·계정 보관·형식별 백업/복원을 담당한다. 대표 영역은 `HaedoNavigation.getSectionForView`를 공유하고 과거 tools/manage view 주소도 정확 목적지로 연다. 열린 메뉴의 안정된 초점과 검색·폴더·기존 선택 자료·미저장 입력을 보존하며 메뉴 이동 때문에 저장/공개/연간계획 형식을 합치지 않는다. [기능 흐름 계약](../design-review/feature-flow-integration.md)이 아래 과거 메뉴 위치 설명보다 우선한다.

- 뉴스의 `discovery-reading*.js`는 같은 조건의 소수 목록과 직접 입력한 판단을 `discoveryReading` 계정·작업공간별 로컬 메타 CAS로 보관하고, 계정 문서 동기화(`account-docs-sync.js`)로 로그인한 모든 기기에 올린다(2026-11-01). 현재 비교는 한 개이며 새 공급·제목·정책으로 옛 응답을 옮기지 않는다. 읽기·도움·목록 선호는 좋아요·읽음 제외·개인 추천 opt-in을 자동 생성하지 않고 구성 백업·글·공개·기존 반응 사본에 넣지 않는다. 삭제 revision/tombstone·실패 입력·같은 세션 재적용·계정 복귀 보호를 유지한다. 번역은 현재 저장된 설정을 재확인하고 끄기는 즉시 반영한다. [사용·모델·보존](../design-review/discovery-quality.md)을 따른다.

- `full-backup*.js`는 설정 → 백업·복원 한 화면이다. 모두 받기 ZIP은 계정의 모든 자료공간을 기존 형식별 파일 그대로 담고 `manifest.json`(크기·SHA-256)·`README.txt`를 더한 묶음이며 하나의 형식으로 합치지 않는다. 계정 문서만 새 `haedo-account-documents-v1`이다. 한 항목이라도 읽지 못하면 전체 ZIP을 만들지 않고 재시도 또는 빠진 항목을 표시한 일부 ZIP만 허용한다. 복원은 검증(목록 밖/누락/해시/형식 불일치 거부) → 미리보기 → 고른 형식만 원래 공간마다 새 사본이며 기존 공간·로컬 계정 문서를 덮어쓰지 않고 정확 버전 참조를 최신으로 치환하지 않는다. 보관 범위·근거 파일과 연표·목표·습관·공개 표지는 각 전용 경로에서 복원한다. [계약·검수](../design-review/full-backup.md)를 따른다.
- 계정 문서(`account-docs-sync.js`, storage `ACCOUNT_DOC_*_PREFIXES`)에 새 접두사를 더하면 `ACCOUNT_DOC_SCHEMA`를 올리고 `tests/account-docs-sync.test.cjs`의 종류 표에 그 번호의 행을 더한다. 번호가 오르면 이전 번호로 동기화한 기기가 한 번 처음부터 다시 받아 건너뛴 문서를 적용한다.
- `preservation*.js`는 선택 저장 글·원본 사진·9칸과 필요한 정확한 원문 버전의 비공개 전용 파일 경로다. 기존 Core·PhotoPost·Blog.hydrate·SourceReference·NineBoard·fflate를 재사용한다. 참조한 원문 버전의 전체 본문 포함을 사전에 안내하고 개인 메모/발췌·미선택 자료·초안·서버 연결·공개 상태는 포함하지 않는다. 구조화 인용 sidecar는 이 전용 파일에서만 함께 이동하며 글별 서버 보관/기존 사진 ZIP 계약은 유지한다. 복원은 새 ID·명시 계정의 새 작업공간이며 원문/사진/근거/9칸/소유 정보를 단일 트랜잭션으로 설치한다. 계정 미연결 자료만 명시 사본화할 수 있고 다른 계정의 공간을 이메일로 추정해 가져오지 않는다. [계약·검수](../design-review/preservation-portability.md)를 따른다.

- 블로그 글별 보관·공개는 `blog-remote.js`/`blog-sync.js`/`blog-manager.js`와 `haedo_blog_private`를 사용한다. 2026-10-20 사용자 결정으로 기본 PhotoPostUI의 명시 글 저장은 본문·모든 원본 사진의 계정 서버 비공개 보관을 기본으로 한다. 2026-11-01 소유자 지시로 범위가 넓어져, 저장한 글과 초안(원본 사진·HEIC 보기용 판 포함)을 `blog-sync.js` 자동 주기로 계정에 올리고 다른 기기에서 자동으로 받는다. 글별 받기·보관 중지 선택은 두지 않는다. 로컬 저장 후 서버 실패는 글을 유지하고 별도 상태·재시도로 안내한다. 기존 원문·구성·공개 페이지 RPC에 사진을 끼워 넣지 않는다. 기본 사진 공개 선택은 0개다. 2026-11-02 소유자 결정으로 공개하는 사진은 모든 형식에서 촬영·위치 정보를 뺀 사본만 쓴다: JPEG·불투명 WebP → JPEG 0.9, PNG·투명 WebP → PNG, HEIC → 보기용 JPEG에서 다시 만든 JPEG, 움직이는 사진은 첫 장면(대화상자에 표시). 공개는 모든 형식에서 등록된 공개 사본뿐이다. 사본은 공개 검토 때 캔버스로 만들고 바이트 허용 목록으로 걸러 낸 뒤(Apple ImageIO의 Exif·iDOT 포함 제거) 미리보기에 그 바이트를 보이며, 비공개 버킷에 별도 객체로 등록한 뒤(`life_blog_publish_prepare_copy`) `life_blog_publish_copies`로 공개한다. 서버는 원본을 공개 미디어로 쓰지 않고 사진 Edge는 메타데이터가 남은 바이트를 내보내지 않는다. 이 공개 경로(`publish_copies`)도 AI 표시(`author`)를 공개 사본에서 지운다. 공개 대화상자는 미리보기와 내용 공개 동의만 둔다([설치·적용 순서](../life-tools-design/blog-installation.md#2026-11-02-공개-사진-사본-저장소-작성-운영-미적용)). 공개는 비공개 문서·공개본 이중 revision과 영속 작업 영수증으로 확인한다. 익명 `blog.html`은 Auth/개인 저장소를 열지 않고, 사진 Edge는 새 요청마다 현재 게시 상태를 검사한다. [모델·검수](../life-tools-design/blog-completion.md)와 [운영 설치](../life-tools-design/blog-installation.md)를 따른다. 인용 sidecar(`post-evidence`)는 계정 문서 동기화로 올리며, 원문/저장 글 9칸 참조의 정확 버전을 최신으로 치환하지 않는다.
- 블로그 자동 동기화 충돌(`blog-sync.js` `resolveConflict`, 2026-11-02 소유자 결정)은 저장한 글도 예외 없이 문서 작성 시각이 늦은 쪽을 남긴다. 서버 문서 시각은 서버 저장 시각으로 자르고, 같으면 서버 쪽을 남긴다. 진 쪽은 `복구 사본 · 제목`으로 남는다. 저장한 판이 나중 초안에 지면 서버가 저장 글을 초안으로 되돌리지 않으므로 저장한 글은 제자리에 그대로 두고, 나중 초안은 그 글의 수정 초안(정확한 판의 `replaces`)이 되며, 진 저장 판의 내용은 비공개 복구 사본 초안으로도 남는다. 공개 주소는 최신 글을 따라간다. 내용이 같으면 사본을 만들지 않는다. 공개 사본은 명시 동작으로만 바뀐다. 근거와 시험은 [계정 연동 규칙](../design-review/account-sync-everywhere.md#충돌복구-규칙)과 `tests/blog-sync-latest.test.cjs`다.

## 탐색·자료실·검색·연표

- 공통 탐색은 `assets/haedo-navigation.js`와 `assets/haedo-shell.css`를 재사용한다. 전역 표시 메뉴는 뉴스·일정·자료·설정이며 내부 ID news/schedule/records/manage를 사용한다(2026-11-02 소유자 결정). 이전 `home`·`tools`는 schedule의 별칭이며 `?section=home|tools`와 그 `&view=…` 주소는 일정의 같은 화면을 연다. `글쓰기`는 섹션이 아닌 별도 조작으로 모든 화면의 같은 자리(데스크톱 메뉴 맨 위, iPhone 오른쪽 위)에 두고, 새 글을 쓰는 동안 현재 화면 표시를 받는다. 뉴스는 기존 external-discovery 화면과 반응·언어 설정을 재사용한다. 일정의 목록(기존 home 모드)은 세 형식의 내 글과 글/초안/보관함·내 글 검색의 대표 읽기 투영이며, 같은 일정 안의 계획(기존 tools 모드)과 `보기 단위` 전환으로 오가고 목록의 탭·검색·스크롤을 되살린다. 원문과 저장한 문장·메모, 묶음·선택 자료 페이지는 자료에서 연다. 연표(`view=time`, `timeline.html`·`workspace.html`)는 일정에 속하고 계획 보기에서 연다. 프로필 편집은 단독 화면이며 작성/읽기/저장 후 일정 목록의 탭·검색·정확 항목 복귀를 보존한다. 발췌·활동을 별도 최상위 영역으로 되돌리지 않는다. 일정의 계획에는 연간 계획·목표·습관·연표(직접 주소·새로고침의 기본 복귀도 계획), 설정에는 계정·작업공간·동기화·각 형식의 백업과 공개 표지·공개 페이지를 둔다. 자료/연표 백업을 하나의 파일로 오해하게 표시하지 않는다. 브라우저 이력은 화면이 바뀌는 이동만 push하고 같은 화면의 갱신은 replace한다. 뒤로/앞으로는 기록된 화면을 앱 안 이동과 같은 저장 보호로 다시 열고, 글쓰기·글 읽기는 `blog=` 주소로 새로고침 뒤에도 같은 작업을 연다([기준](../design-review/subview-navigation.md#브라우저-이력과-새로고침-2026-11-02)).
- 영역별 최소 동작은 `assets/life/workbench*.js`와 `workbench.css`에 둔다. 묶음(기존 activities 경로)·내 페이지·회고는 계정/작업공간별 별도 revision 구성이다. `composition-*.js`의 구성 동기화(2026-11-01부터 `CompositionSync` 자동)는 원문 연결을 먼저 완료한 뒤 따로 시작하며 글쓰기/가져오기 초안·공개 사본을 포함하지 않는다. 원문 도착 기준·독립 CAS·영속 전송 영수증을 유지한다. 충돌 선택은 선택하지 않은 구성과 원문을 같은 트랜잭션의 복구 사본으로 남긴다. [운영 설치 상태](../life-tools-design/composition-installation.md)를 확인하며 SQL 파일 존재를 설치 완료로 간주하지 않는다. 자료·구성 백업은 원문과 구성을 한 트랜잭션에서 읽고 새 사본으로 복원한다. 원문 버전 참조를 최신 버전으로 대체하거나 그룹 편집을 페이지 사본에 자동 전파하지 않는다.
- 기록 검색은 기본 문자 그대로 찾기와 선택적 한글 음절 사이 수평공백 검색을 구분한다. 원문을 정규화하거나 UTF-16 위치를 추정하지 않는다. 40개씩 더보기는 화면 표시만 제한하며 전체 검색·선택·정확 버전 복귀를 유지한다. 변경 기준과 한계는 [검색 품질](../design-review/search-quality.md)을 따른다.
- 통합 검색은 `unified-search*.js`의 읽기 전용 투영이며 원문·저장한 페이지·컬렉션·저장한 9칸 구성의 정확한 항목을 연다. 9칸 항목은 구성/영역 ID와 정확 항목 스냅샷을 확인하고 변경된 결과를 다른 칸으로 대체하지 않는다. 작성 중 초안·미반영 입력·파일 후보·책·공개 서버 사본은 제외하고 검색어를 저장/전송하지 않는다. 계정·작업공간 변경 시 상태를 지우며 일부 읽기 실패를 전체 결과 없음으로 표시하지 않는다. [검색·왕복 계약](../design-review/unified-search.md)을 따른다.
- 이어 읽기는 `assets/life/reading-position.js`와 계정·작업공간별 로컬 메타데이터 한 개를 사용하며, 계정 문서 동기화로 로그인한 모든 기기에 올린다(2026-11-01). 원문 bundle·자료/구성 백업·공개 사본에 섞지 않는다. 실제 읽기 입력만 위치를 갱신하며 검색·발췌·명시적 이전 버전의 목적지를 우선한다. 위치 삭제는 revision을 남겨 늦은 저장을 차단한다. 세부 계약과 검증은 [읽기 위치](../design-review/reading-resume.md)를 따른다.
- 기록 재발견은 `assets/life/rediscovery.js`의 읽기 전용 근거 계산을 사용한다. 선택한 기준 버전·후보 최신 버전의 실제 주제/묶음/공통어만 설명하고 과거 버전의 근거를 승계하지 않는다. `workbench.discovery.excludedPairs`는 기준 원문별 제외이며 전역 분석 제외·원문 삭제가 아니다. 기존 v1은 필드 없이 수용하며 자료·구성 백업 복원에서 source ID를 재매핑한다. 자세한 한계는 `docs/design-review/rediscovery.md`를 따른다.
- 도구·로그인·연표 목록 화면은 `assets/platform.css`를 독립 표면으로 사용한다. `assets/app.css`/daisyUI는 연표 편집기에만 둔다. 공통 제목 행 `.haedo-page-heading`과 `assets/haedo-shell.css`를 재사용하고 중복 계정·복귀·상태 행을 만들지 않는다.
- 연표 등 기존 화면의 색은 `html[data-theme=spring]`의 daisy 변수다. 통합 홈과 자료 화면 `index.html`/`life.html`은 본문 중심의 `assets/life/ui.css` 토큰과 `assets/life/icons.js`를 사용한다. 자료 화면에 새 기능을 더할 때 이 공통 스타일과 승인한 A 인용 아이콘을 재사용한다. 독립 시안은 비교 이력이며 실제 앱 연결·공개 배포와 구분한다.
- `prepare()` → `render()` 흐름, 파생 `fut`와 저장 `future`의 구분, 월별 행복도 집계 우선순위를 보존한다. 표식 위치는 `curveYAt(x)` 기준이다.
- 예정에만 점선을 쓴다. 크로스헤어는 예외이며 `exportSvgText()`와 함께 확인한다. 기본 곡선 2px·축 1px·면 10% 워시를 유지한다.
- 표시 토글은 데이터와 통계를 바꾸지 않는다. DOM 버튼을 제거하면 연결된 핸들러도 함께 수정한다.

## 내 페이지 작성

- 내 페이지 안에서 글을 작성하고 대상을 붙여 저장하면 같은 피드에 나타난다. 컬렉션 선등록이나 별도 ‘페이지에 추가’를 필수 단계로 만들지 않는다. 기존 일반 첨부 글은 `page.posts`, 그 작성 초안은 계정·작업공간별 `page-drafts`이며 계정 문서 동기화로 올린다(2026-11-01). 기본 블로그 작성기의 별도 로컬 형식은 아래 사진 글 계약을 따른다. 초안을 구성 동기화/공개 payload에 섞지 않는다. 첨부는 종류·제목·창작자·출처만 보관하며 개인 메모/태그를 자동 복사하지 않는다. 공개 후보 선택은 게시 완료가 아니다. [저장·실패 복구·Local SQL/배포 계약](../design-review/page-composer.md)을 따른다.

## 사진 글

- 기본 PhotoPost 작성기의 자동 임시저장은 현재 계정·작업공간의 로컬 초안을 갱신한다(기기 간 전달은 위 BlogSync 자동 주기의 몫이다). 마지막 입력 뒤 300ms 유휴 또는 첫 미저장 변경 뒤 최대 2000ms를 기준으로 저장을 예약해 연속 입력으로 저장이 계속 밀리지 않게 한다. 이는 브라우저 타이머·비동기 저장의 완료 시한 보장이 아니다. `visibilitychange`의 hidden과 `pagehide`에서는 이미 모델에 받아들인 변경의 로컬 flush를 최선의 노력으로 시도하며 조합 중 입력·미반영 첨부·처리 중 사진을 강제로 확정하지 않는다. 실제 커밋한 초안은 같은 계정·작업공간의 초안 목록에서 이어 쓰고, BlogSync가 올린 뒤에는 다른 기기에서도 이어 쓴다. OS 강제 종료·discard·마지막 키 입력 보존을 보장하지 않는다. 명시 글 저장 후 비공개 서버 보관과 공개 선택은 기존 계약을 유지한다. [자동 임시저장 계약](../life-tools-design/blog-completion.md)을 따른다.

- `public-cover*.js`는 이미 소유 계정이 공개한 글·연재·9칸 형식 페이지의 URL만 고른 별도 읽기 표지다. 로컬 `public-cover:${workspaceId}` CAS(계정 문서 동기화로 기기 간 같음)와 기존 Share-v1/영속 영수증을 재사용하고 원본문·사진·개인 ID·다른 자료를 wire에 복사하지 않는다. 게시 전 실제 대상 공개 버전과 로컬 준비를 재확인하며 미확인 요청을 새 승인으로 덮지 않는다. 익명 표지는 Auth/개인 저장소 없이 현재 공개 대상만 제한 동시 조회하고 표지 head를 다시 확인한다. 철회/오류 행은 옛 제목·링크를 제거하며 표지와 대상의 공개·철회는 독립적이다. 안전한 공개 UUID와 형식만으로 원래 표지 항목에 복귀한다. [계약·검수](../design-review/public-cover.md)를 따른다.

- `material-writing*.js`의 ‘자료로 글쓰기’는 정확한 자료 버전·비공개 질문/메모·글에 채택할 개요를 계정/공간별 로컬 준비로 보관하고, 아래 `material-continuity-sync.js`가 모든 준비를 자동으로 계정에 올린다(2026-11-01). 완성 글은 기존 PhotoPost/SourceReference이며 질문·자료 메모·미채택 원문을 자동 복사하지 않는다. 글 생성 시 준비 CAS·문서·목록·근거·output 영수증을 같은 트랜잭션으로 저장하고 반복 인계는 같은 글을 연다. 저장 글 ID 교체 때 연결과 영수증도 원자 이동하며 이미 쓴 글을 준비 변경으로 덮지 않는다. 기존 공개/Preservation을 재사용하고 준비 자체를 구성 동기화·공개·근거 ZIP에 포함하지 않는다. [계약·실제 검수](../design-review/material-writing.md)를 따른다.

- `material-continuity*.js`는 자료로 글쓰기 준비의 비공개 기기 이동 경로다. 2026-11-01부터 계정의 모든 준비를 자동 송수신·삭제 전파하며(직접 고르기·동의 단계 없음), 질문·자료 메모·개요와 모든 선택 자료 및 완성 글 근거의 정확 원문 버전 전체를 함께 보낸다. 전체 원문 동기화를 선행하지 않고 첫 수신은 새 독립 공간, 재수신은 계정별 영수증의 같은 준비다. 연결된 글은 원격 CAS로 `null→writing claim→saved exact revision`을 확정하고 소유 기기의 원자 인계만 허용한다. 글·초안·사진은 이 경로가 아니라 BlogSync 자동 동기화로 옮긴다. 완성 글 원본은 BlogSync를 재사용하고, 정확한 글 revision·사진 바이트·인용 근거·준비 연결을 함께 검증·설치한다. 충돌은 선택하지 않은 쪽도 미연결 복구 공간에 보존한다. 일반 글별 서버 보관·공개·ZIP 형식은 유지한다. [계약·검수·설치 범위](../design-review/material-continuity.md)를 따른다.

- 내 페이지의 기본 `글쓰기`는 `PhotoPostUI.begin()`을 사용하며 사진 없는 새 글도 같은 로컬 형식으로 쓴다. 기존 첨부 글은 원래 작성기로 수정하고 새 대상 첨부 글은 접힌 호환 경로로 보존한다. 기본 작성기에도 기존 선택기·첨부 검증기·카드를 재사용한다. 첨부에는 개인 메모/태그를 복사하지 않는다. 공통 피드는 두 저장 형식을 변환하지 않고 수정일 순서로 합친다. 설명은 사진 아래의 안정된 DOM에서 편집하며 Quill embed/history API 결합을 버전 변경 시 재검수한다. [진입·피드·설명·저장 흐름](../design-review/blog-editor-flow.md)을 따른다.
- 사진 글은 `photo-post*.js`의 제한된 Delta와 원본 Blob을 계정/작업공간별 로컬 메타데이터에 보관한다. JPEG·PNG·WebP의 전달된 원본 바이트/해상도·순서·설명·대체 텍스트를 유지하며 자동 리사이즈/재압축을 하지 않는다. 공개용 사본(2026-11-02)은 공개할 때만 만드는 별도 파생물이며 문서·사진 ZIP·백업·보존 파일에 넣지 않고 원본을 바꾸지 않는다. 사진 첨부·초안 저장만으로 공개하지 않으며, 비공개 서버 보관은 위 BlogSync 자동 동기화 계약을 따른다. iPhone HEIC는 원본 바이트와 보기용 JPEG를 함께 보관한다(2026-11-01). 기존 `page.posts`/일반 초안·구성 동기화·공개 payload·JSON 백업과 섞지 않는다. 사진 포함 ZIP 새 사본 복원과 실제 해시/픽셀 검증, 저장 실패·두 탭 CAS·기존 작성기 입력 보호는 [사진 글 검수](../design-review/photo-post-editor.md)를 따른다. 미반영 입력/한글 조합/사진 처리 중 이동으로 입력을 버리지 않는다. Quill·fflate는 공식 vendor 배포와 LICENSE를 보존한다.

- 사진 글 v2는 검토한 첨부와 보관 상태를 추가한다. v1 읽기/ZIP을 유지하고 편집 때만 메모리에서 승격하며 v2→v1 저장은 차단한다. 초안·보관함은 별도 접힌 목록에 두고 보관 글을 일반 피드/검색에서 제외한다. 보관/복원도 문서·요약의 CAS 트랜잭션이며 원본을 삭제하지 않는다. HTML은 원본 바이트를 포함한 독립 읽기 파일이고 ZIP 새 초안 복원과 구분한다. [첨부·보관·읽기 파일 계약](../design-review/blog-writing-completion.md)을 따른다.
- 사진 글 첨부와 컬렉션의 연결(2026-11-02, [글과 취향 함께 저장](../design-review/taste-link.md)): 첨부 확인 폼의 `컬렉션에도 저장`은 새 첨부에서만 기본 켬이고(첨부 수정은 기본 끔) 글 저장과 별도로 컬렉션 CAS에 한 번만 추가한다(중복·개인 메모·태그 복사 없음). 저장 결과와 실패·다시 시도는 그 첨부 카드에 표시하고 글 상태줄·복구 버튼은 쓰지 않는다. 연결은 해제 가능한 연결이다. 첨부 수정·해제는 컬렉션 항목을 지우거나 바꾸지 않고, 원본을 합치지 않는다. 저장 결과가 열린 첨부 폼·한글 조합 입력을 다시 그리지 않는다. 컬렉션 항목의 `이 항목을 붙인 글`은 같은 계정·같은 자료공간의 사진 글만 읽는 비공개 화면이며 공개 화면에 내보내지 않는다. 글 첨부 형식 `{type,title,creator,url}`은 바꾸지 않고 기존 판정 규칙으로 연결을 계산한다. 화면 문구는 `취향`을 단정하지 않고 `컬렉션`이라고 쓴다.

## Obsidian 보관함

- `scripts/import-obsidian-vault.mjs`는 오프라인 원문 보존 어댑터다. 노트/보조 파일을 기존 v1 JSON으로 나누며 개인 원본·감사 목록·Git bundle은 앱 저장소 밖에만 둔다. 원문을 재작성하거나 추출 YAML을 사용자 발췌로 만들지 않는다. 내부 노트 연결은 `links.kind=obsidian_link`의 순서 있는 정확 버전 참조 두 개를 사용한다. 파일 경로를 유지하며 확정할 수 없는 연결은 자동 선택하지 않는다. [계약·검수](../design-review/obsidian-vault-integration.md)를 따른다.

- 검토 보고서는 기존 감사 참조 전체를 유지한 채 `review.html/json`으로 사용자 판단 대상과 첨부/외부 상대 주소/보조 파일 안내를 구분한다. 동일 파일명 후보는 제안이며 확정 연결하지 않는다. 상대 경로·자기 앵커의 목적지가 다르면 묶지 않고, 개인 보고서는 앱 저장소/CI 밖에 둔다.

- 연결 선택은 `assets/life/obsidian-decisions.js`의 Node/브라우저 공유 검증기를 사용한다. CLI의 이전 scripts/lib 경로는 wrapper로 유지한다. 원래 감사 해시·Git 출처·출발 토큰/정확 범위·양쪽 원문 해시를 확인하고, 명시 선택만 새 사본의 연결 정보에 반영한다. 기존 문서 연결의 위치 보완과 새 연결을 구분하며 중복/상충/변경된 계정 ID를 거부한다. 읽기용 보고서/최초 감사는 유지하고 `decisions.json`·`applications.json`에 결과를 따로 둔다. [검토 도구·CLI 계약](../design-review/obsidian-decisions.md)을 따른다.

- Obsidian ZIP은 `obsidian-package.js`의 고정 파일명/용량/원문 검증을 거친다. 계정에는 자료 JSON만 `installWorkspaces()`의 단일 트랜잭션으로 새 사본 복원하며 HTML·Git bundle·개인 감사/선택 이력을 설치하지 않는다. 저장 전 실패와 저장 후 목록 실패를 구분하며 원본 ZIP·기존 공간은 유지한다. [ZIP 통합 복원](../design-review/obsidian-package.md)을 따른다.
