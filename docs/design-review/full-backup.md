# 내 데이터 한 번에 지키기 (설정 → 백업·복원)

2026-11-01. 기준은 main `3ecc0f8`(haedo-v170)이고 이 변경의 SW 캐시는 `haedo-v171`이다. 마이그레이션·서버 쓰기·배포는 없다. 독립 검토(M1~M3, 보조 8건)를 반영해 목록 v2로 고쳤다. 첫 판(목록 v1) ZIP도 그대로 복원한다.

## 목표와 범위

소유자는 Mac·iPad·iPhone에서 한 계정을 쓴다. 이전에는 백업이 여러 화면에 흩어져 있었다.
- 설정: 자료·구성 백업, 내보내기·사본 복원, 컬렉션 백업·복구, 보관 범위·근거 파일
- 연표 목록: 연표·목표·습관 백업
- 글 편집기: 사진 글 ZIP·HTML
- 근거 ZIP

이번 변경으로 설정의 **백업·복원** 화면 하나에서 다음을 한다.

1. **모두 받기**: 계정의 자료공간을 형식별 파일로 나눠 ZIP 하나로 받는다. 형식이 없는 종류는 ZIP에 넣지 않고, 화면·README·manifest에 "넣지 않는 것"으로 따로 적는다.
2. **복원**: 모두 받기 ZIP이나 기존 형식별 파일을 골라 내용을 확인한 뒤, 고른 형식만 새 자료공간 사본으로 복원한다.
3. **형식별 파일**: 기존 형식별 화면을 그대로 연다.

ZIP 안의 파일은 모두 기존 형식이다. 예외는 계정 문서 파일 하나로, 내보내기 형식이 원래 없어서 `haedo-account-documents-v1`을 추가했다. ZIP은 하나의 형식이 아니다. 형식별 파일에 목록 파일 두 개(`README.txt`, `manifest.json`)를 더한 묶음이다. 화면과 README는 "모든 항목"이나 "전부"라고 쓰지 않는다. `complete`는 **읽기 실패가 없다**는 뜻일 뿐이다.

## ZIP 구성

| 경로 | 종류 | 형식(기존 코드) |
| --- | --- | --- |
| `workspaces/NN/library.json` | 자료·구성 | 폴더가 있으면 `life-material-library-backup-v1`, 없으면 `life-workbench-backup-v1`. 자료·구성 화면과 같은 선택이다 |
| `workspaces/NN/collection.json` | 컬렉션 | `life-collection-backup-v1` |
| `workspaces/NN/nine-boards.json` | 9칸 구성 | `life-nine-board-backup-v1/v2` |
| `workspaces/NN/photo-posts/<글ID>.zip` | 사진 글(초안·보관 포함 전부) | `life-photo-post-backup-v1/v2`. 원본 바이트 그대로이며 HEIC는 보기용 JPEG를 함께 담는다 |
| `workspaces/NN/blog-series/<모음ID>.zip` | 연재 모음 | `life-blog-series-package-v1`(`BlogSeriesPackage.pack`) |
| `workspaces/NN/material-writing.json` | 자료로 글쓰기 준비(질문·자료 메모·개요) | 저장소 값 형식 `life-material-writing-v1`(`MaterialWriting.validate`) |
| `workspaces/NN/naver-captures/<원문버전ID>.zip` | 네이버 원문 사진 | `haedo.naver.capture.v1`(`NaverMedia.pack`) |
| `account-documents.json` | 계정 설정·기록 문서 | `haedo-account-documents-v1`(신규) |
| `original-attachments/<파트ID>.zip` | 원본 첨부 | `haedo-private-originals-part-v1`(원본 첨부 서비스 `archive`) |
| `timeline-goals-habits.json` | 연표·목표·습관 | `haedo-platform-backup-v1`(`platform-store.backup()`과 같은 모양) |
| `README.txt`·`manifest.json` | 목록(ZIP의 **마지막** 두 항목) | `haedo-full-backup-v1`, `version: 2` |

JSON 파일은 들여쓰기 없이 쓴다. 기존 복원 파서는 모두 `JSON.parse`라서 그대로 읽는다.

`manifest.json`에 들어가는 항목:
- 공통: `format`, `version`, `createdAt`, `appVersion`(오프라인 캐시 이름), `complete`
- `workspaces`: 순번·로컬 ID·제목·복구 사본 여부
- `files`: 경로·종류·자료공간·형식·형식 버전·개수·바이트·SHA-256. 사진 글에는 글 ID·제목·저장/초안·보관 여부를 더한다.
- `missing`: `reason`으로 둘을 나눈다.
  - `read_failed`: 읽기 실패
  - `skipped`: 파일 경로 규칙에 맞지 않는 ID, 계정 공간 목록에 없는 공간의 계정 문서, 글이 없는 연재 모음
- `notIncluded`: `{kind, label, reason, whereToSave, count?}`
- 계정 ID와 프로젝트 주소는 넣지 않는다.

**넣지 않는 것(`notIncluded`)**: 백업 형식이 없거나 새 사본에 옮기면 안 되는 종류다.

| 종류 | 이유 | 보관 방법 |
| --- | --- | --- |
| 글쓰기 초안 (개수 표시) | 초안 전용 백업 형식이 없다 | 같은 계정 기기에 자동 동기화된다. TXT로도 받을 수 있다 |
| 가져오기 검토 초안 | 형식이 없다 | 검토를 마쳐 자료로 저장하면 자료·구성에 들어간다 |
| 자료 수정 초안 | 형식이 없다 | 수정을 저장하면 새 원문 버전으로 들어간다 |
| 공개 상태·서버 연결 | 새 사본은 공개하지 않는다 | 공개본은 원래 공개 페이지에 그대로 있다 |
| 원본 첨부 | 보관함을 열 수 없을 때만 해당한다 | 원본 첨부 화면에서 파트 ZIP을 받는다 |

**보관 범위·근거 파일은 모두 받기에 넣지 않는다.** 직접 고른 글 20편·256 MiB까지만 담는 선택 형식이고, 내용은 위 파일들과 겹치기 때문이다. 복원 화면은 이 파일을 알아보고 기존 `Preservation.read/restore`로 복원한다.

연표·목표·습관은 이 기기의 `localStorage`에 내려받은 계정 사본이다. 연표 목록을 이 기기에서 연 적이 없으면 0개일 수 있다. 원본 첨부는 이 계정 기기에 보관된 파트만 목록에 올린다(`list({cached: true})`, 카탈로그 요청 없음). 내용이 기기에 없는 파트는 `archive`가 계정에서 받아 온다.

## 받기 동작과 메모리

- 화면을 열면 형식별 개수, 자료공간 수, 예상 크기, "넣지 않는 것"을 먼저 보여 준다(`#fbInventory`, `#fbNotIncluded`). 사진은 저장된 Blob 크기를 더해 계산하고 바이트는 읽지 않는다. 화면을 떠나면 계산을 멈춘다.
- **한 번에 끝까지 쓴다.** 항목마다 다음 순서로 처리한다.
  1. 읽는다.
  2. SHA-256을 계산한다.
  3. 열린 ZIP(fflate `Zip`/`ZipPassThrough`, 무압축)에 쓴다.
  4. 그 항목의 Blob 참조를 버리고 다음 항목으로 간다.
  - 결과 표에는 크기·해시·개수만 남는다.
  - 첫 판은 모든 글 ZIP을 모은 뒤 다시 복사해서, 최대 사용량이 약 2배였다.
- 실패한 항목이 있으면 ZIP을 열어 둔 채 마무리하지 않는다.
  - **실패한 항목 다시 시도**: 실패한 항목만 다시 읽어 뒤에 붙인다.
  - **빠진 항목을 표시한 일부 ZIP 받기**: 이때 마무리한다. `complete: false`, `missing`, 파일명 `-partial`, README의 "[읽기 실패]"가 붙는다.
- `README.txt`와 `manifest.json`은 실제로 쓴 내용을 기록해야 하므로 맨 끝에 쓴다. 복원은 ZIP의 중앙 디렉터리로 찾으므로 위치와 상관없다. 첫 판처럼 맨 앞에 있는 ZIP도 읽는다.
- **메모리의 실제 특성**: 한 번에 메모리에 올리는 입력은 항목 하나다. 사진 글 하나는 최대 약 256 MiB이고, 기존 `PhotoPost.backup`이 그 글의 ZIP을 메모리에서 만든다. 출력 ZIP은 8 MiB Blob 조각으로 쌓이고, 받기를 누를 때까지 브라우저가 보관한다. 브라우저가 이 조각을 디스크로 내리지 않으면(iOS WebKit 포함) 출력 전체 크기만큼 메모리를 쓴다. 그래서 다음처럼 막는다.
  - 예상 크기가 1 GiB를 넘으면 경고한다.
  - ZIP32 한계인 3.5 GiB를 넘으면 모두 받기를 막고 형식별 파일을 안내한다.
  - 파일을 크기별 여러 조각으로 나눠 받는 기능은 아직 없다.
- **크기 한도는 쓸 때와 열 때 같은 기준이다.** 기준은 파일 전체 크기다(로컬 헤더·데이터 서술자·중앙 디렉터리·끝 레코드·README·manifest 포함). 쓰는 쪽은 항목마다 이 값을 미리 계산하고, 마무리 뒤 실제 크기로 다시 확인한다. 그래서 만들 수 있는 ZIP은 항상 열 수 있다. JSON 한 파일의 한도는 쓰기·열기 모두 512 MiB다. 큰 자료공간을 64 MiB에서 막지 않도록 올렸다.
- 받은 뒤에는 다음을 다시 보여 준다(`#fbDownloadResult`, `#fbNotIncludedAfter`): 형식별 파일 수·개수·형식 버전, "하나의 형식이 아닙니다" 안내, 담지 않은 항목, 넣지 않는 것.
- 다운로드 URL은 다음 다운로드, 화면 정리, 10분 뒤 중 먼저 오는 때에 해제한다.

## 복원 규칙

1. **파일 판별**: ZIP과 JSON을 받는다.
   - ZIP은 중앙 디렉터리를 Blob 조각으로 읽는다. 무압축 항목만 받고, 중복·상위 경로를 거부한다. 로컬 헤더가 중앙 디렉터리와 맞는지 확인한다.
   - ZIP 종류는 `manifest.json`(연재 모음은 `series.json`)의 형식으로 정한다. 전체 백업, 사진 글, 연재 모음, 네이버 원문, 근거 ZIP을 구분한다.
   - JSON은 `format`으로 정한다. 자료, 자료·구성, 컬렉션, 9칸, 글쓰기 준비, 계정 문서, 연표·목표·습관, 연간 계획을 구분한다.
2. **전체 백업 검증**: 미리보기 전에 확인하고, 하나라도 맞지 않으면 아무것도 쓰지 않는다.
   - `manifest.json` CRC
   - 버전은 1·2만 받는다. 모르는 버전·형식은 `unsupported_version`.
   - 목록 밖 파일이나 빠진 파일은 `tampered`
   - 각 파일의 크기·SHA-256. 다르면 `tampered`로 거부하고 경로를 표시한다.
   - JSON 내부 형식, ZIP 종류별 형식, 경로·종류·자료공간 일치
   - `complete`와 읽기 실패 목록이 맞는지
   - 크기는 3.5 GiB(ZIP), 512 MiB(JSON)까지
3. **미리보기**
   - 형식·목록 버전·생성 시각·앱 버전·파일 수와 넣지 않는 것을 보여 준다. 첫 판 ZIP이면 새 종류가 없다고 알린다.
   - 형식별 체크박스에 개수·자료공간 수·파일 형식/버전을 붙인다.
   - 연표·목표·습관은 체크박스 없이 "이 파일만 받기"와 "연표 목록에서 복원" 링크만 둔다.
4. **새 사본만 만든다**: 원래 자료공간마다 새 자료공간 하나를 만든다. 형식마다 기존 단일 트랜잭션 함수를 쓴다.

   | 종류 | 복원 방법 |
   | --- | --- |
   | 자료·구성 | `restoreBackup` 후 `installLibraryCopy`·`installWorkbenchCopy`·`installWorkspace`. 고르지 않았으면 같은 제목의 빈 공간을 만든다 |
   | 컬렉션 | `appendBackup` 후 `saveCollection` |
   | 사진 글 | `PhotoPost.readBackup`으로 검증한다. 브라우저에서는 디코딩 크기도 검사한다. 그다음 `savePhotoPost`, 근거가 있으면 `savePhotoPostWithEvidence` |
   | 9칸 | `copies` 후 `saveNineBoardCopy` |
   | 연재 모음 | `BlogSeriesPackage.read` 후 `installBlogSeriesCopy` |
   | 글쓰기 준비 | 정확한 원문이 있어야 하므로 자료·구성을 함께 복원할 때만 한다. 준비마다 새 ID를 주고 글 연결은 비운다(`saveMaterialWriting`의 새 준비 규칙). 연결돼 있던 개수는 결과에 적는다 |
   | 네이버 원문 사진 | 기존 원문 사진 복원과 같이 `NaverMedia.read/copy` 후 `installNaverCaptureCopy`. **원문마다 새 자료공간이 하나씩 생긴다.** 자료·구성 사본에 붙이는 기존 함수는 계정 수집 영수증이 있어야 해서 쓸 수 없다 |
   | 원본 첨부 | 원본 첨부 서비스의 `prepare/install`로 계정 보관함에 파트를 추가한다 |
   | 계정 문서 | `applyAccountDoc(key, {expectedHash: null})`. 로컬에 없을 때만 쓴다 |
5. **정확 버전 연결**
   - `Core.restoreBackup`은 순서를 유지하므로 순번으로 옛 ID→새 ID 표를 만든다. 같은 묶음 안 참조만 옮긴다. 대상은 9칸 근거, 글 인용 근거, 글쓰기 준비, 계정 문서다.
   - 내용·해시는 바꾸지 않고 최신 버전으로 치환하지 않는다.
   - 자료·구성 없이 복원한 9칸은 옛 원문이나 함께 오지 않은 글을 가리키는 근거를 지우고, 그 개수를 결과에 적는다. 사진 글 인용 근거와 같은 처리다. 선택 이유·제목은 남긴다.
6. **글 상태**: 전체 백업에서는 manifest의 저장/초안·보관 상태로 복원한다. 사진 글 ZIP 하나만 고르면 편집기와 같이 새 초안이 된다.
7. **복원하지 않는 것**
   - 공개 표지 설정
   - 연표·목표·습관
   - 연간 계획 전용 파일
8. **같은 백업을 다시 복원하는 경우**
   - 복원을 마치면 그 파일의 복원 버튼은 다시 켜지지 않는다.
   - 이 계정의 기기에는 영수증을 남긴다. 키는 manifest SHA-256(단일 JSON은 파일 SHA-256)이고, 생성 시각과 복원 시각을 함께 둔다.
   - 같은 백업을 다시 열면 "이미 복원했습니다"와 날짜를 보여 준다. "같은 백업으로 새 사본을 하나 더 만듭니다"를 체크해야만 버튼이 켜진다.
   - 영수증은 기기의 `localStorage`에 둔다(최근 50개). 다른 기기에서 연 같은 파일은 경고하지 않는다.
9. **실패 처리**
   - 자료·구성이 실패하면 그 공간의 나머지 형식은 "건너뜀"으로 둔다.
   - 계정 문서 중 일부가 거부되면 그 묶음을 "실패"로 표시하고 개수를 적는다. 다시 복원하면 거부된 문서만 다시 쓴다.
   - "실패한 항목 다시 복원"은 같은 새 사본에 실패·건너뜀 항목만 다시 넣는다.
10. **복원 뒤 상태**: 설치하면 새 공간이 활성이 되므로, 끝나면 원래 공간을 다시 활성으로 둔다. 결과의 "… 열기"로 새 공간을 연다. 새 사본은 계정 자동 연동으로 다른 기기에 동기화되고, 공개는 하지 않는다.

## 진행 중 이동

- 받기·확인·복원 중에 앱 안에서 이동하면(메뉴, 돌아가기, 공간 전환 등) 확인 창이 뜬다. 다른 화면의 `flush` 가드와 같은 방식이다.
  - 취소하면 이동을 막고 "끝난 뒤 이동해 주세요"를 표시한다.
  - 이동을 고르면 남은 단계를 멈춘다.
  - 브라우저를 닫는 경우는 기존 `beforeunload`가 막는다.
- 복원이 중간에 멈추면 이미 만든 새 자료공간 이름과 개수를 알리고 영수증을 남긴다. 다시 백업·복원 화면을 열면 그 안내가 복원 칸 위에 남아 있다(`#fbInterrupted`).

## 메뉴와 기존 주소

- 설정 목록의 파일 항목 여섯 개를 **백업·복원** 하나로 바꿨다(`#lifeBackupOpen`, view `backup`, 대표 영역 manage).
- 백업·복원 화면의 "형식별 파일"에 기존 행이 같은 이름·ID로 있다. 그 행에서 연 화면은 백업·복원으로 돌아오고, 누른 행에 다시 초점을 둔다.
- 기존 직접 주소 `view=transfer|workbench-backup|preservation`은 정확한 화면을 그대로 연다. 뒤로 가면 백업·복원의 해당 행으로 간다.
- `section=manage#lifeBackupMaterials|Planning|Choices`는 백업·복원을 연다.

## 접근성·화면

- 구조: 섹션은 h2로 나눈다. 형식 선택은 `fieldset/legend`와 44px 체크박스 라벨이다. 진행 막대에는 `aria-label`, 상태 줄에는 `role=status`를 단다. 결과·미리보기가 나오면 제목에 초점을 둔다.

## 미검증·한계

- 실제 Apple 기기에서 큰 ZIP의 메모리와 파일 저장(공유 시트)은 확인하지 않았다. 출력 ZIP은 받기 전까지 브라우저 메모리에 남을 수 있다. 크기별 분할은 없다.
- 네이버 원문 사진은 원문마다 별도 새 공간으로 복원되어, 같은 원문이 자료·구성 사본에도 있을 수 있다.
- 글쓰기 준비와 글 사이의 연결은 복원하지 않는다.
- 원본 첨부 파트는 같은 계정에 다시 복원하면 하나 더 생긴다. 다시 열기 경고가 이를 알린다.
- 연표·목표·습관은 이 기기 사본 기준이다.
- 진행 중 이동 확인 창은 코드 경로만 있고 브라우저 자동 검사는 하지 않았다.
- 9칸의 저장 글 참조는 새 글 ID로 옮기지만 revision은 새 사본 기준이다.
- 실제 Supabase 동기화는 FakeCloud로만 확인했다.
