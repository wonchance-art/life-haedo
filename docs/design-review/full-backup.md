# 내 데이터 한 번에 지키기 (설정 → 백업·복원)

2026-11-01. 기준은 main `3ecc0f8`(haedo-v170)이고 이 변경의 SW 캐시는 `haedo-v171`이다. 마이그레이션·서버 쓰기·배포는 없다. 독립 검토 두 차례를 반영했다. 1차(M1~M3, 보조 8건)로 목록을 v2로 고쳤고, 2차에서는 N1과 보조 7건을 고쳤다. 첫 판(목록 v1) ZIP도 그대로 복원한다.

## 목표와 범위

소유자는 Mac·iPad·iPhone에서 한 계정을 쓴다. 이전에는 백업이 여러 화면에 흩어져 있었다.
- 설정: 자료·구성 백업, 내보내기·사본 복원, 컬렉션 백업·복구, 보관 범위·근거 파일
- 연표 목록: 연표·목표·습관 백업
- 글 편집기: 사진 글 ZIP·HTML
- 근거 ZIP

이번 변경으로 설정의 **백업·복원** 화면 하나에서 다음을 한다.

1. **모두 받기**: 계정의 자료공간을 형식별 파일로 나눠 ZIP 하나로 받는다. 형식이 없는 종류는 ZIP에 넣지 않고, 화면·README·manifest에 "넣지 않는 것"으로 따로 적는다.
2. **복원**: 모두 받기 ZIP이나 기존 형식별 파일을 골라 내용을 확인한 뒤, 고른 형식만 새 자료공간 사본으로 복원한다.
3. **형식별 파일**: 기존 형식별 화면을 그대로 연다.

ZIP 안의 파일은 모두 기존 형식이다. 예외는 계정 문서 파일 하나로, 내보내기 형식이 원래 없어서 `haedo-account-documents-v1`을 추가했다. ZIP은 하나의 형식이 아니다. 형식별 파일에 목록 파일 두 개(`README.txt`, `manifest.json`)를 더한 묶음이다. 화면과 README는 "모든 항목"이나 "전부"라고 쓰지 않는다. `complete`는 **읽기 실패가 없다**는 뜻일 뿐이다.

## ZIP 구성

| 경로 | 종류 | 형식(기존 코드) |
| --- | --- | --- |
| `workspaces/NN/library.json` | 자료·구성 | 폴더가 있으면 `life-material-library-backup-v1`, 없으면 `life-workbench-backup-v1`. 자료·구성 화면과 같은 선택이다 |
| `workspaces/NN/collection.json` | 컬렉션 | `life-collection-backup-v1` |
| `workspaces/NN/nine-boards.json` | 9칸 구성 | `life-nine-board-backup-v1/v2` |
| `workspaces/NN/photo-posts/<글ID>.zip` | 사진 글(초안·보관 포함 전부) | `life-photo-post-backup-v1/v2`, `life-post-md-backup-v1`. 원본 바이트 그대로이며 HEIC는 보기용 JPEG를 함께 담는다. 2026-11-11부터 글의 `createdAt`·`updatedAt`도 담는다(아래 "글의 작성·수정 시각") |
| `workspaces/NN/blog-series/<모음ID>.zip` | 연재 모음 | `life-blog-series-package-v1`(`BlogSeriesPackage.pack`) |
| `workspaces/NN/material-writing.json` | 자료로 글쓰기 준비(질문·자료 메모·개요) | 저장소 값 형식 `life-material-writing-v1`(`MaterialWriting.validate`) |
| `workspaces/NN/naver-captures/<원문버전ID>.zip` | 네이버 원문 사진 | `haedo.naver.capture.v1`(`NaverMedia.pack`) |
| `account-documents.json` | 계정 설정·기록 문서 | `haedo-account-documents-v1`(신규) |
| `original-attachments/<파트ID>.zip` | 원본 첨부 | `haedo-private-originals-part-v1`(원본 첨부 서비스 `archive`) |
| `timeline-goals-habits.json` | 연표·목표·습관 | `haedo-platform-backup-v1`(`platform-store.backup()`과 같은 모양) |
| `README.txt`·`manifest.json` | 목록(ZIP의 **마지막** 두 항목) | `haedo-full-backup-v1`, `version: 3` |

JSON 파일은 들여쓰기 없이 쓴다. 기존 복원 파서는 모두 `JSON.parse`라서 그대로 읽는다.

`manifest.json`에 들어가는 항목:
- 공통: `format`, `version`, `createdAt`, `appVersion`(오프라인 캐시 이름), `complete`
- `workspaces`: 순번·로컬 ID·제목·복구 사본 여부
- `files`: 경로·종류·자료공간·형식·형식 버전·개수·바이트·SHA-256. 사진 글에는 글 ID·제목·저장/초안·보관 여부를 더한다.
- `missing`: `reason`으로 둘을 나눈다.
  - `read_failed`: 읽기 실패
  - `skipped`: 파일 경로 규칙에 맞지 않는 ID, 계정 공간 목록에 없는 공간의 계정 문서, 글이 없는 연재 모음
- `notIncluded`: `{kind, label, reason, whereToSave, count?}`
- 계정 ID와 프로젝트 주소는 넣지 않는다.

**넣지 않는 것(`notIncluded`)**: 백업 형식이 없거나 새 사본에 옮기면 안 되는 종류다.

| 종류 | 이유 | 보관 방법 |
| --- | --- | --- |
| 글쓰기 초안 (개수 표시) | 초안 전용 백업 형식이 없다 | 같은 계정 기기에 자동 동기화된다. TXT로도 받을 수 있다 |
| 가져오기 검토 초안 | 형식이 없다 | 검토를 마쳐 자료로 저장하면 자료·구성에 들어간다 |
| 자료 수정 초안 | 형식이 없다 | 수정을 저장하면 새 원문 버전으로 들어간다 |
| 공개 상태·서버 연결 | 새 사본은 공개하지 않는다 | 공개본은 원래 공개 페이지에 그대로 있다 |
| 원본 첨부 | 보관함을 열 수 없을 때만 해당한다 | 원본 첨부 화면에서 파트 ZIP을 받는다 |
| 서버에만 있는 원본 첨부 파트 | 이 기기에 내려받은 파트만 담고, 서버에만 있는 파트는 확인하지 않는다 | 원본 첨부를 열어 목록을 받은 뒤 다시 받거나, 그 화면에서 파트 ZIP을 받는다 |
| 설정 충돌 복구 사본 (개수 표시) | 동기화 충돌 때 남긴 이전 설정 사본은 형식이 없다 | 이 기기의 로컬 기록에 문서마다 최근 5개까지 남는다 |

**보관 범위·근거 파일은 모두 받기에 넣지 않는다.** 직접 고른 글 20편·256 MiB까지만 담는 선택 형식이고, 내용은 위 파일들과 겹치기 때문이다. 복원 화면은 이 파일을 알아보고 기존 `Preservation.read/restore`로 복원한다.

연표·목표·습관은 이 기기의 `localStorage`에 내려받은 계정 사본이다. 연표 목록을 이 기기에서 연 적이 없으면 0개일 수 있다. 원본 첨부는 이 기기에 목록이 있는 파트만 담는다(`list({cached: true})`, 카탈로그 요청 없음). 서버에만 있는 파트는 확인하지 않았다는 사실을 "넣지 않는 것"에 항상 적는다. 목록에 있어도 내용이 기기에 없는 파트는 `archive`가 계정에서 받아 온다. 네이버 원문 사진은 저장된 행에서 개수만 센다(`storage.listNaverCaptures`). 그래서 화면을 열 때 사진을 검증·디코딩하지 않고, 각 사진은 파일로 쓸 때 검증한다.

## 받기 동작과 메모리

- 화면을 열면 형식별 개수, 자료공간 수, 예상 크기, "넣지 않는 것"을 먼저 보여 준다(`#fbInventory`, `#fbNotIncluded`). 사진은 저장된 Blob 크기를 더해 계산하고 바이트는 읽지 않는다. 화면을 떠나면 계산을 멈춘다.
- **한 번에 끝까지 쓴다.** 항목마다 다음 순서로 처리한다.
  1. 읽는다.
  2. SHA-256을 계산한다.
  3. 열린 ZIP(fflate `Zip`/`ZipPassThrough`, 무압축)에 쓴다.
  4. 그 항목의 Blob 참조를 버리고 다음 항목으로 간다.
  - 결과 표에는 크기·해시·개수만 남는다.
  - 첫 판은 모든 글 ZIP을 모은 뒤 다시 복사해서, 최대 사용량이 약 2배였다.
- 각 항목의 크기·해시·형식·버전·개수를 모두 계산한 뒤에 ZIP에 쓴다. 쓴 다음에는 실패할 단계가 없으므로, 실패로 표시된 항목이 ZIP에 남거나 다시 시도에서 두 번 들어가지 않는다.
- 목록 읽기(사진 글·연재 모음·네이버 원문·원본 첨부)가 실패하면 그 목록 하나가 실패 항목이 된다. 다시 시도하면 목록을 다시 읽고 그 안의 항목을 뒤에 붙인다.
- 실패한 항목이 있으면 ZIP을 열어 둔 채 마무리하지 않는다.
  - **실패한 항목 다시 시도**: 실패한 항목만 다시 읽어 뒤에 붙인다.
  - **빠진 항목을 표시한 일부 ZIP 받기**: 이때 마무리한다. `complete: false`, `missing`, 파일명 `-partial`, README의 "[읽기 실패]"가 붙는다.
- `README.txt`와 `manifest.json`은 실제로 쓴 내용을 기록해야 하므로 맨 끝에 쓴다. 복원은 ZIP의 중앙 디렉터리로 찾으므로 위치와 상관없다. 첫 판처럼 맨 앞에 있는 ZIP도 읽는다.
- **메모리의 실제 특성**: 한 번에 메모리에 올리는 입력은 항목 하나다. 사진 글 하나는 최대 약 256 MiB이고, 기존 `PhotoPost.backup`이 그 글의 ZIP을 메모리에서 만든다. 출력 ZIP은 8 MiB Blob 조각으로 쌓이고, 받기를 누를 때까지 브라우저가 보관한다. 브라우저가 이 조각을 디스크로 내리지 않으면(iOS WebKit 포함) 출력 전체 크기만큼 메모리를 쓴다. 그래서 다음처럼 막는다.
  - 예상 크기가 1 GiB를 넘으면 경고한다.
  - ZIP32 한계인 3.5 GiB를 넘으면 모두 받기를 막고 형식별 파일을 안내한다.
  - 파일을 크기별 여러 조각으로 나눠 받는 기능은 아직 없다.
- **크기 한도는 쓸 때와 열 때 같은 기준이다.** 기준은 파일 전체 크기다(로컬 헤더·데이터 서술자·중앙 디렉터리·끝 레코드·README·manifest 포함). 쓰는 쪽은 항목마다 이 값을 미리 계산하고, 마무리 뒤 실제 크기로 다시 확인한다. 그래서 만들 수 있는 ZIP은 항상 열 수 있다. JSON 한 파일의 한도는 쓰기·열기 모두 512 MiB다. 큰 자료공간을 64 MiB에서 막지 않도록 올렸다.
- 받은 뒤에는 다음을 다시 보여 준다(`#fbDownloadResult`, `#fbNotIncludedAfter`): 형식별 파일 수·개수·형식 버전, "하나의 형식이 아닙니다" 안내, 담지 않은 항목, 넣지 않는 것.
- 다운로드 URL은 다음 다운로드, 화면 정리, 10분 뒤 중 먼저 오는 때에 해제한다.

## 복원 규칙

1. **파일 판별**: ZIP과 JSON을 받는다.
   - ZIP은 중앙 디렉터리를 Blob 조각으로 읽는다. 무압축 항목만 받고, 중복·상위 경로를 거부한다. 로컬 헤더가 중앙 디렉터리와 맞는지 확인한다.
   - ZIP 종류는 `manifest.json`(연재 모음은 `series.json`)의 형식으로 정한다. 전체 백업, 사진 글, 연재 모음, 네이버 원문, 근거 ZIP을 구분한다.
   - JSON은 `format`으로 정한다. 자료, 자료·구성, 컬렉션, 9칸, 글쓰기 준비, 계정 문서, 연표·목표·습관, 연간 계획을 구분한다.
2. **전체 백업 검증**: 미리보기 전에 확인하고, 하나라도 맞지 않으면 아무것도 쓰지 않는다.
   - `manifest.json` CRC
   - 버전은 1·2·3만 받는다. 모르는 버전·형식은 `unsupported_version`.
   - 목록 밖 파일이나 빠진 파일은 `tampered`
   - 각 파일의 크기·SHA-256. 다르면 `tampered`로 거부하고 경로를 표시한다.
   - JSON 내부 형식, ZIP 종류별 형식, 경로·종류·자료공간 일치
   - `complete`와 읽기 실패 목록이 맞는지
   - 크기는 3.5 GiB(ZIP), 512 MiB(JSON)까지
3. **미리보기**
   - 형식·목록 버전·생성 시각·앱 버전·파일 수와 넣지 않는 것을 보여 준다. 첫 판 ZIP이면 새 종류가 없다고 알린다.
   - 형식별 체크박스에 개수·자료공간 수·파일 형식/버전을 붙인다.
   - 연표·목표·습관은 체크박스 없이 "이 파일만 받기"와 "연표 목록에서 복원" 링크만 둔다.
4. **새 사본만 만든다**: 원래 자료공간마다 새 자료공간 하나를 만든다. 형식마다 기존 단일 트랜잭션 함수를 쓴다.

   | 종류 | 복원 방법 |
   | --- | --- |
   | 자료·구성 | `restoreBackup` 후 `installLibraryCopy`·`installWorkbenchCopy`·`installWorkspace`. 고르지 않았으면 같은 제목의 빈 공간을 만든다 |
   | 컬렉션 | `appendBackup` 후 `saveCollection` |
   | 사진 글 | `PhotoPost.readBackup`으로 검증한다. 브라우저에서는 디코딩 크기도 검사한다. 그다음 `savePhotoPost`, 근거가 있으면 `savePhotoPostWithEvidence` |
   | 9칸 | `copies` 후 `saveNineBoardCopy` |
   | 연재 모음 | `BlogSeriesPackage.read` 후 `installBlogSeriesCopy` |
   | 글쓰기 준비 | 정확한 원문이 있어야 하므로 자료·구성을 함께 복원할 때만 한다. 준비마다 새 ID를 주고 글 연결은 비운다(`saveMaterialWriting`의 새 준비 규칙). 연결돼 있던 개수는 결과에 적는다 |
   | 네이버 원문 사진 | 백업 ZIP에서: 같은 실행에서 복원한 자료·구성 사본의 **같은 원문 버전**에 붙인다. 옛 ID→새 ID 표로 버전을 찾고, 새 저장소 함수 `attachNaverCaptureCopy`가 `naver-capture:${새 공간}:${새 버전}` 키 하나만 쓴다. 이 함수는 `NaverMedia.checkTarget`으로 본문·해시·글 주소를 다시 맞추고, 이미 사진이 있으면 덮어쓰지 않는다. 계정 수집 영수증이 필요한 기존 `installNaverCaptureForVersion`은 파일 사본에 쓸 수 없어서 이 함수를 추가했다. 자료·구성을 함께 복원하지 않았거나 같은 버전이 없으면 **복원하지 않고** "원문 사진은 자료·구성과 함께 복원하세요"로 알린다. 원문마다 새 공간을 만드는 대체 경로는 쓰지 않는다. 원문 사진 ZIP 하나만 고른 경우에는 원문 사진 화면과 같이 새 자료공간 하나로 복원한다 |
   | 원본 첨부 | 원본 첨부 서비스의 `prepare/install`로 계정 보관함에 파트를 추가한다 |
   | 계정 문서 | `applyAccountDoc(key, {expectedHash: null})`. 로컬에 없을 때만 쓴다 |
5. **정확 버전 연결**
   - `Core.restoreBackup`은 순서를 유지하므로 순번으로 옛 ID→새 ID 표를 만든다. 같은 묶음 안 참조만 옮긴다. 대상은 9칸 근거, 글 인용 근거, 글쓰기 준비, 계정 문서다.
   - 내용·해시는 바꾸지 않고 최신 버전으로 치환하지 않는다.
   - 자료·구성 없이 복원한 9칸은 옛 원문이나 함께 오지 않은 글을 가리키는 근거를 지우고, 그 개수를 결과에 적는다. 사진 글 인용 근거와 같은 처리다. 선택 이유·제목은 남긴다.
   - 9칸의 저장 글 참조는 새 글 ID로 옮긴다. 복원한 글 본문의 해시가 참조한 해시와 같을 때만 `postRevision`을 복원한 글의 revision으로 바꾼다. 다르면 원래 값을 그대로 두고, 다른 판으로 바꾸지 않는다.
6. **글 상태**: 전체 백업에서는 manifest의 저장/초안·보관 상태로 복원한다. 사진 글 ZIP 하나만 고르면 편집기와 같이 새 초안이 된다. 글의 작성·수정 시각은 글 ZIP에 적힌 값으로 복원한다(아래 "글의 작성·수정 시각").
7. **복원하지 않는 것**
   - 공개 표지 설정
   - 연표·목표·습관
   - 연간 계획 전용 파일
8. **같은 백업을 다시 복원하는 경우**
   - 복원을 마치면 그 파일의 복원 버튼은 다시 켜지지 않는다.
   - 이 계정의 기기에는 영수증을 남긴다. 키는 manifest SHA-256(단일 JSON은 파일 SHA-256)이고, 생성 시각과 복원 시각을 함께 둔다.
   - 같은 백업을 다시 열면 "이미 복원했습니다"와 날짜를 보여 준다. "같은 백업으로 새 사본을 하나 더 만듭니다"를 체크해야만 버튼이 켜진다.
   - **영수증은 기기별이다.** 이 기기의 `localStorage`에 계정별로 최근 50개를 둔다. 같은 계정이라도 다른 기기에서 같은 파일을 열면 경고하지 않는다. 브라우저 데이터를 지워도 사라진다.
9. **실패 처리**
   - 자료·구성이 실패하면 그 공간의 나머지 형식은 "건너뜀"으로 둔다.
   - 계정 문서 중 일부가 거부되면 그 묶음을 "실패"로 표시하고 개수를 적는다. 다시 복원하면 거부된 문서만 다시 쓴다.
   - "실패한 항목 다시 복원"은 같은 새 사본에 실패·건너뜀 항목만 다시 넣는다.
10. **복원 뒤 상태**: 설치하면 새 공간이 활성이 되므로, 끝나면 원래 공간을 다시 활성으로 둔다. 결과의 "… 열기"로 새 공간을 연다. 새 사본은 계정 자동 연동으로 다른 기기에 동기화되고, 공개는 하지 않는다.
11. **사본 이름과 표시(M4, 2026-11-02 소유자 결정)**
   - 새 사본 이름은 원래 이름에 복원 날짜(기기 시간 기준 월-일)를 붙인다. 예: `내 자료 (11-02 복원)`. 이 기기에 같은 이름이 있으면 `(11-02 복원 2)`, `(11-02 복원 3)`…로 늘린다. 결과의 "… 열기" 버튼도 이 이름을 쓴다. 원문 사진 ZIP 하나로 만든 공간도 같다.
   - 사본임은 이름이 아니라 계정 문서 `restored-copy:<새 공간 ID>`로 판별한다. 값은 `{format: 'haedo-restored-copy-v1', workspaceId, sourceWorkspaceId, restoredAt}`이고, 공간을 설치하는 트랜잭션 안에서 함께 쓴다. 한 번 쓰고 바꾸지 않는다. `sourceWorkspaceId`는 백업 목록에 적힌 원래 공간 ID다(없으면 `null`).
   - 이 문서는 범용 계정 문서 동기화(`life_account_documents`)로 다른 기기에 간다. 서버 키 형식 제한이 없어 마이그레이션은 없다. 사본 공간이 아직 오지 않은 기기도 문서를 먼저 받아 두었다가, 공간이 오면 같은 표시로 읽는다.
   - `listAccountLibraries`는 표시가 있는 공간에만 `restoredCopy: {sourceWorkspaceId, restoredAt}`를 더한다. `eligible`은 바꾸지 않으므로 사본도 그대로 동기화(BlogSync 포함)·백업된다.
   - 홈 "내 글"은 공간이 아니라 **글 단위**로 겹침을 뺀다(`home.js` `restoredDuplicates`). 모든 eligible 공간의 글을 읽는다.
     - 사본의 글은 표시에 적힌 원래 공간이 목록에 있고 eligible일 때만 그 공간의 글과 짝을 짓는다. 복구 사본(eligible 아님)을 복원한 사본은 짝을 짓지 않는다.
     - "같은 글"은 복원이 바꾸지 않는 내용으로 정한다: 제목·저장/초안·보관 상태, 본문(사진 자리는 순번으로 바꿔 비교), 사진의 이름·형식·크기·해상도·SHA-256(보기용 JPEG 포함) 순서, 첨부. 글 ID·revision·사진 ID는 복원 때 새로 만들어지므로 비교하지 않는다. 시각도 비교하지 않는다(2026-11-11부터 복원한 글이 원래 시각을 갖지만, 그 전에 만든 사본은 복원 시각을 갖는다). 옛 ID→새 ID 대응표는 저장하지 않아 다른 기기에서 쓸 수 없으므로 근거로 쓰지 않았다.
     - 짝은 일대일이다. 원래 공간에서 지운 글, 백업 뒤 고친 글(내용이 다르면 다른 글), 백업 뒤 원래 공간에 쓴 글은 모두 그대로 보인다. 같은 내용의 글 묶음마다 하나만 남긴다. 현재 공간의 글이 있으면 그 글을, 없으면 원래 공간에 가까운 글을 남긴다. 현재 공간의 글은 빼지 않는다. 글을 읽지 못하면 짝을 짓지 않는다. 그래서 어떤 글도 홈에서 아예 사라지지 않는다.
     - 원래 공간이 없는 계정(다른 계정에 복원)에서는 사본 글이 그대로 보인다.
   - 모두 받기는 이 표시 문서를 `account-documents.json`에 넣지 않는다. 다시 복원할 때마다 새 사본에 새 표시를 쓴다.
   - 이 변경 전에 만든 사본에는 표시가 없다. 이름(`내 자료`가 두 개)만으로는 사본인지 확실히 알 수 없어서 소급 표시를 하지 않는다.
   - **구버전 기기**: 이전 앱은 모르는 계정 문서 종류를 건너뛰고 받기 위치(cursor)를 넘겼다. 그래서 계정별 문서 스키마 번호(`accountDocSchema:<계정>`, 지금 2)를 둔다. 이전 번호로 동기화한 기기는 업데이트 뒤 한 번 받기 위치를 0으로 되돌려 다시 받는다. 이미 받은 행은 같은 revision이라 다시 쓰지 않고, 건너뛴 행만 기존 CAS·충돌 규칙으로 적용된다. 미저장 입력과 더 새 로컬 값은 그대로다. 처음 동기화하는 기기는 첫 받기 위치를 쓸 때 번호를 함께 기록한다. 새 문서 종류를 더할 때마다 이 번호를 올린다.
   - **범위 밖과 한계**
     - 설정의 계정 블로그 동기화 개요에 나오는 "글 N개"(`blog-sync.js` 집계)와 개요 목록에는 사본 글도 포함된다. 그래서 홈에 보이는 글 수와 다를 수 있다.
     - 보관 범위·근거 파일 복원과 형식별 예전 화면의 복원으로 만든 새 공간에는 날짜 이름과 사본 표시가 붙지 않는다.
     - BlogSync 순서(기존 동작): 다른 기기에 사본 공간이 도착하기 전에 BlogSync가 사본 글을 받으면, 그 글은 현재 공간이나 첫 공간으로 들어갈 수 있다. 내용이 같으면 그 기기 원래 공간 안에서 같은 글이 둘이 되며, 이것은 같은 공간 안의 글이라 위 규칙으로 접지 않는다. 두 기기 실측은 하지 않았다.
     - 순환 표시(A가 B를, B가 A를 가리킴)는 정상 복원으로는 생기지 않는다. 생기면 처음 반복되는 곳에서 계보 계산을 멈추고, 같은 글 한 쌍 가운데 하나를 남긴다.
     - 같은 백업을 두 번 복원했고 원래 공간에서 그 글을 지웠다면, 두 사본의 같은 글은 서로 짝이 아니므로 둘 다 보인다.
     - 같은 기기에 이전 버전으로 열린 탭이 남아 있으면 그 탭의 홈에는 사본 글이 겹쳐 보일 수 있다. 받기 위치는 같은 기기의 탭들이 함께 쓰므로, 새 버전 탭이 한 번 다시 받은 뒤에 도착한 표시를 이전 버전 탭이 먼저 건너뛰면 그 표시는 이 기기에 오지 않는다(번호가 이미 올라 있어 다시 받지 않는다). 이전 버전 탭을 닫거나 새로 고치면 더 생기지 않는다.
     - 스키마 번호가 오른 뒤 기존 기기는 계정 문서 변경 목록 전체를 한 번 다시 받는다. 이미 받은 행은 revision 비교만 하고 쓰지 않으므로 계정 문서 수만큼의 요청과 비교 비용이 한 번 든다.
     - 홈의 짝짓기 비용: 목록 행(제목·상태·본문·사진 수)이 같은 글만 읽고, 공간마다 한 번의 읽기(`readPhotoPosts`)로 읽는다. 홈 화면은 읽은 글의 비교 내용을 글 ID·revision·수정 시각으로 기억해 바뀌지 않은 글은 다시 읽지 않는다. 검수 측정 조건(글 100개·공간당 원문 약 1 MB, Node 메모리 IDB)에서 수정 전 2.3~3.3초가 73~115 ms로 줄었다(표시 없는 목록과 같은 수준).

## 글의 작성·수정 시각 (2026-11-11)

검수에서 재현한 결함: 날짜가 다른 글을 모두 받기로 백업해 빈 브라우저·빈 계정에 복원하면 모든 글의 `createdAt`·`updatedAt`이 복원 시각이 됐다. 원래 날짜의 일정 D는 비고, M 달력은 복원한 날 칸에만 글이 모이고, 목록 순서도 섞였다. 글 ZIP의 `manifest.json`에 시각이 없었고 `readBackup`이 새 글을 만들 때의 시각을 썼기 때문이다.

- **담는 값**: 글 ZIP(`PhotoPost.backup`)의 `manifest.json`에 `createdAt`·`updatedAt`을 넣는다. 저장소의 값 그대로다(`YYYY-MM-DDTHH:MM:SS.mmmZ`). 형식 이름(`life-photo-post-backup-v1/v2`, `life-post-md-backup-v1`)은 그대로이고 두 값은 **선택 필드**다. 저장 검증이 재는 목록 크기(`inspect`)에는 넣지 않으므로 글 크기 한도는 바뀌지 않는다.
- **읽는 규칙**(`PhotoPost.readBackup`):
  - 두 값은 함께 있어야 한다. 하나만 있으면 거절한다.
  - 저장 검증과 같은 형식 검사를 한다(정규 UTC ISO 시각, 실제 날짜). `updatedAt < createdAt`이면 거절한다. 거절 문구는 기존 `사진 글 날짜를 확인해 주세요.`·`사진 글 날짜 순서를 확인해 주세요.`다.
  - 지금보다 늦은 시각(시계가 앞서간 기기에서 쓴 글)은 그 값만 복원 시각으로 맞춘다. 순서 규칙은 그대로 성립한다. 글을 버리지 않는 이유는, 전체를 잃은 뒤 복원할 때 시계 오차 때문에 글 자체를 못 살리면 안 되기 때문이다.
  - `createdAt`이 일정이 다루는 해(1900~2199, `ScheduleData.valid`)보다 앞서면 두 시각을 모두 복원 시각으로 맞춘다(기준 `1900-01-02T00:00:00.000Z`: 기기 시간대와 무관하게 범위 안에 들도록 하루 안쪽). `updatedAt`만 남기지 않는 이유는 `updatedAt ≥ createdAt` 규칙 때문이다. 2200년 이후는 지금보다 늦으므로 위 규칙으로 걸린다. 검수(2026-11-11)에서 서기 999년 시각의 글이 `복원함`으로 들어간 뒤 첫 화면 목록이 열리지 않았고, 계정에 올라가 다른 기기 목록도 멈췄다.
  - 이미 저장소·계정에 들어온 범위 밖 시각의 글은 `ScheduleData.dayOf`가 날짜 없음(`null`)으로 돌려준다. 목록은 그 글을 `날짜 미확인` 아래에 보여 주고, 달력 보기는 뺀다. 글 하나의 시각 때문에 화면 전체가 멈추지 않는다.
  - 두 값이 없는 옛 ZIP은 이전처럼 복원 시각을 쓴다.
  - `PhotoPost.backupTimes(doc)`가 그 결과를 알려 준다: `kept`·`missing`·`adjusted`.
- **결과 화면**: 복원 결과의 글 항목에 `times`를 남기고, 시각을 살리지 못한 글이 있으면 한 줄로 알린다(`#fbRestoreDates`).
  - `글 N개는 백업에 작성일·수정일이 없어 복원한 시각으로 저장했습니다.`
  - `글 N개는 백업의 날짜가 지금보다 늦거나 1900년보다 앞서 복원한 시각으로 맞췄습니다.`
- **목록 버전 3**: 묶음의 파일 구성은 2와 같다. 이전 앱의 글 ZIP 판독기는 모르는 필드를 거절하므로, 버전을 올려 이전 앱이 묶음을 **미리보기 전에** `unsupported_version`("앱을 새로 고친 뒤 다시 시도")으로 거절하게 했다. 버전을 그대로 두면 이전 앱이 글만 빼고 나머지를 복원한 사본을 만든다. 새 앱은 1·2·3을 모두 읽는다.
  - 한계: 글 ZIP 하나(편집기의 사진 포함 백업)와 연재 모음 ZIP(`life-blog-series-package-v1`, 안에 글 ZIP을 담는다)은 형식 이름이 그대로라서, 새 앱에서 받은 파일을 이전 앱에서 열면 `사진 글 형식을 확인해 주세요.`로 거절된다. 아무것도 쓰지 않는 거절이고 앱을 새로 고치면 읽힌다.
- **단일 글 ZIP**: 같은 판독기를 쓰므로 같은 필드와 같은 규칙을 받는다. 편집기의 `사진 글 백업 열기`로 복원한 새 초안도 원래 시각을 갖고, 범위 밖 시각은 복원 시각이 된다(안내 문구는 전체 복원 결과 화면에만 있다).
- **연재 모음 ZIP**: 안의 글 ZIP을 같은 판독기로 검증하지만, 복원하는 글 문서는 모음 목록(`series.json`)의 것이다. 그래서 글 ZIP의 시각 필드는 검증만 거치고 연재 사본의 시각을 정하지 않는다(이전과 같다). 연재 사본은 일정 목록·달력에 나오는 글이 아니다.
- **복원 규칙과의 관계**: 복원은 여전히 새 사본(새 글 ID, revision 1)만 만들고 기존 글을 덮지 않는다. 바뀐 것은 사본의 두 시각뿐이다.
- **계정 동기화(최신 채택)와의 관계**: 확인한 내용이다.
  - 사본은 새 글 ID라서 계정에 같은 글이 없다. 올릴 때 비교할 상대가 없으므로 과거 `updatedAt` 때문에 충돌이 나거나 지는 일이 없다(`tests/full-backup-dates-browser.cjs`: 6편이 충돌·복구 사본 없이 올라가고 계정 행의 `createdAt`·`updatedAt`이 원래 값이다).
  - 그 뒤의 충돌 판정(`blog-sync.js` `remoteIsLater`)은 문서의 `updatedAt`을 비교한다. 복원한 글을 고치면 `updatedAt`이 지금이 되므로 다른 기기의 옛 내용을 이긴다. 복원만 하고 고치지 않은 글은 보낼 변경이 없어서 판정 대상이 아니다.
  - 초안 올리기 대기(`draftWaiting`)는 `updatedAt`이 최근일 때만 기다린다. 과거 시각의 복원 초안은 기다리지 않고 바로 올라간다.
  - 홈의 사본 접기(`restoredDuplicates`)는 시각을 비교하지 않으므로 그대로다.

## 진행 중 이동

- 받기·확인·복원 중에 앱 안에서 이동하면(메뉴, 돌아가기, 공간 전환 등) 확인 창이 뜬다. 다른 화면의 `flush` 가드와 같은 방식이다.
  - 취소하면 이동을 막고 "끝난 뒤 이동해 주세요"를 표시한다.
  - 이동을 고르면 남은 단계를 멈춘다.
  - 브라우저를 닫는 경우는 기존 `beforeunload`가 막는다.
- 복원이 중간에 멈추면 이미 만든 새 자료공간 이름과 개수를 알리고 영수증을 남긴다. 다시 백업·복원 화면을 열면 그 안내가 복원 칸 위에 남아 있다(`#fbInterrupted`).

## 메뉴와 기존 주소

- 설정 목록의 파일 항목 여섯 개를 **백업·복원** 하나로 바꿨다(`#lifeBackupOpen`, view `backup`, 대표 영역 manage).
- 백업·복원 화면의 "형식별 파일"에 기존 행이 같은 이름·ID로 있다. 그 행에서 연 화면은 백업·복원으로 돌아오고, 누른 행에 다시 초점을 둔다.
- 기존 직접 주소 `view=transfer|workbench-backup|preservation`은 정확한 화면을 그대로 연다. 뒤로 가면 백업·복원의 해당 행으로 간다.
- `section=manage#lifeBackupMaterials|Planning|Choices`는 백업·복원을 연다.

## 미검증·한계

- 실제 Apple 기기에서 큰 ZIP의 메모리와 파일 저장(공유 시트)은 확인하지 않았다. 출력 ZIP은 받기 전까지 브라우저 메모리에 남을 수 있다. 크기별 분할은 없다.
- 자료·구성 없이 고른 네이버 원문 사진은 백업 ZIP에서는 복원하지 않는다. 그 사진만 필요하면 원문 사진 화면에서 원문별 ZIP으로 복원한다.
- 글쓰기 준비와 글 사이의 연결은 복원하지 않는다.
- 원본 첨부 파트는 같은 계정에 다시 복원하면 하나 더 생긴다. 다시 열기 경고가 이를 알린다.
- 연표·목표·습관은 이 기기 사본 기준이다.
- 진행 중 이동 확인 창은 코드 경로만 있고 브라우저 자동 검사는 하지 않았다.
- 9칸의 저장 글 참조 중 백업 뒤 본문이 바뀐 글은 원래 revision을 그대로 두므로 "바뀜"으로 보인다.
- 서버에만 있는 원본 첨부 파트는 담지 않는다(넣지 않는 것에 표시).
- 실제 Supabase 동기화는 FakeCloud로만 확인했다.
