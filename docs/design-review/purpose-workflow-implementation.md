# 목적별 메뉴와 결과물까지의 이동

2026-10-26 UTC(10-27 KST 최종 검수). 기준 배포 main은 `c9c21ef21cda138f1a81bacc808199dedf49b3a3`, 설계는 [기능 목적·워크플로](purpose-workflow.md)다. **구현과 로컬 통합 검수를 마쳤다.** 정확 PR/main CI와 실제 배포 결과는 [PR139 출시 기록](https://github.com/wonchance-art/life-haedo/pull/139)으로 확정한다.

## 이번 작업의 결과

사용자가 홈·뉴스·자료실·계획에서 필요한 대상을 고르고, 같은 대상의 읽기·작성·공개 검토·파일 보관까지 이어 간 뒤 출발한 목록으로 돌아오게 한다. 기능별 화면을 더 만드는 대신 현재 화면·저장·계정 동기화·반환 문맥을 연결한다.

| 영역 | 변경 범위 | 보존할 결과 |

| 공통 탐색·계획 | 표시 이름 ‘계획’, 관련 화면의 복귀 이름 | `tools` ID와 과거 주소·로그인 복귀, 계획별 날짜·저장·복원 방식 |

자료실 전문 목록 진입은 한 번에서 메뉴 열기+선택으로 늘어난다. 같은 익명 자료·화면 폭으로 기본 본문 가시성과 이 비용을 함께 비교한다. 새로 늘어난 메뉴 개수나 검사 수를 효율의 증거로 쓰지 않는다.

새 라이브러리·프레임워크·런타임 자산·저장 스키마를 도입할 필요가 없다. 기존 `HaedoNavigation`, native `details`, `navigate`/`guarded`, PhotoPost/Workbench/BlogManager/AccountBlogUI, PreservationUI의 정확 대상 전달과 저장 보호를 재사용한다. 메뉴 재배치를 데이터 전체 통합·개인 설정 동기화·자동 공개의 근거로 삼지 않는다.

## 검사 실행 규칙

- 기준 앱은 main의 `git archive`로 고정하고 후보와 같은 익명 자료를 사용한다. 계정 자료 경로는 실제 동봉 SDK·IndexedDB와 합성 capability-1 HTTP로 확인하며 운영 개인 자료를 사용하지 않는다.
- 실제 보이는 메뉴를 열고 조작한다. 숨긴 호환 버튼, 테스트 전용 제품 분기, UI를 건너뛰는 상태 조작으로 새 흐름을 통과시키지 않는다. 사전 데이터 준비와 관측·실패 주입은 분리해서 기록한다.
- 기존 검사에서 명칭/진입이 달라진 경우 실제 새 사용자 경로로 이관한다. 대상·상태·데이터·공개 경계의 단언과 제한 시간은 약화하지 않는다. 기존 제품 응답 wrapper를 쓰는 회귀는 그 한계를 명시하고 새 정적 바이트 검증과 구분한다.
- 첫 실패·실행 소스/검사 해시·HTTP 응답·이미지를 보존한다. 원인을 고친 뒤 새 근거 경로에서 필요한 검사만 다시 실행한다. 반복 실행으로 녹색 결과를 고르지 않는다.
- 코드 검토와 실제 조작, 시각 검토와 정량 계측, 합성 서버와 실제 사용자 체험, 로컬 검사와 공개 배포를 구분한다. 후보 동결 후의 결과만 최종 소스에 연결한다.

## 역할과 증거

총괄은 공통 CSS·통합·기준선·출시와 최종 판단, 자료 담당은 라우팅/메뉴/파일 그룹, 글 담당은 정확한 글/계정 목록/복귀, 뉴스 담당은 설정/반응, 계획 담당은 공통 명칭/주소 호환을 맡는다. 별도 검수 담당이 같은 자료의 시각·사용 흐름을 확인하고 독립 검토 담당이 보존 계약과 PWA·출시 조건을 확인한다.

기준 서버와 후보 서버는 별도 포트에서 실행한다. 증거는 `.local/purpose-workflow-20261026/`에 실행별로 남기며 개인 계정 정보는 포함하지 않는다. 실제 기기·Google 로그인·개인 자료의 사용성은 사용자가 제공하는 별도 확인 조건으로 남긴다.

## 검수 중 확인·교정

- 글별 관리의 처음 조회가 실패했을 때 이전 목록에 남아 있던 행으로 정확 판을 검증할 수 있었다. 새로 성공한 photo 조회만 검증에 사용하며 실제 IndexedDB 실패를 주입해 거절을 확인한다.
- 글의 파일 진입 뒤 다른 탭에서 수정될 수 있어 ID만으로 파일을 준비하면 더 새 판이 섞일 수 있었다. 선택한 revision을 초기 목록·준비 전후·파일 생성 전후에 확인한다. 판이 바뀌면 파일과 자동 복귀를 멈추며, 같은 ID의 현재 판은 ‘현재 글 확인’ 명시 선택으로만 연다. 삭제/다른 ID로 교체된 글을 추정해서 열지 않는다.
- 설치 Playwright 1.62.1과 CI 패키지 1.63.0의 `waitForFunction(async () => false)`가 false를 기다리지 않고 반환하는 현상을 제품 없는 탭에서 재현했다. 두 패키지 모두 로컬 Chromium을 사용한 재현이며 CI 브라우저 자체의 결과로 확대하지 않는다. 영향받은 비동기 조건은 원래 제한 시간 안에서 `await page.evaluate` 결과를 실제 확인하도록 바꿨다. 뉴스 저장은 상태 문자열만 기다리지 않고 원격의 정확 source ID·version과 ACK를 대조한다.
- 새 검사 작성 중 SDK fixture 선택·초기 seed 뒤 재열기·실제 details의 summary/중첩 메뉴·비동기 mount 준비·단일 실패 주입 대상·기존 URL의 native back 범위가 맞지 않은 실패를 원본별로 남겼다. 현재 코드와 기준 앱을 대조해 실제 UI 경로로 고쳤고 데이터 단언과 제한 시간은 유지했다. 제품 바이트/fixture 변경을 검출한 중간 실행은 최종 통과로 계산하지 않는다.

## 검증과 출시 상태

정적22 HTML/169 JavaScript/714 로컬 참조와 기존 단위1,498개가 통과했다. 실제 동봉 SDK·계정별 IndexedDB와 합성 HTTP를 사용했으며, 실제 제품 정적 바이트를 대조한 새 집중 검사와 제품 응답 wrapper가 남은 기존 보조 검사의 경계를 구분했다.

같은 익명 자료의 390/820/1440px에서 자료실 첫 본문은 44px 위로 이동했다. 이는 보조행 제거에 따른 기하 변화이며 로딩 속도나 실제 기기 효율 수치가 아니다. 전문 목록 진입에 메뉴 열기 한 번이 늘어나는 비용도 확인했다.

초기 동결 `freeze-1`의 제품275개를 기준으로 시각·뉴스·계획·시작/계정 보존을 확인했다. 최종 `freeze-2`는 글별 관리 성공 문구가 전체 글 개수를 말하던 한 분기만 교정했다. 글6·홈10·SNS2와 PWA9는 최종 제품에서 확인했으며 앞선 결과를 새 해시에서 실행했다고 표시하지 않는다. 원래 검사에서 새 명칭/접힌 진입을 빠뜨린 실패, native back 가정 오류, 비동기 관측 오류, 검수 중 소스 변경은 별도 시도와 원인 기록을 보존했다. SNS 최초23건은 오래된 ‘도구’ 라벨만 원인이었으며 원래 정렬·크기·대비 조건은 모두 충족했다. 새 명칭으로 이관 후 동일 전체 검사를 통과했다.

실행별 원본·source/fixture/runner 해시·실패·화면·다운로드·종료 영수증은 `.local/purpose-workflow-20261026/`에 둔다. 제품과 원문/사진·계정 경계의 미해결 주요 결함은 로컬 검토에서0이다. 전체 격리 PostgreSQL/CI와 실제 배포는 로컬 브라우저 검사로 대신하지 않으며 PR의 정확 HEAD와 main 배포 결과를 별도로 기록한다.

실제 소유자 기기·Google 로그인·개인 원본·직접 읽기 효용은 자동 검수의 결과로 주장하지 않는다. 다음 작업은 [최신 로드맵](../life-tools-design/roadmap.md)의 두 기기 완주와 내부 문서·첨부의 정확 연결이다.

첫 PR CI의 핵심 경험·컬렉션 실패는 닫힌 자료 메뉴 안 버튼을 직접 누르던 검사 경로였다. 원래 실패와 정확 HEAD를 보존하고 실제 메뉴 열기만 추가했다. 같은 경로의 플랫폼·자료 활용 검사도 함께 이관했으며 기존 단언/제한 시간으로 core5·collection12·platform8·product-flow3(27캡처)를 확인했다. 플랫폼 구버전 사이트 옵션 분기는 해당 로컬 실행에서 미실행이며 최종 CI의 실제 범위와 구분한다.
