# 대표 글·연재·9칸을 한 주소에서 읽는 공개 표지

2026-10-19 KST. 기반 후보 `8993ec1` 위의 새 제품 목표다. 이 문서는 총괄 확정 계약·제품/디자인 반대 검토와 공식 오픈소스 비교다. **로컬 구현·범위별 검수를 마쳤으며 같은 최종 후보 전체의 원격 CI는 대기 중이다.** 운영 계정/자료 접근·설치·개인 전송·공개·병합·배포 결과를 주장하지 않는다.

## 목표와 기존 공개 목록의 차이

이미 직접 공개한 대표 글·연재·9칸을 사용자가 골라 순서를 정하고, 짧은 소개와 함께 한 주소에서 읽도록 안내한다. 대표 결과 선택→전체 표지 미리보기→명시 게시→익명 방문자의 글/목차/항목·출처 탐색과 복귀→대상 갱신·철회/부분 오류→표지 갱신·철회까지 하나의 사용자 결과다.

| 기존 기능 | 표지에서 새로 해결할 일 | 보존할 경계 |
| --- | --- | --- |
| 공개 블로그의 시간순 글 목록·소개 | 날짜와 관계없이 대표 결과를 직접 골라 안내 | 전체 공개 글 목록과 기존 주소 유지. 새 피드·검색·정렬 대시보드로 대체하지 않음 |
| 연재의 순서 있는 글 목차 | 연재 자체를 한 대표 결과로 소개 | 연재 안의 글 순서를 표지 편집에서 재편집하지 않음 |
| 선택 영역의 공개 9칸과 상세·출처 | 취향 결과를 글/연재와 같은 출발점에서 선택 | 9칸/항목/표지 이미지를 새로 복제하거나 자동 외부 조회하지 않음 |
| Share-v1·공개 상태·CAS/영속 영수증 | 명시 선택한 공개 주소의 작은 표지 사본을 연결 | 원글·사진·원문·개인 메모·서버 연결을 자동 게시하지 않음 |

대표 결과를 고르지 않았다면 기존 공개 글 목록이 더 단순하다. 이때 가짜 항목이나 자동 추천으로 표지를 채우지 않고, 기존 공개 결과를 먼저 직접 고르도록 한다. 임의 외부 링크 관리·SNS 아이콘·통계·반응 수·꾸미기 테마는 이번 목표가 아니다.

## 최소 사용 흐름과 공개 경계

1. 소유자가 현재 공개 중인 자기 결과를 읽기 전용으로 확인하고 고른다. 선택과 순서는 비공개 편집 상태이며 미리보기만으로 서버 공개 쓰기를 하지 않는다.
2. 공개 표지의 제목·소개·각 항목의 실제 전송 필드를 전체 검토한다. 기본 동의는 해제 상태이고 입력/선택/대상 상태가 바뀌면 이전 동의로 새 내용을 게시하지 않는다.
3. 기존 공개 사본 엔진의 revision CAS·동일 operation 재확인을 사용한다. 미확인 응답을 새 표지 생성이나 원글 재게시로 처리하지 않는다.
4. 방문자는 개인 Auth/IDB를 열지 않고 표지와 현재 접근 가능한 결과만 읽는다. 원글 본문·사진의 공개 권한은 각 결과의 기존 엔진이 검사한다.
5. 한 대상이 철회·삭제되거나 일시적으로 실패하면 그 행에 구분해 표시하고 다른 항목은 읽는다. 실패한 항목의 예전 본문/사진을 fallback으로 노출하지 않는다. 표지 자체의 철회·오류는 표지 전체의 이전 내용을 지운다.
6. 표지에서 목적지를 열고 돌아오면 해당 항목·읽던 위치·키보드 초점으로 복귀한다. URL/복귀 컨텍스트는 정해진 내부 공개 경로만 허용하며 개인 공간 ID나 임의 외부 이동 주소를 넣지 않는다.

표지 철회는 연결된 글/연재/9칸의 철회가 아니고, 대상 철회도 표지 전체 삭제가 아니다. 표지는 원본 보관 파일이나 기기 간 개인 자료 이동 경로가 아니다. 공개 결과만 선택했다는 이유로 소유자 검증·최종 상태 재확인·비공개 필드 whitelist가 생략되지 않는다. 확정 주소는 `cover.html?cover=공개UUID`다. 내부 목적지는 현재 같은 origin/디렉터리의 `blog.html?post=UUID`·`series.html?series=UUID`·`taste.html?nine=UUID`만 사용한다. 추가 query/fragment/credentials·별칭·중첩 표지는 wire에서 허용하지 않는다.

## 확정 데이터·게시 계약

로컬 모델은 `life-public-cover-v1`의 `{id,title,intro,items}`이며 항목은 `{id,kind,publicId}`만 보관한다. 계정/공간별 revision CAS 상태에서 표지 최대 20개·표지마다 항목 최대 20개, 제목 200/소개 2,000자다. 같은 종류/공개 ID의 중복을 거절한다. 빈 제목/항목 0개는 로컬 작성 중 상태로 허용하지만 공개 투영은 제목과 1~20개 항목을 요구한다. 충돌 복구는 최신 목록의 독립 새 표지/항목 ID 사본이며 경쟁자의 항목을 덮어쓰지 않는다.

서버 형식은 기존 `life-share-v1`이다. 항목별 entry는 고정 순번·종류 라벨(예: `1. 글`)과 같은 라벨의 `article` 첨부 한 개/정규 공개 URL만 싣는다. `pinned=false`, `note=null`, `parts=[]`, 첨부 `creator=''`다. 실제 대상 제목·소개·본문·사진은 표지 wire로 복사하지 않고 현재 공개 결과를 읽어 표시한다. 글 항목에 작성자 소개를 글 소개로 추정해 넣지 않는다.

대상 종류 검사는 표지 grammar를 먼저 거절→연재 wrapper→9칸 grammar 순서다. 기존 Share-v1에서 일반 페이지가 정확히 9칸 구조를 가지면 같은 독자로 읽을 수 있다. schema marker를 새로 추가하지 않으므로 원래 제작 경로가 9칸 도구였는지 증명할 수 없으며, 후보 종류는 **9칸 형식**으로 안내한다. 이는 비공개 자료를 읽는 허용이 아니라 이미 공개된 동일 구조의 해석 한계다.

소유자 후보는 공개 중인 자기 글/Share 결과의 안전한 공개 snapshot으로 구성한다. 첫 조회의 글 목록과 Share 한 페이지, 이후 페이지당 최대 50개·읽기 동시 4개 이내이며 성공/개별 오류를 구분한다. 미리보기는 실제 저장된 선택·소유자 후보 소속·현재 대상 revision을 검증하고, 게시 직전과 `auth.verify` 뒤 최종 gate에서 다시 확인한다. 승인한 검토 객체/원격 revision과 맞지 않으면 새 공개 쓰기를 하지 않는다.

재시도는 이미 승인한 URL 포인터만 가진 원래 같은 operation/CAS 요청을 재생한 뒤 현재 head를 다시 읽는다. 원본문·사진·새 공개 UUID를 payload에 추가하지 않는다. 대상의 미래 가용성을 새 승인 조건으로 강제하지 않으며, 철회된 대상 주소는 방문자 화면의 missing 행으로 남길 수 있다. 새 게시의 소유/현재 대상 revision·로컬 입력 최종 gate와 이 영수증 재확인은 구분한다. 원격 응답 유실을 새 operation이나 경쟁자의 공개 덮어쓰기로 처리하지 않는다. pending은 새 게시를 막되 편집·같은 요청 확인·표지 자체의 독립 철회까지 이어지는 복구를 유지한다.

방문자 reader는 표지→선택 대상 최대 3개 동시 읽기→같은 표지 revision/snapshot 재확인 순서다. 연재 안의 자식 글을 표지에서 미리 펼쳐 읽거나 이미지를 요청하지 않는다. 일부 missing/error 행은 이전 제목과 링크를 없애고 다른 성공 행을 유지한다. 같은 내용의 주기 조회는 DOM/구절 선택/스크롤을 유지하고, 표지 철회·숨김·오프라인/오류는 이전 표지 내용을 정리한다. 대상 링크의 임시 `fromCover`/`coverItem`은 wire에 넣지 않는다. 기존 독자 화면의 복귀 helper는 같은 사이트 주소와 현재 표지의 실제 항목 소속을 확인한 뒤 해당 anchor로 돌아간다.

새 SQL/migration·원본 자산 업로드·키/SDK 업그레이드는 없다. Supabase 스킬로 현재 공식 [Database functions/RPC](https://supabase.com/docs/guides/database/functions)와 [API keys](https://supabase.com/docs/guides/getting-started/api-keys)를 MCP에서 확인했다. 공개 키는 사용자 소유 검증을 대신하지 않으며 secret/service_role을 브라우저에 노출하지 않는다. 기존 인증 소유 RPC와 익명 읽기 엔진을 재사용한다. changelog.md는 직접 요청의 프록시 CONNECT 403으로 본문을 확인하지 못했고 우회하지 않았다.

## 디자인 방향과 반대 검토

현재 [DESIGN.md](../../DESIGN.md)·[시각 방향](../../.impeccable/blog-visual-direction.md)·프로젝트 디자인/개발 스킬과 Impeccable direct-context fallback을 적용한다. 엔진이나 자동 hook을 설치/실행했다고 기록하지 않는다. 흰 읽기 면·옅은 초록 회색 캔버스·짙은 틸 조작·자체 Pretendard를 재사용하며 공통 CSS는 총괄이 통합한다.

방문자 화면은 제목/직접 쓴 소개→대표 결과의 순서 있는 한 열이다. 각 결과의 종류·전체 제목·짧은 소개/열기 조작만으로 읽기 대상을 고를 수 있어야 한다. 글마다 큰 그림자 카드·반복 아바타·가짜 썸네일·배지나 큰 장식 hero로 내용 위계를 대신하지 않는다. 표지가 사진 자동 공개의 우회로가 되지 않도록 초기는 텍스트 중심으로 검토한다.

관리 화면도 하나의 편집 표면에서 선택·순서·소개와 전체 미리보기로 이어지게 한다. 기존 프로필/전체 공개 목록과 같은 설명을 중복 작성하게 하지 않되, 비공개 소개를 묵시적으로 공개 소개에 복사하지 않는다. 상태/실패가 입력 DOM·커서·한글 조합을 재생성하지 않아야 한다. 44px 조작·16px 입력·포커스 표시·긴 한글/URL 줄바꿈과 실제 대비를 확인한다.

**반대 검토:** 단순 링크 나열뿐이면 기존 공개 목록 링크 하나가 더 낫다. 이번 가치는 글·연재·취향의 명시 선택과 목적지별 자연스러운 왕복에 있다. 반대로 링크허브 엔진 전체를 도입하면 별도 계정·서버/DB·테마·통계와 공개 정책이 늘어난다. 기존 Share-v1과 각 익명 독자를 재사용하고 선택 투영·현재 대상 확인·복귀 연결만 앱 어댑터로 유지하는 범위가 적합하다. 직접 도입·설계 참고·자체 어댑터의 비교는 [공식 OSS 기록](../life-tools-design/open-source-review.md#대표-공개-결과의-한-주소-표지--2026-10-19-kst)을 따른다.

## 독립 검수 계획과 미검증

독립 종합 담당의 실제 SDK/IDB·격리 SQL fixture를 재사용하고 전체 게시 여정을 별도 suite로 중복 작성하지 않는다. 독립 시각/입력 검수는 같은 합성 한글 자료로 1440/820/390px의 선택 편집·전체 미리보기·익명 표지/부분 오류·목적지 복귀를 묶어 본다. 긴 소개/제목, 빈 목록/하나/여러 종류, 현재 대상 갱신/철회, 입력·한글 조합·초점·스크롤·지연 응답이 핵심이다. 넘침/접근 가능한 이름/44px·16px·대비 측정과 실제 이미지 읽기를 구분한다.

사진 원본·개인 본문/근거/메모·다른 계정/선택하지 않은 결과를 sentinel로 검사하고, 표지 동의로 원글 쓰기·사진 자산 업로드가 발생하지 않음을 확인한다. CAS 충돌 뒤 새 검토·동일 실패 재확인·계정 late·철회 뒤 익명 내용 제거와 기존 공개 결과 불변을 포함한다. Linux viewport/합성 CompositionEvent·Auth/HTTP 경계는 실제 Apple/네이티브 IME·Google OAuth·운영 Storage/Edge·배포 체험과 별개다. 아래는 실제 확정한 범위의 결과다. 최종 커밋·원격 CI는 통합 PR의 HEAD/검사 기록을 따르며, 아직 실행하지 않은 검사나 문서 자신의 SHA를 완료 근거로 선취하지 않는다.


## 독립 시각·입력의 실제 확인

[독립 시각 suite](../../tests/public-cover-visual-browser.cjs)는 종합 담당의 `seedPublicTargets`·기존 격리 SQL fixture를 재사용했다. 공개 글 두 편/고해상도 사진 한 장·연재·9칸과 미선택 비공개 글을 만들고, 실제 공개 제목과 다르게 바꾼 비공개 서버 제목이 후보/미리보기로 새지 않는 경계를 함께 사용했다. 실제 SDK/계정별 IDB·네트워크 없는 PostgreSQL의 별도 테스트 DB이며 Auth·원본 HTTP·실패 응답은 합성 경계다.

- 전체 owner 미리보기의 제목·소개·현재 대상 제목·종류/순서를 1440/820/390px에서 확인했다. 검토만 할 때 공개 쓰기 증가 0·기본 동의 해제·비공개 sentinel/공간 ID·작성자 소개의 자동 복사 0·사진/임베드 DOM 0을 단언했다.
- 한글 조합 중 같은 입력 DOM/실제 값을 유지하고 옛 검토/동의를 폐기하며 게시 쓰기 0, 조합 종료 뒤 새 미리보기·일반 제목 편집의 동의 무효화를 확인했다. 상태 조회의 실제 RPC를 지연한 동안 제목 입력 노드·값·초점/선택 `[4,9]`를 보존했고 늦은 상태가 옛 동의를 복원하지 않았다.
- 익명 표지의 세 실제 목적지와 native link 키보드 이동, 같은 내용의 실제 poll에서 DOM/선택 구절 보존을 확인했다. 개인 저장소 접근은 getter를 거절하도록 감시했다. 한 대상 HTTP를 의도적으로 503으로 만들면 이전 제목/링크를 제거하고 다른 두 항목은 유지하며, 재조회 성공 때 그 행만 현재 공개 항목으로 복구됐다. 이 합성 503을 실제 운영 장애나 SQL 철회 검증으로 표현하지 않는다.

고유 5개 흐름을 **owner 3개 + visitor 2개 분리 실행**으로 확인했다. owner 실행은 첫 3개 통과 뒤 공개 성공 시 빈 상태 문단을 visible로 기다린 검수 대기 오류로 중단됐다. 데이터의 `published` 상태와 본문 조회 완료를 기다리도록 고친 뒤 남은 visitor 2개만 집중 실행했다. 원본/입력/공개 단언을 줄이지 않았으며 원래 5개 전체를 한 번에 통과했다고 쓰지 않는다. `.local/public-cover-visual/final-summary.json`이 분리 근거를 명시하고, 원 owner `report.json`의 실패·visitor의 별도 `report.json`·로그를 보존한다. 최종 후보 전체 5개 실행은 통합 PR의 HEAD/CI에서 확정한다.

3폭의 미리보기·익명 정상·일부 오류 9개 장면을 viewport/전체 문서 두 방식으로 남겼다. 측정한 넘침·작은 조작/입력·접근 가능한 이름·대비 문제 0, console/page/external 0이며 의도한 503 콘솔 1개는 별도 집계다. Node22.23.3/Chromium151.0.7922.173의 검사이며 CI153·Apple 실기·네이티브 IME·실제 Google과 다르다. 마지막 원문/글·근거/모음·9칸 snapshot은 표지 상태 외에 불변임을 확인했다.

실제 이미지도 `owner-whole-preview-1440.png`·`-390.png`, `visitor-live-rows-1440.png`·`-390.png`, `visitor-partial-error-390-full.png`에서 따로 읽었다. 긴 소개/제목과 발췌가 전체 줄바꿈되고, 실패한 행의 상태와 정상 두 행의 읽기 목적지가 구분된다. 계산값을 미적 품질 점수로 삼지 않았으며 추가 장식·새 배치 변경을 반복하지 않았다.

최후 retry·pending 안내를 반영한 전체 소스의 `.local/public-cover/unit-after-retry.log`는 Node22.23.3 단위 848/848(실패/skip 0), `check-after-retry.log`는 정적 22 HTML/133 JavaScript/581 참조·PWA manifest/shell 통과를 기록한다. 후보 셸은 v132다. 정적 검사로 실제 운영 SW126의 기기 업데이트나 오프라인 재실행을 검증했다고 표시하지 않는다.

### 종합 완주와 현재 실행 범위

독립 종합 담당의 `.local/public-cover/final-nine-report.json`·`browser-final-nine.log`는 마지막 재시도 정책을 포함한 실제 SDK/독립 IDB·기존 격리 PostgreSQL의 9개 흐름을 한 번에 통과한 근거다. 로컬 선택/순서 재열기·실제 IDB abort/CAS 입력 보존, 전체 미리보기/동의 무효화, 응답 유실의 같은 요청/현재 head, 익명 글·연재 자식 글·9칸의 native 탐색과 정확 anchor/초점 복귀, 대상의 현재 제목/철회/부분 오류, Auth 최종 확인 중 편집·계정 late 차단, 표지 갱신/독립 철회를 포함한다. 1440/390px 12개 화면·console/page/external 0과 의도 실패 응답을 구분한다.

익명 표지·글·연재 자식 글·9칸과 추가 복구 표지 다섯 문서의 개인 저장소 접근 시도는 0이었고, 글에서 원래 4032×3024 사진의 SHA/실제 디코딩 픽셀을 확인했다. 원본 글/사진/기존 공개 사본 불변과 표지 게시가 대상 게시·원본 자산 업로드를 추가하지 않는 경계를 검사했다. 표시한 원본문/사진은 기존 공개 글을 명시적으로 연 결과이며 표지 자체에 복사·자동 렌더한 것이 아니다.

최종 종합 실행은 JS 12개·HTML 5개의 served SHA가 실행 중 단일값이었고 현재 파일과 같음을 단언했다. 정책 변경 전 8개 성공은 `full-eight-before-retry-policy-report.json`에 따로 보존했으며 최종 9개 근거로 대체했다. 마지막 9번째는 SQL 반영 전 끊긴 승인 요청→대상 old UUID 철회/new UUID 재공개→같은 operation·전체 payload 재생→pending 해소·old missing/new UUID 자동 치환 0→실제 UI의 표지 철회·원래 대상 exact 불변까지 확인했다. 이 로컬 결과를 원격 CI 성공·운영 설치로 표시하지 않으며 동일 최종 HEAD의 전체 검사는 통합 PR에서 확인한다.

### 발견·수정과 검수 도구 정정

첫 owner 실제 검사에서 직계 공개 동의 label의 높이가 19px여서 44px 조작 기준을 만족하지 못했고, 두 동의 문구가 inline으로 붙어 보였다. 기존 CSS가 내부 publication label에만 적용되는 것이 원인이었다. 총괄이 같은 공개/철회 label을 flex·최소 44px·간격/패딩으로 보강했고 이후 3폭 모두 기준을 만족했다. `.local/public-cover-visual/before-label-fix-report.json`·화면과 수정 후 장면을 구분해 보존했다. 미리보기에 스크롤한 뒤 전체 문서를 촬영할 때 중간에 붙는 sticky 탐색은 캡처 위치 현상이었으며 실제 배치 결함으로 오인해 수정하지 않았다.

실제 블로그 글은 공개/사진 읽기가 성공해도 표지 복귀 helper가 필요로 하는 ShareRemote 스크립트가 없어 복귀 링크가 0개였다. `.local/public-cover/return-before-proof.json`은 `ShareRemote` undefined·글 published·복귀 링크 없음과 오류 로그 0을 함께 기록한다. 총괄이 해당 HTML의 누락 의존성 한 줄을 추가했고 종합 전체 실행에서 글·연재 자식 글·9칸의 정확 복귀를 확인했다.

코드 독립 검토에서는 한 항목의 표지/연재도 넓은 9칸 grammar와 겹칠 수 있음을 지적했다. reader는 현재 대상을 cover→series→nine 순서로 구분해 중첩 표지를 9칸으로 표시하지 않도록 보강했고 담당자의 반례 단위 검사를 따른다. 원래 공개 결과가 어디서 제작됐는지까지 증명하는 새 marker/SQL을 넣은 것은 아니다.


반대 검토에서는 아직 반영되지 않은 pending 요청의 대상이 철회되면 재시도를 금지하는 초기 가설이 표지 자체의 철회까지 막는 복구 공백을 확인했다. payload는 이미 동의한 주소만 가지므로 미래 가용성을 새 조건으로 묶지 않고 기존 동일 영수증/CAS를 재사용하는 더 단순한 계약으로 바꿨다. 새 게시의 현재 소유/대상 revision/로컬 검토 gate는 유지한다. 실제 동일 신규 회귀는 보존한 before 소스에서 `pending_blocked`로 실패했고(`.local/public-cover-retry/same-regression-before.log`), 수정 뒤 기존 ShareRemote와 소유자 단위 22/22가 통과했다(`after-unit.log`). 위 최종 실제 SQL 9번째가 같은 경계를 확인했다. 앞 시각 5개는 이 정책 변경 전의 3+2 분리 근거로 유지하며 재시도 계약의 검증으로 대체하지 않는다.
