# 같은 계정의 자료실 자동 보관과 기기 간 이어쓰기

2026-10-24 KST 사용자 요청으로 **자료실의 기존 브라우저별 독립 보관·명시 연결 원칙을 기본 비공개 계정 보관으로 변경한다.** 같은 계정이면 다른 브라우저에서 보내기·받기·백업 복원을 다시 하지 않고 같은 자료를 이어 쓴다. 이전 문서의 로컬 전용/선택 동기화 설명은 당시 이력이며 이 절의 대상 영역에는 새 계약을 적용한다. 이번 목표의 구현·자동 검수를 마치고 실제 서버의 합성 계정 왕복도 확인했으며, 정확한 CI·출시와 실제 사용자 기기 확인은 뒤의 증거 범위로 구분한다.

## 사용 목표와 범위

**A에서 가져오기·분류·발췌 → 독립 B에서 같은 계정 로그인 → 같은 자료·원문·폴더·묶음 읽기 → B에서 수정 → A에서 갱신·이어 읽기**가 기본 흐름이다. IndexedDB는 오프라인 캐시·영속 전송 대기·복구 사본의 내부 층으로 남는다. 로컬 커밋을 서버에 보관된 것으로 표시하지 않으며 서버 영수증을 확인하기 전 캐시/전송 대기를 지우지 않는다.

| 포함 영역 | 계정 보관 동작 | 보존 기준 |
| --- | --- | --- |
| Core 자료·불변 원문 판·발췌/인용·휴지통 | 기존 원문 Sync의 자동 전송/수신 | workspace/source/version/quote ID·원문·BOM/개행·해시·정확 위치 |

작성 중 초안·미반영 가져오기/글 준비·뉴스의 판단/설정·연간 계획·읽기 위치·공개 사본은 각 기존 도메인 계약을 유지한다. 이 기본 자료 보관 때문에 함께 전송하지 않는다. NineBoard의 글/사진 참조는 정확 참조이며 참조한 게시물·사진 바이트가 이번 메타 전송에 포함됐다는 의미가 아니다. 원본 첨부를 열어 받는 것은 외부 서비스 수집·글 삽입·공개 업로드와 별개다.

## 계정 기준과 최초 진입

기존 단일 Supabase 인증·서버 검증 계정·owner/epoch guard를 재사용한다. `life_library_capabilities`의 version/metadataVersion/originalsVersion1을 확인한 뒤 계정 모드를 시작한다. 기능 미설치/미지원·오프라인 실패는 캐시와 대기를 보존하는 명시 상태이며 계정 보관 완료로 표시하지 않는다. 구형 capability0을 명시하는 회귀 환경은 기존 로컬 저장 경로를 유지한다.

계정의 기본 자료실 포인터는 owner 잠금 아래 한 번 결정하고 이후 같은 ID를 반환한다. 적격한 기존 로컬 공간을 우선 제안하되 이미 정한 기본 공간을 다른 기기가 새 기본으로 바꾸지 않는다. 새 서버 공간의 비어 있는 최초 hash/revision과 아직 같은 **pristine** 상태에 한해서만 로컬 이관의 CAS 기준으로 사용할 수 있다. 그 사이 다른 기기가 저장하면 충돌로 보존한다. 예전에 정한 공간이 서버에서 사라졌다고 새 빈 공간을 자동으로 만들어 복구 성공으로 표시하지 않는다.

수신을 먼저 준비하고 전체 계정 카탈로그의 모든 페이지를 읽는다. 일부 페이지 실패/누락은 삭제가 아니다. 배경 설치는 현재 활성 공간을 옮기지 않으며, 최초 목록은 기본 공간·자료·구성/메타 수신 장벽 뒤 표시한다. 현재 입력/한글 조합/편집이 있으면 배경 결과로 DOM 값을 덮지 않는다.

기존 검증된 소유자의 일반 가져오기/복원 공간은 새 정책에 따른 자동 편입 대상이다. 소유자 없는/다른 계정 자료와 저장된 복구 참조 또는 명시된 recovery 표식으로 판별 가능한 자동 복구 사본은 대상에서 제외한다. 과거 material-continuity가 표식 없이 만든 소유 복구 공간은 제목·경로 추정 없이 신뢰성 있게 판별할 수 없어 일반 소유 공간과 같이 같은 계정의 비공개 자료로 이관될 수 있다. 이관은 원래 ID/정확 관계·서버 영수증으로 판단하며 제목·경로가 같다는 추정으로 합치거나 원래 사본을 삭제하지 않는다. 기존 전역 등록 자료의 최초 수신은 호환 경로이며 이미 편집·동기화한 자료실에 원래 그래프를 재수입하지 않는다.

## 저장 순서·일관성·복구

계정 coordinator가 **원문 → 저장 구성 → LibraryMeta** 순서를 조율한다. 기존 Core Sync와 CompositionSync 두 엔진을 유지하고 LibraryMeta는 도메인 adapter로 붙인다. 세 번째 범용 복제 엔진을 만들지 않는다. `source_revision` 도착 기준과 정확 참조 검증을 통과한 메타만 적용한다.

서로 다른 영역 전체가 한 세대의 분산 트랜잭션인 것은 아니다. 원문이 도착하고 구성이 아직 대기 중일 수 있는 **eventual consistency**이며 전체 영역의 확인 없이 전체 보관 완료로 표시하지 않는다. 각 로컬 메타 적용은 한 트랜잭션이고 자식 revision을 현재 로컬 기준으로 올린다. 아직 없거나 다른 공간의 역사적 참조는 원래 관계를 남기며 최신 판/비슷한 제목으로 바꾸지 않는다. 확인 가능한 같은 공간 참조는 정확 source/version/hash/문자 구간을 검증한다.

LibraryMeta는 폴더·Collection·NineBoard 자식 revision 벡터의 단조 투영이며 외곽8 MiB·각 자식 기존2 MiB 한도를 지킨다. 현재 payload를 영속 outbox에 고정한 뒤 전송하므로 ACK 뒤에 생긴 자식 변경도 깨끗한 상태로 잘못 지우지 않는다. 삭제된 연결 공간을 메타 재시도로 다시 만들지 않는다.

- 응답 유실은 같은 operation ID·같은 payload로 재확인한다. 성공 영수증을 현재 서버 head라고 추정하거나 새 operation을 만들어 중복 적용하지 않는다.
- 동시 탭/기기의 다른 revision은 CAS 충돌로 남긴다. 최신 비교 뒤 명시 선택하며 선택하지 않은 메타와 정확 Core 스냅샷을 같은 로컬 복구 사본으로 보존한다. 복구 사본 자체를 다시 자동 업로드하지 않는다.
- IDB abort/용량·서버 불가·형식/해시 실패에서 입력·기존 커밋·전송 대기를 유지한다. 오류/빈 결과/미설치와 성공0건을 구분한다.
- 계정 전환·로그아웃/수명 종료 뒤 늦은 조회·전송·다운로드 결과는 설치/화면 반영을 차단한다. 서비스는 자신의 구독·타이머·요청·브라우저 자원을 정리한다.
- online·focus·visible 복귀와 기존 polling으로 재개한다. 숨긴 화면/중복 실행을 억제하며 새 Realtime 의존성은 추가하지 않는다. 자동 전송의 소요 시간이나 실제 물리 기기의 즉시 일치를 보장하는 표현은 쓰지 않는다.

## 원본 첨부의 자동 보관

기존 전용 계정별 Blob DB는 캐시/영속 원본 업로드 대기로 재사용한다. 이전 로컬 ZIP도 현재 검증된 owner의 것만 자동 전송한다. 한 번 정한 archive ID·manifest·operation ID를 먼저 저장하고 모든 청크 업로드 뒤 immutable manifest RPC가 저장을 확인한 다음 계정 보관으로 표시한다. 새 로컬 원본을 커밋하면 이전 saved 상태를 즉시 pending으로 바꾼다. 일부 청크 실패와 응답 유실은 원본·동일 작업을 유지하고 명시 재시도/온라인 복귀로 이어간다.

원본128 MiB·개별 파일64 MiB·파일500개라는 기존 ZIP 한도를 유지한다. manifest2 MiB, 청크는 최대16개·개당8 MiB이며 비공개 `life-library-originals` bucket의 `${ownerUid}/${archiveHash}/${index4}-${chunkHash}` 주소를 사용한다. object replacement/upsert·public/anon 접근 없이 같은 경로의 기존 object는 내려받아 해시가 같은 경우에만 재사용한다. 업로드 완료와 manifest commit을 구분하고 서버 tombstone/없는 manifest를 옛 성공 영수증으로 부활시키지 않는다.

새 기기는 모든 원격 목록 페이지를 자동으로 읽어 메타만 캐시한다. 목록을 보는 것만으로 ZIP 바이트를 전부 받지 않는다. entries/file/archive 열기의 cache miss에서 manifest·청크 경로/크기/해시·전체 ZIP 해시·저장형 ZIP 구조·각 파일 CRC/SHA·manifest의 실제 offset/파일 목록 일치를 확인한 뒤에만 Blob을 설치한다. 실패하면 부분 archive를 정상 캐시로 남기지 않는다. 이후 파일/ZIP 열기에서도 기존 무결성 검사를 유지한다. HTML/PDF/HEIC를 실행하거나 원본을 다시 압축하지 않는다.

인증된 공용 SDK의 Storage 호출은 같은 계정/epoch를 전후 검증한다. UI와 계정 coordinator가 별도 인스턴스여도 DB에 보관된 같은 operation을 재사용하고 계정 범위의 최소 방송으로 상태를 갱신한다. 열린 원본 목록도 배경 카탈로그 변경을 반영하며 공유 서비스는 모달을 닫았다고 폐기하지 않는다.

### 독립 context와 원본 보존

원형 브라우저 최종3차 **5/5**에서 실제 동봉 SDK·계정별 IndexedDB·익명 FakeCloud의 독립 A/B 여정을 확인했다. 같은 기본 자료실 ID·원문/발췌·폴더/Collection/NineBoard/저장 구성 왕복, offline 변경과 source/meta의 유실 ACK·동일 operation, 충돌의 양쪽 명시 복구, 자동 원본 목록·열 때 ZIP 다운로드와 무결성 검증, 실제 두 expectedRevision0 요청의 최초 CAS 경합을 통과했다. 이 실행의 소스22개가 전후 동일했고 오류/외부 요청0, 컨텍스트11개와 브라우저를 정리했다. 합성 context는 물리 기기나 실제 사용자 자료 전체의 증거가 아니다.

원본 집중19개는 기존 ZIP 검수4개와 원격 adapter·전송 복구 검사다. 8 MiB 경계를 넘는 합성 ZIP 청크 왕복·응답 유실 재개·일부 청크 실패·동시 인스턴스·캐시 commit 실패·계정 epoch 변경·손상/다른 owner·구형 capability0·tombstone·ACK 전 pending을 확인했다. 이 집중 검수의 DB는 직렬화한 native-request 합성 adapter이고 실제 IDB 경계는 위 브라우저 실행으로 구분한다.

첫 통합 브라우저의 손상 청크는 안전하게 거절됐지만 saved 상태가 파일 열기 오류 안내를 숨기는 실제 UI 결함이 있었다. 사용자 동작 오류와 배경 상태·자동 목록 갱신을 분리한 뒤 해당 원형 흐름이 통과했다. 이어 새 기본 공간의 빈 Workbench 최초 수신에서 실제 expectedRevision0 경합을 확인해 초기 기준/영속 작업과 양쪽 복구를 보완했다. 최종5흐름은 원래 단언·제한시간을 유지했고 실제 경합 두 요청도 확인했다. 합성 입력 준비/비동기 대기 조건을 고친 부분과 제품 결함 교정은 첫 기록을 남겨 구분했다.

1440/820/390px 화면을 기록한 뒤 자료 화면의 불필요한 브라우저 보관 설명과 실제로 미확보되지 않은 대상에 뜨던 경고2개를 좁게 교정했다. 마지막 교정의 focused 왕복1흐름과 새3폭이 통과했고 SourceFoldersUI를 포함한 검사 소스23파일은 전후 동일했다. 실제 확보된 분류의 미확보 경고는 숨김/빈 텍스트이며 이전 설명 문구는0, 최신 확인 버튼 뒤 정확 그래프도 유지했다. 실제 미확보1개 경고와 새로운 bundle identity 도착 뒤의 숨김은 별도의 읽기 전용 메모리 UI2사례로 확인했고 쓰기0이다. 이 메모리 검사를 실제 IDB 사례로 확대하지 않는다. 최종 focused 실행의 오류0·컨텍스트2개/브라우저 종료를 확인했으며 앞선 전체5흐름과 마지막 표시 교정 검수의 소스 범위를 구분한다.

### 로컬 SQL과 운영 HTTP

실제 PostgreSQL의 **SQL28개(두 세션 경합2개 포함)**와 PGlite **26개**가 통과했다. 동일한 검토 SQL/고정 실행 환경으로 권한·원자 CAS·같은 operation replay·경로/실제 object 크기·불변 manifest·tombstone 경계를 검수하고 검사 소유 프로세스/컨테이너를 정리했다. PGlite만의 성공을 실제 PostgreSQL이나 hosted Storage 호환으로 대신하지 않았다.

실제 설정된 Supabase에서 합성 A/B 계정의 **HTTP26개(기능24+검사 세션 로그아웃2)**를 통과했다. Core/메타의 정확 Unicode·revision CAS·replay·다른 owner 거절, 비공개 원본 **2,458바이트**의 SHA 왕복·manifest commit/같은 operation replay, 다른 계정·익명의 읽기/쓰기 차단을 확인했다. 익명 FakeCloud 결과와 이 실제 서버 전송은 별도 근거다. 사용자의 개인 자료를 시험 전송하지 않았다.

운영의 최초16개가 통과한 뒤 정상 owner의 Storage 업로드가400 AccessDenied로 거절되는 실제 결함을 발견했다. 현행 Storage preflight는 크기 metadata가 아직 없는 상태로 INSERT 권한을 검사하므로 해당 사전 단계와 최종 object 검증을 구분하는 두 번째 SQL로 교정했다. 이후 실제 업로드/해시·거절 경계는 통과했지만 manifest PUT에서 기존 Storage의 owner 열과 함수 지역 변수 이름이 충돌해42702가 발생했다. 세 번째 SQL은 그 지역 변수 이름과 참조만 바꾸고 권한·경로·한도·불변 검증을 유지했다. 세 검토본 설치 뒤 최종HTTP26개가 통과했다. 최초 실패·단계별 보고서는 보존하며 첫 로컬 통과를 운영 호환 성공으로 소급하지 않는다.

합성 검사에서 새로 만든 source/meta/receipts는 정확한 검사 UUID guard로 한정해 정리하고 남은 대상0을 확인했다. 정책상 불변인 private QA 원본2,458바이트는 테스트 owner에 유지했다. 정리를 위해 일반 사용자 DELETE/UPDATE·bucket 공개 권한을 넓히지 않았다. 전체 프로젝트/기존 사용자 자료 삭제나 정리 완료로 표현하지 않는다.

## 완료 기준과 다음 큰 작업 묶음

이번 완료 기준은 독립 A/B context의 같은 기본 ID 선택→자료/폴더/발췌/묶음/Collection/NineBoard 왕복→원본 ZIP 재선택 없는 목록/열기→오프라인/유실 ACK/동시 변경·양쪽 복구→계정 전환/없는 서버/실제 IDB 실패 보존과 기존 회귀·PWA·권한/설치·출시 근거다. 구현된 메타/원본 클라우드를 다음 작업으로 다시 분할하지 않는다.

1. **실제 두 기기의 자료 활용 완주:** 자동 검수와 별도로 사용 중 기기에서 분류·읽기·수정·파일 열기의 부담을 확인하기 위해서다. **선행:** 이번 릴리스·소유자의 기기/계정·직접 고른 대표 자료/원본. **완료:** A에서 가져오기/분류/발췌→B에서 로그인·같은 정확 원문/원본 열기→B 수정→A 반영→오프라인/앱 복귀·백업을 실제로 대조하고 필요한 수정만 채택한다.
2. **내부 문서·첨부의 정확 연결 활용:** 계정에 보관한 파일과 문서의 원래 링크 목적지를 활용하기 위해서다. **선행:** 명시한 보관함 범위·정확 버전 관계·사용자 연결 선택. **완료:** 동명 파일·헤더/블록·없는 첨부를 구분하고 선택 연결→문서/첨부 왕복→내보내기/복구를 확인한다. 파일 자동 보관만으로 위키 링크 해석·전체 플러그인 지원을 완료한 것으로 표시하지 않는다.
