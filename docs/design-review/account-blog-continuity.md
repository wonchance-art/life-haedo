# 홈에서 서버 글을 찾아 같은 글 이어쓰기

**최신 CI 발견·수정 검수:** [PR123 첫 CI](https://github.com/wonchance-art/life-haedo/actions/runs/39555949573)는 기존 글 관리의 인용 근거 원문 복귀에서 실패해 병합 전에 중단했다. 로컬 원형의 20초 실패를 재현하고 글 관리 렌더 완료 대기와 선택 글 ID의 복귀 문맥 유지를 보완했다. 원래 단언·20초 제한을 유지한 원형 수정 후 1개·확장 focused 1개·전체 글 관리 6/6을 Node22.23.3/Chromium151에서 통과했다. 정확 원문·초점, 지연된 선택행, 전체 관리44개·본문/근거 보존과 추가 원격 쓰기0을 확인했으며 전체 검수의 시각3개·콘솔/페이지 오류0, 수정 후 정적22HTML/148JS/630참조와 독립 검토 차단0을 확인했다. 아래 SQL6·단위1142·10개 소스 해시는 이 복귀 수정 전 런타임의 근거다. 최종 HEAD의 전체 CI125단계와 출시는 아직 미확정이다.

## 목표와 기존 기능의 재사용

한 기기에서 명시 저장한 여행 글을 다른 기기의 홈에서 찾아 받아 쓰고, 수정·재보관한 뒤 선택 공개와 방문자 읽기까지 이어간다. 이미 있는 서버 목록·새 사본 받기·원본 검증·수정·충돌 복구·공개를 새로 만들지 않는다.

착수 당시 홈은 로컬 글·초안·보관함을 읽고 서버 글은 글 관리에서 별도로 찾았다. 기존 수신은 명시할 때마다 새 사본을 만드는 계약이다. 홈의 발견 동선과 같은 서버 글의 현재 로컬 사본으로 재개하는 경로를 연결했다.

## 사용 흐름

1. 홈의 **서버에 보관한 글**에서 본문 중심 계정 목록(`account-blog`)을 연다. 현재 작업공간과 로컬 초안은 유지한다.
2. 계정 서버의 글 메타데이터를 현재 작업공간의 연결 정보와 대조한다. 목록 조회만으로 글 본문·사진을 다운로드하거나 로컬 자료를 업로드하지 않는다.
3. 유효한 연결이 있으면 같은 로컬 글을 다시 연다. 연결된 로컬 글이 서버 최신판과 같다고 추정하지 않고, 서버 새 판·로컬 변경·보관 중지·충돌을 구분한다.
4. 연결이 없으면 사용자가 고른 서버 revision을 확인하고 원본을 받아 현재 공간에 새 로컬 사본을 설치한다. 다른 작업공간으로 강제 이동하거나 새 공간을 만들지 않는다.
5. 서버 새 판은 해당 글 관리 진입에서 읽어 비교하며 로컬 본문을 자동 교체하지 않는다. 충돌은 기존 비교 화면에서 명시 선택하고 선택하지 않은 쪽의 복구 사본과 기존 초안을 보존한다.
6. 작성기의 명시 저장은 기존 비공개 서버 보관을 사용한다. 공개할 내용·사진 선택과 게시·갱신·철회는 기존 별도 흐름을 따른다.

## 정확 재개와 원자 설치 계약

- `openRemote(workspaceId, remoteId, { expectedRemoteRevision, localPostId?, isCurrent? })`는 현재 계정·공간과 선택한 글을 검증한다. `isCurrent`로 화면 수명도 확인해 이동 뒤 늦은 결과를 차단한다. 기존 유효 연결은 같은 ID로 재개하며 열기 자체가 새 사본을 만들지 않는다.
- 새 수신은 선택 row의 정확 revision과 실제 서버 문서를 대조한다. 사진 다운로드·hydrate 뒤 최종 head를 다시 조회해 revision·원래 공간·manifest 내용이 같은지 확인하고 설치 직전 scope도 검사한다. 도중 서버 판이 달라지면 재확인하며 다른 판을 조용히 대신 설치하지 않는다.
- 새 로컬 글·사진 ID를 발급하고 문서·목록 요약·서버 연결·수신 영수증을 한 트랜잭션에 설치한다. 다운로드·검증 실패나 트랜잭션 abort는 부분 문서·연결만 남기지 않는다.
- 같은 공간의 동시 탭·중복 클릭·재진입에서는 영수증과 현재 연결을 다시 확인해 설치를 한 번으로 제한한다. 새 operation만으로 같은 글을 또 만들지 않는다.
- 서버 `remoteId`는 기기 간 같은 글의 논리적 기준이고 로컬 ID는 기기별 사본이다. 수정 저장의 `replaces`로 로컬 ID가 교체되면 연결·영수증도 원자적으로 현재 글을 가리킨다.
- 초안·보관함·명시한 서버 보관 중지 상태를 재개 편의를 위해 자동 변경하지 않는다. 이전 사본·다른 글·개인 메모를 덮어쓰지 않는다.
- 기존 `receive`의 **명시 새 사본 받기**는 유지한다. 이 별도 동작과 같은 글 재개를 동일한 의미로 바꾸지 않는다.
- 해당 글 관리의 `inspectRemote(workspaceId, localPostId, { isCurrent })`는 서버 판을 읽어 비교만 한다. 보관 중지·응답 미확정 전송·게시/철회 대기가 있으면 건너뛴다. 비교 메타데이터만 로컬 revision·상태 CAS·`isCurrent`를 검사하는 native 트랜잭션에서 반영하며 업로드·자동 본문 수신·공개를 시작하지 않는다.

## 보존·권한·실패 경계

- 기존 `Blog.hydrate`와 PhotoPost 검증으로 정확 본문·사진 선언·형식·크기·해시·원본 바이트를 확인한다. 사진을 재압축하거나 새 형식으로 변환하지 않는다.
- 서버 글에 있는 인용 문자열·출처 URL과 별도 구조화 근거를 구분한다. 원문 자료·근거 sidecar·개인 메모·작성 준비가 자동 수신됐다고 표시하지 않는다.
- 읽기·서버 목록·새 사본 설치가 서버 업로드·공개를 새로 시작하지 않는다. 공개 사진은 기본 미선택이며 공개본 갱신·철회는 별도 명시 동작이다.
- 목록·본문·사진·저장 중 계정이나 작업공간이 바뀌면 이전 결과를 차단한다. 타 계정 연결이나 제목 일치로 같은 글을 추정하지 않는다.
- 목록의 성공·빈 목록·조회 실패를 구분한다. 실패를 빈 목록이나 성공으로 표시하지 않고 기존 로컬 글·입력과 재시도 경로를 유지한다. 모든 내부 오류 종류를 별도 화면으로 구분한다고 약속하지 않는다.
- 초안 자동 저장의 300ms/2000ms 기준과 hidden/pagehide의 최선의 노력 보관은 유지한다. 기기 간 초안 자동 이동·실시간 공동 편집·강제 종료 시 마지막 입력 보장을 추가하지 않는다.

## 구현 선택과 오픈소스 재사용

기존 `blog-remote`/`blog-sync`의 계정 확인·CAS·영속 작업 영수증, PhotoPost/Blog 모델, 작성기·글 관리·공개 렌더러를 재사용한다. 새로 필요한 것은 현재 공간의 연결 투영과 원자 수신·재개 어댑터다. 별도 동기화 엔진은 같은 문서·사진 검증과 충돌 정책을 중복하고 기존 영수증과 다른 성공 기준을 만들므로 도입하지 않는다.

동봉 Quill·idb·Supabase SDK와 native DOM을 유지한다. [기존 오픈소스 선정·라이선스 검토](../life-tools-design/open-source-review.md)와 [글 원본·보관 계약](../life-tools-design/blog-completion.md), [앞선 기기 왕복·복구 검수](blog-continuity-usability.md)를 재사용한다. 새 라이브러리·vendor 버전 변경·새 글 형식은 없다. 앞선 검수 수치를 이번 연결 기능의 완료 증거로 재사용하지 않는다.

## 로컬 검수와 증명 범위

- **최종 전체 여정 6/6:** 실제 SDK·IndexedDB·격리 SQL에서 앞선 다섯 흐름인 홈 발견·검색·정확 재개·복귀 초점, 4032px 원본을 포함한 사진 두 개, 초안·중지·양쪽 복구 사본, 한 사진 선택 공개·익명 읽기·철회 후 404를 모두 다시 확인했다. 추가 흐름은 수정하지 않은 수신 기기에서 서버 새 판을 발견→글 관리 진입의 비교만으로 충돌 확인→명시 서버 선택의 새 사본 설치와 기존 사본 중지다. 비교 단계의 서버 저장·업로드·공개 쓰기는 0이며 로컬 본문·두 원본·초안을 보존했다. 명시 선택 뒤에도 같은 공간과 서버 head·비공개 상태를 유지했다.

첫 SQL 연계 여정의 목록 복귀 초점 실패는 렌더 완료 대기로 보완하고 원래 단언·제한 시간으로 전체5개를 통과했다. 확장한 여섯째 흐름의 첫 fixture 실패는 기억된 검색어와 수정 제목의 불일치였으며 화면·SQL로 원인을 확인했다. 검색 기억 유지 단언 뒤 명시 검색어 지우기를 추가하고 제품·원래 단언·25초 제한 변경 없이 최종6개를 통과했다. 로그인 복귀 route는 실패 재현 뒤 Auth24/24, 생성 사이트의 신규 asset은 공개 allowlist 보완 뒤2/2로 확인했다. 실패 증거는 보존하며 최종 CI·출시 성공으로 확대하지 않는다.

전체6개 검수 뒤에는 양쪽 모두 수정됐다고 추정하지 않도록 글 관리 상태 문구 1건만 정리했다. 동작 변경은 없으며 위 10개 해시 동일성은 이 문구 정리 전 검수 시점의 증거다. 최종 CI125단계에서 전체6개를 포함해 최종 HEAD를 다시 검수할 예정이며 성공·출시를 선취하지 않는다.

최종 통합 CI·출시 결과는 변경 PR에 기록한다. 실제 Google·Apple·개인 글 전송과 사용자 기기 조작은 수행하지 않았으며, 합성 lifecycle·화면 폭 검토를 실제 기기 체험으로 표현하지 않는다.
