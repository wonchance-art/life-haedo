# 분류 파일을 자료실에 연결

2026-10-18 UTC. 사용자의 최신 정의는 **외부 여러 곳에 흩어진 내 글을 가져와 통합 관리하는 도구**다. 이번 실행은 기존 분류 JSON을 사용자가 선택해 자료실의 정확한 원문과 연결하고 다시 찾는 흐름이다. [구현 전 화면·보존 계약](../../.impeccable/source-classification-direction.md)을 먼저 작성했다. 기존 미니멀 홈 비교 시안과 사용자 선택 전의 운영 시각 기준은 변경하지 않는다.

## 사용 흐름

`npm run dev` 후 [로컬 자료실](http://127.0.0.1:4173/index.html?section=records)에서 로그인한 계정의 기존 자료를 연다. Git 출처를 보존한 자료가 있는 작업공간에서 아래 흐름을 확인한다.

1. 자료실에서 분류 파일을 고른다. 선택만으로 저장하거나 원문을 가져오지 않는다.
2. 파일 구조와 연결 근거를 검증하고 적용할 분류·연결/미연결 범위를 미리 본다. 다른 출처·변경된 원문·보조 자료를 성공한 글 연결로 표시하지 않는다.
3. 명시적으로 이 계정·작업공간의 브라우저에 적용한다. 기존 자료실에서 출처·주제·형태·확인 필요로 좁혀 읽는다.
4. 정확한 원문 버전을 열고 돌아오면 기존 검색·분류 필터·표시 범위·목록 위치·초점을 복원한다.
5. 새로고침 후 로컬 적용을 유지한다. 분류 메타데이터는 별도 파일로 내보내고 다시 선택할 수 있으며, 연결 지우기는 원문을 남긴다.

필터는 분류 관점이며 원문 태그나 작성자 판정이 아니다. 자동 1차 추정의 확인 필요 상태를 확정 분류와 구별한다. 원문이 아직 없는 항목을 새 자료로 만들거나 최신 원문에 분류를 추정해서 붙이지 않는다.

[실제 UI](../../assets/life/source-classification-ui.js)는 자료실의 접힌 `분류`에서 `분류 파일 불러오기 → 적용 전 검토 → 이 브라우저에 적용`으로 이어진다. 미리보기는 연결 가능·현재 작업공간에서 찾지 못함·본문 불일치/확인 불가·대상 모호함을 나눈다. 연결 가능한 원문이 없으면 적용하지 않으며 다른 작업공간에 있는 자료라고 추정하지 않는다. 적용 후 필터 이름은 `분류 출처 / 주제 후보 / 자료 유형 / 분류 확인`이고, 분류 확인은 확인 필요·주제 미확정·미연결을 구분한다. 원문 상세의 `분류 후보`도 실제 일치한 버전에만 표시한다.

## 정규화와 저장 경계

저장·내보내기 형식은 `format: "life-source-classification-v1"`이다. [순수 모듈](../../assets/life/source-classification.js)의 `parse`는 기존 `schemaVersion: 1` 분류 결과와 정규화 파일을 읽고, `validate`는 정규화 형식을 재검증한다. 입력의 허용 필드만 골라 남기며 DOM·계정·서버를 건드리지 않는다. 파일은 UTF-8 32MiB·자료 10,000개·주제 200개 이내다. 중복 경로/주제 ID, 잘못된 해시·문자열·상대 경로·주제 참조를 거부하고 Unicode 파일명의 원래 표기는 바꾸지 않는다.

| 범위 | 남기는 값 |
| --- | --- |
| 파일 | sourceCommit, taxonomy, records |
| 항목 | path, sha256, isContent, source의 id/label, kind의 id/label, topicIds, primaryTopic, reviewReasons |
| 버리는 값 | title, preview, body와 원작성자/소유자 결론 등 허용 목록 밖의 원본 내용 |

별도 내보내기에도 같은 제한을 적용한다. 제목·본문이 빠져도 상대 경로·분류·출처는 개인 정보일 수 있으므로 공개용 파일로 표시하지 않는다. 개인 분류 JSON·원문·기존 비공개 산출물을 저장소·앱 런타임·검증 캡처에 넣지 않는다.

`분류 파일 내려받기`는 정규화한 `source-classification.json` 다운로드를 요청한다. 다운로드 요청을 실제 파일 보관 완료로 표시하지 않는다. `이 브라우저의 분류 지우기 → 분류표만 지우기`는 적용값만 지우며 원문과 이미 내려받은 파일은 남긴다.

적용값은 [Storage](../../assets/life/storage.js)의 계정·작업공간별 독립 `meta`에 CAS로 저장한다. 상태 형식은 `life-source-classification-state-v1`이며 revision과 정규화 manifest를 갖는다. 지우기도 revision을 올린 `manifest: null` 상태를 남겨 오래된 적용을 막는다. 원문 bundle·버전·기존 태그·링크·발췌를 다시 쓰지 않고, 일반 JSON 백업·구성/원문 동기화·공개 payload에 섞지 않는다. 저장 실패·revision 충돌에는 이전 적용값을 유지하고 재검토할 수 있게 한다. 계정·공간 변경과 늦은 파일 읽기는 다른 범위의 분류를 노출하거나 덮어쓰지 않는다.

## 정확한 연결

현재 연결 범위는 Git 출처를 보존한 Obsidian 가져오기 자료다. `sourceKey`의 원래 상대 경로와 `https://github.com/<소유자>/<저장소>/blob/<40자리 commit>/<경로>`를 함께 확인하고 실제 보관 본문의 SHA-256을 분류 파일과 대조한 정확 버전만 연결한다. 일반 네이버 URL만 가진 다른 가져오기까지 연결됐다고 표시하지 않는다. 분류표의 source는 원래 자료의 플랫폼 정보이며 이 연결 식별자와 역할이 다르다.

보관된 해시 문자열만 맞는 것으로 본문 일치를 대신하지 않는다. 경로만 같거나 파일 출처가 다르면 연결하지 않고, 같은 경로·commit 후보가 여러 저장소에 있으면 모호한 항목으로 분리한다. 본문 미확보/null은 해시를 검증할 수 없어 연결하지 않는다. 이후 편집된 최신 버전에 이전 분류를 자동 승계하지 않으며 원문·UTF-16 구간과 버전 관계는 그대로 둔다.

글/메모와 보조·추출물을 구별한다. 일부 연결 실패와 전체 결과 없음은 다르게 안내하고, 새 분류 파일·새로고침·지우기 뒤에는 기존 자료실 필터와 충돌하는 상태가 남지 않게 한다. 지우기·분류 파일 내보내기는 원문 삭제·자료 백업·동기화·공개가 아니다.

## 구현 선택과 확인 범위

[기존 오픈소스 검토](../life-tools-design/open-source-review.md)의 Core·브라우저 파일 API·로컬 저장/CAS 재사용 결정을 이어 쓴다. 새 분류 SaaS/API는 비공개 메타데이터 전송과 계정·운영 비용을 만들고, 범용 importer/상태 라이브러리는 기존 파일 검증·정확 버전·저장 경계를 다시 구현하게 한다. 이번에는 네이티브 파일 읽기·JSON·기존 해시·저장 엔진을 재사용하고 작은 허용 목록 정규화/연결 어댑터만 유지한다. 새 패키지·DB·schema·네트워크 요청은 추가하지 않는다. 외부 공식 문서나 최신 릴리스·라이선스·보안 권고를 이번 작업에서 원격 확인했다고 주장하지 않는다.

## 실제 분류 파일의 오프라인 대조

개인 분류 파일은 저장소·웹 루트 밖에서 새 순수 모듈로만 정규화하고 기존 비공개 원문 사본과 대조했다. 브라우저·운영 DB·앱 계정은 사용하지 않았다. 전체 **6,899개**를 정규화했으며 노트 작업공간 **3,479개 중 3,478개**는 실제 원문 SHA가 일치하고 본문 null인 **1개**는 연결하지 않았다. 보조 파일 **3,420개**는 모두 일치했다. 모호한 연결과 원문 변경은 각각 **0개**다. 제목·preview·authorship·body·existingTags·copyPath 필드가 정규화 결과에 없음을 확인했다. 이 공개 문서에는 집계만 남긴다.

이 대조는 개인 원문의 주제 정확도·저자 확정이나 사용자 브라우저 설치를 증명하지 않는다. 자동 1차 분류 후보의 정확 원문 연결을 검증한 것이며 기존 서버 자료와 원본 파일은 바꾸지 않았다.

## 앱 검증 상태

Node 전체 **543개**, 기존 검색 브라우저 **7개**를 통과했다. 새 [분류 브라우저 검사](../../tests/source-classification-browser.cjs)는 [최종 8/8](evidence/source-classification/browser-final.json)이다. [전체 실행 7/8](evidence/source-classification/browser-report.json) 뒤, 남은 지연 응답 사례에서 접힌 관리 패널을 visible로 기다리던 검사 helper만 attached 기준으로 수정해 해당 [1/1을 재검증](evidence/source-classification/recheck-report.json)했다. 이를 수정 뒤 전체 8개를 다시 실행한 결과로 표현하지 않는다. 로컬 원시 결과와 별도로 위 파일을 저장소에 보존했다.

Linux Chromium **151.0.7922.173**, 실제 앱/SDK·IndexedDB·두 브라우저 탭과 익명 모의 Auth를 사용했다. 합성 원본 **97개(내용 Markdown 96개·보조 Markdown 1개) / 불변 버전 98개**로 BOM·CRLF·emoji·동명 경로·이전 버전을 다뤘다. console/page 오류·외부 요청·실제 원격 쓰기는 각각 **0**이며 개인 자료는 브라우저·캡처에 넣지 않았다.

- 1440·390px에서 명시적 파일 검토/적용, 네 필터와 기존 검색의 교집합, 40개 더보기, 정확한 이전 버전 읽기와 원래 조건·초점·스크롤 복귀, reload·정규화 내보내기를 확인했다.
- 잘못된 commit/경로/hash와 바뀐 실제 본문을 연결하지 않고, 다른 작업공간에 자동 적용하지 않았다. 저장 중단/재시도는 검토 후보·원본을 보존하고 명시적 지우기는 tombstone으로 지연 저장을 막았다.
- 두 탭의 CAS, 진행 중 읽기/해시 계산보다 늦게 도착한 최신 revision, 지우기 뒤 늦은 읽기, 저장 뒤 해시 대조 중 다른 탭의 갱신, 화면·공간·계정 전환과 익명 진입의 격리를 확인했다. 원문 bundle의 fingerprint는 동일했다.

최초 앱 결함은 390px에서 읽기 복귀 때 관리 패널이 접혀 문서 높이가 줄고 스크롤이 351→0px가 되는 현상이었다. 같은 작업공간의 패널 펼침을 화면 세션에 유지해 복귀를 고쳤다. 확인 불가/null 본문에는 분류 후보 대신 설명만 남기고, 주제 미확정 필터는 보조물과 구별하며, 처리 중 다른 탭의 새 revision이 묻히지 않도록 보완했다.

[기존 앱 모션 9/9·하위 탐색 11/11](evidence/source-classification/regressions.json)도 통과했고 두 흐름의 console/page 오류는 0이다. 네트워크와 HTTP 캐시를 끈 상태에서 새 자산을 서비스워커의 200 응답으로 받고 합성 분류 메타데이터·원문 bundle 불변과 원격 쓰기 0을 확인했다. 의도한 전송/콜백 오류 3건은 실패 복구 검증이며 예상하지 않은 console/page 오류는 0이다. [플랫폼 실행 로그](evidence/source-classification/platform-browser.log)를 함께 보존했다.

실제 Mac/iPad/iPhone·IME·Files·VoiceOver·운영 OAuth/DB·이번 분류의 사용자 계정 적용·공개 배포는 미검증이다. 개인 파일의 오프라인 대조, 익명 앱 검증, PWA 갱신과 운영 반영을 같은 완료로 표시하지 않는다.
