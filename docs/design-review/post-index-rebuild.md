# 글 목록 재구성 · 200개 상한 제거 · 일정 날짜 통일 (2026-11-16)

소유자 결정 8(일정 목록과 달력의 날짜를 처음 쓴 날로 통일)과 10(글 200개 상한 제거, 글 색인 재구성과 함께)의 구현 기록이다. 작업 지시서 A(총괄), 기준 커밋 `c76e693`(`haedo-v220`).

## 무엇이 바뀌었나

- **글 목록 행:** 전에는 작업공간마다 `photo-posts:${ws}` 한 행이 모든 글의 요약과 본문 전체(일반 텍스트)를 들고 있었고, 저장·자동 저장마다 그 행 전체를 읽고 다시 썼다. 이제 글마다 `photo-summary:${ws}:${id}` 한 행을 둔다(id·제목·상태·판·`createdAt`·`updatedAt`·일반 텍스트 `body`·사진 수·첨부 수·숨김). 저장은 그 글의 행만 쓴다.
- **문서가 기준:** `photo-post:${ws}:${id}` 문서가 그대로 원본이다. 목록을 읽을 때(`listPhotoPosts`) 행이 없거나, 형식이 틀리거나, 문서보다 뒤처졌으면 문서에서 다시 만들고, 문서가 없는 행은 지운다. 고치는 쓰기는 읽기와 별도 트랜잭션에서 다시 읽은 뒤 한다. 그 쓰기가 실패해도 이미 문서를 따라 만든 목록을 돌려주므로 잃는 것이 없다. 행과 전체 목록 항목이 서로 맞으면 문서를 읽지 않는다(전의 목록 행과 같은 신뢰). 검증에 실패하는 문서는 전의 목록처럼 보인다. 그 글의 행이 있으면 행으로, 없으면 전체 목록 항목으로 보이고(둘 다 없으면 전에도 목록에 없었다), 그 문서와 행·항목은 고치거나 지우지 않는다. 그래서 BlogSync는 연결을 유지하고, 전체 백업은 그 글을 실패 항목으로 알리며, `scanLocalPosts`도 보고한다(검수 M1: 처음에는 목록에서 뺐고, 연결된 글이면 동기화 주기마다 사진을 다시 내려받았다. 5주기 10회 → 0회로 고정). 검증 오류가 아닌 예외(모듈 누락 등)는 "글 없음"으로 읽지 않고 그대로 던진다. 글이 없는 작업공간은 전체 목록 행이 없어도 쓰지 않는다.
- **상한 없음:** `writePhotoPost`의 200개 검사와 `editsStoredPost`, 계정 없는 자료 편입(`copyUnownedPosts`)의 200개 건너뛰기, 일정 목록의 190개부터의 안내 줄(`postCapacity`·`limitText`·`POST_LIMIT`, 상한 필터)을 없앴다. 첨부 글 `page.posts` 200개(`page-posts.js`, 마이그레이션 `20261012010000`)는 범위 밖이라 그대로다.
- **일정 날짜:** 목록의 정렬과 날짜 머리는 `createdAt`(없으면 `updatedAt`)으로 한다(`HomeUI.writtenAt`). 달력은 원래 `createdAt`을 썼지만 목록 행에 없어서 글마다 문서를 읽었다. 이제 행의 `createdAt`을 쓰고 문서를 읽지 않는다. 글 행의 시각 칸과 "수정 …" 표시는 그대로 `updatedAt`이다(총괄 결정). `작성하던 글` 띠는 가장 최근에 고친 초안을 계속 고른다. 검색 범위 안내는 "처음 쓴 날 기준 최근 순입니다"로 바꿨다.
- **글 몇 개만 읽기:** `readPostSummaries(ws, ids)`는 같은 규칙으로 몇 글의 행만 읽는다. 열린 편집기가 자동 저장 뒤 자기 글과 고치는 대상 글을 확인할 때 쓴다(검수 m2: 전에는 저장마다 목록 전체를 읽었다). `listBlogSyncStates(ws, { posts: false })`는 목록 없이 상태만 읽으며, 일정 목록의 공개 상태 표시가 쓴다.
- **같은 행을 읽는 곳:** `listBlogSyncStates().posts`(BlogSync), `readPreservationCatalog`, 자료 준비의 수정 초안 찾기가 같은 목록 함수(`readPostList`)를 쓴다. `listPhotoPosts`의 모양(배열, 각 항목의 필드)은 `createdAt`이 더해진 것 말고 같다. 순서는 `createdAt` 오름차순(같으면 id)으로 정했다. 전에는 이 기기에 들어온 순서였다.
- **진단:** `scanLocalPosts`의 `indexState`는 글 행과 전체 목록 행이 둘 다 문서와 같으면 `listed`, 둘 다 없으면 `missing`, 그 밖은 `mismatch`다. 저장된 행을 그대로 보고하며 고치지 않는다.

## 과도기 호환 (총괄 결정 B안)

IndexedDB `DB_VERSION`은 올리지 않았다(`meta` 저장소에 행만 더한다). 서비스워커가 다음 판을 받기 전까지 열린 탭이나 다른 기기가 `haedo-v220` 이하를 돌릴 수 있으므로, 한 판 동안 `photo-posts:${ws}`를 계속 완전하게 쓴다.

- 모든 글이 빠짐없이, id·제목·상태·판·`updatedAt`·사진 수·첨부 수·숨김은 문서와 정확히 같게 들어간다. 이전 판의 BlogSync는 이 판 번호로 "올릴 것"을 고르므로 정확해야 한다(틀리면 매 주기 헛 업로드).
- **본문만 잘라 쓴다:** 300자보다 긴 일반 텍스트는 앞쪽 공백을 뺀 첫 300자(서로게이트 쌍은 자르지 않음)다. 이 행은 여전히 저장마다 다시 쓰이고, 크기의 대부분이 본문이었기 때문이다. 내용이 있는 글은 잘린 뒤에도 비지 않으므로 이전 판의 "빈 초안" 판정(목록 숨김·글쓰기 재사용)이 바뀌지 않는다. 이전 판의 미리보기(160~200자)도 그대로 나온다.
- **이전 판이 쓴 글의 감지:** 이전 판은 자기 항목을 본문 전체로 다시 쓴다. 새 판은 전체 목록 항목이 글 행과 다르면(판·제목·상태·시각·수·본문) 그 글을 문서에서 다시 읽는다. 이전 판이 지운 글은 문서가 없으니 행을 지운다. 이전 판 형식(본문 전체) 항목은 다음 목록 때 한 번 잘린 형식으로 다시 쓴다.
- 전체 목록 행이 없거나 깨졌으면, 새 판은 쓰기 전에 문서에서 먼저 다시 만든다(이전 판이 일부만 든 목록을 읽지 않게).

수정 전(27e291d) 세 번 돌린 값은 자동 저장 5.9~8.8 ms(CPU ×4 24.7~49.6 ms)였다. 그때는 편집기가 자동 저장마다 목록 전체(17.2~31.6 ms, CPU ×4 58.9~108.4 ms)를 읽어 저장 개선이 거의 상쇄됐다(검수 측정 CPU ×4: 저장 163 → 47.5 ms, 목록 54.8 → 133.8 ms). 일정 목록의 공개 상태 읽기도 `listBlogSyncStates(ws, { posts: false })`로 목록을 다시 읽지 않는다.

- **목록 읽기는 느려졌다.** 같은 양의 본문을 행 하나가 아니라 250개 레코드로 읽기 때문이다. 같은 페이지에서 따로 잰 값(5회 중앙값): 글 행 250개 `getAll` 14.6 ms, 문서 키 250개 `getAllKeys` 1.2 ms, 전체 목록 행 `get` 1.2 ms, `listPhotoPosts` 전체 29.5 ms. 목록은 화면을 열 때와 BlogSync 주기(30초)마다 두 번 읽는다. 편집기의 자동 저장 뒤 읽기는 이제 목록을 읽지 않는다. 이 맞바꿈을 받아들였고, 목록이 문제가 되면 본문 없는 작은 행과 본문 행을 나누는 것을 실험한다(바꿀 조건: 실기기에서 목록 표시가 눈에 띄게 늦을 때).

- 첫 목록(업그레이드)은 문서 250개를 한 번 읽어 행을 만든다. 그 뒤로는 문서를 읽지 않는다(Node 검사로 고정: 두 번째 목록의 문서 읽기 0, 쓰기 0).
- 남는 비용: 과도기 동안 저장마다 잘린 전체 목록 행(글 수 × 약 0.5~1 KB)을 다시 쓴다. 다음 판에서 이 행을 없애면 저장은 문서와 그 글의 행만 쓴다.
