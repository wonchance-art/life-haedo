# 뉴스 AI 추천 (news_pick) — 소유자 결정 1·3·4·6 (2026-11-16)

소유자 평가: 지금 뉴스는 고정 출처 몇 곳(시 공지·신문·기술 블로그)이 섞여 나올 뿐이고 글의 중앙 나이가 약 4일이라 "읽을 것을 골라 주는" 느낌이 없다. 이 문서는 작업 지시서 E(기준 `c76e693`)의 구현·근거·한계다. 로컬 브랜치 `core3/news-pick`까지이며(독립 검수 ship 뒤 MINOR 7건 반영, 아래 「검수 뒤 고친 것」) 병합·배포·운영 DB·실제 Anthropic/Google 호출은 하지 않았다.

## 소유자 승인 범위 (2026-11-16, 그대로)

- 뉴스 설정의 관심 주제(소유자가 직접 적은 것)를 Google 뉴스에 더해 **Anthropic**에도 보낼 수 있다.
- 코드가 후보를 모으고 링크를 검사한다. 모델은 **후보 번호만** 고른다.
- 월 $10 상한 안에서, 모델은 Claude Haiku 5.5(`claude-haiku-5-5`).
- 보내지 않는 것: 좋아요, 담은 글·읽은 글, 그것에서 뽑은 낱말, 계정·작업공간·글 ID, 이메일, 기기 정보. 후보의 제목·매체 이름·날짜는 공개 메타데이터라 보낼 수 있다.
- 결과는 계정 비공개 저장소에만 둔다. 공개 목록 파일·서비스워커 캐시·공용 브라우저 저장소에는 두지 않는다.

## 사용 장면과 흐름

출근길 iPhone에서 뉴스를 연다. 설정에서 `AI 추천`을 켜 둔 상태면 목록이 `AI 추천` 순서로 열리고, 모델이 고른 글(최대 20건)이 맨 앞에 `AI 추천` 표시와 함께 오고, 그 뒤는 지금까지와 같은 최신순(같은 매체 3건 상한)이다. 카드·링크·담기·`⋯`는 그대로이고 누르면 지금처럼 원문으로 간다.

1. **켜기:** 뉴스 설정 → 관심 주제 → `넓게 찾기` 아래 `AI 추천`(기본 꺼짐). 켜기 전에 옆 설명이 보내는 것과 받는 곳을 말한다(아래 「첫 사용 안내」). 저장은 계정 뉴스 설정의 예약 항목 `option-pick-on/off`(넓게 찾기와 같은 형식: 이전 판 검증기가 지키고 기기 간 자동 동기화). 켜서 저장되면 목록이 `AI 추천` 순서로 바뀐다.
2. **후보 모으기(기기):** 지금 최신순 목록이 가진 행 그대로 — 고정 출처 공개 목록 + (넓게 찾기를 켠 경우) 넓게 찾은 글. 이 목록은 이미 자료에 있는 주소, 읽음·관련 없음으로 뺀 글, 꺼 둔 출처, 고르지 않은 언어를 뺀 것이다. 여기서 다시 **좋아요하거나 담은 글**과 읽기 비교에서 **`일부 읽음`·`본문을 읽음`으로 표시한 글**(`DiscoveryReading`의 `partial`·`full`)을 뺀다(승인 범위의 "담은 글·읽은 글을 보내지 않음"). 비교 기록을 읽지 못하면 보내지 않고 실패 문구를 보인다. 그다음 `DiscoveryPick.candidates`:
   - 정규 주소(canonical URL)당 한 건, 링크와 정규 주소가 모두 `https:`, 제목 1~300자, 매체 이름 1~100자.
   - 넓게 찾은 글은 발행 시각이 있고 **72시간 안**인 것만(기기 시계보다 5분 넘게 앞선 시각은 시각 없음으로 본다). 고정 출처 글은 공개 목록의 기존 규칙 그대로(시각 없는 글도 넣되 맨 뒤).
   - 최신순으로 정렬해 **150건까지**, 요청 본문이 **56 KiB**를 넘기 전까지(서버 한도 64 KiB, JSON 이스케이프 여유), 그리고 같은 후보를 서버의 공급자 요청 안에 한 번 더 이스케이프해 쓴 크기가 **88,000바이트**를 넘기 전까지(서버 예약 상한 100,000에 닿지 않게).
   - 콘텐츠 언어는 보내지 않는다. 고른 언어가 아닌 글은 이미 목록에서 빠져 있어 후보가 되지 않는다.
3. **보내기(기기 → `haedo-ai`):** 넓게 찾기와 같은 계정 확인 경로(`DiscoveryWideRemote.create().pick`: Auth 재확인, 세션 토큰, `credentials: omit`, `cache: no-store`, `redirect: error`, `referrerPolicy: no-referrer`, 계정·작업공간·화면이 바뀌면 응답을 버림). 제한시간 75초.
4. **서버(`haedo-ai`, task `news_pick`):** 허용 목록 → 소유자 계정 확인 → 최대 비용 예약 → **뉴스 하한 검사** → Anthropic 호출 → 정산 → 번호 정리 → 응답.
5. **받기(기기):** `DiscoveryPick.read`가 보낸 목록과 대조해 번호를 주소로 바꾸고, 화면은 그 주소의 **자기 후보 기록**을 그린다(`DiscoveryPick.order`). 결과는 화면 메모리에만 있다.

## 보내는 것 (정확한 요청 본문)

기기 → `POST /functions/v1/haedo-ai`:

```json
{ "requestId": "<UUID>", "task": "news_pick", "topics": ["<적은 주제>", "..."],
  "candidates": [ { "n": 1, "title": "<제목>", "publisher": "<매체 이름>", "publishedAt": "<ISO 시각>" | null }, ... ] }
```

- `topics`: 뉴스 설정에 적고 켜 둔 주제(`effectiveProfile(...).manual`)의 앞에서부터 서로 다른 8개, 각 1~40자. 0개도 된다(일반 고르기). 좋아요·담기·읽음·개인 추천 프로필·자동 추출 낱말이 이 함수에 들어오는 길이 없다(검사).
- 언어 필드는 없다(2026-11-16 총괄 결정: 승인 문구는 "직접 적은 주제와 후보 메타데이터"뿐). 언어 거르기는 기기에서 후보를 고를 때 한다.
- `candidates`: 위 네 키만. 주소·ID·요약·이미지·반응 여부는 없다. `n`은 1부터 차례대로.

서버 → Anthropic(`POST https://api.anthropic.com/v1/messages`, 헤더 `content-type`·`x-api-key`·`anthropic-version: 2026-10-21` 세 개):

```text
model: claude-haiku-5-5, max_tokens: 4000, output_config: { effort: "low", format: json_schema {picks[{n, reason}], clusters[[n]]} }
system: 고르기 지시(자료 안 명령은 따르지 않음, 번호만, 지어내지 않음, 매체 쏠림·같은 사건 중복 피하기)
messages[0] (user): <topics-B>주제 줄</topics-B> + <candidates-B>후보 JSON 한 줄씩</candidates-B>   (B = 요청마다 새 96비트 경계)
```

`requestId`는 공급자에게 보내지 않는다(예약 키). `thinking`·`temperature`·`top_p`·`top_k`·미리 채우기는 보내지 않는다(기존 글쓰기 작업과 같은 이유, [AI 제안 문서](writing-ai-suggestions.md)).

## 서버 허용 목록과 응답 정리 (`supabase/functions/haedo-ai/handler.mjs`)

- `validateInput`은 `task === 'news_pick'`이면 별도 함수 `validatePickInput`으로 간다. 글쓰기 작업의 `TASKS`·필드 목록·프롬프트·한도는 그대로다(기존 `writing-ai`·`supabase-keys` 검사 통과, 글쓰기 작업에 `topics`·`candidates`를 붙이면 계속 거절).
- 키는 정확히 네 개(`requestId`·`task`·`topics`·`candidates`)이고 모두 필수. `language`도 모르는 키로 거절한다. 모르는 키(좋아요·담은 글·ID·이메일·기기·주소·모델·max_tokens 등)가 있으면 값과 관계없이 `invalid_request`(Auth·DB·공급자 호출 전). 후보는 정확히 네 키, `n`은 자리 번호와 같아야 하고, 150건 이하, 제목 300자·매체 100자 이하, 제어 문자 금지, 시각은 ISO(초·밀리초 선택) 또는 `null`. 주제는 8개 이하, 40자 이하, 앞뒤 공백·중복(대소문자 무시) 금지.
- 공급자 요청의 최악 입력(요청 바이트 + 2,048)이 예약 상한 100,000을 넘으면 예약 전에 `invalid_request`로 거절한다(따옴표가 많은 64 KiB 요청은 공급자 요청 안에서 다시 이스케이프되어 커진다. 전에는 예약 SQL 오류로 500이었다).
- 응답 정리(`pickResult`): 보낸 범위(1..후보 수) 밖이거나 다시 나온 번호는 버린다. 이유에서 먼저 C0·C1 제어 문자, 방향 제어(U+061C, U+200E·U+200F, U+202A–U+202E, U+2066–U+2069), 폭 없는 문자(U+200B–U+200D, U+2060, U+FEFF)를 지운다(`cleanReason`, 기기의 `DiscoveryPick.cleanReason`과 같은 목록, 같은 문자열로 검사). 그다음 60자 이하이고 주소(`http`, `www.`, 도메인 모양)·`<`·`>`·짝 없는 서로게이트가 없을 때만 남기고 아니면 빈 문자열. 폭 없는 문자로 끊은 주소도 지운 뒤 다시 보므로 걸린다. 묶음은 2~10개의 보낸 번호, 한 번호는 한 묶음에만. 고른 것이 하나도 남지 않으면 `ai_invalid_response`(정산함). 모델 응답의 다른 필드(주소·제목·날짜)는 기기로 넘기지 않는다.
- 기기도 같은 규칙으로 다시 읽는다(`DiscoveryPick.read`): 요청 ID·작업·상태가 맞아야 하고, 보낸 번호만 주소로 바꾸며, 화면은 그 주소의 원래 후보를 그린다. 모델이 무엇을 쓰든 화면의 제목·링크·시각은 공개 목록(또는 넓게 찾기 응답) 그대로다.
- 로그: 기존 일곱 필드(`at, requestId, task, model, status, inputTokens, outputTokens`)뿐. 주제·제목·매체 이름·이유는 로그와 오류 응답에 없다(검사).

**뉴스 하한(서버 강제):** `news_pick`은 예약 뒤 프로젝트 남은 금액이 $5(`NEWS_PICK_FLOOR_MICRO_USD` = 5,000,000) 아래가 되면 예약을 반환하고 `ai_monthly_limit`으로 거절한다(공급자 호출 없음). 뉴스가 한 달 상한의 절반을 넘게 써서 글쓰기 AI를 막지 못하게 하는 장치다. 글쓰기 작업은 지금처럼 $10 전체를 쓴다(검사). SQL 변경은 없다(기존 `life_ai_reserve`가 돌려주는 `remaining_micro_usd`를 읽는다).

## 부르는 때 (넓게 찾기와 같은 원칙)

- **키:** 보내는 주제, 콘텐츠 언어 설정, 넓게 찾기 켬·끔. 같은 키면 아래처럼 다시 쓰고, 넓게 찾기만 바뀌면 그 자리에서 묻지 않고 다음 열기·갱신 때 묻는다(하루 횟수 규칙 그대로).
- **부른다:** 설정이 켜진 채 뉴스를 열 때(같은 키의 답이 30분 안이면 다시 묻지 않음, 실패 뒤에는 다시 엶에서 한 번 더), `지금 갱신`·`목록 새로고침`(항상), `AI 추천` 순서를 고를 때, 관심 주제나 그 사용 여부·콘텐츠 언어를 바꿔 저장했을 때(다른 기기에서 바뀐 주제를 받았을 때 포함).
- **부르지 않는다:** 15분 자동 갱신(공개 목록만 다시 받고 추천은 그대로), 설정이 꺼졌거나 저장 전·충돌 중, `AI 추천`이 아닌 순서를 보는 동안, 같은 키로 요청 중일 때(`지금 갱신`을 다시 눌러도 진행 중인 요청을 끊고 다시 보내지 않는다. 끊긴 요청도 서버에서 최대치로 청구되고 하루 횟수가 늘기 때문이다).
- 넓게 찾기가 켜져 있고 응답을 기다리는 중이면 그 응답을 받은 뒤 묻는다(넓게 찾은 글도 후보이므로).
- **하루 12회(기기당):** 브라우저 저장소에 `caeyeon_life_news_pick_calls` = `{ day, count }`만 둔다(주제·제목·결과 없음). 저장소를 못 쓰면 화면 메모리로 센다. 12는 "아침·점심·저녁에 열고 몇 번 새로 고침"의 넉넉한 위쪽이고, 기기 3대 최악에서도 서버 하한이 돈을 막는다. 넘으면 `오늘 받을 수 있는 AI 추천을 다 받았어요 · 최신순으로 보여 줘요`(같은 주제의 이전 추천이 있으면 그대로 보이고 문구 없음).

## 화면

- 정렬 메뉴: `최신순`·`관심순`·`개인 추천`·`AI 추천`. `AI 추천`은 설정을 켜야 고를 수 있다. 설정이 켜져 있으면 다른 순서를 고르기 전까지 뉴스가 이 순서로 열린다. `개인 추천`(기기 안 좋아요 표현 비교)과는 별개이며, 반응·언어 변경이 `개인 추천`을 끝낼 때 `AI 추천`은 그대로다(전에는 모든 순서가 기준 순서로 돌아갔다 — 그 동작은 `개인 추천`에만 남겼다).
- 고른 카드: 메타 줄의 글자 표시 `AI 추천`(색에 기대지 않음, 넓게 찾기의 `넓게`와 같은 모양). 이유는 `⋯` → `기사 정보`에 "AI 추천 · <이유> · 제목·매체 이름·발행 시각만 보고 고른 것입니다."로 보인다. 카드 본문에 요약·이유를 넣지 않았다(카드 피드 규칙: 요약 표시 없음).
- 목록 위 한 줄(13px, `role=status`): `AI 추천을 고르는 중 · 그동안 최신순으로 보여 줘요` / `AI 추천 n건 · 그 뒤는 최신순` / 실패 `추천을 가져오지 못했어요 · 최신순으로 보여 줘요`(503 `ai_busy`, 연결 실패·제한시간, 형식이 다른 답, 그 밖) / `이번 달 AI 추천에 쓸 금액을 다 썼어요 · 최신순으로 보여 줘요`(429 `ai_monthly_limit`, 하한 포함) / `이 계정에서는 AI 추천을 쓸 수 없어요 · 최신순으로 보여 줘요`(403 `ai_not_allowed`, 그 화면에서 다시 묻지 않음). 실패하면 이전 추천을 앞에 남기지 않고 최신순 그대로다. 받은 추천이 지금 목록에 하나도 없으면(넓게 찾기를 끔, 그 글들을 담거나 뺌) `추천한 글이 지금 목록에 없어요`와 `다시 추천받기` 버튼이 보인다.
- **목록을 쓰는 중에 온 답:** 사용자가 스크롤·누르기 등으로 목록을 쓰기 시작한 뒤 도착한 답은 카드를 움직이지 않고 `AI 추천 n건 보기` 버튼 뒤에 기다린다(넓게 찾기의 `새 글 n건`과 같은 원칙). 누르면 처음부터 다시 그리고 첫 카드로 초점을 옮긴다.
- 계정 전환·로그아웃·탭 떠남·화면 일시 중지에서는 요청을 중단하고, 늦게 온 답은 버린다(요청 세대·계정 확인 두 겹).

설정 옆 설명(`#discoveryPickHelp`, 켜기 전부터 보임):

보존 문장은 [AI 제안 문서의 첫 사용 안내](writing-ai-suggestions.md)와 같은 근거(공급자 정책 30일 전제)다. 글쓰기 AI처럼 요청마다 미리보기를 띄우지 않은 이유: 이 요청은 자동으로 일어나는 목록 정렬이고, 보내는 내용의 종류가 고정되어 설정 하나로 충분히 설명된다(넓게 찾기와 같은 방식).

## 결과를 어디에 두는가

승인은 "계정 비공개 저장소에만"까지 허용하지만 이번에는 더 좁게 **화면 메모리에만** 둔다. 계정 문서 종류를 새로 만들려면 `storage.js`(다른 작업자 담당)와 동기화 스키마를 바꿔야 하고, 30분이면 다시 묻는 값이라 보관 이득이 작다. 공개 목록 파일·서비스워커 캐시·localStorage·sessionStorage에는 결과가 없다(브라우저 검사: 저장소·캐시 전수 확인, 남는 것은 하루 횟수 `{day, count}`뿐). 공개 목록 파일에 넓게 찾기·AI 결과가 0건이고 수집기·배포 관문이 이 요청을 모른다(단위 검사).

## 결정 3·4·6

- **결정 3(기사 이미지 기본 꺼짐):** 확인만 했다. `DEFAULT_SHOW_IMAGES = false`, 빈 설정의 `showImages`는 거짓(단위 검사 추가). 바꾼 것 없음.
- **결정 6(넓게 찾은 글에도 좋아요):** 넓게 찾은 글은 새 탭으로만 열려 읽기 칸의 좋아요를 쓸 수 없었다. 카드 `⋯`에 `좋아요`/`좋아요 취소`(`aria-pressed`)를 더했다. 저장은 기존 반응 문서(`discoveryActionsExtended`, `google-news` 스냅샷)이고, 좋아요한 넓게 찾기 글은 카드 메타 줄에 하트 표시가 생기며 `⋯`에 `추천에 사용하지 않기`도 생긴다. 좋아요는 기기 안 개인 추천과 계정 동기화에만 쓰이고, 넓게 찾기·AI 추천 요청에는 들어가지 않는다(좋아요·담은 글은 AI 후보에서도 빠진다, 브라우저 검사).
- **결정 4(조건부 출처는 로그인 계정 화면에서만, 공개 파일 금지): 이번에 구현하지 않았다.** 현재 로그인 화면도 **같은 공개 파일**(`assets/life/discovery-feed.json`)에서 목록을 받는다. 조건부 출처(연합뉴스 3·SBS 2·노컷뉴스 1·카카오·토스·LY 기술블로그, 피드 9개)를 공개 파일에서 빼면 로그인 화면에서도 사라진다. 로그인 계정에만 주려면 비공개 전달 경로(예: `haedo-news-wide`에 "고정 RSS" 공급자를 더해 허용 계정에게 비공개 캐시로 주거나, 별도 Edge 함수)가 필요하고, 이는 이 작업의 파일 담당(`haedo-ai`·뉴스 화면) 밖의 서버 작업이다. 공개 파일에서만 먼저 빼면 소유자 화면의 한국어 종합지 대부분이 빠져 이번 목표(뉴스 품질)와 반대가 된다. 그래서 공개 파일은 지금 상태로 두고, 아래 순서를 총괄에 제안한다.
  1. 서버: 조건부 9개 피드를 허용 계정에게만 주는 비공개 경로(넓게 찾기와 같은 허용 계정 표·비공개 캐시·호출 한도). 응답은 지금 공개 목록과 같은 기사 모양.
  2. 화면: 로그인 계정이면 공개 목록 + 비공개 조건부 목록을 합쳐 순위(브라우저 등록부는 이미 이 출처들을 안다).
  3. 공개 수집: 수집기 `SOURCES`에서 9개 피드 제외, 배포 관문의 `extended` 기대 집합을 공개분으로 바꾸고 이전 공개본(조건부 포함)은 과도기 시드로만 허용, 검사 "공개 파일 조건부 출처 0건".
  - 1·2가 배포되기 전에 3만 하면 안 된다.

## 알려진 한계와 미검증

- 받는 쪽(Anthropic)이 후보 목록을 같은 시각의 공개 목록 파일과 비교하면, 빠진 글(좋아요·담기·읽음·관련 없음, 자료에 있는 주소, 꺼 둔 출처·언어)을 추론할 수 있다. 그런 글을 보내지 않는 규칙에서 생기는 구조적 한계이고, 받는 쪽에 빠진 이유는 전해지지 않는다.
- 실제 Haiku 5.5 응답 품질(고른 글이 소유자에게 쓸모 있는지), 실제 토큰 수(한국어 토큰 추정은 측정 아님), 실제 지연은 확인하지 않았다(실제 호출 금지). 소유자 실사용 평가가 필요하다.
- 하루 횟수는 기기·브라우저마다 따로 센다(서버 하한이 돈을 막는다). 개인정보 보호 창·저장소 차단이면 화면을 새로 열 때마다 0부터 센다.
- `haedo-ai`는 소유자 계정 하나만 허용한다. 넓게 찾기 허용 계정 3개 중 나머지 2개에서는 `AI 추천`이 "쓸 수 없어요"로 끝난다.
- 결정 4는 위 이유로 미구현.
- 실제 Mac·iPad·iPhone·Safari·VoiceOver, 실제 Supabase Edge(Deno)에서의 실행은 미검증이다.
