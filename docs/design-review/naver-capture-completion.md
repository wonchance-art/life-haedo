# 네이버 공개 목록·본문·사진의 비공개 보관과 활용

2026-10-21 UTC. 기준 main `d6009ea`의 연결/RSS 보관함을 보존하면서 공개 목록, 불변 본문·사진 수집 판, 계정 내 받기, 원문 읽기·선택 사진 글쓰기와 전용 파일 복원을 연결한 구현 기록이다. **코드와 합성 검수를 실제 네이버 수집·예약 가동 완료로 해석하지 않는다.** 최종 통합 검사·설치·배포는 해당 PR의 HEAD와 실행 기록을 따른다.

## 목표와 구현 범위

**계정 연결 선택 → 확인한 공개 목록과 현재 공간 자료 대조 → 과거 글 명시 선택/기준 목록 뒤 새로 발견한 글 수집 → 본문·사진 확보 범위 검토 → 비공개 서버 보관 → 같은 계정의 목적 공간에 받기 → 정확 원문 읽기·선택 사진 글쓰기·전용 ZIP 복원 → 원래 목록 복귀**를 하나의 흐름으로 연결한다.

첫 목록 확인은 과거 글 전체 다운로드와 다르다. 기준 목록 완료 전에는 새 글 자동 본문 수집을 보류한다. 완료 뒤 처음 발견한 글도 설정 후 실제 작성된 새 게시물이라고 단정하지 않는다. 수집 자료를 사용자가 쓴 글로 추정하거나 홈의 내 글·초안·공개본을 자동 생성하지 않는다. 원문 변경·목록 미등장으로 기존 자료·인용·사진을 삭제하지 않는다.

| 구현 경로 | 동작과 보존 조건 |
| --- | --- |
| 공개 목록·대조 | 같은 계정의 기존 연결을 목적 공간과 분리해 찾는다. 글 번호·페이지·총수·기준 목록·체크포인트를 보관하고 중단/변동/실패를 전체 완료로 표시하지 않는다. blogId/logNo로 기존 네이버 자료를 대조하고 여러 후보를 자동 합치지 않는다. |
| 본문 추출·작은 배치 | MIT 추출부의 에디터별 본문 선택자를 재사용한 제한 어댑터와 Cheerio/slim을 쓴다. 목록·본문·사진을 임대와 진행 상태로 나누고 1회 사진 처리는 최대 2장이다. 접힌 본문 추가 확인 실패와 미지원 요소를 누락으로 남긴다. |
| 불변 서버 수집 판 | 기존 RSS 최초 partial/link_only 행을 수정하지 않고 별도 수집 판·작업·영수증과 비공개 사진 경로를 추가한다. owner RLS와 worker 권한을 분리하고 중지·구독 revision·임대 종료 뒤 낡은 완료를 차단한다. |
| 현재 공간 받기·보완 | 판과 사진 검증 뒤 Core 변경과 sidecar를 단일 트랜잭션에 저장한다. 명시 보완은 기존 source ID/URL과 옛 인용을 유지하며 새 불변 버전을 추가한다. 같은 수집 hash는 재설치하지 않는다. |
| 원문·사진 활용 | 원문은 정확 버전으로, 사진은 별도 영역에서 순서·설명·실패와 함께 표시한다. 실제 본문 속 사진 위치를 복원했다고 주장하지 않는다. 선택 사진과 출처 URL만 기존 PhotoPost의 새 비공개 초안에 복사한다. |
| 전용 파일·복원 | 선택 source/version 하나와 수집 명세·사진 파일만 전용 ZIP에 담는다. 새 계정 소유의 독립 공간으로 복원하고 서버 owner/row ID/사진 경로를 제거한다. 기존 일반 JSON·글 ZIP·Preservation 형식은 바꾸지 않는다. |

## 저장·검증 계약

순수 [NaverCapture](../../assets/life/naver-capture.js)는 서버 row의 정확한 7개 필드와 payload 16개 필드를 검증한다. 글 번호는 30자리까지 문자열이며 [NaverBlog](../../assets/life/naver-blog.js)의 PC/모바일/PostView 정체성을 재사용한다. 서버 사진 경로는 해당 owner·블로그·글·실파일 SHA와 정확히 일치해야 한다.

`body`는 확보한 일반 텍스트/Markdown의 원래 문자열이다. BOM·CRLF·이모지와 UTF-16 위치를 정규화하지 않는다. bodyHash는 그 문자열의 UTF-8 SHA, htmlHash는 추출 전 HTML의 SHA다. 변환 본문을 원형 HTML과 같은 바이트로 표시하지 않는다. 모델은 HTML 원본을 받지 않으므로 htmlHash 형식만 검증하며 재계산은 worker 책임이다.

수집 fingerprint는 재귀 키 정렬 JSON에서 extractedAt과 사진 storagePath만 제외한다. 본문·사진 명세·실패·HTML hash·추출기 버전을 포함하므로 동일 결과 재조회는 중복되지 않지만 HTML/추출기 변경으로 새 판이 생긴 사실을 곧 네이버 작성자의 수정으로 단정하지 않는다.

현재 worker 출력은 text/plain의 partial 또는 link_only다. 모델이 full_text를 표현할 수 있다는 이유로 전체 본문 확보로 승격하지 않는다. 날짜·작성자가 확인되지 않으면 null/빈값, 작성자 관계는 unknown을 유지한다. 서버 raw HTML을 클라이언트에 반환하지 않는다.

사진은 JPEG/PNG/WebP이며 모델 상한은 20장·장당 64 MiB·합계 256 MiB다. worker는 장당 16 MiB로 더 보수적이며 상한/실패를 누락으로 남긴다. URL·바이트·SHA·형식·픽셀·설명·실패를 기록하고 실패한 사진의 파일 메타는 null이다. 모든 사진은 originalStatus:unverified이며 업로드 당시 원본과 같다고 주장하지 않는다.

worker 이미지 헤더 검사는 전체 디코딩을 대신하지 않는다. [NaverMedia](../../assets/life/naver-media.js)는 기존 PhotoPost의 바이트·SHA·실픽셀 검증을 거친 Blob만 표시·원자 저장·파일 복원에 사용한다. 원격 이미지 URL을 화면에서 직접 불러오지 않는다.

[수신 서비스](../../assets/life/naver-capture-sync.js)는 Auth와 계정·공간·화면 generation을 비동기 경계와 마지막 쓰기에서 확인한다. 검토한 기존 source/version이 달라지면 자동으로 최신 판에 보완하지 않는다. 사진만 달라도 새 원문 버전을 만들어 정확한 sidecar를 분리하고, 원문과 사진을 함께 설치한다.

## 파일과 글쓰기의 포함 범위

haedo.naver.capture.v1은 해도 전용 무압축 ZIP이다. 선택 원문 한 개·정확 버전 한 개, {capture_hash,payload}와 사진 파일을 담는다. **개인 메모·발췌·주제·링크 관계·작성한 글·다른 자료·계정 연결·공개 상태는 제외한다.** 일반 ZIP 전체를 지원하는 가져오기가 아니며 경로·헤더·CRC·바이트·SHA·사진 검증에 실패하면 설치하지 않는다.

파일 명세의 localOnly:true와 사진 storagePath:null은 서버 영수증과 구분된다. 복원은 새 공간/source/version ID로 이루어지고 서버에 자동 업로드하지 않는다. 이를 서버 보관 증거로 사용하지 않는다. ZIP 전체는 256 MiB 한도이며 메모리 방식이므로 모든 모바일 기기에서 최댓값을 보장하지 않는다.

선택 사진 글쓰기는 자료에 반영한 정확 수집 판의 사진만 새 로컬 초안으로 복사한다. 선택하지 않은 사진·원문 전체·인용 메모는 자동으로 넣지 않는다. 이후 사용자가 글을 명시 저장하면 기존 글별 기본 비공개 서버 보관 정책을 따르며 사진 공개 선택과 게시 동의는 별도다. 네이버 게시·수정·삭제나 소유권 추정은 하지 않는다.

## 반대 검토와 재사용

추출기 CLI 전체 대신 기존 Auth/RPC·Core 불변 원문·Storage CAS·PhotoPost·fflate를 재사용했다. 새 범위는 목록/재개, 제한 추출 어댑터, 불변 수집 판과 원문 사진 sidecar다. 작성기·공개·뉴스·기존 백업을 다시 만들지 않는다. [공식 후보와 고정 소스](naver-extraction-open-source.md), [실제 재사용 결정](../life-tools-design/open-source-review.md)을 구분한다.

독립 코드 검토는 새 capture B를 보는 중 기존 version A의 사진을 쓰는 공백과 link_only 원문의 조기 반환으로 사진 영역이 빠지는 공백을 발견했다. 사진 작업은 정확 수집 hash가 설치된 버전에만 연결하고, 본문이 없어도 사진 영역을 표시하도록 보완한다. 최종 통합 확인은 PR 검사 기록으로 확정한다.

## 검수와 실제 가동의 남은 조건

운영 복구·재설치는 **기존 연결 base → HTTP 충돌 fix → capture 추가 migration** 순서를 유지한다. 과거 base SQL만 단독 재적용하면 private schema의 전체 함수 권한 초기화가 뒤에 추가된 capture helper 권한까지 제거하므로, 이후 fix와 capture까지 순서대로 재적용해야 한다. 새 capture migration을 정상 순서로 추가 설치하는 동작에는 이 문제가 없으며, 이를 피하려고 이미 설치된 원본 migration을 수정하지 않는다. 전체 재설치와 단일 과거 파일 재적용을 같은 복구 절차로 안내하지 않는다.

순수 모델의 Node/browser VM에서 계정·경로·본문/판 SHA·필드/한도·비동기 중 호출자 변경, raw 본문과 기존 별칭 URL의 Core 가져오기, 서버 row와 파일 사본 분리를 확인했다. worker는 고정 HTML/목록·네트워크 경계·배치·유실 응답과 잠금 파일의 Deno 검사, 주입 fetcher의 합성 실행을 확인했다. 주입 실행은 실제 Edge HTTP나 네이버 응답 검수가 아니다. 격리 PostgreSQL 42개, 설치 조건 12개, 기존 설치 보존 7개 검사를 통과했다. 실제 SDK/IDB·사진 디코딩·실패/경합·계정/공간 전환·UI 왕복과 최종 CI의 결과는 해당 PR 기록을 따른다.

현재 관측 spec364의 enforced 네트워크 정책은 네이버 접근을 허용하지 않는다. 실제 네이버 요청·차단 우회를 하지 않았고 HAEDO_NAVER_INGESTION_ENABLED=false와 DB 준비 상태의 비활성 경계를 유지한다. Cron은 가동하지 않았다. 추가 migration과 Edge v2의 운영 설치는 완료했으며, 수집 준비 상태는 false로 유지했다. 운영 설치를 실수집 성공의 증거로 해석하지 않는다. 실제 개인정보 수집·전체 과거 글 대조·최초 업로드 원본 판정·새 게시 감지·Google/Apple 기기 체험은 미확인이다.

다음 큰 작업은 **실제 네이버 목록 대조부터 예약 수집·재접속 반영·활용까지 운영 완주** 하나다. 이유는 현재 구현의 실제 응답 호환성·접근 조건·예약 실행을 확인해야 하기 때문이다. 선행은 네이버와 실제 필요한 사진 CDN의 승인된 접근, robots/접근 조건·대표 응답 검증, 서버 실행 자격·일정 준비다. URL 발견은 임의 호스트 허용으로 해석하지 않는다.

완료는 실제 목록 미확인 범위·중단 재개, 대표 글 문단/링크/접힘/실패 사진 대조, 같은 계정의 독립 저장소에서 원문·SHA·픽셀 열기, 보완 뒤 옛 인용 보존, 선택 사진 글쓰기·전용 파일 복원, 앱 종료 중 예약 실행·재접속 한 번 반영·중지/실패 복구까지다. **새 게시물이 실제 관측되지 않으면 최초 수집과 반복 멱등만 확인하고 신규 게시 감지는 미확인으로 남긴다.** 이미 구현한 모델·사진 보관·글쓰기 연결을 다시 미구현 과제로 나열하지 않는다.
