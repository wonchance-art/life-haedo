# 네이버 수집 화면과 두 기기 이어짐 검수

2026-11-05. [총괄 F 지시서](https://github.com/wonchance-art/life-haedo/pull/212#issuecomment-6650248345)의 기준은 main `2eebd27`이다. 담당은 `naver-blog-ui.js`, `naver-capture-sync.js`, 네이버 브라우저 검사와 이 문서다. 공유 수집 helper는 C 담당이며 운영 조회·쓰기·실제 네이버 요청·서버 수정·배포는 이번 작업에 포함하지 않는다.

## 검수 범위

기존 합성 Auth/HTTP, 실제 동봉 SDK·IndexedDB·자료 모델·화면을 재사용한다. 두 브라우저 context의 저장소는 독립적이다. 연결 → 과거 공개 글 목록 확인 → 새 글 예약 보관 → 자료의 정확한 원문 판·사진 복원 → 다른 기기 이어짐을 390px와 1440px에서 확인한다. 가짜 서버의 예약·기준선 응답은 UI 계약의 입력이며 실제 cron·robots·네이버 신규 게시 탐지의 증거가 아니다.

현재의 계정 자동 연동을 따른다. 원문과 사진을 다른 기기로 전달하는 과정에서도 정확 판·ACK·불변 영수증을 유지하며, 늦은 응답으로 미저장 입력이나 다른 연결의 선택을 바꾸지 않는다. 사진·본문 확보 범위와 공개 선택은 별개다. 실제 Google 로그인·Apple 기기·원본 업로드 바이트와의 동일성은 이 검사로 확정하지 않는다.

제품 결함은 수정 전 실패, 수정 후 통과, 해당 수정만 되돌린 변이의 실패로 확인한다. 단언·대기 기한을 약화하거나 최종 로컬 사본을 검사 도구에서 직접 심어 성공으로 표시하지 않는다. 기존 통과 근거는 입력 코드와 관련 경로가 같을 때만 재사용한다. 실행 결과·수정 파일·남은 한계는 draft PR의 정확 head 보고로 확정한다.

## 연결 전환의 선택·상태 보존

연결 A의 과거 글을 선택한 뒤 B의 `과거 공개 글 목록 확인`을 누르면, 기존 코드는 선택한 연결만 B로 바꾸고 A의 선택 집합을 유지했다. B 화면의 체크는 0개인데 수집 요청 버튼은 활성 상태여서, 화면에서 고르지 않은 A의 식별자를 B 연결로 요청할 수 있었다. 수정 전 실제 UI와 합성 서버에서 이 불일치를 재현했다.

공개 목록 보기·과거 목록 확인·이미 등록된 주소로 이동하는 세 경로가 같은 연결 전환 함수를 사용한다. 다른 연결로 옮길 때 선택·페이지·공개 목록·사본 목록을 함께 바꾸며, 목록이나 사본을 읽지 못하면 이전 연결의 선택·커서·더 보기·상태 안내를 복원한다. 같은 연결의 새로고침은 선택을 유지한다. 블로그 입력·자동 수집 선택·필터를 전환 때문에 초기화하지 않는다.

독립 검수에서 기등록 주소 이동의 목록 읽기 성공 뒤 사본 읽기가 실패하면, 이전 목록으로 돌아가도 새 연결의 `기준선 완료` 안내가 남는 누락을 발견했다. 상태 문구와 상태 값까지 복원하도록 보완했다. 화면을 복원해도 이미 서버에서 시작한 목록 확인이 취소됐다는 의미는 아니다. 실제 요청의 CAS·계정 제한·수집 동작과 정확 원문·사진 수신 경로는 변경하지 않는다.

## 실행 결과

Node 24.19.0, Chromium 151.0.7922.173에서 실행했다. 새 브라우저 검사 2개 흐름과 기존 연결 검사 5개 흐름, 기존 UI 단위 검사 11개가 통과했다. 새 검사는 390·1440에서 가로 넘침을 확인하고 viewport 캡처 8장을 남겼다. 캡처는 화면 표본이며 아래쪽 기준선 안내의 판정은 DOM 단언을 별도로 사용한다. 예상 밖 콘솔 오류·페이지 오류·외부 요청은 0이고, 의도적으로 넣은 HTTP 503 응답 4개는 정확한 요청 URL·응답 개수와 대조해 별도로 기록했다.

브라우저 입력의 전후 제품 해시, 검사 파일 해시, 합성 본문·사진 SHA/픽셀, 변이 실패 근거는 [검수 요약](evidence/naver-ui-continuity/summary.json)에 있다. 원 실패와 전체 보고서·이미지는 `.local/naver-ui-continuity-*`에 보존하며 개인 자료는 쓰지 않았다. 단위/흐름 통과 개수를 실제 수집 성공으로 해석하지 않는다.

| 검사 | 명령·결과 |
| --- | --- |
| 새 연결·수신·두 context 흐름 | `BASE_URL=http://127.0.0.1:4188 node tests/naver-ui-continuity-browser.cjs` — 2/2 |
| 기존 연결·실패·중지·전환 | `BASE_URL=http://127.0.0.1:4188 node tests/naver-blog-browser.cjs` — 5/5 |
| 기존 UI 상태 | `node --test tests/naver-blog-ui.test.cjs` — 11/11 |
| 원형 UI 변이 | `2eebd27`의 `naver-blog-ui.js`만 브라우저 응답으로 교체 — B 화면에서 A의 선택이 남아 요청 버튼 비활성 단언 실패 |
| 상태 복원 제거 변이 | 수정본의 `captureStatus` 복원만 제거한 브라우저 응답 — 기등록 주소 읽기 실패 뒤 기대 `partial` / 실제 `ready`로 단언 실패 |

변이는 `NAVER_UI_MUTANT=<변이 JS 파일>`·`NAVER_UI_MATCH=Switching`을 같은 새 브라우저 명령에 넘겨 재현한다. 검수 중 공유 작업공간의 제품 파일은 되돌리지 않으며, 변이 응답의 해시도 보고서에 남긴다. 합성 예약은 앱 창을 닫은 뒤 서버 fixture의 목록·작업·사본만 준비한다. 이후 실제 UI 수신으로 생긴 Core ACK·영수증과 다른 context의 자동 원문 수신·사진 복원을 확인한다. 최종 로컬 원문·사진 사본을 직접 주입하지 않는다.

## 총괄의 실제 신규 글 운영 검수 체크리스트

아래는 총괄이 수행할 후속 절차이며 이번 브라우저 검사 결과가 아니다. 기존 설정을 다시 만들거나 전체 과거 글을 재수집하지 않는다. 개인 자료는 소유자가 정한 연결·공간·표본 범위로 한정하고, 공개 보고에는 내용·식별자·키 대신 개수·상태·시각과 대조 결과만 쓴다.

1. **현재 기준을 고정한다.** 검수할 배포 head와 함수 버전, 활성 연결 revision, 기준선 방식·완료 시각·개수, 진행 중 scan의 상태를 기록한다. 기존 `supabase/operations/naver-status-check.sql`을 재사용한다. `count_exact`와 `observed_set`, 연결마다 따로 쌓인 항목 수를 구분한다. `observed_set`은 전체 공개 글 수를 확정한 것이 아니다.
2. **실제 새 게시와 새 발견을 구분한다.** 기준선에 없었던 항목을 허용된 공개 경로에서 관측했는지 대조한다. 과거 글의 공개 전환이나 목록 재노출도 새 발견일 수 있다. 이미 관측한 같은 글의 수정만으로 새 발견이나 신규 게시로 판정하지 않는다. 발행 시각과 이전 관측으로 실제 새 게시를 입증하지 못하면 신규 게시 탐지는 미검증으로 남긴다. 이를 위해 임의의 글을 게시하거나 과거 글을 고쳐서는 안 된다.
3. **앱 종료 중 예약의 결과를 확인한다.** 앱을 닫은 시각 뒤의 cron 실행, worker의 인증·응답, 검증된 목록 완료, 대상 작업 생성·완료, 불변 보관본 생성의 연결을 확인한다. cron `succeeded`나 HTTP 200만으로 글·사진 보관 성공이라고 판정하지 않는다. 15분은 예약 주기이며 전체 목록·사진 완료의 기한이 아니다.
4. **재접속과 두 기기를 대조한다.** 같은 계정에서 다시 접속해 정확한 원문 판과 사진을 연다. 다른 기기에서도 원문 판·본문 해시·영수증의 연결과 저장된 사진의 SHA-256·순서·MIME·실제 디코딩 크기/픽셀을 확인한다. `partial`·`link_only`와 사진 누락을 유지하고 기존 인용·미저장 메모가 바뀌지 않아야 한다. 같은 본문이라는 이유로 다른 사진 판을 선택하지 않는다.
5. **반복과 실패 복구를 확인한다.** 같은 요청·사본을 다시 열고 수신해도 원문 판·사진·작업이 불필요하게 중복되지 않아야 한다. 부분 사진 실패·응답 유실·오프라인 뒤에는 기존 자료를 유지하고 실패한 범위만 재시도한다. 합성 환경에서 넣은 실패와 운영에서 자연 발생한 실패를 별도로 기록한다. 운영 결함을 만들기 위해 키·권한·원자료를 훼손하지 않는다.
6. **중지의 범위를 확인한다.** 소유자가 허용한 연결만 앱에서 중지하고 그 revision 이후 새 자동 작업의 생성과 늦은 결과 수락 여부를 확인한다. 이미 완료된 보관본·사진·인용은 유지해야 한다. 실행 중이던 외부 요청이 즉시 취소됐다고 추정하지 않는다. 전체 서버 준비 관문·cron 중지는 별도 운영 조치이며 개인 연결 중지와 혼동하지 않는다.
7. **정확한 범위로 판정한다.** 실제 새 글이 없다면 UI·보존·예약 가동까지만 완료로 기록한다. 실제 새 게시 탐지, 본문 전체 확보, 원본 업로드 사진 동일성, 다른 기기 복원은 각각의 근거가 있을 때만 완료로 올린다. 실제 기기는 모델명·OS·브라우저와 확인 시각을 함께 남긴다.

과거 10-29 검수의 대표 부분 본문 1개·사진 2개와 반복 관측 기준선, 11-05 11:14 KST 읽기 전용 상태는 [운영 인계 #208](https://github.com/wonchance-art/life-haedo/issues/208)에 있다. 그 시점의 관측을 현재 배포·현재 활성 연결의 성공으로 자동 승격하지 않는다. 운영 설치·과거 근거는 [운영 준비 기록](naver-operational-readiness.md), 정확 판·사진 계약은 [사진 이어짐 검수](naver-media-continuity.md)를 참조한다.
