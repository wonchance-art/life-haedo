# 일정 B2 — 습관·행복도·목표를 일정에서 바로 보고 입력하기 (2026-11-04)

기준 main은 `a49c8a3`이다. 총괄 작업 지시서(11-04)와 결정안 회신을 따른다. 결정 사항은 다음과 같다.

- 경로 A안
- 행복도 대응 `v = (n − 5) / 5`
- 공유 스토어 최신 채택
- 기준 문서 `registry.current` (d7eae0e 검수 뒤 바꿈 — 아래 「기준 연표 문서」)

## 사용 장면

- **시작:** 일정의 일(D)·주(W)·연(Y) 보기를 연다. 첫 화면인 일정 목록은 바뀌지 않는다.
- **일(D):**
  - 그날 할 습관을 체크 상자로 보여 준다.
  - 행복도를 0–10 중 하나로 고른다. `지우기`를 누르면 그날 값만 지운다.
  - 끝나지 않은 목표를 진행률 막대와 함께 보여 주고, 진행률을 바꿀 수 있다.
  - 오지 않은 날에는 체크와 행복도 입력이 막힌다.
- **주(W):**
  - 습관 × 요일 표에서 지난날과 오늘을 체크한다.
  - 날마다 행복도 값을 보여 준다. 값을 누르면 그날로 간다.
- **연(Y):** 계획 칸 아래에 끝나지 않은 목표와 진행률을 둔다.
- **저장 상태:** 두 단계로 표시한다(11-02 결정).
  - `계정에 올리기 대기` → `저장됨 · 계정에 올림`
  - 실패하면 `계정에 올리지 못함 · 다시 시도`와 `다시 시도` 버튼을 보여 준다.
- 기존 `목표`·`습관`·`연표` 화면은 그대로 쓸 수 있다.

## 저장과 동기화

- **저장 형식은 그대로다(11-03 결정).**
  - 목표·습관은 `haedo_items`와 계정별 `caeyeon_life_account_<uid>_items`
  - 행복도는 연표 문서(`haedo_documents`)의 `happiness: [{date, v}]`, v ∈ [−1, 1]
  - 새 동기화 문서는 만들지 않았다.
- **행복도 0–10 ↔ 저장값:** `v = (n − 5) / 5`, 표시 `n = round(5 + 5v)`.
  - 척도 변환은 한 함수(`HaedoData.scaleValue`·`toSignedScale`)만 쓴다. 연표 편집기의 `migrateScale`, 일정의 `happinessOn`·`withHappiness`가 같은 함수를 부른다.
  - `scale`이 없는 옛 문서(0–10)는 읽을 때 변환해 보여 준다. 일정이 쓸 때는 문서 전체를 signed1로 바꾼 뒤 그날 값을 넣는다. 한 문서에 두 척도가 섞이지 않는다.
  - 하루에 한 항목(`date: YYYY-MM-DD`)만 둔다. 월 단위 점(`YYYY-MM`)은 하루 입력으로 보지 않는다.
  - 0.2 간격이 아닌 기존 값(예 0.35 → 7)은 표시만 반올림한다. 그날 다른 값을 고르기 전에는 다시 쓰지 않는다.
- **기준 연표 문서:** 복구 사본이 아닌 문서 중 id가 가장 작은 문서다(`baseDocument`). 모든 기기가 같은 문서를 고른다.
  - `registry.current`는 기기마다 마지막에 연 문서라 기기 사이에 갈릴 수 있어 쓰지 않는다.
  - 문서가 하나도 없으면 보는 것만으로는 만들지 않는다.
  - 첫 행복도 값을 저장할 때만 `emptyDocument("내 연표")`를 만든다.
- **불러오기 시점:** `sync.js`·`platform-store.js`·`schedule-entries.js`는 일정이 이 칸을 처음 그릴 때 불러온다.
  - 첫 화면 경로에 싣지 않으므로 `index.html`·`life.html`은 바꾸지 않았다.
  - 불러오지 못하면 예전처럼 각 편집 화면 링크를 둔다.
- **계정:** 셸이 서버 계정 확인을 마친 개인 화면에서만 `store.ensure(uid)`를 부른다.
  - `HaedoAuth.user.id`와 `storage.account.userId`가 같을 때만 부른다.
  - 같은 계정이면 다시 초기화하지 않아 대기 중인 전송을 잃지 않는다.
  - 로그아웃(`haedo:signed-out`)은 직접 등록한 그대로 스토어를 비운다.
- **깨우기:** `platform-store.js`의 visibilitychange·online 직접 등록을 S2 공통 모듈(`SyncLifecycle.attach`)로 옮겼다.
  - 스토어를 싣는 `habits`·`goals`·`timeline`·`workspace` 페이지에 `sync-lifecycle.js` 줄을 넣었다.
  - 공통 모듈 자체는 바꾸지 않았다.
- **문서마다 올리는 주체는 하나다(검수 B1).**
  - 일정 화면은 `followDocuments()`를 불러, 깨울 때 연표를 다시 받고 자기가 바꾼 문서를 보낸다.
  - 연표 편집기(`timeline.html`)는 자기 `cloudPush`만 쓴다. 스토어는 깨울 때 자기가 만든 문서(행복도를 쓴 문서, 자기 복구 사본)만 다시 보낸다.
  - 목표·습관·연표 목록 화면은 명시 동기화(`sync()`)가 바뀐 문서만 보낸다.
  - 스토어의 `uploadDoc`은 바뀌지 않은 문서(`updated === syncedAt`)를 보내지 않는다.

## 충돌 — 최신 채택, 진 쪽 보존 (11-01 소유자 규칙, 이번에 공유 스토어에 적용)

- **목표·습관:** 양쪽이 바뀌었으면 수정 시각이 늦은 쪽을 채택한다. 같거나 읽을 수 없으면 서버 쪽을 채택한다.
  - 진 쪽은 `caeyeon_life_account_<uid>_items_recovery`에 남긴다. 기존 키는 그대로이며, 자동으로 지우지 않는다.
  - 복구 사본을 먼저 쓴 뒤에 이긴 쪽으로 바꾼다. 복구 사본을 쓰다 실패하면 아무것도 바꾸지 않고 항목을 `conflict` 상태로 둔다.
  - 이전 판의 수동 `conflict` 항목도 다음 pull에서 같은 규칙으로 정리한다.
  - 서버 행이 사라진 경우:
    - 이 기기에서 그 뒤에 고쳤으면 새 행으로 다시 보낸다.
    - 고치지 않았으면 복구 사본에 남긴 뒤 이 기기에서도 뺀다.
  - 같은 진 쪽 판(같은 id·수정 시각·내용)은 한 번만 남긴다. pull과 push가 같은 충돌을 정리해도 겹치지 않는다.
  - 목록을 읽는 사이 전송이 끝난 항목은 그 목록으로 지우지 않는다(목록이 낡아 삭제로 보이던 문제).
  - 복구 목록 값이 깨져 있으면 원래 글자 그대로 `..._items_recovery_damaged`에 따로 두고 새 목록으로 이어 간다. 충돌·백업·복원을 막지 않는다.
- **행복도의 충돌(검수 M1):** 행복도는 하루 값 하나라 문서 단위 최신 채택을 쓰지 않는다.
  - 서버 판이 바뀌었으면 서버 판을 다시 받아 그 위에 이 기기가 아직 못 올린 날짜 값만 다시 넣고 조건부 쓰기를 다시 한다(최대 3회).
  - 복구 사본은 만들지 않는다. 다른 기기가 더한 사건 등은 주 문서에 그대로 남는다.
  - 이 기기에서 행복도 외의 편집이 함께 있으면 아래 문서 규칙을 따른다.
- **연표 문서:** 문서 단위로 최신 채택한다. 진 쪽은 같은 목록에 `<이름> 복구 사본 (YYYY-MM-DD HH:MM)` 문서로 남고, 다른 미동기화 문서처럼 계정에 올라간다.
  - 진 쪽 내용이 이긴 쪽이나 이미 있는 복구 사본과 같으면 새로 만들지 않는다.
  - 복구 사본의 복구 사본은 이름 끝을 겹쳐 붙이지 않는다(` 복구 사본 (…)`는 하나만).
- **알림과 목록(검수 M4):** 충돌 대화상자는 뜨지 않는다.
  - 일정과 목표·습관 화면의 상태 줄에 "다른 기기와 겹친 변경 N개를 복구 사본으로 남겼습니다."와 `보기`·`확인`이 나온다.
  - `확인`을 누르면 문장이 사라진다. 사본은 지우지 않는다. 확인 표시는 기기마다 따로 둔다.
  - `보기`는 목표·습관 복구 사본 목록(`habits.html#recovery`)을 연다. 항목마다 `새 항목으로 되살리기`가 있고, 새 id의 항목으로 더한다. 진 상대 항목과 사본은 그대로다.
- **복구 사본의 계정 동기화(검수 M4):** 목표·습관 복구 목록은 기존 `life_account_documents`의 계정 문서 `platformRecovery:<계정>:items`로 모든 기기에 간다.
  - 새 표·마이그레이션은 없다. 문서 종류가 늘어 `ACCOUNT_DOC_SCHEMA`를 3으로 올렸다. 이전 판에서 동기화한 기기는 변경 목록을 한 번 처음부터 다시 읽는다.
  - 일정 화면이 열려 있을 때 기기 목록과 계정 문서를 서로 더한다(`rid` 기준). 양쪽 다 더하기만 하고 지우거나 바꾸지 않는다.
- **백업과 복원:**
  - `store.backup()`과 전체 백업의 연표 부분(`timelineSnapshot`)에 `recovery`를 넣었다. 깨진 값은 `recoveryDamaged`로 원래 글자 그대로 담는다.
  - 목표·습관 화면의 백업 가져오기는 `recovery`를 검증한 뒤 이미 있는 사본과 겹치지 않게 덧붙인다(바꾸지 않는다). `recoveryDamaged`도 덧붙인다.
- **다시 시도:** `conflict` 항목은 받기로 먼저 정리한 뒤 보낸다(`store.retry()`). 예전에는 `conflict` 항목에 다시 시도가 아무것도 하지 않았다.
- **연표 편집기:** 자체 `cloudPush`와 탭 사이 겹침은 작업 3에서 같은 규칙으로 맞췄다([연표 편집기의 최신 채택](timeline-latest-wins.md)).

## 입력 보호

- **텍스트 칸이 없다.** 체크 상자·라디오·진행률 막대만 쓰므로 한글 조합을 덮을 칸이 없다.
- **진행률 막대:** 원격 반영이나 기록 갱신이 끌고 있는 막대를 다시 그리지 않는다. 손을 뗀(change·blur) 뒤에 다시 그린다.
- **포커스:** 다시 그린 뒤 같은 컨트롤로 되돌린다.
- **체크:** 저장된 값에서 뒤집으므로 같은 상자를 연달아 눌러도 한 번씩만 반영된다. 원하는 상태가 이미 저장돼 있으면 쓰지 않는다.
- **늦은 응답:** 스토어의 계정 세대 확인을 그대로 쓴다. 다른 화면·계정이 된 뒤의 알림은 칸이 무시한다.

## 화면 — 좁은 화면의 주 표

- 760px 이하에서는 표를 화면 폭에 맞춘다. 습관 이름 칸을 4.5em으로 줄이고 요일 칸을 고르게 나눈다.
- 390px에서 월–일이 모두 보이고 표 안 가로 스크롤도 없다. 줄인 이름은 말줄임으로 보이고, 전체 이름은 체크 상자 이름과 `title`에 있다.

## 한계

- 실제 Mac·iPad·iPhone 확인은 하지 않았다.
- **시계가 섞인 비교:** 목표·습관과 문서의 최신 판정은 이 기기의 편집 시각과 서버가 찍은 올린 시각을 비교한다. 두 시계는 같지 않다.
  - 기기 시계가 크게 틀리면 늦은 쪽 판정이 뒤바뀔 수 있다. 어느 쪽이 이기든 진 쪽은 복구 사본에 남아 잃지 않는다.
  - 같은 기기 안의 탭 사이 목록 합치기는 서버 시각끼리, 기기 시각끼리만 비교한다(작업 3 문서).
- 다른 탭이 연표 목록(registry)을 같은 순간에 쓰는 경쟁은 작업 3에서 합치기로 좁혔다. 남는 한계는 그 문서에 적었다.
