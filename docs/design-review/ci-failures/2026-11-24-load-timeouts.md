# 부하 때만 나는 브라우저 검사 실패: `page.goto`·`ready()` 시간 초과와 초안 탭 누름 (2026-11-24)

- 대상: 로컬 통합 실행(load average 19–33, 브라우저 검사 여러 개 동시)에서만 나고 낮은 부하 재실행에서는 통과한 실패.
  - `notes-menu-browser` `page.goto` 15초, `home-entry-browser` 10초, `settings-browser` 12초(int5 `8d1a02d`, 모두 `waiting until "load"`).
  - `unified-home-browser` `ready()` 15초(`goto`는 끝났고, 실패 직후 화면에는 자료 화면이 떠 있었다).
  - `account-library-browser` 한 번 멈춤(W4, [W4 보고](../notion-w4-report.md)의 미해결 항목).
- 측정 환경: 이 컨테이너(4 vCPU, 16GB), Chromium 153(`chromium-1243`), Playwright 1.63, `scripts/dev-server.py`. 다른 세션이 같은 기계를 함께 쓴다. 실제 Apple 기기 측정이 아니다.
- 측정 도구는 검사 파일을 바꾸지 않는 `NODE_OPTIONS=--require` 탐침이다. 모든 `goto`·`reload`의 시간, 시간 초과 때 페이지 상태(`readyState`, 받은 리소스, 남은 리소스, 해석한 스크립트 수, 시작 안내 문구)를 남긴다.

## 1. `goto` 시간 초과: 기계가 넘치게 할당된 동안의 CPU 부족

### `goto`가 기다리는 것

- 다섯 검사 모두 기본값 `waitUntil: 'load'`로 `index.html`을 연다. 공용 맥락(`makeContext`)은 서비스워커를 막는다(`serviceWorkers: 'block'`). 따라서 load 전 서비스워커 설치·사전 캐시는 없다.
- `index.html`은 동기 `<script>` 158개(5.1MB), 스타일시트 31개, 미리 받는 글꼴 1개(2.0MB)를 연다. 요청은 약 198개, 본문은 약 7.6MB다.
- load는 DOMContentLoaded 뒤 0–80ms 안에 온다. 스크립트가 모두 동기이므로 `domcontentloaded`로 바꿔도 줄어드는 시간이 없다. `commit`으로 바꾸면 같은 일이 `ready()`의 제한시간으로 옮겨 갈 뿐이다.
- Playwright는 경로 가로채기(`context.route`)가 하나라도 있으면 HTTP 캐시를 끄고 모든 요청을 Node 쪽으로 보낸다(`Network.setCacheDisabled`, `Fetch.enable` 패턴 `*`). 공용 맥락은 가짜 인증 서버 때문에 항상 가로챈다. 그래서 검사 안의 모든 `goto`·`reload`는 캐시 없는 첫 방문 비용을 낸다.

### 낮은 부하의 비용(한 번의 `goto`)

| 항목 | 값 |
| --- | --- |
| `goto`(공용 맥락, 부하 2 안팎) | 0.45–0.6초. `settings-browser` 33회 중앙값 0.6초, 최대 0.84초 |
| 마지막 스크립트 응답 → DOMContentLoaded | 20–150ms. 받기와 실행이 겹쳐 진행된다 |
| 주 스레드 스크립트 실행 합(추적) | 80–174ms. 큰 것: `quill.js` 26–28ms, `page-composer.js` 11ms |
| 프로세스별 CPU(6회 평균) | 렌더러 0.80–0.94초, 브라우저 0.34–0.49초, 네트워크 0.20–0.29초, GPU 0.04초, 개발 서버 0.11–0.13초, 검사 Node 0.11–0.18초. 합 약 2.1 CPU초 |
| 가로채기의 몫 | 가로채기 없는 맥락보다 CPU 약 0.38초(+27%) 더 쓴다 |

- 제한시간(10–15초)은 낮은 부하 비용의 15–20배다. 실패하려면 한 번의 탐색이 그만큼 느려져야 한다.

### 부하를 올린 측정

| 조건 | `goto` 결과 |
| --- | --- |
| 브라우저 검사 6개 동시(부하 17–20) | 검사별 최대 2.5–4.0초, p90 1.6–2.4초. 실패 0 |
| 같은 6개 + 바쁜 반복 16개(부하 28–35) | 최대 8.3초(`home-entry`, 제한 10초), 다른 검사 최대 3.1–6.2초 |
| `unified-home` 해당 검사 8개 동시 × 3회(부하 약 37) | `goto` 최대 6.8초(제한 15초), 실패 0 |
| 부하 20에서 측정 탐색 | 문서 응답 직후부터 DOMContentLoaded까지가 거의 전부다. 응답 대기 중앙값 약 1초, 마지막 스크립트 응답과 DCL 차이 20–150ms |

- 시간은 응답을 받으며 스크립트를 실행하는 데 쓰이고, 네트워크·서버를 기다리는 구간은 없다. 시간 초과 순간에도 남은 리소스는 0개였다(아래).
- 부하가 두 배가 되면 최대값도 대략 두 배다. 원래 실패 때는 int5의 같은 검사들이 평소보다 2.5–5배 오래 걸렸다(`settings` 143초 대 28초, `notes-menu` 663초 대 237초).

### 결정적 재현

- 렌더러만 느리게 하는 CDP `Emulation.setCPUThrottlingRate`로 측정했다(공용 맥락, 부하 2 안팎).

| 배율 | `goto` | `ready`까지 |
| --- | --- | --- |
| 1 | 0.55초 | 0.64초 |
| 4 | 1.0–1.2초 | 1.5–1.7초 |
| 8 | 2.3–2.5초 | 3.2–3.4초 |
| 16 | 5.4–6.0초 | 7.6–8.5초 |

- 32배에서 `settings-browser` 전체를 돌리면 종료 코드 1이고, 두 검사가 int5와 같은 `page.goto: Timeout 12000ms exceeded`로 실패한다. 그때 기계의 부하는 1.3–1.5였다.
  - 한 번은 `readyState: loading`, 스크립트 158개 중 93개 해석, 받은 리소스 190개, 남은 리소스 0개, 시작 안내 `홈을 여는 중입니다.`였다.
  - 다른 한 번은 load가 12.15초에 왔다(제한 12초 직후).
- 결론: `goto` 제한시간은 첫 화면 스크립트를 실행하는 렌더러 주 스레드가 다 쓴다. 기계가 넘치게 할당돼 이 일이 15–20배 이상 느려질 때만 실패한다.

### 앱 쪽에 느리거나 끝없는 대기가 있는가

- 없다. load 전에 서비스워커·IndexedDB·원격 응답을 기다리지 않는다. 시간 초과 순간에도 남은 리소스는 0개였다.
- 실제 사용자 비교(로그인 전 `index.html`, 같은 기계, 2026-11-24):

| 대상 | 첫 방문(캐시 없음) | 다시 방문(서비스워커·HTTP 캐시) |
| --- | --- | --- |
| 배포 판 `wonchance-art.github.io/life-haedo` | DOMContentLoaded 0.87–1.20초 | 84–195ms |
| 로컬 개발 서버 | 0.44–0.61초 | 62–172ms |

- 사용자는 두 번째 방문부터 캐시로 5–10배 싸게 연다. 검사는 가로채기 때문에 매번 첫 방문 비용을 낸다. 사용자 체감 문제로 고칠 근거는 이번 측정에 없다.
- 첫 방문 비용을 줄이려면 158개 스크립트의 지연 로드 같은 구조 변경이 필요하다. 이번 범위가 아니며 별도 판단 대상이다.

### 고치지 않은 것과 이유

- 제한시간은 올리지 않았다. 낮은 부하에서 15–20배 여유가 있고, 실패는 실행 방식(동시 실행 수)에서 온다.
- `waitUntil` 변경은 효과가 없다(위 "goto가 기다리는 것").
- 개발 서버의 연결 유지(HTTP/1.1)는 시험했으나 더 느렸다. 같은 198개 요청이 1.3초 걸렸고, 지금 서버는 0.12초다. 서버 처리는 탐색 CPU의 약 6%다.
- 가로채기 없이 캐시를 쓰려면 가짜 인증 서버를 경로 가로채기가 아닌 별도 서버로 바꿔야 한다. 검사 180여 개의 공용 기반을 바꾸는 일이라 이번에 하지 않았다.

### 권고(저장소 밖, 통합 실행 스크립트)

- 4 vCPU에서는 브라우저 검사 프로세스를 동시에 두 개까지만 돌린다. 각 검사를 시작하기 전에 1분 부하가 `2 × nproc`(여기서는 8) 아래로 내려올 때까지 기다린다.
- 측정상 부하 20 안팎에서는 최대 `goto`가 4초(제한의 27–40%)였고, 부하 35 안팎에서는 8.3초(제한의 55–83%)였다.
- CI(`pages.yml`)는 한 job 안에서 검사를 하나씩 돌리므로 바꿀 것이 없다.

## 2. `unified-home` `ready()` 15초: 재현 안 됨

- 실패 지점은 `unified-home-browser.cjs` 396행 `ready(page)`다. `goto`(load)는 이미 끝난 뒤였다. 기록은 scratchpad `revC/moved/unified-home-fail1/`에 있다.
- `ready()`의 조건은 `HaedoLife.Shell.storage`와 `#lifeApp`이 보이는 것이다. 이를 위해 가짜 인증 서버 확인, 계정 자료 준비, 화면 붙이기가 끝나야 한다.
- 측정에서 load 뒤 `ready`까지는 낮은 부하에서 0.1–0.4초, 부하 37에서 최대 2.5초(72회), 렌더러 32배에서 2.0–4.3초였다. 15초가 되려면 CPU 비례로 40–100배가 필요하다. 앞 절의 원인만으로는 설명되지 않는다.
- 앱에는 인증 확인 제한(`VERIFY_LIMIT_MS` 10초)과 자동 재시도(2·5·15초)가 있다. 실패가 이 경로를 탔다면 15초를 넘을 수 있다. 하지만 이번 측정에서는 그 경로가 한 번도 열리지 않았다.
- 다시 나오면 실패 순간의 `#lifeStartup` 문구로 단계를 가른다. `로그인을 확인하고 있습니다.`이면 인증 확인, `계정 자료를 확인하고 있습니다.`이면 계정 자료 준비, 재시도 단추가 있으면 확인 실패다. 공용 `ready()`가 시간 초과 오류에 이 문구를 함께 남기게 하는 것이 다음 후보다. `ready`를 쓰는 검사가 많아 이번에는 바꾸지 않았다.

## 3. `notes-menu` 초안 탭 누름이 빗나감(새로 찾음, 고침)

- 재현: 위 부하 실험(검사 6개 + 바쁜 반복 16개)에서 전체 실행 1회가 실패했다. 해당 검사 8개 동시 실행(부하 약 40)에서는 32회 중 1회 실패했다.
  - 실패 지점은 `locator.click: Timeout 15000ms`, `#homePostList .home-draft-open` "쓰다 만 익명 초안"이다. 실패 화면에는 `글` 탭이 선택돼 있고 검색어가 비어 있다.
- 페이지 안 기록(탐침): `#homePostSearch` 입력 `''` 뒤의 click 대상이 `#homeTab-drafts`가 아니라 `.life-app`이었다. 탭 전환은 일어나지 않았다.
- 기전:
  1. `fill('')`이 검색 칸에 초점을 주면 그 스크롤이 `assets/life/ui.css`의 `html{scroll-behavior:smooth}`로 애니메이션이 된다. 낮은 부하에서도 약 0.7초 동안 중간 위치 40개를 지난다(1535 → 72).
  2. 이어지는 `click`의 위치 계산과 실제 누름 사이에 페이지가 계속 움직인다.
  3. 같은 기전이 `tests/helpers/instant-scroll.cjs` 주석에 이미 적혀 있다.
- 고친 것(검사만): `notes-menu-browser`의 맥락에 기존 `instantScroll`을 적용한다. 앱의 스크롤 호출은 원래 `behavior: 'instant'`라 앱 동작은 같다. 단언과 제한시간은 그대로다.
- 확인:
  - 고친 뒤 입력과 누름 사이의 scroll 이벤트는 1–2회다(초점 이동과 Playwright의 화면 안으로 가져오기가 각각 한 번에 이동). 고치기 전에는 약 40회였다.
  - 낮은 부하 전체 실행은 종료 코드 0(9/9)이다.
  - 같은 부하 실험(해당 검사 8개 동시 × 5회, 바쁜 반복 12개, 부하 21–40)에서 40회 모두 종료 코드 0이다. 고치기 전 실패율이 낮아(약 1/33) 이 숫자만으로 충분한 증거는 아니다. 기전 확인은 위 scroll 이벤트 수로 한다.
- 변이 확인(고친 검사가 앱 결함을 계속 잡는가):
  - `home.js`에서 초안 탭 누름이 탭을 바꾸지 않게 하면 같은 지점에서 종료 코드 1이다.
  - `ui.js`의 복귀 스크롤을 200px 어긋나게 하면 273행 위치 단언에서 종료 코드 1이다.
- 같은 원인을 검사마다 따로 막은 곳: `integrated-release`·`publish-recovery`(맥락에 즉시 스크롤), `subview-navigation`(`clickAtRest`), `core-experience`·`reading-quality`(스크롤이 멎을 때까지 대기), `life-rediscovery`(`scrollend` 대기).
  - 공용 `makeContext`에 `instantScroll`을 넣으면 한 곳에서 막힌다. `makeContext`를 쓰는 검사가 170여 개라 전체 브라우저 재실행이 필요해서 이번에는 하지 않았다.

## 4. `account-library` 멈춤: 재현 안 됨

- 부하 23–24에서 4개를 동시에 실행했다. 모두 종료 코드 0(220–226초)이었다. 그 전 기록은 W4 보고의 75회 통과와 int5 실행이다.
- `tests/helpers/stall-watch.cjs`는 그대로 둔다. 다시 멈추면 30초 뒤 실패로 끝나고, 주 스레드 응답 여부·뷰포트·주소·마지막 콘솔 줄을 남긴다.

## 남은 일

- `unified-home` `ready()` 15초의 원인은 모른다(위 2절).
- 1–3절의 수치는 이 공유 컨테이너 한 대의 측정이다. GitHub Actions 러너의 수치는 아니다.
- 원래 실패 순간의 부하 구성(다른 세션의 Docker·PostgreSQL 등)은 다시 만들지 못했다. 부하 실험은 브라우저 검사와 바쁜 반복으로 대신했다.
