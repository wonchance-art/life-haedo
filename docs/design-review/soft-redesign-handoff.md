## 총괄 질문에 대한 시안 세션 권고 (2026-11-02)

총괄이 운영 DB에서 개수 SQL을 실행한 결과를 근거로 한다.
- 사진 글 4개, 활성 공개 사본 0개
- Markdown이 잃는 서식(밑줄·정렬·제목 1·2·링크)은 모두 0
- 빈 문단이 있는 글 1개

모든 항목은 소유자 확인 뒤 적용한다.

### 1. 메뉴 대응 — 총괄 초안에 동의, 세부 대응

- **섹션 ID:** 새 섹션은 `news`(뉴스)·`schedule`(일정)·`records`(자료)·`manage`(설정)로 둔다. 이전 ID는 별칭으로 남겨 옛 주소가 계속 열리게 한다. `home`·`tools`는 `schedule`로 연결한다.
- **화면 대응:**

  | 지금 | 새 자리 |
  | --- | --- |
  | `home`·`blog`·`account-blog`(내 글) | 일정 목록. 내 글이 날짜·시간 왼쪽 칸 행으로 보인다. |
  | `tools`·`annual-plan`, `goals.html`·`habits.html` | 일정: Y의 목표, W의 습관, D의 그날 체크 |
  | `timeline.html`·`workspace.html` | 일정 Y·Q·M. 연표 편집은 Y·Q 화면에서 한다. |
  | `public-cover`·`public-pages` | 설정 > 공개 페이지. 글 한 편의 공개는 글의 `⋯ → 공개하기`로 옮겼다. |
  | `records`의 모든 보기, `write`(자료로 글쓰기) | 자료. 글쓰기는 `+ 글쓰기`로도 들어간다. |
  | `manage`의 보기 | 설정 |

- **`?section=` 대응:**
  - `home` → 일정 목록
  - `tools` → 일정 Y, `tools&view=annual-plan` → 일정 Y의 계획 칸
  - `records` → 자료, `manage` → 설정, `news` → 뉴스
  - 로그인 뒤 `index.html` 기본 화면 → 일정 목록
- **PRODUCT.md 계약:** "로그인 후 내 글·글쓰기 우선"은 뜻을 유지하고 형태만 바뀐다.
  - 로그인 뒤 첫 화면은 일정 목록이고, 내 글이 날짜순 행으로 맨 앞에 보인다.
  - `글쓰기`는 모든 화면에서 같은 자리에 둔다(데스크톱 왼쪽 메뉴 맨 위, iPhone 오른쪽 위 연필).
  - 이 문장으로 `PRODUCT.md`(대표 탐색 두 곳), `AGENTS.md` 전역 메뉴 항목, `DESIGN.md` 탐색 절을 함께 고치고, 결정일 2026-11-02를 적는다.

### 2. 글 저장 형식 — 권고를 (A) Markdown 정본으로 바꾸고, 단계를 둘로 나눈다

- **권고를 바꾼 이유:**
  - (B)를 권했던 근거는 "기존 글의 서식 손실"이었다. 운영 결과로 그 위험이 0에 가깝다(서식 0, 빈 문단 1).
  - 고른 편집 엔진(Tiptap)은 Markdown을 직접 다루고, 직접 만든 확장 약 150줄로 바이트 동일 왕복이 됐다.
  - (B)는 Tiptap ↔ Delta 변환을 하나 더 두거나, 마지막 배포가 2024년인 Quill을 확장해야 한다.
  - (A)는 Obsidian 파일 형식과 저장 형식이 같아 변환이 한 번 줄어든다. 읽기 렌더러(markdown-it)도 이미 있다.
- **단계:**
  - **D1**(지금 착수 가능): v2 형식 그대로 화면만 바꾼다. 제목 먼저, 공개 알약과 글 정보, 저장 상태 문구, 공개 대화상자, 지금 Quill 도구를 떠 있는 막대로. 형식 변경은 없다.
  - **D2**: 새 형식(예: `life-post-md-v1`)과 Tiptap 블록 편집(체크·코드·구분선·자료 인용·`[[연결]]`·`/` 메뉴)을 넣는다.
- **D2 이행 규칙:**
  - 한꺼번에 변환하지 않는다. v2 글은 v2로 읽히게 두고, 새 편집기에서 처음 고칠 때 「정확」 변환기로 바꾼다.
  - 원래 v2 문서는 복구 사본으로 남긴다.
  - 빈 문단은 `&nbsp;` 문단으로 보존한다. markdown-it은 `html:false`에서도 엔티티를 풀어 보인다.
  - D2를 출시하기 전에 전체 백업을 받는다.
  - 서버에는 새 형식 검증(본문 크기, 앞부분 속성 `title`·`date`·`tags`, 사진 목록)을 마이그레이션으로 추가한다.
  - 공개 사본은 Markdown에서 만들고 결정 14의 변환을 거친다. 백업·ZIP·보존 파일 판독기도 함께 고친다.
- **2번 밑줄·정렬:** 새 편집기에서 뺀다. 운영 사용 0이고 Markdown으로 저장되지 않는다.
- **4번 판 기록:** 지금은 만들지 않는다. 소유자 한 명의 흐름에서는 복구 사본과 백업으로 충분하다. 쓰면서 필요가 생기면 다시 본다.
- **7번 충돌 규칙:** 이름은 `복구 사본`으로 통일한다. 규칙은 "최신 쪽 채택"을 따르되, 현재 코드의 예외 하나를 남기기를 권한다.
  - 예외: "글 저장(완성)은 그 글의 어떤 초안보다 최신 상태로 본다."
  - 이 예외가 없으면, 늦게 동기화된 기기의 초안이 이미 완성·공개된 글을 초안으로 되돌릴 수 있다.
  - 어느 쪽이든 진 쪽은 복구 사본으로 남으므로 잃는 데이터는 없다.
  - 예외를 남기면 `AGENTS.md` 규칙 문장에 이 정의를 덧붙인다.
  - 소유자가 예외 없는 최신 우선을 고르면 `blog-sync.js`의 `finishedElsewhere` 분기와 그 시험을 바꾼다.

### 3. 공개 사진 — 총괄 기본안(촬영·위치 정보를 뺀 사본)에 동의

- 공개에는 모든 형식에서 촬영·위치 정보를 뺀 사본을 쓴다. 원본은 비공개로 남는다. 지금 공개된 사진이 0장이라 옮길 것이 없다.
- 만드는 방법:
  - EXIF 회전을 먼저 적용한 뒤 캔버스로 다시 인코딩한다. JPEG는 품질 0.9 정도, PNG는 무손실이다.
  - 움직이는 WebP는 첫 장면만 쓴다고 알리거나 공개 대상에서 막는다.
- 공개 대화상자의 "원본·촬영 정보 공개 동의" 확인은 빼고, 미리보기와 내용 공개 동의만 남긴다.
- 공개된 바이트에 EXIF·GPS가 없음을 시험으로 확인한다.

### 4. 상태 문구 — 총괄 기본안(두 단계로 바꾸기)에 동의

- `synced` → `저장됨 · 계정에 올림`. 새 화면에서는 평소에 숨긴다.
- `pending`·`not_enabled`·`paused` → `저장됨 · 계정에 올리기 대기`
- `error` → `저장됨 · 계정에 올리지 못함 · 다시 시도`
- `conflict` → `다른 기기 변경을 맞추는 중 · 진 쪽은 복구 사본으로 남김`
- 이전 문구를 확인하는 시험은 같은 변경에서 함께 고친다.
