# 화면 디자인 전문가 기준

2026-11-02 사용자 지시: 기존 디자인 캔버스 방식은 유지한다. 대신 시안을 만들기 전에 비슷한 기능을 구현한 앱을 먼저 조사하고, 아래 전문가 기준으로 품질 기준을 높인다. 이 문서는 새 화면과 개편 시안에 적용한다. 작은 문구 수정이나 버그 수정에는 적용하지 않는다.

제품 사실은 [PRODUCT.md](../../PRODUCT.md), 시각 토큰은 [DESIGN.md](../../DESIGN.md), 금지 목록 원문은 [Impeccable craft-floor](../../.agents/skills/impeccable/reference/craft-floor.md)와 [디자인 스킬 비교 기록](impeccable.md)을 따른다.

## 1. 시작 전 — 레퍼런스부터

1. **사용 장면을 한 문장으로 쓴다.** 누가, 어느 기기(Mac·iPad Chrome·iPhone)에서, 어떤 상황에서, 무엇을 끝내려고 이 화면을 여는지 쓴다. 예: “퇴근길 iPhone에서 지난달 어떤 날이 좋았는지 찾아 그날 글을 연다.”
2. **비슷한 기능을 출시한 앱 3–5개를 조사한다.** 공식 도움말이나 실제 화면처럼 확인할 수 있는 근거를 우선한다. 앱마다 “사용자가 보는 것과 하는 일”을 한 줄로 적고 출처와 확인일을 남긴다.
3. **가져올 패턴과 피할 패턴을 나눈다.** 가져올 패턴은 구현할 수 있는 화면 결정으로 쓴다. 해도의 원칙(비공개 기본, 정확한 원문 버전, 기능어 문구, 압박 없는 기록)과 부딪히는 패턴은 피할 것으로 남긴다.
4. **화면 모드를 정한다.** 찾기·고르기·체크는 Operate, 원문·글 읽기는 Read다. 한 화면에서 두 모드가 섞이면 어느 쪽이 주인지 정한다.

조사 결과는 디자인 캔버스의 조사 보드나 해당 기능의 설계 문서에 둔다. 레퍼런스의 시각을 그대로 베끼지 않는다. 가져오는 것은 동작과 정보 배치다.

## 2. 방향 — 한 문장과 토큰 계획

- 화면 방향을 한 문장으로 정한다. 예: “사진과 제목이 앞서고, 숫자는 문장 속으로 물러난다.”
- 토큰은 DESIGN.md의 것을 쓴다(Pretendard, 틸 `#145b50`, 캔버스 위 흰 읽기 면, 12–16px 반경, 44px 조작). 새 색이나 글꼴이 필요하면 이유를 적는다.
- 강조는 화면마다 한 곳에만 둔다. 나머지는 차분하게 둔다.

## 3. 합격선

다음을 모두 넘어야 시안으로 보여준다.

- **위계:** 제목, 본문, 보조 정보가 크기와 굵기로 세 단계 이상 구분된다. 실제 사진과 제목이 숫자나 틀보다 먼저 보인다.
- **문구:** 기능어만 쓴다. 날짜는 `10월 28일 수요일`, 개수는 `글 5편, 기록 29개`처럼 문장으로 쓴다. 범례는 짧은 견본 한 줄로 둔다.
- **접근성:** 조작 44px 이상, 작은 글자 대비 4.5:1 이상, 입력 글자 16px 이상, 색만으로 뜻을 전하지 않는다. 키보드 초점과 이름이 있어야 한다.
- **상태:** 빈 상태, 불러오는 중, 실패, 긴 제목, 이전 버전, 계정·공간 전환 중 하나 이상을 시안에 함께 둔다.
- **기기:** 1440·820·390px에서 배치가 무너지지 않는다. 화면 크기 모사를 실제 Apple 기기 확인으로 보고하지 않는다.
- **보존:** 정확한 원문 버전, 비공개 기본, 저장과 공개의 구분을 화면이 흐리지 않는다.

## 4. 금지 목록

[craft-floor](../../.agents/skills/impeccable/reference/craft-floor.md)와 Anthropic frontend-design 금지 목록에서 해도에 자주 생기는 것만 추렸다.

- 작은 날짜·개수에 고정폭 글꼴 쓰기.
- 가운뎃점으로 이은 지표 줄(`글 30 · 사진 86 · 자료 512`).
- 제목이나 내용 위에 붙인 분류 라벨과 열 머리글.
- 가는 선과 격자로 칸을 나눈 표·달력.
- 2px 이상의 색 왼쪽 테두리 카드. 인용은 예외다(아래 사용자 결정).
- ✓ 같은 글자를 아이콘 대신 쓰기. 아이콘은 `assets/life/icons.js`를 쓴다.
- 진행 막대나 작은 그래프가 내용을 대신하는 화면. 숫자 옆에 함께 두는 목표 막대는 예외다(아래 사용자 결정).
- 같은 모양 카드의 반복, 연속 기록 압박이나 가짜 반응 수 같은 게임식 장치.

## 5. 검수

1. 위 금지 목록과 합격선을 직접 대조한다.
2. 다른 에이전트에게 독립 검토를 맡긴다. 검토자에게는 결론이 아니라 스크린샷과 기준 문서를 준다.
3. 이전 판과 나란히 놓고, 잃어버린 기능이나 정보가 없는지 확인한다.
4. 사용자 결정이 검토 의견과 다르면 사용자 결정을 따르고, 그 이유를 기록한다.
5. 아래 Apple HIG 원칙 질문에 답한다.

### Apple HIG 원칙 질문

[Apple Human Interface Guidelines의 Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)는 2026-06-08에 다시 소개됐다(확인일 2026-11-02). 8원칙을 해도의 검수 질문으로 옮긴다.

| 원칙 | 검수 질문 |
| --- | --- |
| Purpose | 이 화면에서 가장 중요한 일 하나가 첫눈에 보이는가? |
| Agency | 모드에 가두지 않고, 되돌리기나 복구가 가까이 있는가? |
| Responsibility | 비공개 기본, 외부 전송(번역 등), 저장과 공개의 차이가 드러나는가? |
| Familiarity | 사람들이 아는 패턴인가? 같은 기능은 같은 모양과 같은 자리인가? 누르면 바로 반응하는가? |
| Flexibility | 1440·820·390, 키보드·터치에서 조작 위치와 맥락이 유지되는가? |
| Simplicity | 빼도 되는 요소가 남아 있지 않은가? 필요한 것은 가까이 있는가? 단순함은 미니멀리즘과 다르다. |
| Craft | 정렬, 간격, 문구, 전환이 다듬어졌는가? |
| Delight | 반응은 담기·체크 같은 순간에만 짧게 두고, 장식으로 채우지 않았는가? |

## 6. 에이전트에게 줄 프롬프트

아래 문단은 디자인 작업을 다른 에이전트에게 맡길 때 그대로 붙여 쓴다.

```text
당신은 한국어 개인 기록 앱 '해도'의 시니어 제품 디자이너다. 시안을 그리기 전에 다음 순서를 지킨다.
1) 사용 장면을 한 문장으로 쓴다(기기·상황·끝낼 일).
2) 같은 기능을 출시한 앱 3–5개의 공식 근거를 찾아 '가져올 패턴'과 '피할 패턴'으로 나누고 출처를 남긴다.
3) 화면 방향 한 문장과 DESIGN.md 토큰 계획을 쓰고, 강조는 한 곳에만 둔다.
4) docs/design-review/expert-design-brief.md의 합격선과 금지 목록을 넘는 시안만 만든다.
5) 결과를 이전 판과 비교하고, 잃은 기능·정보와 미검증 부분을 따로 보고한다.
실제 개인 기록을 쓰지 않고 익명 예시만 쓴다. 문구는 기능어로만 쓴다.
```
