## 목표와 범위

사용자가 요청한 것은 이미 만들어진 기능을 실제 사용 흐름에 맞춰 연결하고, 특히 설정과 도구에 흩어진 관련 항목을 통합하는 것이다. 기본 화면에서는 읽기·작성·계획에 집중하고 해당 자료에 필요한 작업은 그 화면에서 연다. 같은 목표의 진입·복귀·저장 보호·기존 주소 호환을 한 묶음으로 구현한다.

기존 화면·저장 모델·계정 연동·아이콘·탐색 구조를 재사용한다. 새로운 기능 허브, 런타임 라이브러리, 자동 공개, 자료 스키마 또는 계획의 자동 변환은 필요하지 않다. `홈·뉴스·자료실·도구·설정` 다섯 기본 메뉴는 유지한다.

## 기준 화면에서 확인한 분산

- 도구는 연간 계획, 네이버 연결, 관심 확인, 새 글 찾기, 다시 찾기, 회고, 책 만들기, 목표, 습관을 한 목록에 둔다. 뉴스가 이미 기본 메뉴인데 새 글 찾기가 여기에도 있고, 뉴스 설정에 있는 관심 확인도 반복된다.
- 설정은 현재 자료공간·계정 보관과 함께 Obsidian 갱신, 원본 첨부, 글 관리, 공개 표지, 공개 페이지, 여러 형식의 백업을 나열한다. 자료를 읽거나 글을 관리하다가 설정으로 옮겨야 해당 작업을 찾는다.
- 홈은 이미 프로필·글 관리·서버 글 진입이 있고, 가져오기는 이미 네이버 연결 진입이 있다. 이 기존 경로를 살려 대표 위치를 정한다.
- 자료 선택에서 묶음·자료 페이지·회고로 보내는 흐름은 구현돼 있다. 일반 메뉴 통합이 정확한 선택 자료를 전달하는 이 흐름을 대체하지 않는다.

현황 진입점은 `assets/life/ui.js`의 `renderTools`, `renderManagement`, `renderHeader`, `sectionFor`, `routeMode`, `writeRoute`와 `assets/life/home.js`의 `profileHeader`, `assets/life/discovery-ui.js`의 뉴스 설정이다.

자료실의 컬렉션·묶음·선택 자료 페이지와 검색·가져오기·글쓰기는 기존 사용 경로를 유지한다. 메뉴를 줄이기 위해 필요한 동작을 숨기거나 삭제하지 않는다. 자료 메뉴를 펼친 상태에서만 활용과 가져오기·관리 항목을 구분하고, 기본 화면에 설명 문단이나 새 상시 패널을 추가하지 않는다.

계획 도구의 인접 배치는 저장 데이터의 통합을 뜻하지 않는다. 연간 계획·목표·습관의 날짜, 완료 의미, 저장·백업 형식은 그대로다. 자료·구성, 연표·목표·습관, 컬렉션, 근거 전용 파일의 포함 범위도 별도 표시한다. 여러 파일 진입을 묶었다는 이유로 전체 자료가 한 파일에 포함된다고 표현하지 않는다.

## 구현 계약

### 경로와 대표 영역

`sectionFor`와 `HaedoNavigation`의 최초 활성 메뉴 판정을 같은 대표 위치로 맞춘다. `routeMode`는 알려진 기존 view를 먼저 해석해 과거 `tools`/`manage` 주소로도 같은 기능을 열고 `writeRoute`로 새 대표 영역을 표시한다. 새 주소에서 새로고침한 경우에도 같은 기능을 유지한다.

- `interests`는 뉴스에 속한다. `section=news&view=interests`를 뉴스 피드로 덮지 않는다.
- `discover`, `reflection`, `books`, `naver-blog`, `naver-capture`, `obsidian-update`, `source-trash`는 자료에 속한다. 기존 정확한 원문 읽기와 가져오기 검토 문맥은 유지한다.
- `blog`, `public-cover`, `public-pages`는 홈에 속한다. 기존 `account-blog`와 홈에서 시작한 작성·읽기 문맥을 유지한다.
- 연간 계획은 도구, 동기화·백업은 설정에 속한다. 알려지지 않은 view를 임의의 화면이나 외부 주소로 해석하지 않는다.

### 메뉴와 복귀

제목행의 native `details`와 기존 버튼·아이콘을 재사용하는 것이 첫 선택이다. 일반 disclosure에 완전한 메뉴 키보드 계약을 구현하지 않은 `role=menu`를 붙이지 않는다. 펼치기·닫기, Tab/Shift+Tab, Escape, 접근 가능한 이름, 최소 44px 조작 영역을 유지한다.

기존 `guarded`는 제목행에서 누른 조작을 `navigationTrigger`로 기록한다. 이동 시 기존 `navigate`/`persistDrafts`/각 기능의 `flush`를 사용하고, 저장 실패에서는 현재 입력·화면·주소를 유지한다. 메뉴 버튼에는 안정된 ID 또는 focus key를 부여한다. `returnFromSubview`는 돌아온 화면의 같은 조작을 찾고 필요한 `details`를 펼쳐 초점·스크롤을 복원한다. 조회가 늦거나 계정·작업공간이 바뀐 경우 이전 응답이 새 화면을 바꾸지 않아야 한다.

연간 계획에서 목표·습관으로 이동할 때도 `guarded`의 입력 잠금과 현재 탐색 토큰을 사용한다. 모든 저장이 끝나고 같은 계정·작업공간·화면임을 확인한 경우에만 명시적 성공값으로 주소 이동을 허용한다. 앞선 계획 저장이 성공했더라도 뒤의 다른 `flush`가 실패하면 이동하지 않는다. 이 보완은 화면 배치나 표시 문구를 바꾸지 않는다.

주소로 직접 열었거나 새로고침해 임시 진입 문맥이 없으면 새 대표 상위 화면으로 돌아간다. 이 메모리를 영속 자료·백업·서버에 추가하지 않는다. 뉴스의 내부 설정 복귀, 자료 선택의 `arrangeRecords`, 원문·관련 자료·책의 정확 버전 복귀를 일반 메뉴 복귀로 대체하지 않는다.

### 보존 범위

자료·폴더·원본의 기존 계정 보관, 초안과 실패 입력, 정확 원문 버전·UTF-16 발췌, 자료 선택, 홈의 탭·검색·글 ID, 뉴스의 반응·옵션과 공개/비공개 선택을 유지한다. UI 메뉴를 열거나 영역을 바꾸는 것 자체가 새 업로드·분석·공개 동의가 되어서는 안 된다.

## 검증 계획과 근거 경계

기준 화면은 해당 main 커밋의 `git archive`를 별도 디렉터리와 서버에 고정해 캡처한다. 실제 기존 앱·SDK·IndexedDB와 합성 capability-1 계정 HTTP, 기존 익명 6자료/12발췌를 사용한다. 최종 화면도 같은 자료와 1440·820·390px 조건으로 비교한다. 소스 해시·실제 응답 바이트·화면 경로와 캡처 해시를 실행 기록에 남긴다. 개인 자료·운영 계정은 사용하지 않는다.

완료 판단은 다음을 나누어 기록한다.

1. **기능·복귀:** 새 메뉴의 모든 기존 목적지, 과거 주소, 새 주소 새로고침, 같은 진입점 복귀, 저장 실패 차단, 계정/공간 변경 보호, 자료 선택→회고/글쓰기 왕복.
2. **화면:** 세 폭의 기본 화면과 열린 메뉴를 직접 확인하고 가로 넘침, 44px 조작, 키보드·초점, 대비와 설명/제목 중복을 점검한다. 본문 집중을 기능 수나 테스트 수로 대신 판단하지 않는다.
3. **출시:** 최종 소스 기준 정적·관련 회귀·CI·PWA 갱신·배포 바이트와 배포본 흐름을 구분한다. 이전 릴리스 결과를 이번 변경의 통과 근거로 재사용하지 않는다.

실제 Apple 기기·Google 로그인·개인 자료·OS 파일 보관·사용자의 반복 사용 유용성은 자동 브라우저 검수와 구분한다.

### 독립 초기 검토

고정 기준 main의 12화면과 구현 후보의 기본 12화면·메뉴 6화면을 같은 익명 자료로 캡처했다. 후보의 203개 소스 해시는 실행 전후 같았고 실제 정적 응답 953건도 해당 바이트와 일치했다. 세 폭의 메뉴 Escape 복귀와 자료 메뉴에서 다시 찾기·회고·책·휴지통을 열었다가 같은 조작으로 돌아오는 10조건을 확인했다. 검사한 화면의 가로 넘침·44px 조작·대비·이름·16px 입력 실패와 콘솔·페이지 오류는 없었다. 이 결과는 메뉴 통합의 전체 회귀 통과나 출시 완료를 의미하지 않는다.

수정이 필요한 조건도 실제로 확인했다. 자료 메뉴의 회고 조작에 키보드 초점을 둔 상태에서 정상 자료 변경 트랜잭션을 발생시키면 헤더 재생성 뒤 초점이 `BODY`로 옮겨졌다. 같은 화면의 열린 메뉴와 안정된 조작의 초점을 보존하도록 수정했다. 최초 진단의 거절된 변경에는 이벤트가 없었으므로 초점 보존 근거로 사용하지 않았고, revision을 올린 유효한 실제 저장으로 위 실패를 확인했다.

초기 전체 페이지 캡처에는 일부 탐색 표시의 전환 중 프레임이 포함되었다. 원본 초기 근거는 `.local/feature-flow-integration-20261024/baseline/`과 `review-initial/`에 보존한다.

### 수정 후 독립 검토

같은 익명 자료와 세 폭에서 기본 12화면·메뉴 6화면·읽을 수 있는 메뉴 viewport 6화면을 캡처했다. 현재 실행 중인 유한 애니메이션의 실제 종료와 두 프레임을 기다렸으며 CSS로 동작을 끄거나 바꾸지 않았다. 자료·홈 메뉴의 세 폭 viewport와 도구·설정의 390px 이미지를 직접 검토했다. 도구는 계획 세 항목으로 줄었고 설정은 자료공간·계정 보관과 파일 종류별 작업에 집중한다. 자료 메뉴의 두 그룹과 홈의 공개 조작은 펼쳤을 때만 나타난다.

수정 후 203개 소스 해시는 실행 전후 같았고 정적 응답 953건이 해당 바이트와 일치했다. 기존 10조건과 정상 저장의 변경 이벤트 중 메뉴 초점 보존까지 11조건을 통과했다. 마지막 조건은 실제 `stored` 결과·변경 revision 8 이벤트를 확인했으며 전후 모두 `records:menu:reflection` 버튼에 초점이 남았다. 화면 계측 실패·콘솔·페이지 오류·외부 요청은 없고 세 컨텍스트와 브라우저를 종료했다. 독립 근거는 `.local/feature-flow-integration-20261024/review-final/independent-review.json`이며 해당 실행의 `ui.js` SHA-256은 `7aba211bf65808fe578cc46ccab6550e8d03cd9286c71b28ad99aba03ac591f0`이다.

원본 첨부→정확 원문 이동의 코드도 함께 검토했다. 같은 자료공간에서는 검색·폴더를 유지하고, 다른 공간을 명시적으로 선택했을 때만 이전 문맥을 초기화한다. 비동기 조회 뒤 현재 작업공간·탐색 범위를 재확인하고, 돌아오면 자료 메뉴의 동일한 원본 첨부 조작을 연다. 이 코드 검토를 별도의 원본 ZIP 왕복 실행 결과로 합산하지 않는다. 전체 회귀·PWA·최종 PR/main CI·운영 배포는 총괄 검증 기록을 따른다.

마지막 계획 이동 변경은 별도의 독립 탐색 검토도 통과했다. 기존 브라우저 검사 수정은 옮겨진 진입 조작을 현재 메뉴로 연결하는 범위이며 원문·저장·실패 복구의 기존 단언을 완화하는 근거가 아니다. 이전 실패·불충분한 진단은 원기록에 남겼다. 최종 CI·공개 배포 완료는 위 브랜치의 출시 기록이 확정되기 전까지 주장하지 않는다.

### 첫 PR CI에서 드러난 검사 진입·준비 순서

첫 PR CI(`40054069257`, HEAD `54ff4b38a401514bc824ee9a90fe245b675cbb03`)의 새 집중 통합 11흐름은 통과했다. 별도 기존 검사에서 다음 두 실패를 확인했고, 원래 실패 로그와 로컬 재현을 보존했다.

- 뉴스 언어의 의도적으로 멈춘 읽기 2례: 새 뉴스 진입에 공통 `nav()`를 사용하면서 읽기 해제 전에 화면 완료를 기다리는 교착이 생겼다. 실제 뉴스 링크 클릭으로 진입한 뒤 기존 해제·완료 대기를 진행하도록 고쳤다. 다른 15례와 원문·설정·외부 요청 단언 및 대기 제한은 유지했다. 수정 후 전체 17례가 통과했고 실행 전후 대상 소스 해시가 같았다.
- 9칸의 계정 전환: 인증과 저장소 객체가 준비된 순간에 새 계정의 작업공간 생성까지 끝났다고 간주해 빈 작업공간 ID를 읽었다. 공식 로그의 실패 위치와 실제 `shell` 초기화 순서를 대조했다. 같은 계정의 실제 화면 표시·활성 작업공간과 조회 후 저장소 범위를 함께 확인하도록 바꿨다. 첫 보강에 사용한 비동기 `waitForFunction`도 준비되지 않은 Promise를 통과시키는 것이 설치된 도구 코드와 빈 페이지 실험에서 드러났다. 그 실패를 보존하고 각 조회 결과를 실제로 기다리는 Node 측 조건 확인으로 교정했으며 원래 20초 제한과 모든 저장·노출·보존 단언을 유지했다. 수정 후 동일 전체 8례가 통과했고 대상 제품 소스 해시는 실행 전후 같았다. 최종 CI·배포 결과는 출시 기록에 남긴다.

별도 로컬 언어 진단에서는 두 탭 충돌 후 숨겨진 재확인 버튼을 누르지 못한 1례도 있었다. 읽기 전용 진단 1회와 수정 후 전체 실행에서는 재현되지 않았고 첫 CI의 같은 사례도 통과했다. 이 사례의 원인이 규명되거나 별도로 수정됐다고 주장하지 않는다. 검사 조건 완화나 통과할 때까지의 반복 실행 없이 최초 실패와 각 진단을 보존한다.
