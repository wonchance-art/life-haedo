# 하위 화면의 위치와 작업 복귀

2026-10-09 KST. 홈·탐색 로드맵의 다음 단위다. 목표는 **홈/검색/도구/관리에서 작업 화면으로 이동 → 입력 또는 확인 → 들어온 위치로 복귀**다. root가 디자인·구현·통합 검토를 담당했다. 책 확장은 보류하며 기존 책/회고 기능을 추가하지 않았다.

## 재현한 문제와 결과

[변경 전 관찰](evidence/subview-navigation/before.json): 가져오기 상단은 `기록`, 자료 백업 상단은 `관리`로 표시됐다. 글쓰기/가져오기에 들어온 위치로 돌아가는 공통 조작이 없었고, 백업 화면에서 선택된 `관리` 메뉴를 다시 눌러도 `transfer` 화면에 그대로 머물렀다.

| 조작 | 변경 후 |
| --- | --- |
| 하위 화면 제목 | 가져오기·글쓰기·연표·묶음·내 페이지·다시 찾기·기기 간 동기화·자료 백업/구성 백업·공개 페이지 관리 중 실제 화면 이름 |
| 상단 뒤로가기 | 홈에서 들어오면 홈, 검색 목록에서 들어오면 해당 목록, 도구/관리에서 들어오면 그 목록으로 복귀 |
| 선택된 기본 메뉴 다시 누르기 | 해당 영역 목록으로 이동. 검색에서 연 원문은 기존 정확 검색 복귀 경로 재사용 |
| 주소로 직접 연 화면 | 기억된 진입점이 없으므로 기록/도구/관리의 기본 상위 목록으로 복귀 |
| 저장 실패 | URL·현재 화면·입력 유지. 저장 재시도 후 복귀 가능 |
| 느린 홈 조회 | 다른 메뉴를 즉시 사용할 수 있음. 늦은 조회가 다른 화면이나 초점을 바꾸지 않음 |

후속 검토에서 묶음 제목을 바꾼 뒤 홈의 같은 항목에 초점이 돌아오지 않는 실패를 [재현](evidence/subview-navigation/group-before.log)했다. 홈 조작은 전환 전에 초점을 유지하고, 묶음의 기존 ID를 복귀 키로 사용하도록 수정했다. 내 페이지 편집 버튼의 홈 복귀도 함께 검증했다.

글쓰기의 기존 내부 뒤로가기는 공통 상단으로 합쳤다. `lifeWritingClose` 조작 ID와 저장 보호는 유지한다. 단독 WritingUI의 기본 복귀는 그대로이며 공통 프레임을 제공하는 경우에만 내부 중복 조작을 생략한다. 기존 원문 읽기·관련 기록·책의 전용 복귀 계약을 새 일반 복귀로 대체하지 않았다.

## 구현 판단과 보존

기존 `navigate`, 저장 `flush`, `returnToResults`, 공통 아이콘/버튼/제목 행을 재사용한다. 복귀 정보는 UI 인스턴스의 Map에 화면 이름·작업공간 범위·초점 대상·스크롤만 보관한다. 다른 작업공간 선택/복원과 계정 폐기에서 초기화한다. 원문·정확 버전·발췌·초안·백업·동기화·공개 스키마에 추가하지 않는다. 저장에 실패하면 복귀 정보도 새 대상으로 확정하지 않는다.

반대 검토: 하위 화면마다 별도 사이드바나 안내 문구를 추가하면 프레임이 커진다. 기존 제목 행의 20px 도형/44px 조작을 재사용하는 쪽을 택했다. 탐색 라이브러리나 새 상태 저장 모듈 없이 기존 화면 경계를 연결하므로 신규 의존성·운영 SQL·인증 설정이 없다. 공식 Impeccable 4.5.0 지침의 Operate/craft-floor와 [프로젝트 도입 기록](impeccable.md)을 직접 참고했다. 외부 제품의 최신 릴리스를 이번에 새로 비교하거나 Impeccable 실행 엔진을 사용했다는 뜻은 아니다.

이번 상단 뒤로가기는 **앱 안의 복귀 조작**이다. 브라우저의 Back/Forward는 기존 영역 이동 이력 계약을 유지한다. 모든 하위 작업·원문·입력 상태를 브라우저 이력으로 직렬화하는 기능은 추가하지 않았다. 새로고침하면 화면 진입점 기억이 초기화되고 기본 상위 목록을 사용한다. 저장된 초안과 자료는 초기화되지 않는다.

## 브라우저 이력과 새로고침 (2026-11-02)

소유자 결정: 브라우저 뒤로 가기는 앱 안의 직전 화면으로 간다. 위 "앱 안의 복귀 조작만 다룬다"는 판단을 이 절이 대체한다. 구조 검토가 a8d4a65에서 재현한 세 결함을 고쳤다.

- **새로고침:** 글쓰기·글 읽기는 주소에 `blog=`로 작업을 남긴다. 값은 `new`·`profile`·`photo.<글 ID>`·`plain.<저장 글 ID>`·`draft.<페이지 초안 ID>` 중 하나다. 다시 불러오면 같은 편집기나 같은 글을 연다. 첫 저장 전에 떠난 새 글은 저장된 것이 없으므로 새 글쓰기로 연다. ID는 무작위 식별자이며 본문·제목은 주소에 넣지 않는다.
- **옛 주소 `index.html?view=page`:** `blog`가 없으면 기존 의미인 선택 자료 페이지로 연다. 이 주소만으로는 어느 글인지 알 수 없다. 빈 새 글을 열면 사용자의 초안을 되찾아 주지 못하고 빈 초안만 늘어난다. 직접 링크 검사가 이 의미를 고정해 왔다. `?compose=1`은 계속 새 글쓰기다.
- **이력 기준:** 각 기록의 `history.state.haedo`에는 식별자만 둔다. 화면 이름, 원문·버전·글·작업공간 ID, 글 작업 종류, focusKey·focusId·focusTag, 스크롤, 홈 탭이 여기에 해당한다. 바로 전 기록의 요약(`back`)과 문서 실행 ID(`doc`)도 함께 둔다. 사람이 읽는 초점 이름, 글 제목, 결과 구절, 검색어, 자료로 글쓰기 seed는 이 탭의 메모리(`historyDetails`)에만 둔다. 통합 검색 계약에 따라 검색어는 영속 저장하지 않는다. 메모리에 없으면(새로고침 뒤) 내용 없이 식별자로만 복원한다. 이때 홈 검색어는 비어 있고, 초점은 ID로 찾거나 제목으로 간다.

| 이동 | 기록 |
| --- | --- |
| 다른 화면으로 이동(전역 메뉴, 목록→하위 화면, 자료 읽기, 글쓰기·글 읽기, 자료로 글쓰기 시작) | `pushState` |
| 같은 화면에서 다른 원문 열기, 다른 글·초안 열기 | `pushState` |
| 앱 안 돌아가기의 대상이 바로 전 기록과 같은 화면 | `history.back()`(닫은 화면은 앞으로 기록에만 남는다) |
| 앱 안 돌아가기의 대상이 바로 전 기록이 아님(예: 주소로 직접 연 화면의 상위 목록) | `pushState` |
| `push` 대상이 현재 기록과 주소·화면이 같음 | `replaceState` |
| 같은 원문의 다른 버전 선택, 검색어·필터, 저장 후 편집→읽기, 새 글에 ID가 생김 | `replaceState` |
| 렌더 때 주소 정규화, 작업공간 전환, 브라우저 뒤로/앞으로로 연 화면 | `replaceState` |

- **위치:** push 직전에 `history.state.haedo.idx`로 현재 위치를 다시 읽는다. 그래서 한 문서 안에서 연속한 기록의 idx는 항상 1씩 늘고, 되돌릴 때 쓰는 idx 차이가 실제 이동 칸 수와 같다. 브라우저를 되돌릴 때는 도착할 때마다 실제 위치(`history.state`)에서 목표 기록까지의 칸 수를 다시 계산한다. 그래서 그 사이에 뒤로 가기를 더 눌러도 목표에서 벗어나지 않는다. 브라우저가 이동하는 동안(`history.go`/`back`이 도착하기 전)에는 기록을 쓰지 않는다. 새 이동은 그 이동이 끝난 뒤에 기록된다. 기록된 화면을 여는 중에 누른 뒤로 가기는 여는 화면의 기록으로 되돌린다. 열기에 실패하면 지금 보이는 화면의 기록으로 되돌린다. 상태 없는 조각(`#…`) 링크 기록은 바로 다음 칸으로 센다.
- **뒤로/앞으로:** `popstate`가 오면 기록된 화면을 `navigate()`로 다시 연다. 기존 flush와 복귀 규칙을 그대로 쓰고, 초점·스크롤은 앱 안 돌아가기와 같은 방식으로 되살린다. 저장이 실패하거나 한글 조합 중이면 이동하지 않는다. 이때 브라우저를 지금 보이는 화면의 기록으로 되돌리고(`history.go`), 오류 문구와 입력을 남긴다.
- **이동·저장 중의 뒤로 가기:** 화면 이동이나 저장이 진행 중일 때 도착한 뒤로 가기는 적용하지 않는다. 브라우저를 지금 보이는 화면의 기록으로 즉시 되돌리고, 진행 중인 이동은 그 뒤에 기록한다. 끝난 뒤 다시 누르면 된다. 브라우저가 그 뒤로 가기를 이동이 기록된 뒤에 처리하면, 앱이 한가할 때 도착한 것이므로 평소처럼 그 기록의 화면을 연다. 두 경우 모두 보이는 화면과 현재 기록이 일치하고, 앞뒤 기록의 칸 수가 맞는다.
- **자료실 메뉴와 글 작업:** 다른 영역 메뉴로 떠나면 글쓰기·글 읽기 작업 표시를 끝낸다. 자료실의 선택 자료 페이지는 글 작업을 물려받지 않는다. 같은 영역 안의 이동(예: 글 읽기 → 근거 원문 → 글 읽기)은 기존 계약대로 작업을 유지한다. 근거 원문이 홈 영역으로 표시되고 다시 글로 돌아오는 흐름이 이 값을 쓴다.
- **OAuth:** 콜백 값(`code`·`token_hash`·토큰·오류 등)은 어떤 기록에도 복사하지 않는다.
- **오프라인:** 서비스워커는 `blog`·`compose`가 붙은 앱 주소도 설치된 셸로 연다.
- **자료로 글쓰기의 `돌아가기`(#mwClose):** 자료 읽기에서 시작했다면 출발한 원문의 같은 버전으로 돌아간다. 읽던 위치와 '이 자료로 글쓰기' 초점도 되살린다. 작성 준비는 저장된 채 남고, 다시 누르면 같은 준비를 이어서 연다. 다른 작업이 진행 중이면 이동하지 않고 그 사실을 알린다. 상단 제목 줄의 돌아가기는 기존 계약대로 그 원문의 출발 목록(뉴스·자료실 등)으로 간다.
- **남은 제약:**
  - 자료 읽기·자료로 글쓰기 화면을 새로고침하면 기존처럼 상위 목록이나 선택 자료 페이지가 열린다.
  - 새로고침 전의 기록으로 뒤로 가면 문서를 새로 불러오므로 주소 기준으로 연다.
  - 후속 과제: 세션이 만료된 뒤 로그인을 거치면 `assets/platform-auth.js`의 `safeNext`와 `assets/life/shell.js`의 `loginPath`가(`assets/haedo-navigation.js`의 로그인 링크도 `safeNext`를 쓴다) `blog`를 보존하지 않는다. 그래서 로그인 뒤 선택 자료 페이지가 열린다. 허용 키에 `blog`(정규식 `^(?:new|profile|(?:photo|plain|draft)\.[A-Za-z0-9_-]{1,128})$`)를 추가하는 일은 인증 담당 범위에서 따로 한다.
  - iOS 백그라운드 탭 복원과 스와이프 뒤로 가기는 실제 기기에서 확인하지 않았다.
