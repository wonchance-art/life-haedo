# 추천·탐구·콘텐츠와 채널 연결 구조

2026-10-29. 현재 코드와 [제품 목적](../life-tools-design/product-purpose.md), [읽기 메모](reading-decision-journey.md), [계획·회고](planning-practice-review.md)를 잇는 **미래 확장 설계**다. 앱·SQL·외부 계정 설정·운영 자료를 변경하지 않았다. 아래 논리 객체·작업 이름은 현재 존재하는 테이블/RPC 선언이 아니다.

## 1. 확정한 시작점과 후속 범위

사용자는 **내가 읽을 탐구 자료를 추천받는 SNS 계정부터 시작**하기로 확정했다. **최초 운영 시범은 SNS 자체 추천에서 발견하고 읽으면 완결**된다. 자체 엄선·연구 재정렬·해도 저장은 실제 필요를 확인한 뒤 두 번째 묶음으로 검토한다. 플랫폼·계정은 운영 설계에서 고르며 새 SNS 홈을 해도 페이지로 대체하지 않는다.

| 선택 | 목적 | 공통으로 만들 결과 | 선택 뒤에만 필요한 연결 |
| --- | --- | --- | --- |
| **최초 운영 시범** | 관심 질문에 도움이 되는 자료 받기 | SNS 자체 추천에서 발견·원문 읽기·종료 | native SNS 계정·관심 선택 |
| 후속 첫 통합 구현 | 다시 찾기·선택 자료 비교의 필요 해결 | 연구 재정렬·정확 근거/판단·계정 재개 | 선택 링크/허용 feed 수신·해도 저장 |
| 후속 AI 콘텐츠 | 조사한 근거로 내 콘텐츠 만들기 | 검토 가능한 초안·채널별 사본 | 명시 생성 요청·근거 범위·예산 |
| 후속 외부 발행 | 원하는 계정에 선택 콘텐츠 전달 | 확인 가능한 발행 결과 | 지정 계정의 발행 권한·명시 게시 의도 |

후속 통합에서 해도와의 접점은 플랫폼 중립 수신함과 URL 입력이다. 최초 시범은 SNS의 원래 추천·팔로우·읽기 조작만으로 진행할 수 있다. 선택하지 않은 타임라인 전체 수집·자동 반응·DM 발송·게시 예약은 포함하지 않는다. 이 문서 작성 자체는 SNS 계정 생성·팔로우 변경을 실행하지 않는다.

현행 [PRODUCT.md](../../PRODUCT.md)의 ‘SNS 연동은 수신 전용’과 [SNS 원칙](../life-tools-design/README.md)의 ‘원본 SNS 글을 게시·수정·삭제하지 않음’을 유지한다. 아래 외부 발행은 명시적인 미래 확장으로만 다룬다. 해도 블로그 공개가 외부 SNS 쓰기 권한을 뜻하지 않는다.

## 3. 전체 흐름과 역할

```text
최초 운영 시범: SNS 자체 추천 → 발견 → 원문 읽기 → 종료

필요 확인 뒤 후속 첫 통합 구현: 선택 링크/허용 feed + 질문/내 자료
  → 수신함·후보 정리 → 추천 목적에 맞는 선택
  → 정확 근거 묶음 → 읽기·비교·내 판단
      ├─ 종료 / 계정 메모 / 기존 목표·습관 연결
      └─ 콘텐츠 의도 → 대표 초안 → 선택 채널 사본 [후속 확장]
           → 검토한 발행 의도 → 외부 결과 확인 → 제한된 성과 관찰
```

화살표는 자동 실행 권한이 아니다. 수집·중복 제거·정해진 갱신은 허용된 범위에서 자동화하고, 질문의 의미·주장 채택·실천·공개 범위는 사용자가 결정한다. AI는 제한된 자료의 설명·비교·초안 후보를 만든다.

뉴스는 새 후보, 자료실은 근거·탐구·개인 메모, 홈은 내 글과 발행 결과, 계획은 실제 실천을 담당한다. 새 최상위 운영 대시보드나 채팅 화면을 선행 조건으로 추가하지 않는다.

최초 운영 시범에는 새 수신함·재정렬·계정 저장 구현이 필요하지 않다. **후속 첫 통합 구현**을 선택하면 허용 입력 adapter·후보 정규화·연구 목적 재정렬·정확 원문/판단 저장·계정 재개를 연결한다. packet은 논리 계약부터 사용하고 독립 편집기/저장소를 먼저 만들지 않는다. brief·대표 초안의 AI 생성·channel variant·publish intent·외부 analytics·게시 scheduler는 그 뒤로 미룬다.

아래 4–13절은 후속 통합과 미래 확장의 경계다. 최초 SNS 운영 시범을 시작하거나 완료하기 위한 선행 작업 목록이 아니다.

## 4. 수신함·링크 입력과 추천 목적

수신 항목은 owner/공간·입력 경로·원래 URL/플랫폼 ID·관측 시각·확보 범위·권한 근거·처리 상태를 가진다. API 수신, 공식 내보내기, 사용자가 붙인 링크/본문을 구분한다. 입력 경로가 다르다고 같은 글을 덮지 않는다.

canonical URL은 중복 후보를 찾는 단서다. 플랫폼 계정·게시물 ID·원문 판·실제 본문 해시를 함께 확인한다. 수정된 본문은 새 판이며, 비공개 글의 동일 URL을 다른 owner에게 노출하지 않는다.

링크만 들어오면 제목/URL·미확보 범위를 보관한다. 접근 제한·로그인 필요·삭제·수집 실패는 빈 본문 성공으로 바꾸지 않는다. 개인 SNS 피드를 공개 discovery-feed.json이나 공개 CI 산출물에 넣지 않는다.

새 수집 adapter는 현재 공식 API/허용 내보내기를 확인한 뒤 선택한다. 서버 URL 가져오기는 허용 프로토콜·리디렉션·DNS/IP·크기/시간 제한을 검사하며 내부 주소·자격 증명 포함 URL을 거절한다. 원문 속 지시를 도구 실행 명령으로 사용하지 않는다.

추천 목적은 ‘다음에 읽을 가치’, ‘현재 질문의 빈 근거 채우기’, ‘다른 설명 비교’, ‘발행 소재 후보’로 구분한다. 각 실행은 목적 하나와 질문/언어/기간/출처 범위의 정확 revision을 참조한다.

이번 재정렬의 목적은 앞의 세 가지이며 발행 소재 점수는 사용하지 않는다. native SNS 추천 알고리즘 자체를 제어한다고 약속하지 않고 사용자가 제공했거나 수신을 허용한 후보만 비교한다. SNS 계정의 클릭/좋아요를 조작해 추천을 훈련시키는 자동화를 기본 도입하지 않는다.

연구 재정렬은 질문 관련성·원 출처 접근성·확보 범위·자료 종류·관측 가능한 새로움/다른 관점을 따로 기록한다. 제목/태그만 가진 후보에서 연구의 방법론 품질·결론 신뢰도를 판정하지 않는다. 같은 후보 집합에서 기존 관심/최신순과 비교하고 설명 가능한 규칙으로 충분하면 모델 호출을 추가하지 않는다.

좋아요·담기·읽기 전 의향·실제 읽기·도움·발행 성과는 다른 신호다. 기존 추천 정책은 그대로 재현 가능한 기준선으로 남긴다. 도움을 누르지 않은 것을 무용함으로, 담기를 동의로, 조회수를 신뢰성으로 바꾸지 않는다.

결과에는 현재 일치 이유·알고 있는 범위·누락/오래된 자료를 표시한다. 다양성과 근거 품질은 별도 검토하며 AI가 만든 초안·성과를 다시 독립 원문처럼 추천하는 자기 강화 순환을 막는다.

## 5. evidence packet: 정확 근거 묶음

근거 묶음은 사용자 질문과 선택한 근거의 **고정된 참조 집합**이다. 별도 원문 저장소를 만들지 않고 기존 source/sourceVersion을 참조한다. 논리 필드는 packet ID/revision·질문 revision·선택 시각·source refs·확보 범위·권리/사용 범위·포함 이유다.

구절이 있으면 SourceReference.build/resolve를 재사용한다. 링크만이면 URL·source/version·null 본문/hash와 확보 범위를 유지하고 구절 검증 경로에 넣지 않는다. 번역문·AI 요약은 원문과 구별한 파생물이다.

선택 자료 전달에는 MaterialContinuity의 필요한 원문만 고르는 방식과 해시 검증을 참고한다. 해당 함수는 준비 모델을 요구하므로 packet 때문에 빈 작성 준비를 만들거나 전송 payload를 그대로 전용하는 것은 금지한다.

원문 판이 오래되었어도 정확 참조로 유효할 수 있다. ‘옛 판’과 ‘해시 불일치’를 구별한다. 새 판 도착은 기존 packet을 변경하지 않으며 사용자가 갱신하면 새 packet revision과 검토 범위를 만든다.

AI에 보낼 때 packet 전체가 아니라 요청에 필요한 최소 구절/문맥·확보 범위를 확정한다. 출처가 본문 주장을 뒷받침하는지 검사하고, 인용 밖 모델 주장에는 미확인 표시를 남긴다. 개인 메모는 별도 선택 없이는 포함하지 않는다.

## 6. 후속: content brief와 canonical draft

content brief는 질문·독자·목적·형식·길이·언어·포함/제외할 주장·근거 packet revision·작성 주체를 담는 제작 의도다. 막연한 관심 프로필 전체를 매 요청마다 복제하지 않는다. 탐구만 하면 brief를 만들 필요가 없다.

canonical draft는 채널 중립 대표 초안의 정확 판이다. 사용자가 채택한 주장·문단·인용·사진과 생성/편집 이력을 연결한다. 한 채널의 글자수 제한 때문에 대표 초안이나 원문을 잘라 덮지 않는다.

기존 작성 준비는 수동 탐구/개요 작성의 독립 기능으로 유지한다. 채택 블록의 MaterialWriting.project와 기존 PhotoPost 작성기를 재사용하되 question/note를 자동 복사하지 않는다. AI를 사용하지 않은 글에도 같은 발행 선택이 가능해야 한다.

새 AI 결과는 요청한 생성 결과 후보로 계정 보관하되 기존 로컬 PhotoPost 초안·모든 작성 준비를 조용히 업로드하지 않는다. 채택 시 기존 작성기의 새 초안 또는 명시 선택한 초안의 새 판으로 연결하며 원래 입력을 보존한다.

대표 초안은 기존 저장 글 ID/revision을 참조할 수 있다. 생성 요청·근거 packet·검토 상태는 별도 메타로 연결하고 PhotoPost Delta나 Core.note에 기계용 JSON을 숨기지 않는다. 동일 원고를 두 개의 독립 원본으로 운영하지 않는다.

## 7. 후속: channel variant와 검토

채널 사본은 canonical draft revision·채널 종류/계정·언어·형식·선택 사진·링크·본문·변환 규칙 revision을 가진다. 변환은 길이·줄바꿈·링크·미디어 제한을 처리하고 주장/수치/인용을 임의 강화하지 않는다.

대표 초안이 수정되면 기존 사본은 옛 대표 판을 가리킨다고 표시한다. 새 사본을 만들거나 사용자가 검토해 갱신한다. 채널에 맞춘 수정도 대표 초안으로 자동 역전파하지 않는다.

채널 미리보기는 문구·미디어·대상 계정·공개 범위를 보여 준다. 출처 링크가 빠지거나 인용이 잘린 경우 별도 확인이 필요하다. 제공 API에서 지원하지 않는 형식은 파일/복사 전달로 끝내고 성공 게시로 표시하지 않는다.

채널 연결은 계정 ID와 필요한 capability를 검증한다. 읽기·개인 수신함 전달·공개 게시·수정·삭제·성과 읽기 권한을 분리한다. OAuth 연결만으로 모든 capability나 모든 자료에 권한이 생기지 않는다.

## 8. 후속: publish intent와 외부 결과

게시 의도는 owner·정확 외부 계정·variant ID/revision·미디어 해시·공개 범위·예약 시각/시간대·명시 선택·operation ID를 고정한다. 별도 범위가 승인된 반복 정책이 없다면 초안 생성/저장이 게시를 예약하지 않는다.

현행 BlogSync.publish의 정확 local/remote/public revision·영속 publishPending·원격 재조회 원칙을 참고한다. 해도 블로그 remote와 외부 provider는 다른 adapter이며 기존 RPC를 SNS 발행 API로 이름만 바꾸지 않는다.

외부 작업은 다음 최소 상태를 구별한다. 상태 이름은 논리 계약이며 기존 storage 스키마에 추가한 값이 아니다.

| 상태 | 근거 | 가능한 다음 동작 |
| --- | --- | --- |
| 검토 대기 | 사본만 존재 | 편집·명시 발행 선택·종료 |
| 전송 대기 | 확정 의도/영수증·예산 확보 | worker가 같은 operation을 인수 |
| 전송 중 | 만료 있는 작업 lease·요청 digest | 동일 작업의 이중 실행 차단 |
| 외부 처리 대기 | provider가 비동기 job ID 반환 | 같은 job을 조회, 공개 완료와 구분 |
| 성공 | 정확 계정/외부 객체/판 또는 결과 URL 확인 | 결과 열기·별도 수정/철회 의도 |
| 실패 | 외부 미실행이 확인된 거절 | 범위 수정 또는 같은 작업의 제한 재시도 |
| 결과 미확인 | 전송 뒤 timeout/응답 유실 | 조회·조정 후 상태 확정, 새 게시 재전송 금지 |
| 취소 | 외부 실행 전 중단 확인 | 기록 유지·새 의도는 새 operation |

provider가 지원하면 idempotency key를 사용한다. 미지원이면 외부 객체/작업 ID와 조회 API로 조정한다. 정확히 확인할 방법이 없으면 미확인 상태를 유지하고 사람이 결과를 확인하게 한다. exactly-once 외부 쓰기를 보장하지 않는다.

취소는 아직 실행하지 않은 단계만 멈춘다. 외부 게시 성공 뒤 취소 요청은 별도 철회 작업이며, 연결 해제나 내부 삭제가 외부 게시 삭제를 뜻하지 않는다. 이미 전송된 비공개 메시지도 회수 가능성을 추정하지 않는다.

SNS에서 자료를 ‘받기’가 사용자 계정으로 메시지를 보내는 방식이라면 그것도 외부 쓰기다. 공개 게시와 별도의 개인 전달 의도·수신 대상·허용 내용/주기·영수증을 사용한다. 단순 SNS 링크 입력에는 이런 전송을 만들지 않는다.

## 9. 후속 채널 analytics와 현재 추천 평가

성과는 provider·정확 계정/게시물·측정 구간·지표 정의·관측 시각·수집 권한을 붙인 읽기 전용 snapshot이다. 지연·누락·샘플링·API 제한을 표시하고 다른 플랫폼의 조회수/참여율을 같은 분모로 합산하지 않는다.

발행 성공은 조회·독자 이해·사용자 실천의 성공이 아니다. 분석은 다음 소재·형식 선택을 돕되 자동 게시량 증가·자극적 표현 최적화·개인 관심 프로필 변경의 권한을 만들지 않는다.

추천 품질은 사용자가 직접 판단한 도움·근거 복귀·재입력 감소와 비교한다. 소규모 평가의 기준선/후보 조건을 고정하고, 공급 변경과 알고리즘 변경을 나눠 해석한다. 상시 개인 행동 추적을 기본 도입하지 않는다.

생활 계획으로 잇는 경우 [기존 목표/습관 선택 연결](planning-practice-review.md)을 사용한다. 콘텐츠 생산 수·글 조회수·월 항목 배치일을 생활 수행 실적이나 실제 완료일로 변환하지 않는다.

## 10. 계정 보관·CAS·삭제 경계

이 절의 새 도메인 정책은 해당 기능을 구현할 때 적용한다. 후속 첫 통합 구현에서 필요한 후보·설정·근거/판단만 연결하고 후속 제작/발행용 저장 구조를 미리 생성하지 않는다.

새로 확정한 수신함 설정·packet·brief·생성 결과·variant·발행 의도/영수증은 비공개 서버 계정 보관이 기본이다. 브라우저는 표시 캐시·미전송 입력·복구를 담당하며 실제 서버 ACK 전에는 계정 보관 완료로 표시하지 않는다.

소유자는 project+인증 user, 내용 범위는 owner+workspace다. 외부 계정 연결은 owner 단위로 두고 해당 연결을 사용할 workspace 권한을 확인한다. 제목·이메일·공유 URL만으로 소유권이나 같은 객체를 추정하지 않는다.

각 도메인에 ID/revision·expectedRevision·operation ID·삭제 tombstone/세대를 둔다. 같은 operation/digest는 같은 결과, 같은 operation/다른 digest는 거절한다. 서로 다른 도메인의 여러 HTTP 요청을 하나의 원자 저장으로 표현하지 않는다.

원문·작성 준비·대표 글·채널 사본·발행 이력은 독립 수명이다. 연결 해제는 관계만 끊고 선택하지 않은 원본을 삭제하지 않는다. 원문 휴지통은 기존 정확 참조를 보존하되 새 채택 가능 여부를 따로 검사한다.

영구 삭제는 사용자에게 보인 범위에 따라 파생 사본/첨부/AI 전달 기록의 보존 정책을 적용한다. 삭제된 근거 본문을 숨은 packet 사본으로 계속 재사용하지 않는다. 필요 최소 영수증과 상태만 남기며 외부 게시의 삭제 결과는 별도로 확인한다.

기존 v1 자료/계획/사진 파일의 엄격한 형식을 유지한다. 새 관계/발행 이력을 포함한 파일은 명시 새 외곽·선택 범위·새 ID 매핑을 정의하고 계정 토큰·외부 실행 권한·진행 중 작업을 복원하지 않는다. 복원은 게시 재실행 트리거가 아니다.

## 11. generation 취소·stale 결과·장애 복구

작업은 owner/space·입력 revision/해시·정책 revision·generation을 캡처한다. 계정 전환·명시 취소·선택 대상 교체 시 generation을 올리고 늦은 결과가 새 화면/자료를 덮지 않게 한다. 기존 BlogSync.guard와 UI 탐색 세대 검사를 참고한다.

네트워크 abort는 provider 실행 취소 증거가 아니다. 생성 응답이 늦으면 이전 요청의 결과 후보로 격리하고 자동 채택하지 않는다. 입력은 보존하며 새 요청으로 잘못 보고하거나 같은 내용을 중복 과금하지 않도록 영수증을 확인한다.

입력 revision이 달라진 결과는 stale로 표시하고 검토 후 새 기준에서 다시 실행한다. 원문 hash 불일치·권한 상실은 중단, 구버전이지만 일치하는 근거는 정확 과거 판으로 유지한다. 모든 stale 자료를 최신 판으로 치환하지 않는다.

작업 재시도는 일시 오류만 제한 횟수·지수 지연·최대 기한으로 수행한다. 권한/정책/검증 오류·예산 초과는 자동 반복하지 않는다. 결과 미확인 쓰기는 조정 작업부터 수행하며 서버 재시작 뒤에도 같은 영수증으로 이어간다.

## 12. trigger와 비용 한도

| 트리거 | 기본 동작 | 추가 실행 조건 |
| --- | --- | --- |
| 화면 열기·외부 링크 방문 | 읽기/조회 | 생성·게시·반응 쓰기 없음 |
| 자료 수신 | 후보 검증·중복 식별 | 본문 확보는 허용 공급/범위 안에서만 |
| 사용자 탐구/재정렬 요청 | 선택 후보·질문·정책으로 한 작업 | 선택 근거·범위·모델 사용 시 비용 한도 확인 |
| 선택한 정기 갱신 | 허용 출처/질문·주기에 한정 | 만료·일일 예산·동시 실행 제한 유지 |
| 후속 초안 수정·생성 완료 | 새 후보/판 보관 | 다른 채널 생성·게시 연쇄 실행 없음 |
| 후속 예약 시각 | 확정 게시 의도 검증 | 연결·권한·판·예산·취소 상태 재확인 |

예산은 owner별 일/월 한도와 작업별 입력 bytes·자료 수·토큰·출력 길이·모델 비용·wall time·외부 요청 수로 제한한다. 실행 전에 예상액을 원자적으로 예약하고 실제 사용량/미확인 금액을 구분해 정산한다.

동시 작업이 남은 예산을 각자 전부 쓰지 않도록 예약/lease를 서버에서 처리한다. 무료 한도 소진도 자동 유료 전환 사유가 아니다. 실패·취소 때 이미 발생한 모델/외부 비용을 0원으로 되돌리지 않는다.

## 13. 구현 배치와 Supabase 원칙

기존 순수 모델·CAS·계정 확인·영속 작업 패턴부터 재사용한다. 첫 adapter 하나의 수신/생성/결과 확인을 구현하고, 두 번째 실제 adapter에서 중복이 확인된 부분만 공통화한다. 범용 workflow engine·새 플랫폼을 먼저 도입하지 않는다.

브라우저는 편집·선택·미리보기·상태 조회를 맡고, 서버 작업자는 제한된 수집/AI/예약과 외부 자격 증명을 담당한다. 구체 런타임은 필요 실행 시간·예약/재시도·비용을 확인해 정한다. 브라우저 탭의 생존을 정기 작업의 보장으로 삼지 않는다.

논리 저장 책임은 내용/정확 판, 관계/정책, 작업/영수증, 외부 연결 자격 증명으로 나눈다. 이를 반드시 네 개 테이블이나 새 DB로 구현한다는 뜻은 아니다. 새 공개 API 이름·schema·migration은 구현 시 실제 권한과 기존 계약을 확인한 뒤 확정한다.

Supabase의 exposed schema는 명시 grants와 RLS를 모두 검토한다. SELECT/UPDATE/INSERT/DELETE의 owner·workspace 조건을 확인하고 UPDATE에는 USING/WITH CHECK를 함께 둔다. 인증 역할 자체를 객체 접근 권한으로 취급하지 않는다.

비밀키·service_role·SNS refresh token은 브라우저/공개 파일/로그에 두지 않는다. view는 security_invoker와 접근 권한을 검토한다. privileged RPC는 좁은 실행 권한·서버 owner 검사·고정 search_path가 필요한지 확인하며 권한 오류를 우회하려고 추가하지 않는다.

2026-10-29 공개 문서 확인: [Supabase changelog](https://supabase.com/changelog.md), [API 보안](https://supabase.com/docs/guides/api/securing-your-api), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security). Supabase 스킬을 읽었으며 운영 프로젝트·DB·토큰에는 접속하지 않았다. 설치 버전/정책/새 API 지원 확인은 구현 관문이다.

## 14. 한 여정의 완료 기준

**최초 운영 시범 완료:** 선택한 SNS 계정의 자체 추천에서 읽고 싶은 자료를 발견하고 원문을 읽거나 종료할 수 있다. 추천 도움·부담은 실제 체험으로 확인한다. 해도 저장·자체 재정렬·계정 ACK·발행 검수는 이 시범의 완료 조건이 아니다.

**필요 확인 뒤 후속 첫 통합 구현 완료:** 선택 링크/허용 feed 수신 → 연구 재정렬 이유 확인 → 원문/내 판단 → 같은 계정 재개·정확 근거 복귀를 끝낸다. 아래 검수는 이 통합을 구현할 때 적용하며 AI 콘텐츠 제작·발행은 계속 별도 후속이다.

- 기존 자료/준비/글·뉴스·계획의 형식과 저장 경계를 유지하고 최초 입력·재열기·A/B 계정 재개를 확인한다.
- 같은 원문 URL의 새 판·CRLF/이모지 인용·link-only·누락/삭제·다른 owner에서 정확 근거를 검증한다.
- 입력 변경·IME·늦은 응답·취소·중복 클릭·서버 충돌·외부 응답 유실·예산 경합을 같은 작업 ID로 재현한다.
- 외부 모의 응답 통과와 실제 허용 수신의 검증을 구별한다. 후속 발행을 구현할 때 별도 테스트 계정의 쓰기/미확인 결과 조정을 검수하며 개인 계정 게시를 시험 데이터로 사용하지 않는다.
- 390/820/1440px에서 본문·출처·저장/실패 상태와 원래 맥락 복귀를 확인한다. 실제 기기·실사용 도움은 별도 기록한다.

완료 보고는 최초 운영 시범의 실제 읽기 경험과 후속 통합의 계정 ACK·정확 근거·미확인 범위를 구분한다. 생성 수·게시 수·검사 개수를 생활 가치나 탐구 품질의 증거로 삼지 않는다.
