# 연간 계획: 연도·나이와 월별 흐름

2026-10-23 KST · 기존 해도의 **도구 → 연간 계획**에 추가하는 독립 계획 표다. 사용자 제공 공유 대화에서 생년월일·연도/생일 기준·나이 표시·연간/월 계획·분기·키보드 추가·자동 저장·백업/복원을 확인했다. 그 대화에 연결된 기존 호스팅 화면은 HTTP401로 접근할 수 없어 실제 화면이나 기존 저장 형식까지 확인한 것으로 보지 않는다. 기존 사이트의 개인 브라우저 저장을 읽거나 가져오지 않는다.

## 사용 흐름과 이번 범위

**생년월일/표시 기준 → 연도·나이와 연간 계획 → 같은 위치의 12개월 계획 → 수정·저장·재열기 → 전용 파일 보관·명시 복원**을 한 묶음으로 다룬다. 목표·습관·연표나 외부 캘린더를 대신하거나 자동 변경하지 않는다.

| 입력 | 자동 처리 | 결과 |
| --- | --- | --- |
| 선택한 생년월일, 연도/생일 기준, 만 나이/한국 나이/동시 표시 | 시간대 없는 달력 날짜의 연도·월·일을 직접 검증하고 해당 표시 구간과 나이 계산 | 연도와 나이를 붙인 연간 계획 행 |
| 직접 쓴 연간 계획과 날짜가 있는 월 계획 | 비어 있는 달도 남긴 12구간·분기 정렬, 기준 변경 시 원래 날짜로 재배치 | 여러 해의 계획 흐름 비교와 계속 편집 |
| 입력 변경 | 같은 계정·작업공간의 로컬 CAS 저장, 충돌/실패 시 입력 유지 | 같은 브라우저에서 다시 열기와 명시 복구 |
| 전용 JSON 파일 | 엄격한 형식·날짜·용량 검사와 미리보기, 사용자가 선택한 뒤 현재 계획만 교체 | 다른 브라우저로 옮길 수 있는 독립 계획 사본 |

처음에는 현재 한국 날짜의 연도 한 행으로 시작하고 생년월일은 비어 있다. 생년월일이 없어도 연간·월 계획을 쓸 수 있으며, 생일 기준은 유효한 생년월일을 입력한 뒤 선택한다. 연간 계획에서 Enter는 다음 연도를 추가하거나 기존 다음 행으로 이동하고 Shift+Enter는 줄바꿈이다. 한글 조합 확정 Enter로 새 행을 만들지 않는다. 월 계획에서는 Enter가 줄바꿈이고, 다음 연도 버튼도 제공한다.

## 날짜·나이와 기준 변경

- **연도 기준:** 1월1일부터 다음 해1월1일 전까지를 12개월로 나눈다. 만 나이는 해당 연도의 생일 전·후를 구분하고 한국 나이는 연도와 출생 연도의 차이+1로 계산한다. 생일 기준의 만 나이는 해당 생일에서 시작하는 구간이다. 출생 전과 생년월일 미입력을 실제 나이로 추정하지 않는다.
- **생일 기준:** 해당 연도의 생일부터 다음 생일 전까지를 12개의 `[시작, 끝)` 구간으로 나눈다. 생일의 일자를 각 월의 마지막 날까지 보정하되 이전 달의 보정 결과를 연쇄 적용하지 않는다. 예를 들어31일 기준이 짧은 달에서 보정됐어도 다음 긴 달의31일을 잃지 않는다. 해당 월 구간의 실제 날짜를 확인할 수 있어야 한다.
- **2월29일:** 평년의 기념일을2월28일로 취급하는 이 도구의 표시 정책이다. 윤년·월말·연말·출생 전의 경계를 별도 검수한다.
- **월 계획의 날짜 보존:** 월 계획은 표시 칸 번호가 아닌 실제 `YYYY-MM-DD` 날짜·ID·텍스트로 보관한다. 기준이나 생년월일을 바꿔도 이 세 값을 고쳐 쓰지 않는다. 새로 보이는 구간으로만 투영하며, 필요한 이전/다음 연도의 파생 행도 표시해 연초 계획이 사라진 것처럼 보이지 않게 한다.
- **연간 계획의 의미:** 연간 문장은 사용자가 정한 연도 행에 남는다. 표시 기준을 바꿨다고 날짜가 있는 월 계획으로 자동 변환하거나 다른 연간 문장에 합치지 않는다.

편집 가능한 연도는1900~2199다.1900년 초의 기존 월 계획이 생일 기준에서1899년 구간으로 투영되면 파생 행으로 읽되 새1899년 연간 문장을 만들지 않는다.2199년 생일 행의 일부 구간은2200년까지 이어지므로 허용 범위 밖 날짜의 새 월 계획 추가는 차단한다. 경계의 표시는 기존 유효 계획을 버리는 근거가 아니다.

연간 행 삭제는 그 행의 연간 문장만 지운다. 날짜가 있는 월 계획은 남으며 필요하면 파생 행으로 계속 표시한다. 월 계획은 각 항목에서 별도로 삭제한다. 한 행 삭제를 해당 기간 전체 자료 삭제로 해석하지 않는다.

## 저장·복구·파일의 경계

새 계획은 기존 해도의 검증된 로그인·현재 작업공간·Storage 트랜잭션을 재사용한다. 별도 `annualPlan` 로컬 메타데이터이며 원문 bundle·workbench·글쓰기 초안·뉴스 설정을 수정하지 않는다. 조회만으로 새 저장을 만들지 않고 쓰기는 정확한 base revision의 CAS로 확인한다. 다른 탭의 변경을 감지하면 현재 입력을 보존하고 최신 저장본 확인과 사용자의 명시 재적용으로 해결한다. 오류가 났는데 저장 완료로 표시하거나 보이지 않는 자동 덮어쓰기로 충돌을 없애지 않는다.

입력 DOM·커서와 한글 조합을 유지하며 저장 요청을 직렬 처리한다. 이동 전에 저장을 마치고 실패가 남으면 입력을 버린 채 이동하지 않는다. 늦은 읽기/쓰기 결과는 다른 계정·공간의 화면에 반영하지 않는다. 화면 숨김/종료의 저장은 최선의 노력이며 OS 강제 종료 직전의 마지막 입력 보존을 보장하지 않는다.

전용 백업에는 생년월일·표시 설정·연간 문장·날짜가 있는 월 계획이 들어가므로 개인 파일로 보관한다. 계정·작업공간 ID와 로컬 revision은 제외한다. 복원은 새 파일의 포함 범위를 미리 확인한 뒤 **현재 공간의 연간 계획만** 교체하며, 현재 계획을 먼저 파일로 보관할 수 있어야 한다. 파일 취소·형식 오류·한도 초과는 저장을 변경하지 않는다. 전체 파일 한도2 MiB 안에서 저장본도 내보내고 다시 읽을 수 있도록 내용에는512바이트의 메타데이터 여유를 남기고 전용 파일은 압축 없는 간결한 JSON으로 만든다. 해도의 일반 자료/구성 JSON·사진 ZIP·선택 근거 ZIP에 이 계획을 자동 포함하거나 서버/외부 캘린더에 동기화하지 않는다.

### 2026-11-11 다른 탭·기기의 변경은 오류가 아니다 (기기 간 동기화 검수 M5)

2026-11-01 소유자 지시(모든 데이터 자동 동기화, 선택지 없음, 미저장 입력·한글 조합은 덮지 않음)에 맞춰 위 문단의 "최신 저장본 확인과 사용자의 명시 재적용"을 대체한다. 재현한 결함은 이렇다. 입력 칸에 커서만 둔 기기에 다른 기기의 변경이 도착하면 `저장하지 못함`이 뜨고, `최신 계획 확인` → `내 입력 다시 적용`을 누를 때까지 이후 입력이 저장되지 않으며 화면 이동도 막혔다.

- **저장되지 않은 입력이 없을 때:** 저장소의 최신 계획을 조용히 받아 화면에 반영한다. 커서가 있는 칸은 같은 입력 요소를 그대로 두므로 값·커서 위치가 유지되고, 나머지 칸만 다시 그린다. 그 칸의 내용이 다른 쪽에서 바뀌었으면 값을 최신으로 맞추고 커서 위치는 길이 안에서 유지한다.
- **저장되지 않은 입력이 있을 때:** 계정 문서 동기화와 같은 항목별 3-way 병합(`AccountDocsSync.mergeDocument('annualPlan')`, 기준은 이 화면이 마지막으로 저장·확인한 계획)으로 내 입력을 최신 계획 위에 합쳐 저장한다. 다른 칸의 변경은 양쪽 모두 남는다. 저장 중에 CAS가 어긋난 경우도 같은 병합 뒤 다시 저장한다.
- **같은 칸을 양쪽이 바꿨을 때:** 이 화면의 저장되지 않은 입력을 남긴다. 아직 저장되지 않은 입력이 가장 늦은 수정이고, 입력 중인 칸을 원격 내용으로 바꾸지 않기 위해서다. 다른 쪽 내용은 이 기기의 계정 문서 복구 사본(`merge_conflict`, 문서당 최근 5개)으로 남기고, 화면의 `복구 사본 N개`에서 바로 읽을 수 있다.
  - 순서: 복구 사본 저장이 성공한 뒤에만 다른 쪽 내용을 덮어쓴다. 복구 사본을 저장하지 못하면 덮어쓰지 않고 `저장하지 못함 · [다시 시도]`를 보인다.
  - 방금 추가한 빈 연도 행도 저장되지 않은 입력이다. 그 연도를 다른 쪽이 먼저 채웠다면 이 화면의 빈 행이 남고 다른 쪽 내용은 복구 사본으로 간다(검수 m4, 동작은 그대로 두고 기록).
- **설정(생년월일·기준·나이 표시·분기)을 양쪽이 바꿨을 때:** 설정별로 합치며, 같은 설정을 양쪽이 바꾸면 최신 쪽만 남는다(이 화면에 저장되지 않은 값이 있으면 그 값). 설정의 진 쪽은 복구 사본을 만들지 않는다(계정 문서 동기화의 "설정류는 최신 쪽만"과 같다. 검수 m2, 기록).
  - 설정별로 합친 결과가 "생일 기준인데 생년월일 없음"이 되면 이 화면에서 생년월일을 지울 때와 같이 연도 기준으로 맞춘다. 다른 쪽이 고친 무관한 칸은 계획에 그대로 남는다.
- **합친 계획을 저장할 수 없을 때(보관 한도: 연도 200개·월 계획 2,400개·크기):** 이 화면의 계획 전체를 남기고 다른 쪽 계획 전체를 복구 사본(`conflict_remote`)으로 둔다. 이때는 다른 쪽이 고친 다른 칸도 계획에 들어오지 않으며, 화면 안내도 "같은 칸"이 아니라 한도 때문이라고 적는다.
- **한글 조합 중:** 조합 중인 칸의 DOM은 건드리지 않고 다른 칸만 갱신한다. 조합이 끝나면 그 글자를 계획에 반영해 저장한다. 조합 중인 칸이 다른 행으로 옮겨져야 하는 변경(다른 기기의 기준·생년월일 변경)은 조합이 끝난 뒤 다시 그린다.
- **`저장하지 못함 · [다시 시도]`:** 이 기기가 실제로 저장하지 못했을 때(IndexedDB 쓰기 실패)와 저장할 수 없는 입력(생년월일 범위)에만 쓴다. 그 상태에서도 다른 기기의 변경은 화면에 반영하고, 다시 시도하면 내 입력을 그 위에 저장한다.
- 수동 `최신 계획 확인`·`내 입력 다시 적용`·`다른 탭의 계획` 펼침은 없앴다. 화면으로 돌아올 때(앱 전환 뒤 복귀)도 저장소를 다시 읽는다.
- **되돌리기:** `삭제 되돌리기`·`적용 되돌리기`는 계획 전체를 이전 상태로 돌리므로, 다른 쪽 변경이 도착하면 닫는다(되돌리면 방금 도착한 내용이 지워진다). 그 되돌리기로만 되살릴 수 있던 내용은 복구 사본(`undo_discarded`)으로 남기고 화면의 `복구 사본`에서 읽을 수 있다. 삭제는 지운 항목만, 복원 적용은 적용 전 계획 전체다.
- 복구 사본을 `닫기`나 새로고침 뒤 다시 보는 화면은 아직 없다(기기에는 남는다).
- 검사: `tests/life-annual-plan-sync-browser.cjs`(두 기기·두 탭·조합·저장 실패), `tests/life-annual-plan-browser.cjs`의 두 탭 CAS 항목(새 규칙으로 고침). 조합은 Chromium `Input.imeSetComposition`이며 실제 한글 키보드·Apple 기기 확인이 아니다.

## 화면과 기존 기능 재사용

모드는 **Operate**다. 해도의 공통 탐색·도구 복귀·한국어 글꼴·아이콘을 재사용하고 계획 표 내부는 사용자가 요청한 흑백·얇은 구분선·텍스트 중심으로 절제한다. 소개 카드·큰 수치·통계·가짜 샘플 계획을 기본 화면에 넣지 않는다. 생년월일·표시 기준·백업/복원은 접힌 설정에 둔다.

연도와 연간 문장은 고정 기준이 되고12개 월 칸은 해마다 정렬을 유지한다. 비어 있는 달도 표시해2026년1·3분기와2027년2·4분기의 차이가 같은 위치에서 읽히게 한다. 작은 화면에서는 표 자체의 명시적 가로 스크롤을 허용하고 페이지 전체의 가로 넘침·가려진 입력·조작 불가를 구분한다. 월/분기/연도 머리글과 입력의 접근 가능한 이름,44px 조작 영역과 키보드 초점을 확인한다. 화면 폭 모사를 실제 Apple 기기 검증으로 표시하지 않는다.

직접 도입·참고·자체 구현 비교는 [공식 오픈소스 검토](../life-tools-design/open-source-review.md#연간-계획의-날짜표와-로컬-저장--2026-10-23)를 따른다. 범용 캘린더나 날짜 polyfill 코드를 복사하지 않고 기존 CAS와 작은 제한 날짜 모델을 재사용한다. Supabase 인증 SDK·운영 스키마·RPC·외부 일정 등록은 새로 추가하지 않는다.

## 구현·로컬 검수 결과

정적22 HTML·162 JavaScript·687참조와 전체 단위1,328개를 통과했다. 전체 단위의 실패·취소·skip·todo는0개다. 연도/나이의 윤년·월말·출생 전·경계 투영, 기준 전환의 날짜/ID/텍스트 불변, 백업의 엄격한 입력·용량, 계정/작업공간·CAS 보존을 확인했다. 새 모듈은 브라우저 동봉 파일이며 새 npm 의존성은 없다.

로컬 Chromium151의 **브라우저10/10**은 기존 도구 진입, 연간 Enter·한글 조합/Shift+Enter, 연간·월 계획 저장/재열기, 생일·분기·생년월일 해제 뒤의 날짜 보존, 전용 백업 취소/불량/명시 복원, IDB 저장 실패 재시도, 두 탭의 최신 확인/명시 재적용, 계정/공간 변경과 늦은 쓰기 거절, 연간 삭제/복원 되돌리기 후 새 입력 보존, 저장 대기 중 다른 파일을 고른 복원 의도 승계 거절을 확인했다. 실제 동봉 SDK·계정별 IndexedDB와 익명 FakeCloud Auth를 사용했고 콘솔/페이지 오류·금지 외부 요청·개인 정보 유출·원격 쓰기는0이다. 제품10파일과 검사 원형의 SHA는 실행 전후 동일하며 컨텍스트10개와 브라우저를 종료했다.

1440·820·390px에서 문서 폭이 각 뷰포트와 일치하고12개 열의 정렬·44px 조작·키보드 초점·실제 포인터 도달을 확인했다. 표만1460px 너비의 가로 스크롤 영역을 가지며390px에서는 첫 화면에 연간 계획을 먼저 보여 주고 월 칸은 가로로 이동해 본다. 모바일에서12개월을 한 화면에 전부 표시한 결과가 아니다. 실제 Apple 기기의 터치·한글 키보드 확인은 별도다.

최종 소스와 같은1440/820/390 캡처를 읽은 독립 검토의 판단은 **ship**이다. 삭제/복원 되돌리기가 후속 입력을 덮는 문제, 저장 대기 중 새로 선택한 백업으로 복원 의도가 바뀌는 문제, 넓은 표의 우선순위, 데스크톱 탐색의 조작 가림, 모바일394px 넘침의5개 보완을 해결로 판정했고 검토 범위의 새P0/P1 차단은0개다. 선언된 흰 바탕 위 본문·보조 글자 대비는15.52:1·6.10:1이다. 새 캡처나 엔진 실행을 추가한 것으로 표시하지 않으며 이 소스/기존 캡처 검토와 자동 동작 통과를 구분한다.

초기 실패와 수정은 보존했다. 최초 전체 단위2건은 새3개 파일의 공개 배포 allowlist 누락이 원인이었고, 처음 추정한 git 추적 문제와 구분해 `prepare-site.mjs`를 보완한 뒤 원형 빌드 검사와 전체1,328개를 통과했다. 별도 실제 재현에서 한도 근처의 유효 계획을 백업할 때 JSON 외곽이8바이트 초과하는 문제를 확인해512바이트의 여유와 간결한 전용 JSON으로 보완했다. 첫 브라우저10개 중5개 실패는 데스크톱의 겹친 조작 영역3건·모바일의 문서4px 넘침1건·합성 공간을 추가한 뒤 목록 갱신을 누락한 검사 fixture1건이었다. 제품 문제와 검사 준비 문제를 나눠 수정하고 최종10개를 원래 단언/제한시간으로 통과했다. 첫 실패를 없었던 것으로 합산하지 않는다.

정확한 최종 PR/main CI·공개 파일·배포본의 결과는 [출시 기록](https://github.com/wonchance-art/life-haedo/pulls?q=is%3Apr+head%3Acodex%2Fannual-plan-20261023)에 확정 후 갱신한다. 이 문서의 로컬 완료를 공개 배포 완료로 읽지 않는다. 실사용자의 계획 작성 효용·실제 Apple 기기·기존 보호된 초안 사이트의 데이터 이전은 별도 미확인이다.

## 다음 큰 작업 묶음

1. **실제 연간 계획 작성부터 월별 조정까지:** 화면의 기능 검증을 실제 계획 품질과 연결한다. **선행:** 사용자가 직접 고른 연도·표시 기준과 대표 계획, 실제 주 기기. **완료:** 연간 방향→월 배치·분기 비교→일정 수정→저장·재열기→파일 이동·복원까지 끝내고 필요한 개선만 채택한다.
2. **계획과 기존 목표·습관의 선택 연결:** 같은 내용을 반복 입력하는 부담이 실사용에서 확인될 때만 진행한다. **선행:** 연결할 실제 사용 장면과 각 도구의 날짜/완료 의미·동기화 범위 합의. **완료:** 사용자가 고른 계획만 연결하고 원래 일정·목표·습관을 보존하며 해제·충돌·백업 복구까지 확인한다. 자동 일정 생성이나 외부 캘린더 쓰기는 이 설계만으로 켜지 않는다.

기존 다국어 공급·추천 실독 평가·네이버 수집 운영의 남은 조건은 [전체 로드맵](../life-tools-design/roadmap.md)에 보존한다. 이번 도구가 그 기능들을 완료한 것으로 바꾸지 않는다.
