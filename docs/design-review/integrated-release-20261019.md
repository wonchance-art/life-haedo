## 목표·이번 범위

방문자에게는 실제 운영 앱에서 글·연재·9칸·대표 표지를 읽는 흐름을, 소유자에게는 기존 글·사진·자료 준비의 보존과 기기 이어쓰기를 제공하는 한 출시다. 이미 검수한 기능을 다시 만들거나 출시 준비를 여러 작은 기능 작업으로 나누지 않는다. 새 수집·추천·AI·편집기·외부 의존성을 추가하지 않는다.

이번은 통합 출시의 실행 기록이다. 앞선 [#98 통합·배포 준비 문서](../life-tools-design/blog-release-integration.md)의 ‘미배포’와 각 기능 문서의 ‘당시 미병합’은 그 시점의 범위/이력이며 현재 목표의 금지 규칙으로 다시 적용하지 않는다. 실제 개인 글·사진의 새 서버 전송/운영 게시는 자동 수행하지 않는다. 실제 Google·Apple·Files에 접근하지 않았다면 미확인으로 남기고 합성 검증을 실제 체험으로 바꾸어 쓰지 않는다.

## 서버 설치의 최소 차이

[기존 블로그 설치 기록](../life-tools-design/blog-installation.md)은 `20261017144744_life_blog_originals`와 `haedo-blog-media` Edge의 당시 설치 근거다. 그 문서의 작업공간/영수증/블로그 행 수를 이번 운영 조회 값으로 재사용하지 않는다. 설치 담당이 현재 migration 이력·함수/권한·비공개 Storage/Edge 상태를 읽어 새 차이를 확정한다. 이미 설치한 blog 원본 migration·버킷·Edge를 출시를 이유로 재설치하지 않는다.

준비 기기 이어쓰기의 [20261019005829_life_material_continuity.sql](../../supabase/migrations/20261019005829_life_material_continuity.sql)을 빠진 migration 한 건으로 운영에 설치했다. 확정 SQL SHA-256은 `70308323a8d711fd5ef69fe5f763ba7cc7bd75e43db2cbba5e6edc98570c5a07`이다. 실제 history version `20261019005829`의 statement 한 개와 로컬 파일이 이 동일 바이트임을 확인했다. 개발 시의 `20261018161658` 파일을 실제 history 번호에 맞춰 이름만 바꾸고 참조를 정합화했으며 SQL 재작성·중복 설치·기존 이력 변경은 하지 않았다. 공개 표지·연재·9칸에는 새 서버 schema가 필요하지 않다. 설치 전후 기존 자료/글·사진 선언·공개 사본·영수증의 수와 객체/권한 범위를 대조하되 개인 본문·사진·계정 토큰을 검수 로그에 복사하지 않는다.

준비 migration은 BEGIN/COMMIT의 트랜잭션으로 두 private 테이블과 소유자 RPC를 만든다. 개인 자료를 새로 넣는 시험과 schema 설치는 구분한다. 실제 설치 실패 시 부분 성공을 추정하지 말고 이력·객체 상태를 다시 읽는다. 원래 자료를 변환하거나 글/사진을 새 계정으로 재배정하는 절차는 없다. 소유자 확인·직접 테이블 권한 차단·익명 private RPC 거절과 기존 공개 읽기를 확인한 뒤 정적 앱을 연결한다. 이번 설치의 실제 결과는 아래 운영 근거와 표에 기록한다.

## PWA·산출물·보존 확인

현재 소스의 셸은 SW133이고 로컬 저장소는 `life-tools-v1`·DB version 1을 사용한다. 숫자만으로 호환성을 보증하지 않는다. 신규 모음/준비/표지의 메타데이터와 기존 사진 Blob·sidecar·pending 영수증을 가진 합성 데이터로 업데이트 후 재열기를 확인한다.

`PREVIOUS_RELEASE`는 실제 배포 코드로 맞춘다. 착수 시 workflow에는 과거 `9479866`이 남아 있으므로, 이번에는 총괄이 확정한 운영 `88ccfe5`·SW126을 기준으로 갱신한다. 과거 v119→후보 검수는 보조 회귀로 남길 수 있지만 현재 운영 업데이트 증거를 대신하지 않는다. `scripts/prepare-site.mjs`의 명시 허용 목록·SHELL 전체 바이트·공개 설정을 동일 산출물에서 확인하고, 개인 파일·SQL fixture·서버 키가 배포에 포함되지 않게 한다.

기존 서비스워커를 지우지 않고 업데이트한다. 새 서비스워커 활성화가 이미 열린 탭의 실행 중 JavaScript까지 교체하는 것은 아니다. 기존 탭의 미저장 입력을 먼저 보관하고 열려 있는 앱 탭을 다시 연 뒤 새 자료 준비를 사용한다. 오래된 탭에서 연결 글을 계속 수정하는 경우도 위 저장 ID 이관 위험과 같은 경계이므로 강제 새로고침·DB 버전 변경·입력 폐기로 해결하지 않는다. 설치가 중간에 실패하면 기존 완전한 셸이 계속 사용 가능한지 확인한다. 따뜻한 오프라인 재열기와 실제 글꼴 디코딩/자원 바이트는 담당 검수의 실행 범위로 기록한다. 공개 본문·원본 미디어·RPC 응답은 새로 캐시하지 않는다. 실제 Apple PWA/Files와 Chromium의 이 검사는 별개다.

## 실패 복구와 더 단순한 대안

- 이미 체인이 포함된 최종 후보를 한 번 검수해 배포하는 편이 PR마다 main을 연속 변경하며 여러 번 배포하는 것보다 후보/캐시 일치를 확인하기 쉽다. 실제 포함 관계를 먼저 확인한다.
- SQL 설치가 실패하면 정적 배포 완료로 넘어가지 않고 트랜잭션/이력 상태를 확인한다. 기존 자료를 유지한 채 누락 설치나 정확한 수정 후보로 복구한다. migration down·원본 삭제·버킷 정책 완화는 기본 복구 절차가 아니다.
- 정적 앱에 결함이 있으면 기존 데이터 형식을 읽는 호환 수정 후보와 새 캐시 버전으로 전진 수정하는 방법을 우선 검토한다. 오래된 SW126 앱이 새 준비·표지·모음/근거를 충분히 읽는다고 추정해 그대로 되돌리지 않는다. 독립 저장 검토에서 운영 88cc의 `savePhotoPost`에는 새 준비 output·영수증 이관이 없어, 새 기능을 사용한 뒤 saved 글이 새 ID로 교체되면 준비가 옛 ID를 가리키는 위험을 확인했다. 본문이 남는 것과 준비에서 재열리는 것은 다르다. 사용 후에는 현재 storage의 이관/CAS를 유지한 UI/RPC 비활성화·호환 전진 수정으로 복구한다. 사용 전의 단순 정적 복귀와 구분하고 검증한 호환 후보가 없다면 안전한 되돌림이 준비됐다고 쓰지 않는다.
- static 배포를 되돌려도 서버 글·사진·공개 상태가 과거로 돌아가거나 이미 내려받은 파일이 회수되지 않는다. 기존 DB/Storage/브라우저 사본을 보존하고 문제의 범위와 복구 결과를 별도로 확인한다.
- 실제 계정/Apple 기기 접근이 없으면 해당 체험은 미확인으로 남긴다. 이를 대신해 운영에 개인 시험 글/사진을 만들거나 단계마다 같은 권한 질문을 반복하지 않는다. 실제 체험이 가능한 범위에서는 기존 [Google·Apple 체험 절차](../life-tools-design/blog-release-integration.md#여행-글-한-편의-실제-googleapple-체험)를 재사용하며 새 설치 도구를 만들지 않는다.

## 이번 통합에서 추가로 확인한 경계
