# 네이버 블로그 연결과 새 글 가져오기

2026-10-21 KST · 구현·로컬 검수와 수집 비활성 상태의 서버 설치를 마쳤다. 실제 네이버 접근은 현재 실행 환경에서 403으로 차단돼 수집은 가동하지 않았다. 합성 계정의 서버 연결 검수와 실제 사용자 블로그의 글 수집·정기 실행·프런트 배포는 구분한다. 사용자가 제공한 블로그 ID·URL은 공개 문서·샘플·CI 산출물에 기록하지 않는다. 최종 커밋·원격 CI·프런트 출시는 변경 PR의 HEAD와 실행 기록을 따른다.

## 목표와 이번 범위

블로그 ID 또는 URL을 등록하고, 서버가 확인한 글 목록에서 이미 자료로 보관한 글과 아직 보관하지 않은 글을 구분한다. 사용자가 시작한 연결은 계정의 비공개 서버 구독으로 저장하며, 허용된 피드의 새 글을 정기적으로 서버 보관함에 수집한다. 연결 화면을 열거나 목록을 확인할 때 수집이 준비된 활성 구독의 새 항목만 현재 작업공간의 자료로 반영한다. 비활성 구독의 보관 항목은 사용자가 **이 공간에 받기**를 눌러 받는다. 닫힌 앱의 로컬 저장소를 서버가 직접 갱신하거나 화면 타이머를 서버 자동 수집으로 표현하지 않는다.

기존 네이버 가져오기는 URL·복사한 본문·포함 범위를 직접 제공하는 경로다. 기존 뉴스 자동화는 고정된 공용 출처의 링크 메타데이터를 공개 공급하는 경로다. 두 기능의 가져오기·원문 검증·불변 버전·계정 저장·CAS는 재사용하지만, 개인 구독을 공용 뉴스 JSON이나 공개 수집 작업의 입력으로 합치지 않는다. [기존 네이버 입력](social-import.md), [기존 뉴스 자동화](discovery-automation.md)를 따른다.

## 시작부터 재열기까지

1. 사용자가 블로그 ID/URL을 입력하고 서버에 저장될 연결 범위를 확인한다. 네이버 로그인 비밀번호나 브라우저 쿠키를 요구하지 않는다.
2. 서버에 연결을 저장한다. 화면에는 연결 저장 결과와 실제 수집 상태를 각각 표시한다. 연결 저장 성공을 글 수집 성공으로 표시하지 않는다.
3. 확인한 피드 항목을 현재 자료의 글 정체성과 대조해 이미 보관·미보관·판단 필요 상태를 보여준다. 확인 범위·시각과 본문 확보 여부를 함께 표시한다.
4. 허용된 수집이 활성화되면 새 항목만 계정의 비공개 서버 보관함에 저장하고, 연결 화면에서 활성 구독의 미보관 항목을 기존 원문을 덮지 않는 멱등 투영으로 현재 자료실에 연결한다. 첫 확인 시 피드에 이미 있던 항목도 이 범위에 포함될 수 있으므로 자동 수집을 켜기 전에 안내한다. 반복·동시 실행과 중간 실패 뒤 재시도도 같은 글을 불필요하게 늘리지 않아야 한다.
5. 자료를 열어 출처·확보 범위·정확 버전을 확인하고 기존 인용·글쓰기·백업 경로를 사용한다. 연결을 중지해도 이미 보관한 자료·메모·근거·공개본을 삭제하지 않는다.

## 글 정체성과 원본 보존

- 네이버 글 정체성은 검증된 블로그 ID와 글 번호로 구분한다. PC·모바일·게시물 조회 URL의 별칭을 대조하더라도 기존 source ID·원래 URL·불변 sourceVersion·발췌 위치를 일괄 재작성하지 않는다. 제목·날짜·본문 유사성만으로 같은 글을 확정하지 않는다.
- 여러 기존 자료가 같은 글 후보로 연결되면 임의로 합치거나 삭제하지 않는다. 본문 해시가 같은 다른 글도 서로 다른 글일 수 있다. 기존 링크만 보관한 자료와 실제 본문을 확보한 자료를 구분한다.
- 발견한 항목, 서버에 저장한 항목, 현재 공간에 투영한 항목은 서로 다른 상태다. 피드에서 사라진 항목을 원문 삭제로 해석하지 않으며, 일부 목록을 확인하고 전체 블로그에 미수집 글이 없다고 표시하지 않는다.
- 서버 보관함은 구독·글 번호별 최초 수집 사본을 불변으로 보관한다. 반복 피드의 같은 글은 기존 항목을 갱신하지 않는다. 로컬에 이미 부분/전체 본문이나 링크가 있으면 자동 투영으로 교체하지 않는다. 본문 보완은 기존 재가져오기에서 검토하고 새 불변 버전으로 저장하며, 기존 인용·9칸·글·메모는 원래 정확 버전을 유지한다. 네이버 글의 수정·삭제 자동 동기화는 이번 범위가 아니다.
- 블로그 주소 등록은 외부 서비스의 소유권 인증이 아니다. 등록 자료를 자동으로 해도의 직접 작성 글이나 PhotoPost로 승격하지 않는다. 작성자·날짜·포함 범위·누락은 확인된 공급값만 사용한다.
- 본문이 없으면 본문 미확보로 남긴다. 피드의 요약·HTML을 전체 글로 표시하지 않으며 사진·동영상·첨부 원본의 미보관을 드러낸다. 외부 사진 재압축·자동 미러링과 네이버 원본의 게시·수정·삭제는 이번 계약이 아니다.

## 계정·수집·전송 경계

구독과 서버 보관함은 소유 계정만 접근한다. 다른 계정·다른 작업공간으로 늦은 응답을 투영하지 않으며, 중지 이후 시작한 수집이나 오래된 실행 결과가 중지 상태를 되돌리지 않아야 한다. 작업 재시도와 투영은 기존 계정 확인·revision/CAS·원자 저장과 영수증을 재사용한다. 연결 저장·수집·투영 실패를 기존 자료 전체의 빈 상태나 삭제 성공으로 표현하지 않는다.

로컬 자동 반영은 목록 RPC의 계정·구독·글 ID와 본문 SHA를 검증한 뒤 기존 `Core.prepareImport`·`commitLocal` CAS를 사용한다. 같은 블로그/글 번호에 대응하는 기존 자료가 있으면 부분 본문도 자동 교체하지 않는다. 다른 탭이 먼저 저장하면 최신 bundle을 읽고 정체성을 다시 대조한다. 서비스는 화면 인스턴스별로 생성·종료하며, 계정·공간·화면이 바뀌면 이전 요청을 취소한다. `commitLocal`의 선택적 화면 guard는 소유 확인 뒤·변경 적용 전·bundle 저장 전·마지막 저장 결과 직전에도 검사해 같은 계정의 화면 이탈까지 트랜잭션을 중단한다. 기존 호출의 요청 형식과 기본 동작은 유지한다.

서버 수집은 `HAEDO_NAVER_INGESTION_ENABLED=false`를 기본값으로 둔다. 실제 허용 피드·robots·현행 접근 조건을 확인하기 전에는 가동하지 않는다. 현재 403을 우회하기 위해 대체 프록시·사용자 쿠키·브라우저 세션을 사용하지 않는다. 등록 자체는 보관할 수 있지만 화면에는 자동 수집이 아직 가동되지 않았음을 명시한다.

서버 일정의 설계 참고는 Supabase 공식 [Schedule Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions)의 `pg_cron`·`pg_net`·Vault 조합이다. 예약 설정·함수 배포·권한·비밀값·실제 실행 영수증이 확인돼야 정기 운영을 완료로 판단한다. 문서의 존재나 로컬 fixture 성공으로 운영 일정을 설치했다고 간주하지 않는다. 개인 구독 식별자·수집 본문·키는 공개 저장소·공개 피드·로그·화면 검수 자료에 넣지 않는다.

구현의 [SQL](../../supabase/migrations/20261021093111_life_naver_subscriptions.sql)은 구독·불변 항목의 owner RLS와 읽기 권한, 인증된 연결 저장/목록 RPC, service-role 전용 claim/finish를 분리한다. 임대·구독 revision과 중지 상태가 달라지면 늦은 수집 완료를 적용하지 않고, 같은 완료 작업은 요청 해시가 같은 영수증으로 재생한다. SQL 파일 자체는 cron을 설치하지 않는다. [Edge 진입](../../supabase/functions/haedo-naver-blog/handler.mjs)은 사용자 요청을 Auth에서 확인하거나 일정 요청의 서비스 자격을 확인하고 환경값·DB 준비값이 모두 허용할 때만 고정 RSS 호스트를 조회한다. 개인 식별자·본문·원천 오류 메시지를 응답 로그용 상태로 내보내지 않는다.

## 더 단순한 대안과 반대 검토

수동 붙여넣기만 남기면 반복 수집 부담을 줄이라는 이번 요구를 충족하지 못한다. 반대로 처음부터 전체 과거 글·본문·사진을 크롤링하거나 별도 CMS·범용 큐를 도입하면 접근 조건과 보존 범위를 검증하기 전에 비용을 늘린다. 기존 수신·원문 모델과 작은 계정 구독/서버 보관함 어댑터를 우선한다. 실제 피드가 제공하지 않는 과거 범위는 별도 수동 가져오기로 보완하고 범위 한계를 표시한다. 전체 목록이나 추가 본문 수집이 실제로 필요하고 공식 접근 수단이 확인될 때 그 범위만 재검토한다.

공식 rss-parser 3.13.0(MIT)·fast-xml-parser 5.11.2(MIT)의 배포·고정 LICENSE·공개 보안 권고를 비교했다. 새 의존성 없이 기존 수집기의 제한 RSS2·DTD/entity 거절·HTML 평문 투영 경계를 참고한다. 범용 파서가 아니며 지원 밖 입력은 이전 성공 상태를 유지한 실패로 처리한다. 직접 권고 0개와 전이 의존성 미감사를 구분한 [공식 출처·선택을 바꿀 조건](../life-tools-design/open-source-review.md#개인-네이버-블로그-연결수집--2026-10-21-utc)을 따른다.

브라우저의 예기치 않은 console/page/external 오류는0이며 의도한503 console1은 별도로 분류했다. 기존 합성 원본은4032×3024·241477바이트·SHA256 `fa367de519b37177ce5c6b01ccbaec5b83ac20ae9129755a73c9051e10a2af7d`로 유지됐다. 390px 준비 보류와1440px 자료 대조 이미지를 독립 검토해 상태·원문 범위·자동 수집 설명을 확인했다. 전체 페이지 캡처의 고정 탐색 위치를 실제 화면 넘침으로 판정하지 않는다. 820px·Apple 실기·실제 IME·사용자 평가를 이 두 폭 검수로 대신하지 않는다.

브라우저 근거는 `.local/naver-blog/report-final-whole.json`·`browser-final-whole.log`, backend는 `.local/naver-backend/report.json`·`checker-http409-final.log`, hosted는 `.local/naver-blog/hosted.json`·`hosted-http-after.log`다. 이들은 작업 환경의 합성 검수 기록이며 공개 자료나 운영 개인 데이터 사본이 아니다. 초기 fixture 오류와 원인 미확정의 첫 진입 timeout도 별도 로그/화면으로 남겼으며, 이후 집중 진단 및 최종 전체 통과를 원인 규명이나 실제 기기 보장으로 확대하지 않는다.

운영에는 원본 SQL SHA256 `f8df4ce0c509e906ec4bcd761ce786d687c1f00cfa9c77a9b692b4a6f4334cdd`와 후속 [HTTP409 보완](../../supabase/migrations/20261021094614_naver_conflict_http409.sql) SHA256 `888ae12baf8e14046b646ca9c9e19c8bef5b2d1e2b0c927b7023264a6322c554`를 설치했다. Edge `haedo-naver-blog` v1은 자체 Auth 확인을 수행하는 `verify_jwt=false` 설정으로 배포됐으며 수집 gate는 기본 비활성이며 DB ready=false를 확인했다. 운영 메타데이터11조건을 확인했고 advisor의 새 WARN은0, 의도한 비공개 deny-all INFO2를 구분했다. 실제 사용자 자료·네이버 요청·수집 활성·cron 가동은0이다. 합성 A 소유의 정확한 테스트 작업공간에 연결된3행만 최종 정리했고 잔존0·진행 중 저장 요청0·ready=false를 확인했다. 기존 원본과 다른 계정/기능의 행을 삭제하지 않았다.

관리 도구가 기록한 운영 migration 버전은 원본 `20261021094258`, HTTP409 보완 `20261021094759`이며, 저장소의 CLI 생성 파일명과 설치 시각은 구분한다.

### 실제 HTTP에서 발견한 충돌 응답 보완

첫 native PostgreSQL 검수는 충돌을 SQLSTATE `40001`로 즉시 거절했지만, 실제 hosted REST에서는 같은 CAS 충돌 요청이 두 번 각각30초 동안 응답하지 않았다. Supabase 공식 [custom error code와 무한 트랜잭션 재시도 안내](https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b)는 PostgREST14의 해당 동작과 `PT409` 사용을 설명한다. native PG 성공은 Data API의 HTTP 전달 성공을 입증하지 않았던 경계다.

이미 설치한 원본 migration을 고치지 않고, 추가 migration에서 연결 저장 함수의 두 CAS 예외만 `PT409`로 변경했다. owner·revision·입력·권한·자료 보존 계약은 유지했다. 동일 hosted SDK/REST 충돌이 즉시 HTTP409로 끝나고 명시 중지가200으로 완료되는 after를 따로 확인했다. timeout 후 테스트 행 삭제만으로 정리했다고 판단하지 않고 이전 재시도가 새 연결을 다시 만들 수 있었던 점도 확인한 뒤, 진행 요청 종료와 잔존0을 검증해 합성 행을 정리했다. 오류 문구·개인 ID·서비스 키를 공개 증거로 복사하지 않는다.

## 완료 기준과 남은 실제 조건

완료 검수는 다음 한 흐름을 기준으로 한다.

- ID/URL 검증→계정 구독 저장→연결 저장/수집 가동 상태 구분→확인한 목록의 기존/새/보류 대조.
- 합성 피드의 첫 수집→동일 입력·동시 실행 재시도→새 항목만 추가→부분 실패 뒤 복구→기존 본문·정확 근거 보존과 별도 본문 보완 경로 확인.
- 서버의 앱 종료 중 실행과 현재 계정의 로컬 투영을 각각 확인하고, 중지·재개·계정/공간 전환·늦은 결과에서 중복·다른 소유 자료 변경·원격 공개 0을 확인.
- 1440·820·390px에서 긴 제목/주소·미확보 본문·가동 보류·부분 실패·재시도와 키보드/초점/한글 입력을 확인. 사진·본문을 제공하지 않은 fixture를 실제 네이버 수집 성공으로 표현하지 않음.

실제 네이버 피드·robots와 접근 조건 확인, 허용된 서버 가동 및 일정 실행, 실제 Google·Mac/iPad 체험은 합성 검수와 별도로 기록한다. 다음 제품 목표는 [최신 로드맵](../life-tools-design/roadmap.md)에서 전체 사용자 흐름으로 정하며 구독 저장·RPC·화면마다 별도 다음 작업을 만들지 않는다.
