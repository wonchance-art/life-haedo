# 연표 편집기의 최신 채택과 탭 사이 겹침 (2026-11-04)

총괄 작업 3이다. B2(#187)가 남긴 미해결을 정리한다. 총괄 지시(11-04)에 따라 따로 내지 않고 #187 검수 수정에 합쳤다(#190은 대체됨). B2에서는 공유 스토어(`platform-store.js`)가 최신 채택 규칙을 따랐다. 그런데 연표 편집기(`assets/app.js`)는 자체 `cloudPush`와 문서 목록을 따로 써서 규칙이 달랐다. 기준은 #187 head `d7eae0e`이다.

## 원래 문제

- **서버 충돌이 멈춰 있었다.** 다른 기기가 같은 문서를 먼저 올리면, 이 기기의 전송은 조건부 쓰기(CAS)에서 실패하고 `conflict` 상태로 멈췄다. 받기(`cloudPullAll`)도 양쪽이 바뀐 문서를 그대로 두었다. 수동으로 고를 길이 없어 동기화가 멈춘 채로 남았다.
- **탭 사이 덮어쓰기가 있었다.** 연표 탭은 문서 목록(`REG`)과 열린 문서(`DATA`)를 메모리에 들고 통째로 저장했다.
  - 다른 탭(일정의 행복도 입력)이 같은 문서나 목록을 바꾼 뒤 연표 탭이 저장하면, 그 변경을 덮었다.
  - 재현: 다른 탭이 목록에 문서를 더한 뒤 오래된 목록을 든 탭이 저장하면, 그 문서가 목록에서 사라졌다. 아래 「검사」의 역검사로 확인했다.

## 바꾼 것 (`assets/app.js`)

- **서버 충돌(`cloudPush`의 CAS 실패, `cloudPullAll`의 양쪽 변경):** 수정 시각이 늦은 쪽을 채택한다. 같으면 서버 쪽이다.
  - 진 쪽은 먼저 `<이름> 복구 사본 (YYYY-MM-DD HH:MM)` 새 문서로 남긴다. 그다음 이긴 쪽을 쓴다.
  - 로컬이 이기면: 서버 판을 복구 사본으로 남기고, CAS 기준을 서버 판으로 맞춘 뒤 다시 보낸다.
  - 서버가 이기면: 이 기기 판을 복구 사본으로 남기고 서버 판을 연다.
    - 항목 편집기(`popEd`)가 열려 있으면 바꾸지 않는다(미저장 입력·한글 조합 보호). 편집기가 닫힌 뒤 다음 받기에서 같은 규칙을 다시 적용한다.
  - 서버 행이 사라졌으면 이 기기 판을 새로 보낸다.
  - 복구 사본은 다른 문서처럼 계정에 올라간다. 새 행이 더해질 뿐 기존 행은 지우지 않는다.
  - 진 쪽 내용이 이긴 쪽이나 이미 있는 복구 사본과 같으면 복구 사본을 만들지 않는다.
- **다른 탭의 쓰기:**
  - `storage` 이벤트로 열린 문서와 목록을 받아들인다. 항목 편집기가 열려 있을 때는 받아들이지 않는다. 끌기 등 포인터 조작 중에는 조작이 끝날 때까지 미룬다(#187 재검수 minor 6).
  - 받아들일 때 자기 대기 전송을 버리지 않는다. 받아들인 판에는 이 탭이 저장한 편집도 들어 있으므로, 계정에 없는 만큼 다시 보낸다(재검수 M2).
  - 되돌리기·다시 하기 기록과 선택은 남는다. 받아들인 판을 넘어 되돌리면, 그 판을 먼저 복구 사본으로 남긴 뒤 되돌린다. 그래야 다른 탭의 변경이 조용히 사라지지 않는다.
  - 그 경우 다음 저장(`persist`)에서 디스크 판이 이 탭이 마지막으로 본 판과 다르면, 디스크 판을 먼저 복구 사본으로 남기고 이 탭의 편집을 쓴다. 이 탭의 편집이 더 늦은 쪽이다.
- **문서 목록 저장(`saveRegistry`):** 디스크 목록과 합친다.
  - 이 탭이 모르는 문서는 더한다. 단, 본문이 있는 것만 더한다. 지웠거나 가져오기를 되돌린 문서는 다시 넣지 않는다.
  - 다른 탭이 지운 문서(디스크 목록에 없고 본문도 없음)는 이 탭 목록에서도 뺀다. 열려 있는 문서는 편집 중이라 남긴다(재검수 minor 3).
  - 같은 문서의 `syncedAt`은 늦은 쪽으로 맞춘다. 한 탭이 올린 결과를 다른 탭의 다음 CAS가 쓴다.
  - `updated`는 같은 시계끼리만 비교한다. 깨끗한 항목(`updated === syncedAt`)의 값은 서버 시각이고, 올리지 않은 편집의 값은 기기 시각이다.
    - 디스크 쪽이 서버에서 더 나아갔으면: 이 탭에 올리지 않은 편집이 없을 때만 디스크의 `updated`를 쓴다. 둘 다 올리지 않은 편집이면 늦은 기기 시각을 쓴다.
    - 서버 기준이 같으면: 디스크에만 올리지 않은 편집이 있거나, 둘 다 있고 디스크가 늦을 때 디스크 쪽을 쓴다.
    - 서버 기준이 더 낡은 디스크 항목은 이 탭의 이전 상태라 쓰지 않는다.
  - 처음에는 `updated`를 늦은 쪽으로만 맞췄다. 기기 시계가 서버보다 앞서면, 올린 직후 자기 이전 편집 시각이 서버 시각을 이겨 문서가 계속 "올리지 않음"으로 남고 탭 복귀마다 다시 보냈다. 아래 B1 검사가 이를 잡았다.
- **복구 사본 이름:** `<이름> 복구 사본 (YYYY-MM-DD HH:MM)`이다(`HaedoData.recoveryName`). 사본의 `profile.name`에도 같은 이름을 넣어, 복원하거나 고쳐도 이름이 유지된다. 공유 스토어의 복구 문서도 같은 함수를 쓴다. 사본의 사본은 끝을 하나만 둔다.
- **올리는 주체(#187 검수 B1, 재검수 M1·M2):** 한 문서의 업로드는 탭·페이지를 통틀어 하나씩만 한다(문서별 Web Lock, `HaedoSync.exclusive`).
  - `cloudPush`는 잠금 안에서 디스크 목록을 먼저 합친다. 다른 페이지가 같은 판을 이미 올렸으면 보내지 않는다.
  - 받기(`cloudPullAll`)는 서버가 그대로인데 이 기기에서 바뀐 문서를 보낸다. 다시 연 뒤에도 그렇다.
  - 저장 상태는 열린 문서의 상태로 보인다. 올리지 않은 편집은 `계정에 올리기 대기`다.

## 바꾸지 않은 것

- 서버 쓰기는 기존 `HaedoSync.writeSnapshot`(조건부 PATCH)을 그대로 쓴다.
- 문서 삭제·가져오기·문서 전환의 동작은 그대로다.
- 공유 링크 보기(`RO`)는 저장하지 않는다.

## 검사 — `tests/timeline-latest-wins-browser.cjs`(10)

실제 앱과 연표 탭·일정 탭을 같은 브라우저에서 띄우고, 서버 시각을 붙이는 메모리 테이블을 썼다.

1. 일정 행복도(11-03 8) → 연표 사건 → 일정 행복도(11-02 3) → 연표 사건 순으로 번갈아 썼다.
   - 서버 문서에 네 변경이 모두 있었다(손실 0).
   - 복구 사본 0, 서버 행 1.
2. 연표 항목 편집기를 연 채 일정이 행복도를 썼다.
   - 열린 문서는 바뀌지 않는다.
   - 저장하면 일정 판이 `내 연표 복구 사본`으로 먼저 남고 편집이 저장된다. 둘 다 계정에 올라간다(행 2).
   - 스토어 `backup()`에 복구 사본이 들어 있고, `importDocs` 복원으로 같은 이름의 새 사본이 생긴다.
3. 다른 기기의 서버 쓰기
   - 로컬이 늦으면: 서버 판이 복구 사본으로 남고 이 기기 판이 올라간다.
   - 서버가 늦으면: 이 기기 판이 복구 사본으로 남고 서버 판이 열린다. 서버는 덮이지 않는다.
4. 문서 목록 합치기
   - 다른 탭이 더한 문서가 오래된 목록 탭의 저장 뒤에도 남는다.
   - 지운 문서는 다시 들어오지 않는다.
5. 올리는 주체 하나(B1 재현). 서버 시계가 페이지 시계보다 늦은 조건이다.
   - 편집 직후 탭 복귀: PATCH 1회. 두 번째 편집과 탭 복귀: PATCH 1회 더.
   - 충돌 표시 0, 복구 사본 0, 목록에 없는 본문·서버 행 0.
   - 목표·습관 화면의 탭 복귀는 깨끗한 문서에 PATCH를 보내지 않는다.
   - 변이: 스토어가 소유와 무관하게 다시 보내고 변경 확인도 없으면(d7eae0e 동작) 실패한다. 목록 합치기를 처음 방식(`updated` 늦은 쪽)으로 되돌려도 실패한다.

6. R3·R6·R6b(재검수 M1·M2): 실패 중 행복도 → 다시 연 뒤 전송, 탭 닫힘 뒤 연표 탭이 편집과 행복도를 모두 보냄, 대기 중 상태 표시. 상세는 [일정 B2](schedule-b2.md)의 「검사」.

## 한계

- 두 탭이 같은 순간(같은 밀리초 근처)에 목록을 쓰는 경쟁은 localStorage에 잠금이 없어 완전히 막지 못한다. 합치기와 `storage` 이벤트로 창을 좁혔다. 본문은 저장 전 확인이 있어 진 쪽이 복구 사본으로 남는다.
- 늦은 쪽 판정은 각 기기의 시계에 따른다.
- 실제 Mac·iPad·iPhone 확인은 하지 않았다.
