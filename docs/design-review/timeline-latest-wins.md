# 연표 편집기의 최신 채택 — 되돌림 기록 (2026-11-04)

총괄 작업 3(#190)으로 시작해 #187에 합쳤던 연표 편집기(`assets/app.js`) 변경은 **되돌렸다.** 지금 `app.js`는 main과 같다. 다른 점은 `migrateScale`이 공용 척도 함수(`HaedoData.toSignedScale`)를 쓰는 것 하나뿐이다.

## 왜 되돌렸나

- 소유자 결정(2026-11-04) "습관·목표 먼저"로 일정은 행복도를 쓰지 않는다. 그러면 연표 문서를 쓰는 곳은 연표 편집기 하나다.
- 이 변경들은 일정과 연표 편집기가 같은 문서를 함께 쓰는 상황을 다루려던 것이다. 쓰는 곳이 하나면 필요 없다.
- 네 차례 독립 검수마다 두 쓰는 곳 사이의 새 경쟁이 나왔다. 그래서 고쳐 쌓기보다 쓰는 곳을 하나로 다시 설계하기로 했다(로드맵 후속).

## 시도한 것(참고)

- 서버 충돌(CAS 실패, 받기의 양쪽 변경) 때 늦은 쪽을 채택하고, 진 쪽을 `<이름> 복구 사본` 문서로 남김
- `storage` 이벤트로 다른 탭의 쓰기를 받아들이고, 저장 전에 디스크 판을 확인함
- 탭 사이 문서 목록 합치기(같은 시계끼리만 비교)
- 문서별 Web Lock으로 한 번에 하나만 올리기, 업로드 시간 제한
- 열린 문서는 디스크 판으로만 보내고, 편집기가 닫힐 때 받아들이기

## 다음 설계가 지켜야 할 실패 사례

검수와 검사에서 실제로 재현한 것들이다. 단일 쓰는 곳 설계의 완료 조건으로 쓴다.

1. 한 문서를 두 경로가 따로 올려 PATCH가 두 번 나가고, 다음 편집이 충돌로 멈춤(B1)
2. 기기 시계가 서버보다 앞서면, 탭 사이 목록 합치기가 올린 편집을 계속 "올리지 않음"으로 남김
3. 페이지를 다시 열면 누가 올릴지 아무도 기억하지 못해, 못 보낸 값이 영영 남음(M1)
4. 다른 탭의 판을 받아들일 때 자기 대기 전송을 취소하고 "동기화됨"으로 표시함(M2)
5. 항목 편집기가 열린 탭의 메모리 판이 다른 탭의 값을 덮고, 문서가 깨끗한 상태로 표시됨(P1–P3)
6. 편집기를 닫는 동작과 받아들이기의 순서 때문에 입력이 사본 없이 사라짐(Esc → blur/change보다 먼저 받아들임)
7. 탭의 localStorage 보기는 다른 탭의 쓰기보다 늦게 맞춰짐. 낡은 목록을 통째로 되쓰면 다른 탭의 "올리지 않음"을 "보냄"으로 덮음. 목록만 보고 "이미 보냄"을 판단하면 편집을 잃음.
8. 기다리던 값을 업로드 성공으로 잘못 처리해 잃음. 지워진 기준 문서 때문에 영구 대기함.

## 지금 상태(main과 같음)

- 연표 편집기는 CAS가 실패하면 `conflict`로 멈추고, 사람이 고른다.
- 탭 사이의 문서 목록 저장은 메모리 목록을 통째로 쓴다.
- 공유 스토어는 연표 문서를 깨울 때 올리지 않는다. 목표·습관 화면의 명시 동기화와 가져오기만 올린다. `tests/timeline-single-writer-browser.cjs`가 이것을 확인한다.
