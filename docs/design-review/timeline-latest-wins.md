# 연표 편집기의 최신 채택과 탭 사이 겹침 (2026-11-04)

총괄 작업 3이다. B2(#187)가 남긴 미해결을 정리한다. B2에서는 공유 스토어(`platform-store.js`)가 최신 채택 규칙을 따랐다. 그런데 연표 편집기(`assets/app.js`)는 자체 `cloudPush`와 문서 목록을 따로 써서 규칙이 달랐다. 기준은 #187 head `d7eae0e`이다.

## 원래 문제

- **서버 충돌이 멈춰 있었다.** 다른 기기가 같은 문서를 먼저 올리면, 이 기기의 전송은 조건부 쓰기(CAS)에서 실패하고 `conflict` 상태로 멈췄다. 받기(`cloudPullAll`)도 양쪽이 바뀐 문서를 그대로 두었다. 수동으로 고를 길이 없어 동기화가 멈춘 채로 남았다.
- **탭 사이 덮어쓰기가 있었다.** 연표 탭은 문서 목록(`REG`)과 열린 문서(`DATA`)를 메모리에 들고 통째로 저장했다.
  - 다른 탭(일정의 행복도 입력)이 같은 문서나 목록을 바꾼 뒤 연표 탭이 저장하면, 그 변경을 덮었다.
  - 재현: 다른 탭이 목록에 문서를 더한 뒤 오래된 목록을 든 탭이 저장하면, 그 문서가 목록에서 사라졌다. 아래 「검사」의 역검사로 확인했다.

## 바꾼 것 (`assets/app.js`)

- **서버 충돌(`cloudPush`의 CAS 실패, `cloudPullAll`의 양쪽 변경):** 수정 시각이 늦은 쪽을 채택한다. 같으면 서버 쪽이다.
  - 진 쪽은 먼저 `<이름> 복구 사본` 새 문서로 남긴다. 그다음 이긴 쪽을 쓴다.
  - 로컬이 이기면: 서버 판을 복구 사본으로 남기고, CAS 기준을 서버 판으로 맞춘 뒤 다시 보낸다.
  - 서버가 이기면: 이 기기 판을 복구 사본으로 남기고 서버 판을 연다.
    - 항목 편집기(`popEd`)가 열려 있으면 바꾸지 않는다(미저장 입력·한글 조합 보호). 편집기가 닫힌 뒤 다음 받기에서 같은 규칙을 다시 적용한다.
  - 서버 행이 사라졌으면 이 기기 판을 새로 보낸다.
  - 복구 사본은 다른 문서처럼 계정에 올라간다. 새 행이 더해질 뿐 기존 행은 지우지 않는다.
  - 진 쪽 내용이 이긴 쪽과 같으면 복구 사본을 만들지 않는다.
- **다른 탭의 쓰기:**
  - `storage` 이벤트로 열린 문서와 목록을 받아들인다. 항목 편집기가 열려 있을 때는 받아들이지 않는다.
  - 그 경우 다음 저장(`persist`)에서 디스크 판이 이 탭이 마지막으로 본 판과 다르면, 디스크 판을 먼저 복구 사본으로 남기고 이 탭의 편집을 쓴다. 이 탭의 편집이 더 늦은 쪽이다.
- **문서 목록 저장(`saveRegistry`):** 디스크 목록과 합친다.
  - 이 탭이 모르는 문서는 더한다. 단, 본문이 있는 것만 더한다. 지웠거나 가져오기를 되돌린 문서는 다시 넣지 않는다.
  - 같은 문서는 `syncedAt`·`updated`를 각각 늦은 쪽으로 맞춘다. 한 탭이 올린 결과를 다른 탭의 다음 CAS가 쓴다.
- **복구 사본 이름:** `<이름> 복구 사본`이다. 사본의 `profile.name`에도 같은 이름을 넣어, 복원하거나 고쳐도 이름이 유지된다. 공유 스토어의 복구 문서도 같게 맞췄다.

## 바꾸지 않은 것

- 서버 쓰기는 기존 `HaedoSync.writeSnapshot`(조건부 PATCH)을 그대로 쓴다.
- 문서 삭제·가져오기·문서 전환의 동작은 그대로다.
- 공유 링크 보기(`RO`)는 저장하지 않는다.

## 검사 — `tests/timeline-latest-wins-browser.cjs`(4)

실제 앱과 연표 탭·일정 탭을 같은 브라우저에서 띄우고, 서버 시각을 붙이는 메모리 테이블을 썼다.

1. 일정 행복도(11-03 8) → 연표 사건 → 일정 행복도(11-02 3) → 연표 사건 순으로 번갈아 썼다.
   - 서버 문서에 네 변경이 모두 있었다(손실 0).
   - 복구 사본 0, 서버 행 1.
2. 연표 항목 편집기를 연 채 일정이 행복도를 썼다.
   - 열린 문서는 바뀌지 않는다.
   - 저장하면 일정 판이 `내 연표 복구 사본`으로 먼저 남고 편집이 저장된다. 둘 다 계정에 올라간다(행 2).
   - 스토어 `backup()`에 복구 사본이 들어 있고, `importDocs` 복원으로 같은 이름의 새 사본이 생긴다.
3. 다른 기기의 서버 쓰기
   - 로컬이 늦으면: 서버 판이 복구 사본으로 남고 이 기기 판이 올라간다.
   - 서버가 늦으면: 이 기기 판이 복구 사본으로 남고 서버 판이 열린다. 서버는 덮이지 않는다.
4. 문서 목록 합치기
   - 다른 탭이 더한 문서가 오래된 목록 탭의 저장 뒤에도 남는다.
   - 지운 문서는 다시 들어오지 않는다.

## 한계

- 두 탭이 같은 순간(같은 밀리초 근처)에 목록을 쓰는 경쟁은 localStorage에 잠금이 없어 완전히 막지 못한다. 합치기와 `storage` 이벤트로 창을 좁혔다. 본문은 저장 전 확인이 있어 진 쪽이 복구 사본으로 남는다.
- 늦은 쪽 판정은 각 기기의 시계에 따른다.
- 실제 Mac·iPad·iPhone 확인은 하지 않았다.
