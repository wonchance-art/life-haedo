# 한국어 검색 엔진의 첫 개선

현행 검색은 입력의 앞뒤 공백만 제거하고 하나의 구절을 문자 그대로 찾는다. 한글 띄어쓰기를 다르게 기억했을 때 같은 원문을 놓치는 사례를 확인했다. 이번 변경은 사용자가 고르는 `ignoreKoreanSpacing` 옵션만 추가한다. 기본 검색, 원문, 저장 구조와 가져오기 해시는 바꾸지 않는다.

## 계약

```js
Core.searchSources(bundle, query, { ignoreKoreanSpacing: true });
Core.matchesSearchText(note, query, { ignoreKoreanSpacing: true });
```

두 함수는 같은 패턴을 사용한다. 완성형 한글 음절 사이의 수평 공백(`\p{Zs}`와 탭)을 0개 이상 허용한다. 예를 들어 `정원산책`과 `정원 산책`은 원문의 `정원\t  산책`을 찾는다. 띄어쓰기를 무시해 먼저 일치한 구절의 실제 원문 범위를 반환하므로 literal 검색이 찾던 뒤쪽 구절보다 앞쪽 구절을 찾을 수 있다. 옵션을 끄면 기존 결과로 돌아간다.

줄바꿈, 문장 부호, 한글과 영문 사이의 공백, 영문 단어 사이의 공백은 합치지 않는다. 순서가 바뀌거나 떨어진 다중 단어를 AND 검색하지 않으며, NFC/NFD 정규화도 하지 않는다. `정원에서 천천히 산책`은 `정원산책`으로 찾지 않는다. 검색어에 직접 입력한 줄바꿈과 정규식 문자는 기존처럼 문자 그대로 검색한다.

검색어는 계속 UTF16 500단위 이내다. 옵션은 객체의 `ignoreKoreanSpacing` 필드만 지원하며, 지정한 값은 boolean이어야 한다. `matchesSearchText`는 문자열에 대한 boolean만 반환하고 빈 검색어는 true다. 기존 메모 검색 UI의 기본 비교 규칙은 UI에서 그대로 유지하고 이 함수는 옵션을 켰을 때 사용한다.

## 보존과 비용

native `/iu` 정규식으로 수정하지 않은 원문을 검색한다. 검색 결과의 `sourceId`, `sourceVersionId`, 첫 일치 구간과 snippet은 기존 엔진 경로로 만든다. UTF16 `match.index`와 실제 일치 문자열 길이를 사용하므로 emoji, CRLF, 반복 구절 및 이전 버전의 raw locator를 보존한다. 제목에서만 일치하면 본문 위치를 만들지 않는다. `matchesSearchText`의 메모 일치도 원문 locator가 아니다.

공백 반복 패턴은 한글 리터럴 음절 사이에만 놓인다. 수평 공백과 음절은 서로 겹치지 않으며 중첩 반복을 추가하지 않는다. 500단위의 반복 음절 검색어와 24,000단위의 실패 원문도 검사했다. 이 검사는 시간 제한을 걸어 통과시키는 성능 약속이 아니며, 긴 반복 원문에서는 후보 위치별 비교 비용이 발생한다.

`validateWorkspace`를 매 검색마다 호출하는 기존 검증을 유지한다. 원문 캐시나 검증 생략은 추가하지 않았다. 초기 진단에서 검증이 엔진 시간의 큰 부분을 차지했지만, 전체 화면 성능에는 DOM 생성과 메모/출처 조회 비용도 있으므로 엔진 측정을 UI 지연으로 보고하지 않는다.

## 재현과 검증

- 초기 익명 사례: 띄어쓰기 생략·중복, CRLF 줄바꿈, NFC/NFD 양방향, 떨어진 단어, 역순 단어, 제목/본문을 걸친 구절에서 literal 검색은 0건이었다. exact CRLF+emoji 및 직접 NFD 검색은 정상이며 원문 slice와 quote가 일치했다. 이는 기존에 명시한 literal 계약의 한계다.
- `node --test tests/life-core.test.cjs`: 기존 28개와 새 3개, 총 31개 통과. 이전 버전·첫 일치 raw UTF16·제목·수평 공백·배제 경계·정규식 문자·엄격한 입력 검증을 포함한다.
- `node tests/search-quality-benchmark.cjs`: 100/1,000/10,000개 익명 합성 원천, 원천당 1버전과 약 1,650 UTF16단위 본문. 발췌는 없고 네트워크·저장·렌더 비용은 제외한다. 첫 호출, 3회 워밍업 후 15회 median/p95를 기록하며 시간에 대한 합격 기준은 없다.
- `SEARCH_CORE_PATH`에 이전 core 사본 경로를 주어 같은 fixture를 재현할 수 있다. `SEARCH_BENCH_OUTPUT`은 JSON 파일 저장 경로다. 이번 비교 기준은 `55d07f2`의 core다.

로컬 결과는 `.local/search-quality/baseline.json`, `core-search-baseline.tap`, `core-after.tap`, `engine-before.json`, `engine-after.json`에 있다. 초기 VM 진단은 검증 비용을 분리하기 위한 실험일 뿐 앱에 사용하지 않는다. 정식 benchmark는 검증을 전부 실행한다.

같은 Node v24.19.0 환경에서 before와 after를 순서대로 실행한 엔진 median(ms)은 아래와 같다. 10,000개 fixture의 본문 합계는 약 1,653만 UTF16단위, UTF8 약 39.45MB다. 공유 환경의 실행 변동이 있으므로 시간 차이를 속도 개선으로 해석하지 않는다.

| 자료 수 | 선택 구절 before → after | 빈 검색 before → after | 띄어쓰기 옵션 after / 결과 수 |
| --- | --- | --- | --- |
| 100 | 1.36 → 1.30 | 1.34 → 1.28 | 1.11 / 100 |
| 1,000 | 12.87 → 12.07 | 12.26 → 11.68 | 12.33 / 1,000 |
| 10,000 | 134.21 → 133.22 | 131.12 → 128.54 | 207.57 / 10,000 |

10,000개 옵션 검색의 p95는 425.89ms다. literal `자료의출처`는 0건이므로 10,000건의 raw quote/locator/snippet을 만드는 옵션 결과와 직접적인 속도 비교 대상이 아니다. 같은 10,000건을 만드는 exact `자료의 출처`와 옵션 `자료의출처`를 순차 재측정한 `.local/search-quality/same-hit-control.json`에서는 before exact median/p95 134.70/152.21ms, after exact 145.16/179.71ms, after 옵션 136.48/156.71ms였다. 이 변동도 공유 환경의 단일 측정을 속도 약속으로 삼지 않는 이유다. 원문 전체 검증은 10,000개 after median 127.70ms이며 그대로 유지한다. 많은 일치 결과를 DOM에 한꺼번에 만드는 문제는 UI에서 별도로 제한해야 한다.

NFD 문서는 한글 공백 옵션으로 해결되지 않는다. 후속 정규화 검색을 한다면 정규화된 문자열의 index를 원문에 바로 적용하지 말고 원문 UTF16 구간 매핑과 새 경계 검사를 먼저 설계해야 한다. 다중 단어 검색 역시 첫 열기 위치와 일치 설명을 별도로 정해야 한다.
