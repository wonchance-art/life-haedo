# 가져온 글에서 개인 결과물까지 — 활용·수집·검색 품질

2026-10-13 KST. 디자인·구현·통합 책임자 Codex. #75 `a2879bb` 위의 `codex/input-output-quality` 후속이다. 병합·운영 SQL·공개 배포는 Local 담당이며 이번 변경은 새 SQL·저장 형식·외부 전송을 추가하지 않는다.

## 완료한 사용 목표

파일 일부 실패 → 해당 파일만 다시 선택 → 출처 검토·자료 보관 → 통합 검색 → 정확 원문 읽기 → 회고 → 내 페이지 초안·첨부·비공개 저장/미리보기 → 원래 회고 복귀 또는 Markdown 받기. 기존 기능을 연결하며 책 확장과 자동 SNS 수집·AI·자동 공개는 추가하지 않았다.

| --- | --- | --- |
| 1 활용 | 페이지 초안 만들기가 ‘원고 파일로 보관’ 안에 있어 파일 기능으로 오해하기 쉬움 | 직접 쓴 회고 아래 `페이지 초안으로` / `파일로 받기`를 나란히 표시. 상단 활용 아이콘으로 이동. 파일의 원문 포함 옵션은 별도 상세에 유지 |

| 4 시각 | 짧은 회고에도 12줄 입력창·큰 최소 높이로 조작이 멀어짐. 파일 실패 설명이 긴 문단 | 4줄부터 본문 길이에 따라 자동 높이, 8rem 최소 높이. 두 활용 조작은 한 행, 수집 설명은 짧은 안내와 보관 범위 펼침. 기존 토큰·아이콘·본문/피드 스타일 재사용 |
| 5 실제 체험 | 에이전트 검사를 사용자 평가로 대신할 위험 | [익명 샘플·체험 과제·피드백 양식](../usability/input-output-trial.md). 앱에 추적/분석 전송이나 별도 피드백 저장소를 만들지 않음 |

체험은 `npm run dev` 후 기존 인증 환경에서 로그인 → 기록 → 가져오기로 시작한다. 회고만 체험하려면 도구 → 회고 → 지금의 생각 작성 → 활용 아이콘 또는 본문 아래 조작을 쓴다. 작성한 회고만 새 비공개 페이지 초안으로 복사하며 원문/근거/첨부는 자동 복사하지 않는다. 사용자가 회고에 직접 인용한 글은 텍스트 그대로 옮겨지므로 저자·출처는 직접 대조한다.

## 대안·보존 계약

- **활용 조작을 파일 상세 안에 유지**하면 메뉴가 적지만 다른 결과물의 입구가 숨는다. **새 전역 메뉴/모달**은 실제 본문과 작업을 분리한다. 채택한 배치는 본문 아래 두 조작과 상단 이동 아이콘이며 공개 완료를 암시하지 않는다. 실제 사용자가 여전히 찾지 못하면 같은 과제로 배치를 다시 비교한다. 이번 선택은 설계 검토이고 사용자 선호 검증을 완료한 것이 아니다.
- **전체 파일 재선택**은 성공한 초안을 중복으로 만들 수 있다. 새 파일 업로더 도입보다 기존 `File`·`TextDecoder`·검토초안 CAS를 재사용했다. 최초 선택과 재선택이 같은 읽기/보관 함수를 사용한다. 파일당 1 MiB, 묶음 5 MiB, 10개 제한 유지. 계정/작업공간 변경과 중단·새 선택 후 늦은 읽기는 적용하지 않으며 이미 성공한 원자 저장은 보존한다.
- 파일 참조·권한을 영속 저장하지 않는다. 새로고침 뒤에는 저장된 검토초안/확정 결과만 복구한다. 읽기 실패·미읽음 파일은 다시 선택해야 한다. 저장 실패로 메모리에만 남은 입력은 기존 `입력 확인`/`다시 초안 보관`으로 복구하며 새 파일로 덮지 않는다. 다른 파일을 다시 골랐다면 해당 행의 새 검토 입력이 되는 것이지 기존 자료 수정이 아니다.
- **검색 인덱스/worker 추가** 전에 100·1,000·5,000개 익명 원문을 측정했다. 가장 큰 병목인 중복 순회를 먼저 제거했다. 전체 본문·UTF-16 위치·과거 버전·기본 문자 검색/선택적 한글 공백 무시를 유지한다. 저장된 검색 사본이나 서버 요청은 없다. 표시 제한과 전체 검색 범위는 별개다.
- 가져오기 입력·원문 확보 범위·작성자·날짜·중복 판정은 기존 UI를 검증해 재사용했다. URL만으로 본문을 가져오거나 작성자를 추정하지 않는다. 원문·발췌·계정별 저장·동기화·백업·공개 범위 변경 없음.

[오픈소스 비교](../life-tools-design/open-source-review.md#입력활용-품질-묶음--2026-10-13-kst)는 Uppy Core 6.2.0, FilePond 4.32.12의 공식 배포·MIT·유지관리·공개 권고를 확인했다. 파일 업로드 서버·플러그인 계층을 필요로 하지 않아 도입하지 않았고 새 의존성이 없다.

## 검증 증거

Linux Chromium **151.0.7922.173** / Playwright **1.63.0**, 익명 모의 Auth와 실제 IndexedDB. 운영 자료·자격 증명은 쓰지 않았다.

- 정적: HTML **18**, JS **72**, 참조 **320**, PWA 통과. Node **437/437**.
- [통합 흐름](evidence/input-output-quality/report.json) **6/6**, 홈·부분 실패·검색·원문·활용·비공개 피드 **18개 화면 상태**(1440·820·390px). 실제 파일 선택/재선택 → 검토 → 출처 입력 → 보관을 거쳤다. CRLF 원본과 정확한 버전 보존, 수정한 페이지와 회고 분리, 변경 후 검색 캐시 갱신, 중단된 이전 파일 읽기가 새 재시도를 덮지 않음을 확인했다. console/pageerror/외부 요청 0.
- 회고→페이지 실패/충돌 **5**, 전체 순환 **9**, 기존 통합 검색 **9**, 여러 파일 가져오기 **8**, 회고/목차 왕복 **3**, 회고 읽기 **5**, 가져오기/발췌/복귀 **3**, 블로그·Instagram 수동 입력 **9** 통과. 기존 전체 순환에서 비공개 저장·모의 게시/철회·JSON 새 사본 복원도 확인했다.
- 공개 산출물 플랫폼 **9/9**, **SW v99→v100**과 기존 자료 보존. 의도적 전송/콜백 실패 3건은 별도. 실제 Google·운영 HTTP를 증명하는 검사가 아니다.
- 새 통합 브라우저 검사는 GitHub CI에 추가하고 보고서를 artifact로 보관한다. 최종 커밋의 전체 CI 결과는 PR에서 확인하며 Cloud의 Chromium151과 GitHub 고정 브라우저를 구분한다.

## 성능 결과와 한계

[같은 브라우저에서 이전/변경 후 비교](evidence/input-output-quality/search-browser-performance.json). 익명 원문 5,000개 + 정확 발췌 5,000개, JSON 약 23.25 MB. 각 검색 7회, p50은 중앙값, p95는 7회 중 최댓값으로 근사했다. cold 첫 호출도 포함한다. 아래 값은 기기 보장이 아니며 해당 실행의 측정치다.

Node 예비 측정에서 메모 일치 중앙값 **224→84ms**, 같은 Chromium 최종 비교에서는 **280.7→103.9ms**였다(p95 **303.8→111.4ms**). 본문 검색 중앙값은 **92.8→83.2ms**다. 1,000개 실제 검색 화면의 탐색/로딩은 약 **657ms**, 입력→두 프레임은 **29~72ms**, 종류 전환은 **34ms**였다. 타이밍과 heap의 원자료는 위 JSON을 기준으로 한다. 최종 표본은 같은 앱 화면에서 IDB에 1,000개를 설치하고 검색 화면을 다시 열어 로딩·입력 이벤트부터 두 프레임·종류 전환을 별도로 측정했다. 화면은 20개만 렌더링했고 검색 모델 결과 수는 모두 유지했다.

CDP heap 값은 GC를 강제하지 않은 순간 값이며 최대 메모리·누수 검사를 뜻하지 않는다. 모델 비교에는 DOM/IDB 시간이 들어가지 않으며 별도 `ui` 항목만 실제 IDB 로드/렌더 흐름을 포함한다. CPU 제한·모바일 Safari·사용자 개인 자료 분포는 미측정이다. 실제 자료에서 긴 작업이나 입력 지연이 확인되면 다음에는 전체 검증 반복 비용/입력 스케줄링/worker를 비교한다. 원문 검증을 생략하거나 정확 검색을 유사도 검색으로 바꾸지 않는다.

재현: `node scripts/measure-private-search.cjs`. 같은 브라우저 전후 비교는 호출자가 #75의 `assets/life/unified-search.js`를 별도 로컬 파일로 보존하고 `SEARCH_BASELINE_FILE`로 지정한다. 측정 스크립트는 앱에 배포하지 않는다.

## Local 실행과 다음 우선순위

1. Local 변경을 보존하고 **#74 → #75 → 이번 후속 PR** 순서로 통합한다. base는 `codex/unified-private-search`이며 squash 여부에 따라 main 대비 차이를 재정리한다. 통합에 포함된 선행 PR을 다시 중복 병합하지 않는다.
2. 이번에는 **추가 SQL 없음**. #74의 기존 #71 게시 글 SQL 설치 확인만 기존 인계대로 수행한다. 개인 자료 삭제·과거 합성 운영 테스트 재실행을 하지 않는다.
3. 최종 CI와 diff 확인 후 Local에서 병합·배포, 기존 설치의 SW v100 갱신·로그인·파일 선택/재선택·회고 초안·파일 다운로드를 확인한다. 저장 형식을 바꾸지 않아 UI/성능 커밋을 각각 되돌릴 수 있으며 사용자 자료를 지우는 롤백은 필요하지 않다.
4. [체험 양식](../usability/input-output-trial.md)으로 iPad Chrome·iPhone·Mac의 실제 한글 입력, Files 재선택, 회전/분할, 실제 개인 자료 검색을 확인한다. 브라우저 폭 모사를 실기 검증으로 보고하지 않는다.
5. 다음 우선순위는 실제 사용에서 막힌 수집/탐색 개선 → 실제 자료 규모의 성능 → 사용자가 필요로 한 입력 제공자 검토다. 새 기능 수·PR 수를 이유로 자동 SNS/AI/책 확장에 착수하지 않는다.
