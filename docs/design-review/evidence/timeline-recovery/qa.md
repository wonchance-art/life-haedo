## 확인한 사용 흐름

1. 390·820·1440px에서 기기의 익명 연표를 상단 복구 영역에서 발견했다. 백업 다운로드와 소유 확인 전에는 사본 만들기가 비활성이다. 내려받은 백업에는 정상 원문과 손상된 JSON 원본 문자열이 모두 보존된다.
2. 390px에서 두 연표 중 첫 업로드가 성공하고 둘째가 POST 500으로 실패했다. 재시도는 **둘째의 같은 ID만** 보냈다. 총 POST 3회, 고유 사본 2개이며 첫 성공을 반복 전송하거나 새 ID로 중복 생성하지 않았다. 재개 후 두 사본 모두 저장 상태가 일치했다.
3. 다시 연결 화면을 열어 실행해도 새 사본·추가 POST가 없다. 원래 registry·정상 연표 JSON·손상 원본 문자열을 바이트 단위로 대조했다. 계정 사본의 사건·기간·행복도·생각·CRLF·emoji 데이터도 그대로였다.
4. 기기 원본이 없는 경우 연표 연결은 숨겨지고 백업 선택이 보인다. 실제 filechooser 이벤트로 익명 JSON을 넣어 새 계정 사본의 저장을 확인했다.
5. 지연된 첫 업로드가 있는 동안 계정을 바꾼 뒤 응답을 풀었다. 새 계정에는 사본이 없고 둘째 원문 전송도 없으며, 이전 계정 작업의 성공 안내가 표시되지 않았다. 이미 시작된 첫 요청은 이전 계정으로만 수행됐다.
6. 정상 원격 목록만 있을 때는 복구 영역을 숨기고 원래 제목·정확한 문서 링크를 유지했다. 기존 백업 관리에서 파일 선택을 열 수 있었다.

## 실행 이력·한계

최초 after 실행에서 테스트가 문구를 “기기/기존”으로 한정하고, 한 연표의 제목·편집 링크를 둘로 세어 5개 기대가 실패했다. 기록 수/계정 범위와 문서 제목 행을 기준으로 보정했고 저장·원본·전송 assertion은 그대로 유지했다. 정상 원격 목록의 복구 안내 숨김은 root가 확인한 의도다. 최초 JSON 결과를 지우지 않았다. 마지막 오류 문구 개선 뒤 6개 전체 흐름을 한 번 더 확인해 모두 통과했고, 6장 화면은 이 최종 실행의 결과다.

변경 전에는 정상 연표 1개와 손상 원본 1개, 변경 후에는 부분 성공의 재시도 검사를 위해 정상 연표 2개와 손상 원본 1개를 사용했다. 화면의 연표 개수가 같은 전후 비교라고 주장하지 않는다.

실제 Apple 기기, Files, Google 로그인, 운영 연표 복구는 미검증이다. 서버에서 저장된 뒤 응답만 유실되는 경우는 이번 실패 모사가 아니며 기존 CAS 충돌 처리를 바꾸지 않았다. 사용자 연표의 실제 저장 위치를 찾거나 복원했다고 보고하지 않는다.
