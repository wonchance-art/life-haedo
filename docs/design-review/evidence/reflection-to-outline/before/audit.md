# 회고 → 목차 구성, 변경 전 실제 흐름 감사

2026-10-09 KST. 현재 앱을 4186 동결 서버로 보존한 뒤 390/820/1440px에서 실제 UI로 자료 6개·원문 버전 7개·이전 버전 발췌 1개를 가져왔다. 기존 workshop 익명 자료를 재사용했고, 오래된 첫 원문과 현재 생각에는 기존 익명 책 샘플의 서로 다른 문단을 덧붙였다. 원문 2,217자·현재 생각 920자이며 동일 문장을 반복한 부하 샘플이 아니다. 계정 HTTP만 모사했고 원문/구성은 직접 IDB에 심지 않았다.

[화면 갤러리](index.html) · [전체 측정 및 실행별 결과](combined-report.json)

## 먼저 해결할 세 가지

1. **원문과 현재 생각이 한 화면의 작업처럼 느껴지지 않는다.** 390px에서 첫 원문 행은 y627, 현재 생각 입력은 y2018이다. 연도별·묶음별 전환, 목차와 묶기, 기간, 선택 수, 저장 안내를 지나서야 원문 제목이 나온다. 큰 두 폭도 첫 원문 y557, 생각 입력 y1948이다. 첫 화면에 현재 생각은 보이지 않고, 원문 본문도 기본 접힘이라 제목과 관리 정보 위주다. 이는 선택·저장 결함이 아닌 정보 우선순위 문제다.
2. **긴 글을 읽고 쓰다가 목차로 갔다 돌아오는 비용이 크다.** 390px에서 생각 입력이 보이는 위치의 목차 버튼은 viewport 위 약 1897px, 큰 두 폭은 1631px 떨어져 있다. 목차 버튼을 클릭하면 위로 올라가 전환되고, 닫으면 다시 상단으로 돌아온다. 생각 값은 그대로지만 입력 위치와 펼친 원문은 이어지지 않는다. 긴 원문 상자는 높이 384px이고 내부 스크롤이 따로 있다. 820/1440에서는 내부 실제 높이가 1835/1805px였다. 생각 textarea도 높이 337px에 내용 1208px(390) 또는 759px(큰 두 폭)라 바깥 페이지와 원문/생각 내부 스크롤을 함께 사용한다.
3. **목차 화면도 후보보다 설정과 설명을 먼저 보여준다.** 390px의 첫 후보 시작은 y693, 책 만들기는 y1904다. 제목·질문 입력과 두 안내 문단이 상단을 차지하고, 첫 화면에서는 첫 장 제목까지 하단 도크와 겹친다. 큰 두 폭도 첫 후보 y681, 생성 버튼 y1892다. 후보를 고르는 단계인 만큼 후보와 완료 행동을 더 일찍 보여 주고 질문·범위 설명은 필요할 때 확인할 수 있는 위치가 적절하다. 화면에는 일반 '이 브라우저에 저장됨' 표시와 '목차 후보는 임시' 안내가 함께 있으므로 저장 상태의 적용 범위도 더 명확해질 여지가 있다.

맨 위로 이동한 viewport 기준, px 반올림이다. 실제 진입 스크롤은 JSON의 `arrival`에 별도로 남겼다. 아래 숫자는 반드시 사용자가 수동 스크롤해야 하는 거리라는 뜻은 아니다.

## 보존 확인과 후속 비교 조건

세 폭 모두 필터가 선택/회고를 바꾸지 않는 것, 2016~2019년 보기에서 미상 자료를 유지하는 것, 묶기 검토에서 미상 자료를 명시 해제한 뒤 정확한 과거 원문과 2019 원문 두 개만 묶는 것, 묶음별 후보가 선택 범위를 확대하지 않는 것을 확인했다. 목차 후보를 열고 모드를 바꾼 뒤 닫아도 현재 생각과 정확 버전, 발췌·원문 내용은 같고 책은 생성되지 않았다. 콘솔 오류/페이지 오류/예상 밖 외부 요청/운영 쓰기는 0이다.

수정 후에도 같은 자료·같은 폭으로 비교한다. 우선 현재 생각과 원문 사이 이동, 작성 중 목차 진입, 후보 검토와 복귀 맥락이 개선됐는지 본다. 보기 필터를 저장된 선택이나 원문 내용에 합치는 방식으로 화면만 단순화하면 안 된다.

실제 Apple 기기, native 한글 IME, 소프트 키보드, 개인 자료, 운영 DB는 검증하지 않았다. 390px 최초 실행은 긴 원문 상자의 위치를 측정했고, 뒤의 820/1440 실행은 내부 스크롤 끝도 조작했다. 최초 자동 측정에서 원문 선택 summary의 잘못된 클래스 선택자가 null을 냈으며 이 항목은 이미지로 확인했다. 다른 좌표는 실제 존재하는 ID/행을 사용했다. 후속 스크립트는 해당 선택자도 바로잡았다.
