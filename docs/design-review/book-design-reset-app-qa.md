# 책 화면 A안: 실제 앱 독립 QA

2026-10-08. 사용자가 선택한 A안을 실제 비공개 책 화면에 적용한 뒤, 기존 기능과 화면 품질을 나누어 검사했다. 이 문서는 [메모리 시안 QA](book-design-reset-qa.md)와 별개다. 실제 `index.html`, 동봉 인증 SDK, 격리된 IndexedDB를 사용했고 인증 HTTP만 모사했다.

## 검사한 자료와 범위

[익명 책 백업](evidence/book-edition/reader-book-backup.json)을 **실제 복원 UI로 새 작업공간에 설치**했다. 장 4개·개정본 1개·이전/최신 원문·발췌·제외한 해석을 포함한 기존 샘플이다. 목록, 2장 「쉬는 동안 생긴 기준」의 집필, 첫 장부터 시작하는 전체 읽기를 1440×1000, 820×1000, 390×844px에서 비교했다.

Chromium 151.0.7922.173, 820/390px의 터치 설정, reduced-motion을 사용했다. 화면 위 기준 캡처와 실제 진입 시 스크롤 위치를 별도 기록했다. 복원 직후 일회성 안내는 닫고 촬영했다. 앱 코드나 기존 테스트 파일은 이 QA에서 수정하지 않았다.

## 기능 회귀

새 배치에 영향을 받는 기존 검사 **18/18**, 새 원고 배치 검사 **3/3**가 통과했다. 서로 다른 실행의 동일 케이스를 중복 합산하지 않은 결과다. 마지막 목차 경계 보완 뒤 root가 전체읽기 6개를 다시 실행해 통과했으며, 나머지 회귀와 실행 시각을 분리해 보존했다.

기존 `책 열기` 버튼은 편집 진입으로 남아 있어 테스트 helper나 기대치를 바꿀 필요가 없었다. 관리·개정본·출력 UI는 원고 뒤로 이동했지만 기존 접근 이름과 ID를 유지했다. 실제 받은 책자 HTML을 Chromium PDF로 만들고 본문·링크를 확인한 검사가 포함되며, 운영체제 인쇄 창에서 사용자가 저장한 PDF를 검증한 것은 아니다.

원본 결과는 `.local/book-design-reset-app/regressions/*/report.json`, 실행 시각과 범위는 `regressions/execution-summary.json`에 보존했다. 원본 보고서를 덮어쓰기 전에 이전 보고서도 `before-report.json`으로 복사했다. [최종 합산 보고서](evidence/book-design-reset/app/combined-report.json)는 각 최종 실행의 시각·원본 경로·검사 이름과 최초 실패 이력을 함께 기록한다. 마지막 읽기 재실행은 `regressions/reading-final-report.json`이며 새로운 6개로 계산하지 않았다.

## 새 배치에서 추가한 검사와 발견 이력

긴 장 제목의 자동 줄바꿈과 단일 줄 값 계약, Enter/줄바꿈 문자 입력·합성 composition 종료, 긴 원고 중간에서 입력할 때 바깥 스크롤과 caret 보존, 읽기→같은 장 집필 복귀, 근거 패널의 키보드 펼침/접힘을 별도로 검사했다. 합성 composition 이벤트는 실제 Apple 한글 IME 검증을 대신하지 않는다.

최초 기대치 1건은 앱 결함이 아니었다. 2장을 편집하다 전체읽기를 열면 처음에는 책의 1장이 보인다. 이때 상단 **집필**은 현재 보이는 1장을 편집해야 한다. 이전에 편집한 2장을 무조건 여는 기대를 제거하고, 읽기 목차에서 2장으로 이동한 후 같은 장과 caret를 비교하도록 보완했다.

이어 실제 경계 결함을 확인했다. 390px에서 읽기 목차로 2장에 이동하면 이전 장의 하단 여백이 y113.86까지 남았고, `bottom > 110`으로 현재 장을 고르는 로직이 그 여백을 1장으로 판단했다. 화면에 보이는 2장 대신 1장 집필로 이동했다. root가 실제 고정 도구막대 아래에서 가장 넓게 보이는 장을 선택하도록 고쳤다. 최종 세 폭에서 목차→2장→상단 집필이 정확히 2장으로 복귀했다. 원고 손실은 없었다. 최초 기대치 보정과 이 실제 결함은 각각 원본 실행 보고서에 남겼다.

추가 실패 2종은 검사 방법의 문제였다. 1440px에서 고정 x좌표가 가운데 원고 밖을 누르던 문제는 입력창 좌표를 사용해 고쳤다. 또한 Playwright의 `locator.click`은 이미 화면에 보이는 고정 읽기 버튼을 누르기 전 스크롤 여백 규칙에 따라 페이지를 34px 이동했다. 앱은 그 클릭 시점의 위치를 정확히 복원했다. 버튼 중심이 실제 버튼인지 hit-test한 뒤 화면 좌표로 탭/클릭해 입력 직후 위치까지 유지되는지 확인했다. 복귀 허용 오차를 늘려 통과시키지 않았다.

최종 [새 배치 보고서](evidence/book-design-reset/app/layout-report.json)의 세 폭에서 입력 전·후, 자동저장, 실제 pointerdown, 읽기 왕복 뒤의 pageY는 각각 **390px: 631 / 820px: 600 / 1440px: 600**으로 같았다. caret와 선택한 장, 원고 값도 보존됐다. 긴 제목은 입력창 내부 스크롤 없이 줄바꿈되지만 저장 값의 줄바꿈은 기존 단일 줄 제목 규칙대로 정리된다. 원문·개정본·기존 회고 값은 변하지 않았다.

390px의 실제 저장 실패는 원고 화면을 유지하며 [상단 오류·복구 조작](evidence/book-design-reset/app/save-error-390.png)을 표시했다. 오류 영역은 y64~208px이고, 원고를 잃지 않은 채 다시 저장할 수 있었다. 새 읽기 화면이나 출력으로 넘어가지 않았다. 이 검사는 영구 테스트 `tests/book-manuscript-layout-browser.cjs`로 추가했으며 CI 환경 변수를 지원한다.

## 실제 화면 비교

좌표는 변경 전 감사와 같이 페이지 위 기준 px이며 반올림했다. 정상 상태의 관리·저장 조작을 원고 뒤로 옮기고 상단을 간결하게 만든 효과다. 숫자를 줄이려고 본문 글자를 작게 만들지는 않았다.

| 폭 | 첫 책 행 y 전→후 | 집필 첫 글자 y 전→후 | 읽기 첫 글자 y 전→후 | 최종 입력창 높이 / 내부 내용 높이 |
| --- | ---: | ---: | ---: | ---: |
| 1440 | 222→110 | 591→304 | 590→249 | 926 / 926 |
| 820 | 222→110 | 591→304 | 590→249 | 1037 / 1037 |
| 390 | 182→72 | 597→276 | 681→244 | 1292 / 1292 |

실제 집필 진입은 390px에서 26px, 큰 두 폭에서 54px 자동 스크롤하므로 첫 글자는 모두 약 y250에 도착한다. 페이지 위 좌표가 사용자가 반드시 수동으로 지나야 하는 거리라는 뜻은 아니다. 읽기 진입은 390px에서 스크롤 0, 큰 두 폭에서 4px이다. 원고 textarea는 내용 전체 높이로 늘어나 별도 내부 스크롤이 사라졌다. 본문은 모바일 17px/줄높이 32.3px, 큰 두 폭 19px/37.05px이다.

최종 기본 9화면과 긴 제목 3화면에서 가로 넘침, 44px 미만 조작, 16px 미만 입력, 접근 이름 누락, 계산된 대비 실패는 없었다. 기본 화면 최소 텍스트 대비는 5.384였다. console/pageerror/예상하지 않은 외부 요청/운영 쓰기는 0이었다. 이 수치만으로 사용성 합격을 판단하지 않는다.

## 해석과 한계

본문을 먼저 보여 주고 관리 조작을 보조 위치로 옮기는 방향이 이전 감사의 주된 문제를 해결한다. 숫자로 된 대비·조작 크기 통과만으로 디자인 품질이 보장된다고 판단하지 않았다. 원고가 보이는 위치, 한글 문단의 밀도, 저장·오류의 발견 가능성, 실제 복귀 동작을 따로 확인했다.

실제 iPad/iPhone/Mac, Safari, 소프트 키보드 가림, native 한글 IME, Files와 실제 인쇄 대화상자는 이 환경에서 검증하지 않았다. 모의 인증·익명 자료만 사용했으며 운영 DB·개인 자료·실제 SNS에 접근하지 않았다. 여러 권의 실제 장기 집필 자료를 사용한 유용성 평가도 별도다.

## 전체 CI에서 발견한 검사 경로 보정

첫 전체 CI `37845795654`의 정적/Node 검사는 통과했고 브라우저에서는 workshop·completion·import 세 묶음이 실패했다. GitHub check annotations와 로컬 재현을 대조했다. 다른 통과 결과와 이 실패를 합쳐 전체 CI 성공으로 보고하지 않았다.

- workshop은 원고 점검 뒤 상단 집필이 항상 이전 1장으로 돌아간다는 가정이었다. A안의 집필은 현재 보이는 장을 연다. 점검의 **해당 장 확인** 또는 장별 편집을 명시적으로 누르고 정확한 장 ID를 확인하도록 보정했다. 새 상단 집필 계약은 별도 세 폭 layout 검사에서 계속 확인한다.
- completion·import와 후속 workshop 모바일 경로는 집필/읽기 중 숨긴 전역 dock를 바로 클릭하고 있었다. 실제로 보이는 **책 목록 → 홈/관리** 경로를 사용하도록 바꿨다. 강제 클릭·직접 라우트 이동으로 화면을 우회하지 않았다.
- 원문·정확 버전·발췌·자료 개수·계정·개정본·JSON·Markdown·PDF의 기존 assert는 삭제하거나 완화하지 않았다. 이번 보정은 테스트 조작만 바꾸며 앱 코드는 `b550dcd` 그대로다.

workshop의 세 화면 폭 전체 작성·개정·백업·PDF 흐름과 계획 실패 복구, completion의 세 폭 복원·원문·HTML/PDF 및 모바일 책/계정 경계, import의 연결·취소·복구 경로를 재검증했다. 개별 최초 실행과 실패 사례만 재검사한 범위는 [후속 보고서](evidence/book-design-reset/app/ci-recheck-report.json)에 기록한다. 최종 커밋의 전체 CI 결과는 [PR #55](https://github.com/wonchance-art/life-haedo/pull/55)에서 확인한다.
