# D2 준비 — Markdown 정본 형식 `life-post-md-v1`과 v2 → Markdown 변환 (2026-11-04)

## B3 서버 공개 투영 — 로컬 구현·독립 검수 완료, 운영 반영 전 (2026-11-05)

기준은 main `321e00b`와 [B3 착수 지시](https://github.com/wonchance-art/life-haedo/issues/212#issuecomment-6652546434)다. B1은 PR216으로 병합·배포됐다. [최신 운영 확인](https://github.com/wonchance-art/life-haedo/issues/212#issuecomment-6653067297)에 따르면 소유자가 SQL Editor에서 B1을 적용했고 총괄이 함수 6개 해시/ACL·트리거 2개·행 수 보존·기존 글 6/6 검증을 확인했다. B1 운영 적용 관문은 해제됐으며, B2에는 A 병합·B3 운영 반영·구형 탭 교체 초안 보호·변환 거부 글 편집 경로가 남았다. 작업자가 운영에 접근하거나 적용한 것은 아니다.

- **명시 공개만:** 새 md 공개 요청은 기존 공개 선택·사진 사본·영수증 흐름을 유지한다. `blog-sync`가 새 md 요청의 형식만 영속 대기에 기록하고 `blog-remote`가 `haedo-blog-publish`로 보낸다. 오래된 형식 표시 없는 대기는 기존 RPC를 그대로 쓰며, 이미 보관된 요청을 다른 내용이나 새 요청 ID로 바꾸지 않는다. 브라우저가 Markdown·ops·소유자 ID를 보내지 않는다.
- **서버 원문:** Edge가 실제 Auth 사용자와 서버 세션을 확인하고, 사용자 JWT로 prepare RPC를 호출해 저장된 원문·revision·해시를 읽는다. 같은 요청의 영수증이 있으면 원문을 다시 해석하지 않고 그 결과를 돌려준다. 신뢰할 수 없는 요청 본문을 정본으로 쓰지 않는다.
- **하나의 codec:** Edge는 저장소의 실제 `post-markdown.js`와 기존 `PhotoPost`·`Blog.publicSnapshot`을 상대 경로로 직접 불러온다. 파서 사본이나 PostgreSQL Markdown 해석기는 만들지 않는다. 선택 사진·AI 표시 제거·서식 투영은 같은 코드가 수행한다. UUID는 공개 때마다 새로 생기므로, 사진 ID의 대응을 고정한 뒤 클라이언트·Edge 결과의 바이트를 비교한다.
- **공개 확정:** Edge가 commit 직전에 사용자 JWT를 한 번 더 확인하고, service 전용 commit RPC가 소유자/현재 세션·원문 해시/revision·공개 revision·등록한 사진 사본과 실제 Storage 메타데이터를 다시 확인한다. 공개 사진 ID는 기존처럼 `doc.photos`의 선택 순서로 만들고, 공개 사본·미디어 참조·영수증을 같은 트랜잭션에 저장한다. 제목·첨부는 서버 원문에서 가져온다. 기존 v1/v2 publish 정의·동작은 유지한다.
- **비공개 보호:** 직접 호출한 기존 RPC의 md 공개는 계속 거부한다. 새 commit은 DB의 실제 `service_role`만 호출할 수 있으며 사용자 정의 GUC나 요청의 role 문자열을 신뢰하지 않는다. 서비스 키는 Edge 내부에서만 사용하고 `sb_secret_`은 apikey 헤더에만 둔다. 로그와 오류 응답에 본문·토큰·키를 남기지 않는다.
- **인계 항목:** `life_blog_markdown_publication_unavailable`과 `life_blog_update_required`는 글 보존과 다음 행동을 알리는 문구로 표시한다. 기존 공개 사본에는 원문 형식 식별자가 없으므로 `validationBodyOps`의 빈/사진 종료 호환 판독은 유지한다. 저장된 v1/v2 원문과 서버 v2 공개 검증은 원래 계약 그대로이며, 공개 판독기를 임의로 좁히지 않는다. 실행형 gzip 고정본을 골든 JSON으로 바꾸는 검토는 B3 출시 후에 한다.

B3 설치는 한 DO 문장 안에서 정의 변경과 행 수/해시 전후 보호를 끝내며, 문장별 커밋 모드와 중간 오류에서도 원자성을 검사한다. 운영 설치 순서와 선행 조건은 [B3 설치 안내](../../supabase/operations/post-markdown-publish-install.md)를 따른다. 실제 운영 적용·배포·두 기기 검증은 이번 로컬 구현·격리 검수와 구분한다.

## B1 기반 구현 — 2026-11-05

총괄 [집중 구현 지시서](https://github.com/wonchance-art/life-haedo/issues/212#issuecomment-6650230384), [접점 승인](https://github.com/wonchance-art/life-haedo/issues/212#issuecomment-6650334085), [공개 계약 결정](https://github.com/wonchance-art/life-haedo/issues/212#issuecomment-6650375672)에 따른다. 아래의 ‘미결’과 검사 전용 설명은 최초 변환기 당시 기록이다.

- **본문:** `PostMarkdown.parse/toDelta/canonicalize/remapPhotos`로 허용 문법과 정확 사진 참조를 검증한다. 저장은 정본 Markdown 하나이며 `ops`를 함께 저장하지 않는다. 비정본 입력은 조용히 고치지 않고 거부한다. v1/v2 읽기·저장은 유지하며 md-v1에서 구형 형식으로 낮춰 쓰는 것을 거부한다. 교체 대상 판도 검증해 미래 형식의 원본을 지우지 않는다.
- **편집기 실험:** Tiptap 3.32.2 독립 어댑터와 재현 가능한 vendor 번들을 준비했다. `getMarkdown/setMarkdown`, 사진·AI 표시, 실행 취소, 조합 중 교체 금지, 편집기별 선택 정보 검증을 제공한다. 미지원 목록은 적용 전에 안내하고 기존 입력을 유지한다. 연구·라이선스·번들 크기는 [오픈소스 비교](../life-tools-design/open-source-review.md)에 있다.
- **보관:** `life-post-md-backup-v1` ZIP은 본문·첨부·원본 사진·HEIC 보기용 바이트를 보존한다. 전체 백업·연재·보존 파일은 기존 형식과 함께 읽고 새 사본의 사진 ID만 재매핑한다. 전체 백업의 목록과 내부 ZIP이 Markdown/기존 형식 경계를 넘으면 거부한다. 기존 v1 ZIP이 읽기 과정에서 v2 사본으로 바뀌는 호환 복원은 유지한다. 비공개 계정 transport는 Markdown 그대로 보관하고 읽기 투영만 기존 ops를 사용한다.
- **서버:** 새 migration은 비공개 문서의 허용 키·문자열/바이트 한도·사진/HEIC/첨부 메타데이터를 검증한다. PostgreSQL은 Markdown을 실행하거나 해석하지 않으므로 정본 문법·해석 후 글자 수·본문 사진 참조의 의미 검증은 클라이언트 codec의 책임이다. SQL을 완전한 CommonMark 검증기로 표시하지 않는다. 기존 v2 validator는 보존하며 md→v1/v2 덮어쓰기는 같은 revision이어도 거부한다.
- **공개:** 클라이언트 읽기/공개 미리보기는 기존 ops 사본 형식으로 투영하고 공개 AI 표시를 제거한다. 그러나 서버의 md 공개는 `life_blog_markdown_publication_unavailable`로 명확히 거부하며 기존 공개 사본·영수증을 바꾸지 않는다. 기존 v2 공개·철회는 유지한다.
- **공개 투영 보존:** [PR216 재검수 결정](https://github.com/wonchance-art/life-haedo/pull/216#issuecomment-6651273594)에 따라 v1/v2 공개 투영은 main과 전체 JSON 바이트까지 같게 유지한다. 연산 분할·속성 순서·미선택 사진 제거 때의 줄바꿈을 정규화하지 않는다. 모든 형식의 공개 사진 배열과 새 ID 배정은 `doc.photos`의 선택 순서를 따라, 공개 미리보기의 사본 배열과 캡션·이미지 짝을 유지한다. Markdown은 `toDelta`로 읽은 본문에 같은 사진 선택·AI 표시 제거 규칙을 적용하며, v2와 연산 경계가 달라도 문단·서식·사진 순서·캡션이 같은지 실제 렌더 결과로 비교한다. 저장 원문과 비공개 읽기는 바꾸지 않는다. 사진으로 끝나는 사본은 검증용 배열에서 이미 있는 완결 줄을 끝으로 옮겨 검사하며, 화면 배열에 줄을 더하거나 실제 글자·연산 한도를 늘리지 않는다. 고정 main 원본의 SHA 검증·바이트 비교와 실제 공개 동의 화면의 사진 매핑 회귀를 검사한다.
- **미활성:** `photo-post-ui.js` 본체를 바꾸지 않았다. 독립 Tiptap 어댑터는 제품 페이지에 등록하지 않았고 자동 변환도 없다. 운영 DB·배포·CACHE 판올림은 하지 않는다. 이미 배포된 구형 앱은 md 형식의 직접 읽기·쓰기를 거부한다. 다만 기존 v2 수정 초안으로 md 원본을 교체하는 과거 결함은 아래 B2 전제 조건과 같이 남아 있다. 구형 앱의 오류 문구도 소급 변경하지 못한다.

검수에서 발견한 기존 링크의 공백/역슬래시 보존 실패, 2부터 시작하는 목록 입력의 저장 실패, 다른 편집기의 선택 정보 재사용, 미지원 미래 판 교체, 보존 파일 사진 재매핑 누락과 전체 백업 형식 불일치를 재현하고 고쳤다. 최초 실패와 변이 결과는 작업공간 `.local/` 및 `/tmp/d2-*`에 보관한다. 실제 Apple 한글 입력기·키보드·운영 두 기기 검증은 자동 브라우저 조합 이벤트 검사와 구분한다.

실행: `npm run check`, `npm test`, `node tests/post-markdown-editor-browser.cjs`, `node tests/run-post-markdown-sql-postgres.cjs`. SQL 검사는 격리 PostgreSQL에만 설치하고 기존 행·권한·v2 공개 회귀와 새 거부 경로를 확인한다. 브라우저 검사는 독립 어댑터를 390·1440px에서 열며 제품 작성기 연결의 증거가 아니다. CI 등록과 운영 적용은 총괄 담당이다.

**PR216 CI 후속:** 첫 head `5b5886d`는 전체 SQL 재생에서 과거 account-sync 설치 묶음이 `valid_document/publish`를 옛 정의로 되돌려 실패했다. 두 설치 생성기와 산출물을 고쳐 검토된 D2 정의를 같은 원자 설치 안에서 보존한다. D2 전에는 알려진 과거 정의를 쓰는 원래 설치를 유지하고, 알 수 없는 변경·불완전 D2 설치는 중단한다. 기존 카탈로그 동일성 단언을 바꾸지 않는다. `node tests/run-post-markdown-install-replay.cjs`는 D2 전 재설치·D2 후 재설치·설치 후 D2와 드리프트 거부를 확인한다. `npm run test:sql-replay`는 PostgreSQL이 실제 있는 환경에서 `SQL_REPLAY_REQUIRED=1`로 실행해야 하며 SKIP은 검증 성공이 아니다. 통합 설치 검사의 고정 migration 목록에도 B1 경로와 정확 SHA를 등록했다.

다음 순서는 **B3 서버 공개 연결 → B2 작성기 연결**이다. B3는 서버 Edge가 동일 `post-markdown.js`를 재사용해 저장된 Markdown을 기존 공개 ops로 투영하고 Markdown 클라이언트 미리보기와 서버 결과의 일치를 검증하는 것이 완료 기준이다. v2와 Markdown의 연산 경계는 달라도 되며, 같은 본문의 문단·서식·선택 사진·캡션 짝은 렌더 결과로 검증한다. B2는 A 병합과 B3 운영 반영 뒤 처음 수정할 때의 변환·원래 판 복구 사본·자동 저장·사진·계정 이어쓰기를 연결한다. B3 운영 전에는 B2를 병합하지 않는다.

구형 앱 증거는 `tests/fixtures/post-markdown-old-client/`에 기준 main 두 모듈의 원본을 압축·SHA 고정해 보관한다. `tests/photo-post-old-client.test.cjs`는 Git 기록이나 네트워크 없이 직접 읽기/쓰기 거부·기존 교체 결함·md 수정 초안 거부를 각각 검증한다.

B2 전제 조건: md 글의 수정 초안도 반드시 md-v1으로 만들고 변환 저장의 revision을 올린다. 구형 앱의 직접 저장 거부만으로 보호를 주장하지 않는다. 실제 구형 `storage.js`의 교체 저장은 대상 형식을 검증하지 않아, 같은 판을 가리키는 v2 수정 초안이 md 원본을 지울 수 있다. 또 최신 값 우선 BlogSync에서 원격 v2가 로컬 md를 이기면 현재 퇴행 방어가 `photo_post_update_required`로 멈추므로, 원문·복구 사본을 지키는 충돌 처리까지 B2 전에 연결해야 한다. `blog.html`·`series.html`·`cover.html`은 지금 공개 ops만 받는다. md 문서의 codec 의존성 등록과 지원하지 않는 형식 안내는 B3에서 함께 검증한다. 운영 행 해시의 메모리 사용은 [설치 전 크기 확인](../../supabase/operations/post-markdown-install.md)을 따른다.

### 본문 용량과 변환 중단 조건 — PR216 검수 보완

- Markdown을 읽을 때 같은 서식의 이웃 문자열 연산을 합친다. 한 v2 연산에 들어 있던 `가\n` 2,600줄·25,000줄이 각각 5,200·50,000개의 연산으로 부풀던 문제를 고쳤다. 25,000줄은 기존 본문 50,000자 한도까지이며 변환 뒤에도 1개 연산이다. 사진 경계와 서로 다른 글자·블록 서식은 합치지 않는다.
- 파서 토큰 상한은 `6 × 50,000 + 10 × 5,000 + 2 = 350,002`다. 기존 허용 입력인 빈 목록 50,000줄은 줄당 6개 토큰과 목록 여닫기 2개가 필요하고, 기존 5,000개 연산의 인라인 표시 경계에 연산당 10개를 더한 유한 예산이다. Markdown 1 MiB·본문 50,000자·합친 연산 5,000개·중첩 깊이 제한은 유지한다. 빈 목록 50,000줄도 잘라내지 않고 같은 1개 연산으로 되돌린다.
- Linux Node 24의 상한 사례 1회 측정(기존 검증 → 변환 → 재해석 → 새 형식 검증)은 빈 목록 50,000줄·Markdown 450,000바이트에서 약 1,312ms, 프로세스 최대 RSS 385,640 KiB였다. 반복 파싱을 포함한 프로세스 측정이며 편집기의 입력 지연이나 실기기 메모리 측정이 아니다. 최대 크기 문서의 iPhone·iPad 체감과 메모리는 미검증이다.
- **모든 유효 v2 글이 변환되는 것은 아니다.** 예를 들어 굵게 표시한 `a\n` 3,000줄을 한 연산으로 보관한 v2는 유효하지만, 새 형식에서는 글자와 줄바꿈의 의미가 달라 6,000개 연산이 필요하다. 긴 제목·인용·내용 있는 목록도 같은 경계에 걸릴 수 있다. `fromV2`는 해석한 연산이 기존 5,000개 한도를 넘거나 해석 후 문자열 합계가 50,000자를 넘으면 `post_markdown_conversion_limit`로 후보를 반환하기 전에 중단한다. 원래 문서·사진은 수정하지 않으며, 회귀 검사는 원본의 정확한 불변과 기존 검증 통과를 함께 확인한다. **B2는 변환 한도·문단 경계 오류를 잡아 기존 형식과 원본을 유지하고 변환 저장을 하지 않아야 한다.** 한도를 늘리거나 일부 본문을 버려 성공으로 표시하지 않는다.
- **사진 앞 미종결 문단은 변환하지 않는다.** `앞` + 사진 + `뒤\n`과 `앞\n` + 사진 + `뒤\n`은 같은 Markdown으로 바뀌지만, 기존 v2 서버가 사진을 공개에서 빼면 각각 한 문단·두 문단이 된다. Markdown 정본만으로 원래 경계를 되찾을 수 없으므로 `fromV2`는 사진 앞에 줄바꿈 없이 남은 글자가 있으면 `post_markdown_conversion_boundary`로 중단한다. 기존 v2 공개 결과·본문·사진을 그대로 보존하고, 저장 형식에 보조 필드를 추가하거나 원문에 줄바꿈을 몰래 넣지 않는다. 명시적 줄바꿈 뒤의 사진은 변환을 허용하고, 미선택 사진을 뺀 뒤에도 v2와 같은 문단이 보이는지 브라우저에서 검증한다. B2는 이 오류를 사용자에게 설명하고 원문·기존 형식·복구 경로를 유지해야 한다.
- 공개 투영은 v2에 추가 정규화를 적용하지 않는다. 본문 50,000자·5,000연산·공개 사본 2 MiB 한도는 기존과 같다. Markdown 읽기의 이웃 연산 합치기와 변환 용량 초과 거부는 유지한다.

## 문서 모양 — `life-post-md-v1`

`PostMarkdown.fromV2(doc)`가 만드는 모양이다. v2 문서에서 본문 `ops`만 `markdown`으로 바뀐다.

| 키 | 내용 |
|---|---|
| `format` | `"life-post-md-v1"` |
| `markdown` | 본문(아래 문법). 끝은 줄바꿈 하나 |
| `photos` | 본문에 보이는 사진만, 본문 순서대로. 각 사진 기록(바이트·digest·HEIC 보기용 사본)은 v2 그대로. 본문에서 쓰지 않는 사진 기록은 버린다(앱 저장 `photo-post.js`와 같은 동작). D2 이행에서 그 기록은 원래 v2 문서의 복구 사본에만 남는다 |
| 나머지 | `id`·`revision`·`title`·`status`·`replaces`·`createdAt`·`updatedAt`·`attachments`·`archived`를 그대로 옮긴다 |

## 본문 문법 (CommonMark + 해도 표시 세 가지)

- **문단·제목:** Delta 한 줄이 블록 하나가 된다. 제목 1·2는 `# `·`## `다.
  - 줄은 앱이 v2 본문을 읽는 방식(`blog-public-ui.js` `render`, 편집기 Quill)과 같게 나눈다. `\n` 하나가 한 줄을 끝내며, 빈 줄도 줄이다.
- **목록:**
  - `- `는 글머리 목록, `1. `은 번호 목록이다. 번호는 1부터 다시 센다.
  - 같은 종류의 목록이 바로 이어지면 둘이 합쳐지지 않게 표시를 바꾼다(`*`, `1)`). HTML은 쓰지 않는다.
- **인용:** 이어진 인용 줄은 `>` 빈 줄로 나눈 한 인용 묶음이다.
- **빈 문단:** `&nbsp;`. markdown-it은 `html:false`에서도 이 엔티티를 풀어 보인다.
  - NBSP 한 글자만 있는 문단도 같은 `&nbsp;`가 되어, 다시 읽으면 빈 문단과 구분되지 않는다. 둘 다 같은 빈 줄로 보인다. 어떤 글자를 빈 문단 표시로 쓰든 그 글자 하나만 있는 문단과 겹치므로 이 한 가지는 같다고 정한다(검사도 이 하나만 같게 본다).
- **굵게·기울임:**
  - CommonMark 규칙(left/right-flanking)으로 그대로 읽히면 `**`·`*`를 쓴다.
  - 그렇지 않으면 `<strong>`·`<em>`을 쓴다. 예: 닫는 문장부호 바로 뒤의 한글(`"천천히"라고`), 공백으로 시작하거나 끝나는 범위, 다른 `*`와 맞닿는 경우.
  - 이모지도 CommonMark에서는 문장부호다.
- **링크:** `[글](주소)`. 주소에 공백·괄호·`<>`가 있으면 `<주소>`로 쓴다.
  - 주소의 `\`와 `&`는 역슬래시로 이스케이프한다. 그래서 `&amp;`·`&copy;` 같은 글자가 풀리지 않고 쓴 그대로 남는다. `<주소>` 안의 `<`·`>`도 `\<`·`\>`로 쓴다.
- **사진:** `![대체 텍스트](haedo-photo:사진ID "설명")`. 파일로 내보낼 때만 `photos/…` 경로로 바꾼다.
  - 사진은 Quill의 블록 embed라 `\n`을 갖지 않는 독립 블록이다. 사진 뒤 글은 다음 블록이 되고, 사진이 이어지면 각각 블록이 된다. 사진 앞에 줄을 끝내지 않은 글이 있으면 보통 문단으로 끝낸다(앱 렌더러와 같다).
  - `[사진, "\n"]`은 사진과 빈 문단이다. 편집기와 공개 화면 모두 사진 아래 빈 줄을 보인다.
  - 설명은 textarea 값이고 공개 화면은 `pre-wrap`으로 보인다. 그래서 줄바꿈을 `&#10;`(`\r`은 `&#13;`)로 그대로 둔다. `\`·`"`·`&`는 역슬래시로 이스케이프해 엔티티가 풀리지 않는다. 대체 텍스트의 줄바꿈도 같다.
- **AI 글 표시:** `<span data-author="ai">…</span>`. 편집기 DOM과 같은 표시다.
  - HTML 주석(`<!-- -->`)은 쓰지 않는다. 줄 첫머리의 `<!--`는 CommonMark에서 HTML 블록이 되어 문단이 깨진다(무작위 검사에서 재현).
- **글자 보호:**
  - 글 속의 `\` `` ` `` `*` `_` `[` `]` `<` `>` `~`와 엔티티처럼 보이는 `&…;`는 이스케이프한다.
  - 줄 첫머리의 `#`·`>`·`-`·`+`·`1.`·`1)`·`---`·`===`도 이스케이프한다.
  - 제목 끝의 ` #`, 링크 바로 앞의 `!`도 이스케이프한다.
  - 줄 앞뒤의 공백·탭은 바깥 한 글자를 문자 참조(`&#32;`·`&#9;`)로 쓴다. 그래야 들여쓰기·코드 블록·강제 줄바꿈이 되지 않는다.
  - 줄 맨 앞의 U+FEFF는 `&#xFEFF;`로 쓴다. `source-markdown.js`와 Obsidian 같은 도구는 BOM을 지우고 읽으므로, 그대로 두면 뒤의 `#`·`---`·`- `가 제목·구분선·목록이 된다.
  - 글 속의 `\r`은 Markdown에서 줄 끝이라 `&#13;`로 쓴다. 정규화해 지우지 않고 글자를 그대로 남긴다(제목이 갈라지거나 이미지 문법이 깨지지 않는다).
- **강조 판정의 공백:** markdown-it 15의 `isWhiteSpace`와 같은 집합(0x09–0x0D, 0x20, 0xA0, 0x1680, 0x2000–0x200A, 0x202F, 0x205F, 0x3000)만 공백으로 본다. JS `\s`는 U+2028·2029·FEFF도 포함해 `**`가 글자로 남는 경우가 있었다.
- **빠지는 것:** 밑줄과 정렬. 글자는 남고, 뺀 개수(`dropped.underline`·`dropped.align`)를 돌려준다. Quill `formatLine`이 사진 embed에 붙인 정렬도 센다.

## D2 렌더러가 지켜야 할 것

- 지금 읽기 렌더러(`source-markdown.js`)는 `html:false`다. 새 형식은 아래처럼 읽는다.
  - `html_inline`은 정확히 이 6개 문자열만 허용한다: `<strong>` `</strong>` `<em>` `</em>` `<span data-author="ai">` `</span>`. 다른 속성·태그·대소문자 변형은 글자로 보인다.
  - 태그는 짝을 맞춘다. 짝이 없는 여는 태그·닫는 태그는 글자로 보인다.
  - `html_block`은 끄거나 글자로 그린다(이 변환은 HTML 블록을 만들지 않는다).
  - 외부 Markdown(Tiptap/marked 직렬화, Obsidian)을 `html:true`로 그대로 받지 않는다. 가져올 때 같은 허용 목록을 거친다.
  - 링크 `href`와 사진 주소는 저장된 대상에서 이스케이프만 풀어 그대로 쓴다. `normalizeLink`를 거치면 `%zz`가 `%25zz`, `|`가 `%7C`처럼 바뀐다(위험한 주소를 막는 `validateLink`는 그대로 둔다).
  - `linkify:false`, `typographer:false`로 고정한다. 켜면 글 속 주소가 링크가 되고, `(c)`가 ©, 곧은 따옴표가 굽은 따옴표로 바뀐다.
  - AI 표시는 비공개 읽기에서는 보이고 공개에서만 뺀다(2026-11-04 소유자 결정, 11-02 결정을 바꿈).
    - 비공개 읽기(단일 글·비공개 연재): span을 표시로 그린다.
    - 공개 사본·서버 `publish`: span을 없애고 글자만 남긴다.
    - HTML 읽기 파일(내보내기): 표시하지 않는다(글자만).
- `haedo-photo:` 주소는 렌더러가 사진 Blob URL로 바꾼다. 공개 사본은 결정 14의 메타데이터 없는 사본만 쓴다.

  - U+2028·2029·FEFF 등 6개 문자 옆 강조
  - 줄 맨 앞 U+FEFF(BOM을 지운 뒤 읽어도 같은 블록), 줄을 끝내지 않은 글 뒤의 사진, 사진에 붙은 정렬 개수
- 무작위 v2 문서: 기본 1,500개(CI). 생성기는 실제 Quill 모양을 만든다: 사진에 `\n`을 붙이지 않고, 사진이 이어지기도 하며, 줄을 끝내지 않은 글 뒤에 사진이 오고(정렬이 붙기도 한다), 설명에 줄바꿈이 있다. 글자에는 U+FEFF도 든다. 글자에는 NBSP·U+2028·U+3000·`\r`·`&amp;`·`&#65;`가, 링크에는 엔티티·한글·공백·`\`·`<>`가 든다.
  - 검수 수정 뒤 로컬에서 `POST_MARKDOWN_FUZZ=20000`으로 시드 5개(20261104·1·2·3·4) × 20,000개를 모두 통과했다.
  - 처음 판은 시드 4개(20261104·1·77·4242) × 20,000개를 통과했다. 위 결함은 생성기가 그 모양을 만들지 않아 드러나지 않았다.
  - 무작위 검사가 찾은 결함 5개는 고친 뒤 통과했다.
    - 줄 첫머리 AI 주석이 HTML 블록이 됨
    - 이모지 서로게이트 판정
    - 링크 앞 `!`가 이미지가 됨
    - 제목 끝 ` #`이 닫는 표시로 사라짐
    - 밑줄만 다른 조각으로 나뉜 줄의 `9)`가 목록 표시가 됨
