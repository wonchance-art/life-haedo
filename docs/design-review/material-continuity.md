# 자료 준비를 다른 기기에서 이어 같은 글 완성하기

2026-10-19 KST. 자료 선택·비교·개요에서 PhotoPost 완성으로 이어지는 기존 작업 위의 후속 목표다. 아래는 총괄이 확정한 구현 계약과 확인한 범위별 결과다. **로컬 구현과 범위별 검수를 마쳤으며, 같은 최종 후보 전체의 원격 CI는 대기 중**이다. 소스 파일이나 SQL 파일의 존재를 설치·동작 성공으로 표시하지 않는다. 병합·배포·운영 개인 자료 전송은 이번 범위에 포함하지 않는다.

## 목표·기존 기능·새 공백

Mac에서 자료와 개요를 준비한 뒤 같은 계정의 다른 기기에서 **한 준비를 직접 받아** 기존 PhotoPost로 글·사진을 완성한다. 완성 글 원본을 기존 글별 보관으로 직접 보낸 뒤 준비와 연결해, 처음 기기에서도 같은 논리적 글과 정확 인용 근거를 다시 연다. 충돌 양쪽 보존·선택 공개/철회·근거 ZIP의 새 공간 복원까지 한 결과로 확인한다.

기존 자료 선택·개요·한 번의 글 초안 인계, PhotoPost/Quill 편집, 글별 BlogSync와 원본 사진, 익명 공개, 정확 근거 파일을 재사용한다. 준비가 브라우저 전용인 점과 일반 BlogSync가 구조화 인용 sidecar를 옮기지 않는 점이 새 공백이다. 새 편집기·전체 작업공간 동기화·홈/검색/추천·자동 공개를 만들지 않는다.

## 보관·공개·파일의 포함 범위

| 데이터 | 선택 준비의 비공개 서버 보관 | 완성 글·공개·근거 파일 |
| --- | --- | --- |
| 준비 제목·질문·개요와 자료별 메모 | 직접 고른 준비 한 개의 실제 내용을 검토·동의한 뒤 포함 | 질문·메모는 글/공개/근거 ZIP에 자동 포함하지 않음. 명시적으로 문단에 복사한 내용만 글 본문 |
| 준비에 고른 원문 버전 | 인용하지 않은 비교 자료까지 선택 버전의 **전체 본문**과 필요한 출처 포함. 링크 전용은 본문 확보로 표시하지 않음 | 근거 ZIP은 완성 글이 채택한 근거의 정확 버전만 포함하며 전체 본문 포함 가능성을 기존 방식으로 안내 |

로그인·준비 선택·미리보기·서버 목록 읽기는 전송 동의가 아니다. 준비의 입력/자료가 검토 뒤 바뀌면 이전 동의로 새 내용을 보내지 않는다. 일시 중지는 서버 사본 삭제나 공개 철회가 아니다. 준비의 비공개 보관을 글의 공개 완료로 표시하지 않는다.

## 가장 단순한 사용 흐름과 디자인

기존 작성 준비 본문 아래 접힌 이어쓰기 영역을 둔다. 현재 브라우저 보관·선택 준비의 서버 상태·완성 글 보관 상태를 짧게 구분하고, 글을 쓰는 동안 상시 상태 패널이나 별도 대시보드를 만들지 않는다. 준비가 없는 경우에도 서버의 제목/수정일 목록을 명시 조회해 받을 수 있다.

첫 받기는 선택 준비와 필요한 정확 원문만 가진 새 작업공간으로 설치한다. 같은 계정에서 같은 서버 준비를 다시 받으면 기존 연결의 같은 공간/준비로 돌아가며 관련 없는 공간의 입력을 덮지 않는다. 의도한 새 독립 사본은 연결을 풀고 새 글을 만들 수 있는 별도 결과다. 단순 재시도나 성공 뒤 열기 실패를 새 사본 만들기로 처리하지 않는다.

현재 DESIGN.md의 흰 본문·차콜·틸·Pretendard, 기존 필드·44px 조작·16px 입력을 따른다. 1440/820/390px에서 제목·비공개 질문·자료/개요가 중심이고 긴 원문/충돌 비교는 필요한 때 펼친다. `이 브라우저`/`서버 보관`/`다른 기기에서 작성 중`/`갱신 대기`/`미확인 요청`/`충돌`/`일시 중지`를 실제 저장 사실에 맞게 구분한다. 보관 성공 뒤 후속 읽기가 실패하면 설치된 준비를 다시 여는 조작만 제공한다. 원본과 입력을 버리는 새로고침을 복구 방법으로 강요하지 않는다.

Impeccable의 direct-context fallback과 프로젝트 디자인/개발 스킬을 적용한다. 엔진·자동 hook을 새로 설치하거나 실행 점수를 주장하지 않는다. 홈/검색/추천의 다른 세션 파일과 공통 시각 토큰은 수정하지 않으며 공통 CSS는 총괄 한 명이 통합한다.

## 확정 보존 계약

전송 모델은 `life-material-continuity-v1`의 `{format,bundle,plan,output}`이다. 한 준비만 포함하고 `plan.output`은 wire에서 항상 null이다. bundle은 모든 선택 자료 버전과 saved output refs의 최소 합집합이며 `records/links/resumeHints/tombstones`는 빈 배열이다. 16MiB 전송 한도와 기존 준비 모델 한도를 넘으면 잘라내지 않고 거절한다. 본문 SHA와 SourceReference의 정확 UTF-16 구절을 확인하고, 수신 ID 재매핑 뒤 변경 없는 내용을 편집으로 오인하지 않도록 원래 wire↔local 연결을 보관한다.

출력 상태는 `null → writing → saved`로 진행한다. writing의 글 ID·claim ID는 saved에서 그대로 유지하고 saved revision만 전진할 수 있다. 연결된 준비는 원격 CAS로 작성 권리를 확정한 뒤 그 기기의 영속 claim으로 기존/새 PhotoPost·근거·준비 영수증을 원자 설치한다. 다른 기기에 미완성 output이 있으면 그 글을 만들었던 기기에서 마무리하도록 표시하고 두 번째 글을 자동 생성하지 않는다. 독립 fork만 새 준비/원격 ID와 output:null로 시작한다.

이미 작성·서버 보관한 준비를 처음 연결할 수도 있다. saved 수정으로 바뀐 로컬 글 ID와 기존 BlogSync의 고정 원격 ID를 구분해 최초 claim에 기존 원격 ID를 확인해 사용한다. 기존 보관 글/공개 주소의 연결을 새 로컬 ID로 바꾸거나 다른 글을 복제해 이 차이를 숨기지 않는다.

saved output은 기존 BlogSync로 보관한 **정확 원격 글 revision**에 연결한다. 받기는 해당 revision의 검증된 manifest·사진 원본과 실제 refs를 확인한 뒤 원문/준비/글/근거/연결을 한 로컬 트랜잭션으로 설치한다. 서버 글이 descriptor보다 앞섰으면 옛 근거를 최신 글에 붙이지 않고 갱신이 필요한 상태로 막는다. 일반 BlogSync의 전송 형식을 바꾸거나 다른 글의 sidecar를 자동 이동하지 않는다.

로컬 폼 revision과 원격 메타 CAS는 구분한다. 영속 outbox의 같은 operation을 재확인하고 과거 성공 영수증을 현재 서버 head로 추정하지 않는다. 충돌 선택은 최신 검토 revision/fingerprint와 일치해야 하며 선택하지 않은 쪽은 연결 없는 독립 사본으로 보존한다. 저장 claim·새 공간·원문·글/근거의 실패는 부분 설치를 남기지 않는다. 계정/공간 전환·dispose·IME·미적용 구절은 기존 flush와 최종 guard를 통과해야 하며 늦은 응답이 다른 준비의 내용·동의·초점을 바꾸지 않는다.

글의 수정 상태는 output이 가리킨 saved 본문뿐 아니라 그 saved 글을 `replaces`하는 별도 편집 초안도 확인해야 한다. 비교에 실제로 보여준 글·근거·해당 초안의 snapshot으로 동의를 고정하고 최종 저장 트랜잭션에서도 대조한다. 비교 뒤 다른 입력을 읽고 새 지문으로 바꿔 검토한 것으로 간주하지 않는다. 완성 글 전송도 검토 manifest를 기존 BlogSync의 선택적 사전조건으로 넘겨, 검토 뒤 추가된 사진/본문이 업로드 전에 거절되도록 한다. 일반 글별 전송 payload나 공개 선택 형식은 바꾸지 않는다.

## 반대 검토와 선택 근거

- 전체 원문 동기화를 선행하면 준비 한 개만 고른 의도와 다르게 다른 자료·메모까지 전송될 수 있다. 기존 WritingSync의 `sourceReady` 전제 전체를 복사하지 않고 CAS/큐/영수증·계정 경계 패턴과 정확 closure 검증을 재사용한다.
- 원격 글 ID만 준비에 싣는 방식은 가장 작지만 일반 BlogSync가 구조화 refs를 옮기지 않아 정확 원문 복귀와 근거 파일 복원이 끊긴다. 이번 연결의 정확 saved 글과 sidecar closure만 결합하는 범위가 필요하다.
- 글 원본 보관 성공 뒤 준비 descriptor 갱신이 실패할 수 있다. 이때 이미 보관한 글을 새로 만들거나 조용히 되돌리지 않고 준비 연결 갱신 대기로 남겨 같은 작업을 재확인한다.
- 자동 문자 병합은 개인 질문·메모와 정확 원문 버전·단일 글 claim의 의미 충돌을 해결하지 않는다. 이번에는 양쪽을 읽고 직접 선택·보존하는 CAS가 더 단순하다. [공식 오픈소스 비교](../life-tools-design/open-source-review.md#자료-준비-한-개의-명시-기기-이어쓰기--2026-10-19-kst)를 따른다.

## 검수 계획·현재 상태

대표 자료는 옛 CRLF/이모지 원문 두 편과 링크 전용 한 편, 비공개 질문·자료 메모·채택 문단/인용이다. A에서 검토·보관→독립 IDB의 B에서 받기→정확 버전 대조/기존 글·원본 사진 두 장 완성→명시 원본 보관/준비 연결 갱신→A에서 같은 글·근거 재열기→충돌·응답 유실·계정 late·commit 뒤 조회 실패→한 사진 선택 공개/갱신/철회→근거 ZIP 새 공간 복원의 해시·픽셀·UTF-16을 확인한다. 미선택 sentinel과 기존 자료 불변을 함께 검사한다.

종합 UI/격리 SQL은 독립 담당의 fixture·보고서를 재사용한다. 별도 시각 검사는 3폭 실제 전송 범위·동의 기본 off/재검토, 읽기/대기/오류/충돌/미확인 상태, 한글 조합·선택 구절·입력 DOM/초점과 늦은 응답을 집중 확인한다. 같은 전체 사용자 여정을 새 suite로 중복 작성하지 않는다. 계산한 대비·44px/16px·넘침·이름과 실제 화면 읽기를 구분해 기록한다.

아래 로컬 범위별 검사와 최종 후보 전체의 원격 검사를 구분한다. 실제 Apple 기기·네이티브 IME·Files·Google OAuth·관리형 서버의 개인 업로드/게시·운영 설치·병합·배포는 합성 Auth/격리 DB/Linux Chromium의 통과와 별개다. 최종 커밋·원격 CI 결과는 통합 PR의 HEAD/검사 기록을 따른다. 문서에 자기 커밋 SHA나 아직 실행하지 않은 CI 성공을 선취하지 않는다.

총괄의 마지막 현재 소스 검사 `.local/material-continuity/unit-final-complete.log`·`check-final-complete.log`에서 Node22.23.3 단위 807/807(실패/skip 0), 정적 21 HTML/127 JavaScript/536 참조·PWA manifest/shell 통과를 확인했다. 이번 후보는 PWA v131이며 YAML/diff 검사도 통과했다. 정적 PWA 검사는 실제 설치 기기에서의 업데이트·오프라인 체험 결과가 아니다.

### 독립 시각·입력과 원문 재추적

[시각/입력 suite](../../tests/material-continuity-visual-browser.cjs)의 원래 5개 집중 흐름을 확인했다. 실제 SDK/독립 IDB와 공유된 네트워크 없는 PostgreSQL 컨테이너 안의 새 테스트 DB를 사용했다. `.local/material-continuity-visual/report.json`은 pass=true이며 Node22.23.3/Chromium151.0.7922.173, console/page/external 0, 실제 합성 material RPC 쓰기 3회/운영 쓰기 0이다. 준비 범위와 완성 글 범위는 1440/820/390px, 변경 오류는 820px로 7개 장면을 viewport/전체 문서 각 한 장씩 기록했다. 계산한 넘침·이름·작은 조작/입력·대비 문제 0과 실제 이미지 읽기를 구분한다.

검토만 할 때 쓰기 0·동의 기본 off, 질문/자료 메모·선택 원문 전체/파일 경로/작성자 확인, 한글 조합 중 이전 동의 차단과 같은 입력 노드 보존, 수정 뒤 옛 동의로 전송 0, 서버 목록 응답 지연 중 커서/초점 보존, A 검토의 해시 응답을 지연한 뒤 B로 전환해 A의 옛 결과/연결 상태가 끼어들지 않음을 확인했다. 완성 글이 추가로 채택한 버전까지 원문 검토에 들어가고 실제 `ops.insert.photo`의 설명/대체 텍스트와 파일명·80×100px 시험 원본 메타데이터가 보이며, 별도 원본 전송 동의는 off/사진 자산 업로드 0이었다. 고해상도 원본의 왕복/공개/파일 검증은 아래 종합 담당의 별도 근거와 구분한다.

초기 서버 프로세스 종료에 따른 접속 거절, 초기에는 없는 `aria-busy="false"`를 요구한 검수 대기, 상위 fixture의 `holdNext=null`과 새 메서드의 이름 충돌은 환경/검수 도구 문제였다. 실제 준비 상태와 `holdMaterialNext`로 바로잡았고 원래 전송·입력·시각 단언을 줄이지 않았다. 실패/중간 보고서를 최종 통과로 합산하지 않는다. 별도 수정 초안 보호와 원문 재추적의 후속 근거는 아래에 따로 적는다. 이 원래 5개 통과를 최종 HEAD의 전체 검사로 표시하지 않는다.

동일 공간 재수신의 추가 실제 반례도 확인했다. 영구 시각 suite의 6번째 흐름은 두 독립 IDB에서 새 원문 생성→같은 공간 받기→정확 CRLF 본문→실제 원문 읽기→같은 준비/자료 복귀를 단언한다. 마지막 부모 연결 수정 뒤 이 흐름만 `--new-source-only`로 실행해 `.local/material-continuity-visual-new-source/report.json`에서 통과·console/page/external 0을 확인했다. 앞 5개/7장면의 보고서를 덮지 않았고 같은 최종 후보 전체 6개 실행은 원격 CI에서 확인한다.

### 종합 완주·실제 보존 보강

독립 종합 `.local/material-continuity/report.json`은 고유 10개 흐름/1440·390px의 12개 화면을 기록한다. 첫 8개 통과와 수정 초안/정확 saved revision의 집중 2개 통과를 합친 **8+2 분리 검사**다. 두 실행의 주요 런타임 7개 모듈 SHA가 동일함을 검사했으며 한 번의 연속 10개 실행으로 표현하지 않는다. 이 근거 뒤 부모 bundle 연결 수정이 추가되어, 최신 원문 재추적은 위 집중 검사로 보완했다. 최종 HEAD 전체의 10개/6개 통과는 원격 CI 결과에 따라 확정한다.

실제 SDK·독립 IDB·격리 SQL에서 선택 준비 한 개의 전체 정확 원문/내 입력, 단일 작성 claim·응답 유실의 동일 요청, 같은 글/근거 왕복, 실제 4032×3024·1200×1800 원본의 SHA/디코딩 픽셀, 한 사진만 선택 공개·익명 읽기·철회/원본 404, 채택 근거 ZIP의 새 공간 복원을 확인했다. 미선택 준비/질문/메모는 공개와 근거 파일에서 제외했고, 잘못된 본문 해시·구절/추가 원문·다른 계정·late 응답·최종 IDB 영수증 abort에서 부분 설치하지 않음을 검사했다. console/page/external 0과 의도한 실패 응답은 보고서에서 구분한다.

별도 편집 초안은 saved 글과 다른 ID로 보관돼 기존 saved 문서만 비교하면 수신 때 이어쓰기 문맥에서 빠질 수 있는 실제 보존 공백이었다. 최종 보강은 그 초안의 본문·사진·근거까지 읽기 지문/트랜잭션 검토에 포함하고, 자동 전송에서 제외됨을 표시한다. 실제 수신은 `local_changed`로 막히며 양쪽 준비·saved 글·미완성 초안 전체를 확인한 뒤 명시 선택해야 한다. 집중 검사는 원래 초안 불변, 선택하지 않은 쪽의 연결 없는 복구 공간, 새 사진 ID 일대일 재매핑 뒤 원본 바이트/픽셀·본문/속성·정확 refs 2개를 확인했다. 최신 `conflict-with-unfinished-editing-draft-390.png`도 직접 읽어 각 본문/사진 메타데이터와 독립 선택을 구분했다. 준비만 충돌한 다른 화면을 글 비교 증거로 쓰지 않는다.

코드 검토로 찾은 최초 saved 글의 로컬 교체 ID/원격 canonical ID 차이와 비교 후 새 지문으로 검토를 갱신하는 경합은 기존 연결 ID·처음 표시한 지문·최종 트랜잭션 대조로 보강했다. 완성 글 전송은 검토한 manifest를 기존 BlogSync의 선택적 사전조건으로 전달해, 새 사진/본문을 업로드한 뒤 뒤늦게 거절하지 않고 업로드 전에 막는다. 각각 단위/격리 동작 근거를 따르며 모든 정적 후보에 수정 전 실제 브라우저 재현이 있었다고 주장하지 않는다.

새 종합 9번째 검사에서 독립 서비스 호출 후 UI의 상태 갱신을 생략한 대기는 검수 도구 문제였다. 저장소에는 충돌이 있고 화면은 이전 상태였으며 실제 `연결 상태 다시 확인`을 거쳐 비교하도록 고쳤다. 원래 충돌·초안·원본 보존 단언을 줄이지 않았다. 원격 CI·운영 설치·실기 결과를 이 로컬 근거로 대체하지 않는다.

### 원격/SQL 확인과 설치 조건

원격/SQL 담당의 `.local/material-continuity/backend-report.json`·`backend-final.log`는 수송 단위 3개와 실제 격리 PostgreSQL 8개 흐름 통과를 기록한다. 소유자별 비공개 테이블/RLS·직접 테이블 권한 0·고정 search path, 두 실제 DB 연결의 claim CAS, 실제 글 행 잠금과 종료 경합, UTF-16/잘못된 NULL 거절, 원문 후보 3,000개 중 선택 closure·목록 20개 keyset, 같은 migration 재적용 뒤 기존 head/영수증의 SHA 보존을 포함한다. 이를 운영 설치나 실제 Google 인증 통과로 표시하지 않는다.

CLI로 생성한 신규 [준비 이어쓰기 migration](../../supabase/migrations/20261018161658_life_material_continuity.sql)은 기존 [글 원본 migration](../../supabase/migrations/20261017144744_life_blog_originals.sql)을 선행 조건으로 한다. 두 migration을 설치한 **격리 DB**와 합성 Auth/원본 Storage·Edge HTTP 경계에서 검사했으며 새 준비 migration의 운영 설치는 하지 않았다. 운영 환경에서 사용 가능한 상태인지와 로컬 파일/검수의 존재를 구분한다. 관리형 설치·배포를 실제 수행한 경우에만 별도 설치/출시 기록을 추가한다.

**선행:** 이번 기기 이어쓰기의 통합 PR/CI와 보존 계약을 마친 뒤, 다른 채팅의 최신 파일·목표를 확인해 공개 표지와 겹치는지 먼저 대조한다. 총괄이 마지막으로 확인한 상대 범위는 홈/관심/추천·한국어 의미모델이지만 이번 설계 시점 추가 조회 도구가 없어 최신 상태를 더 확인하지 못했다. 그러므로 조건부 후속 후보이며 비공개 홈·검색·수집/추천을 별도로 고치지 않는다. 기존 익명 블로그/Share-v1·공개 글 토큰·연재/9칸을 재사용할 수 있는 범위를 먼저 정한다.
