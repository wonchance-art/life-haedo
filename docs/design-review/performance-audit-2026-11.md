# 성능 점검과 최적화 우선순위 (2026-11)

2026-11-02 KST. 기준 `origin/main` `8da96de`. 읽기 전용 측정이며 제품 코드·검사는 바꾸지 않았다. 목표는 소유자의 iPhone·iPad·Mac 실사용에서 **첫 열기, 재방문, 홈 → 글쓰기, 글 열기, 뉴스, 자료실, 설정**의 기다림을 줄일 작업을 측정값으로 고르는 것이다.

**이 문서의 수치는 로컬 Chromium의 모사 측정이다.** 390×844·CPU 4배 감속·Fast 4G 조건은 iPhone을 대신하는 근사이며 실제 Apple 기기·Safari/WebKit·실제 회선의 결과가 아니다.

## 방법과 환경

- **실행:** `python3 -m http.server 4637 --bind 127.0.0.1`로 worktree를 그대로 제공했다. 서비스워커 갱신 실험만 같은 커밋을 `git archive`한 임시 사본(4638)에서 하고, 그 사본의 `sw.js` 캐시 이름만 올렸다. 저장소의 `sw.js`는 바꾸지 않았다.
- **브라우저:** Playwright 1.63.0, Chromium 153.0.8010.12 headless, Node 22.23.4. Linux 4코어 공용 장비.
- **로그인 상태:** 기존 하네스를 재사용했다. `tests/unified-home-browser.cjs`의 `makeContext()`, `tests/life-sync-browser.cjs`의 `FakeCloud`(블로그·계정 문서·자료·구성·글쓰기 RPC 포함)와 세션 주입, `startup-performance-browser.cjs`의 자료공간 시드 방식이다. 계정 자료실 기능(capability 1)을 켰다.
- **자료:** 익명 합성 자료만 썼다. 원문 60개짜리 기본 자료공간 1개를 두었다. 준비용 기기에서 실제 글쓰기 화면으로 글 6편을 쓰고 서버 동기화까지 마쳤다. 측정 기기는 IndexedDB가 빈 새 컨텍스트로 이 글들을 받는다. 사진 글은 포함하지 않았다.
- **모바일 모사:** 390×844, DPR 3, `isMobile`·터치, CDP `Emulation.setCPUThrottlingRate(4)`. 네트워크는 DevTools Fast 4G 프리셋과 같은 값(지연 165 ms, 하향 8.1 Mbps, 상향 1.35 Mbps)을 CDP로 걸었다.
- **개인 HTTP:** 가짜 응답은 CDP 네트워크 감속을 거치지 않으므로, 요청마다 165 ms를 더해 같은 왕복 시간을 주었다. 실제 Supabase의 지연·처리 시간과는 다르다.
- **압축:** `http.server`는 압축하지 않는다. 그래서 측정 전송량은 원본 크기와 같다. GitHub Pages는 텍스트를 gzip으로 보내므로, 파일별 `gzip -6` 크기를 따로 계산해 "gzip 추정"으로 표시했다(woff2는 원본 크기).
- **수집:**
  - CDP Network 이벤트: 요청 수, encoded/decoded 바이트, 서비스워커 응답 여부, 순서.
  - CDP Tracing: `EvaluateScript`, `v8.compile`, `FunctionCall`, `ParseHTML`, `UpdateLayoutTree` 등 주 스레드 시간.
  - `PerformanceObserver`: long task, paint, LCP.
  - 화면 준비 표시: MutationObserver로 실제 DOM을 확인했다.
    - 비로그인: `#lifeWelcome`이 보이는 시점.
    - 로그인: `#homePosts[aria-busy=false]`에 글 6개가 있는 시점.
  - Coverage: CDP Profiler precise coverage, CSS rule usage.
  - 화면 전환: 페이지 안에서 `click()`부터 대상 DOM이 준비된 첫 animation frame까지 쟀다.
- **표본:** 첫 열기는 조건별 3회, 데스크톱 참고값은 1회다. 서비스워커 재방문은 3회, 대기 측정은 보이는 상태 2분과 숨김 상태 1분이다.
- **장비 부하:** 같은 장비에서 다른 세션이 브라우저 검사를 돌려 1분 부하가 20 이상으로 오른 때가 있었다.
  - 각 표본 전에 부하가 2.5 이하가 될 때까지 기다리게 했다.
  - 첫 전체 실행은 부하 13~22에서 돌아 시간 수치를 버렸다. 요청 수·바이트는 재실행과 같았다.
  - 표의 첫 열기 수치는 조용한 장비에서 다시 잰 값이다. 부하 2.2~2.5에서 시작했다.
  - 예외: 비로그인 모바일 1회는 기다린 끝에 부하 27에서 시작했다. 결과 8.22초가 나머지 두 번(8.04·8.19초)과 같아, 이 경로는 네트워크가 지배한다고 보고 포함했다.
- **측정 스크립트:** 작업 범위상 이 문서만 커밋하므로 스크립트는 저장소 밖 임시 공간에 두었다. 재현하려면 위 하네스로 같은 조건을 만들면 된다.

## 2. 재방문

### 서비스워커 설치 후 (모바일 모사, 같은 계정·IndexedDB 유지, 3회)

| 항목 | 값 |
| --- | ---: |
| 홈 글 표시 | **3,015 ms** (2,436–3,172) |
| 첫 그림 · DOMContentLoaded · 앱 화면 노출 | 732–1,408 · **1,868** (1,258–2,046) · 2,706 |
| 정적 요청 | 174개 모두 서비스워커 캐시, 네트워크 0 |
| 준비 + 3초 구간의 개인 요청 | 27–30개, 그중 `/auth/v1/user` 17–19개 |
| 주 스레드: 평가 · HTML 해석 · 스타일 · FunctionCall | 204–265 · 254–440 · **515–577** · 339–393 ms |
| long task | 2–7개, 합 125–475 ms |

- 데스크톱 무감속 진단 실행에서 재방문의 홈 표시 전 개인 요청은 5개(계정 확인 3개)뿐이었다. 나머지는 홈 표시 뒤의 배경 재확인이다.
- 재방문 대기의 대부분은 **DOMContentLoaded까지 스크립트·CSS를 해석하는 1.9초**다. 이 중 스타일 계산이 가장 크고, V8 코드 캐시 덕분에 스크립트 평가는 작다. 예를 들어 `quill.js`는 첫 열기 159~201 ms에서 재방문 12 ms로 줄었다.

참고로 서비스워커 없이 IndexedDB만 남긴 재방문은 모바일 모사 9.6초(데스크톱 1.3초)였다. Playwright 요청 가로채기가 HTTP 캐시를 끄므로, 이 값은 정적 파일을 모두 다시 받는 상한이다. GitHub Pages의 실제 HTTP 캐시 동작은 재현하지 않았다.

### 서비스워커 설치·갱신 비용

| 항목 | 값 |
| --- | ---: |
| 설치 요청 | 197개 (셸 목록 196개 포함) |
| 설치 바이트 | 7.85 MB 원본, gzip 추정 3.44 MB |
| 설치 시작 시각 | 탐색 후 19.7초. 모바일 모사에서 홈 준비 완료(21.6초)보다 1.9초 앞서 시작해 홈의 글 수신과 겹친다 |
| 설치 소요 | 1.1초, 활성화 22.0초 |
| 새 버전(캐시 이름만 변경) 갱신 | **196개 전부 재요청, 7.84 MB**, 활성화까지 4.7초 |

- 설치 소요는 무감속 값이다. 서비스워커의 요청은 페이지의 CDP 네트워크 감속을 받지 않는다. Fast 4G에서는 gzip 기준 바이트만으로 약 3.4초가 걸린다.
- 갱신 결과는 `sw.js`의 `cache.addAll(...{cache:'reload'})`와 같다. 파일 내용이 같아도 캐시 이름이 바뀌면 전부 다시 받는다. `git log --first-parent`로 보면 2026-10-19 이후 `main`에서 캐시 이름이 33번 바뀌었다(최근 1주 9번). 기기마다 배포 1회에 gzip 약 3.4 MB를 다시 받고, 그중 2.06 MB는 바뀐 적 없는 글꼴이다.

### 1. 원격 호출마다 반복되는 계정 서버 확인을 동기화 주기 단위로 정리

- **근거:**
  - 새 기기 첫 열기에서 앱 화면 전 요청 56개 중 37개가 `/auth/v1/user`이고, 모두 직렬이다.
  - 모바일 모사에서 첫 개인 요청부터 블로그 목록 요청까지 11.4~12.3초 걸렸다.
  - 대기 중 요청의 57%(분당 35.5/62)가 계정 확인이다.
  - 재방문도 준비 + 3초 구간에서 17~19개를 보낸다.
- **방향:** 시간으로 승인을 재사용하는 캐시는 만들지 않는다. 2026-10-24 결정과 Supabase `getUser` 문서 취지를 유지한다.
  - `bootstrap`·`reconcile`·각 sync `cycle` 같은 한 주기의 시작에서 `auth.verify()`를 한 번 한다.
  - 그 결과(epoch·uid·access token)를 주기 안의 `list/read/head/write`에 넘긴다.
  - 원격 호출 직전에는 서버 왕복 없이 현재 epoch와 세션 token이 같은지만 확인한다. 다르면 `request_cancelled`로 끊는다. 다음 주기는 다시 서버에 확인한다. BlogSync가 이미 쓰는 "주기마다 다시 확인" 모델과 같다.
  - 서버 권한은 지금처럼 PostgREST가 요청마다 JWT를 검증하고 RLS의 `auth.uid()`로 판정한다.
- **파일:** `assets/life/remote.js`(`getAccount`·`authorized`), `assets/platform-life-remote.js`(`borrowedAuth.getUser`), `assets/platform-auth.js`(`verify`), `assets/life/library-remote.js`·`composition-remote.js`·라이브러리 메타 원격 모듈, 각 sync 엔진의 주기 진입점.
- **UI·디자인 파일:** 건드리지 않는다. 디자인 세션과 병행할 수 있다.
- **기대 효과:**
  - 새 기기 앱 화면 노출 전 직렬 왕복이 약 37회 줄어든다. 왕복 165 ms면 약 6초다.
  - 대기 요청은 분당 62에서 약 27로 준다.
  - 실제 효과는 운영 Supabase 왕복 시간에 비례한다.
- **데이터 안전:**
  - 계정 전환·로그아웃·세션 갱신 중의 늦은 응답이 이전 계정 저장소에 쓰지 못하게 하는 epoch/uid guard를 그대로 둔다.
  - 주기 중간의 토큰 갱신은 "다른 토큰"으로 보고 주기를 끊고 다시 시작한다.
  - 저장 실패·미저장 입력 보존과 outbox·CAS 의미는 바꾸지 않는다.
  - 공개 홈은 서버 계정 검증 전 개인 저장소를 열지 않는다는 규칙을 유지한다. 시작 시 `shell.start`의 서버 확인은 남긴다.
- **검증:**
  - `tests/platform-auth.test.cjs`와 `tests/platform-life-remote.test.cjs` 단위 검사.
  - 계정 전환·로그아웃·늦은 응답 브라우저 회귀: `life-sync-browser.cjs`, `account-wide-home-browser.cjs`, `startup-performance-browser.cjs`의 보존 검사.

### 2. 서비스워커 증분 갱신과 설치 시점 유휴화

- **근거:**
  - 캐시 이름만 바꾼 갱신이 196개·7.84 MB(gzip 추정 3.43 MB)를 모두 다시 받았다.
  - 2주간 `main`에서 33번 갱신됐다.
  - 그중 글꼴 2.06 MB는 2026-10-18에 추가된 뒤 바뀌지 않았다. 벤더 JS·CSS(gzip 약 0.3 MB)도 같은 기간에 새 라이브러리 추가(10-22·10-23) 말고는 수정이 없었다.
  - 첫 설치는 홈 글 수신과 겹쳐 시작한다(탐색 19.7초, 홈 준비 21.6초).
- **방향:**
  - (a) 글꼴과 `vendor/`를 버전 이름이 붙은 별도 캐시(예: `haedo-static-pretendard-1.3.9`)에 둔다. 앱 캐시 이름이 바뀌어도 지우지 않는다. 노력이 가장 작고 갱신 바이트의 약 70%를 줄인다.
  - (b) 앱 파일은 파일별 내용 해시 목록을 두고, 같은 해시는 이전 캐시에서 복사한다. 빌드 없이 하려면 해시를 `sw.js`에 적고 `npm run check`가 실제 파일과 대조하게 한다.
  - (c) `shell.js`의 `scheduleWorker()`를 첫 동기화 주기가 끝난 뒤나 `requestIdleCallback`으로 늦춘다.
- **파일:** `sw.js`, `assets/life/shell.js`(`scheduleWorker`), `scripts/check.mjs`·`scripts/prepare-site.mjs`·`scripts/verify-prepared-site.mjs`, `tests/service-worker.test.cjs`.
- **UI·디자인 파일:** 건드리지 않는다.
- **데이터 안전:**
  - 캐시에는 정적 셸만 있고 개인 데이터는 없다.
  - "부분 셸은 설치하지 않는다"(`addAll` 원자성)와 "한 설치 버전의 모듈만 제공한다"를 유지해야 한다. 해시가 틀리면 버전이 섞인 모듈을 줄 수 있으므로, 해시 대조를 검사로 강제한다.
  - 발견 피드 캐시와 OAuth 쿼리 비캐시 규칙은 그대로 둔다.
- **검증:**
  - `tests/service-worker.test.cjs`에 갱신 시 바뀐 파일만 요청하는 사례와 해시 불일치 시 설치 거부 사례를 더한다.
  - 이 문서의 갱신 실험(서버 GET 수 = 바뀐 파일 수)을 다시 실행한다.
  - 오프라인 재방문과 이전 버전에서 올라오는 PWA 갱신을 확인한다.

### 3. 2 MB 글꼴 첫 다운로드 줄이기

- **근거:**
  - 첫 열기 gzip 추정 전송량 3.20 MB 중 2.06 MB(64%)가 글꼴이다.
  - 모바일 모사에서 글꼴이 0.25~4.5초 동안 스크립트와 회선을 나눴다.
  - 사전 캐시 설치량의 60%가 글꼴이다.
- **방향:**
  - Pretendard 공식 배포의 동적 서브셋(`unicode-range`로 나눈 woff2 묶음)을 검토한다. 실제 파일 수·크기·라이선스는 도입 전에 공식 릴리스에서 확인한다. 이번 세션에서는 해당 저장소에 접근할 수 없어 확인하지 못했다.
  - 서브셋 방식이면 사전 캐시는 전체 조각을 담거나 자주 쓰는 조각만 담는다. 오프라인에서 드문 글자가 시스템 글꼴로 대체되는 정도를 함께 판단한다.
  - 최소안은 `index.html`의 `rel=preload`를 빼 스크립트에 회선을 먼저 주는 것이다. 이득은 작고, 글꼴 교체 시점이 늦어진다.
- **파일:** `assets/haedo-type.css`, `index.html`(preload), `vendor/pretendard/*`, `sw.js`, `vendor/pretendard/README.md`(출처·확인일 기록).
- **UI·디자인 파일:** **건드린다.** 디자인 세션 이후로 잡는다. 글꼴 교체 순간의 흔들림과 한글 표시를 디자인 책임자가 판단한다.
- **데이터 안전:** 데이터 경로와 무관하다. 사용자 글의 드문 한글·한자·기호가 다른 글꼴로 보이는 것은 시각 품질 문제로 판단한다.
- **검증:** 1440·820·390 화면과 한글 표본·실제 글 본문의 시각 비교, 첫 열기 전송량 재측정, 오프라인 재방문, 실제 iPhone Safari 확인(사용자).

### 4. 새 기기에서 홈 글 목록을 자료실 전체 준비와 분리

- **근거:** `shell.js`는 `accountLibrary.bootstrap({foreground:true})`가 끝나야 `UI.mount`와 홈을 연다. 홈의 블로그 목록은 계정 전체 글이고, 자료실의 원문·구성·메타 수신과 독립적이다. 그런데도 새 기기에서는 블로그 목록 요청이 직렬 사슬 58~59개 뒤에 나간다. 후보 1을 적용하면 이 사슬이 짧아지므로 남은 이득은 1 적용 후 다시 측정해 판단한다.
- **방향:** 서버 계정 확인 직후 홈 글 목록(로컬 → BlogSync 수신)을 먼저 그리고, 자료실 준비는 배경에서 이어 간다. 자료실 화면만 준비 상태를 보인다.
- **파일:** `assets/life/shell.js`, `assets/life/ui.js`(`mount`), `assets/life/home.js`, `assets/life/account-library.js`.
- **UI·디자인 파일:** **건드린다**(`home.js`·`ui.js`의 준비 상태 표시). 디자인 세션 이후로 잡는다.
- **데이터 안전:**
  - 확인 전 개인 DOM 비노출, 계정·세대 guard, 기본 자료공간 생성 경합을 그대로 지킨다.
  - 자료공간 확인 전에 홈에서 글쓰기를 열 경우, 새 글이 들어갈 자료공간이 정해지기 전에 저장되지 않게 해야 한다.
- **검증:** `startup-performance-browser.cjs`(새 기기·캐시 재방문), `account-wide-home-browser.cjs`, `blog-platform-home-browser.cjs`, 이 문서의 새 기기 측정.

### 5. 화면별 CSS 분리

- **근거:**
  - 재방문에서 가장 큰 주 스레드 항목은 스타일 계산 515~577 ms(모바일 모사)다.
  - 홈은 불러온 CSS 280 KB 중 약 23 KB만 쓴다.
  - 상한 실험에서 홈 CSS 4개만 남기면 스타일 계산이 503 ms에서 264 ms로, DOMContentLoaded가 1.98초에서 1.71초로 줄었다(모바일 모사 중앙값). 홈 표시 시간 차이는 표본 변동 안에 있었다.
  - 따라서 기대 효과는 재방문 첫 화면 약 0.2~0.3초(모사)다. 실제 iPhone의 스타일 엔진에서 다시 재야 한다.
- **방향:** 홈·공통(`haedo-shell`·`haedo-type`·`haedo-motion`·`ui`의 공통부·`home`)만 첫 화면에 두고, 자료 구성·뉴스·사진 글·연재·보존 등 화면 CSS는 해당 화면을 처음 열 때 `<link>`로 붙인다. 서비스워커 사전 캐시는 유지한다.
- **파일:** `index.html`·`life.html`의 `<link>`, `assets/life/*.css`, 화면 진입 코드(`ui.js`·각 `*-ui.js`), `sw.js`.
- **UI·디자인 파일:** **건드린다.** 디자인 세션 이후, 디자인 책임자가 통합한다.
- **데이터 안전:** 데이터 경로와 무관하다. 화면이 스타일 없이 잠깐 보이는 문제와 오프라인 첫 진입을 확인한다.
- **검증:** 모든 화면 3폭의 시각 비교(기존 디자인 검사 스크립트), 오프라인 첫 진입, 스타일 계산 재측정.

### 6. 보이는 상태의 동기화 타이머 묶기

- **근거:**
  - 보이는 상태에서 분당 62요청이 30초마다 약 30개씩 묶여 나간다.
  - 숨김 상태는 이미 분당 2요청이라 조정할 이유가 없다.
  - 후보 1을 적용하면 분당 약 27요청으로 먼저 줄어든다. 그 뒤 남은 묶음을 판단한다.
- **방향:**
  - AccountLibrary·CompositionSync·WritingSync·AccountDocsSync·BlogSync의 30초 타이머를 한 스케줄러로 묶는다. 변화가 없는 주기가 이어지면 받기 간격을 60~120초로 늘린다.
  - `focus`·`visibilitychange`·`online`의 즉시 받기와 로컬 변경 직후 올리기는 유지한다.
- **파일:** 위 다섯 모듈과 `sync.js`·`material-continuity-sync.js`, `assets/life/shell.js`.
- **UI·디자인 파일:** 건드리지 않는다.
- **데이터 안전:**

- **검증:** 대기 측정 재실행, 두 기기 동기화 브라우저 회귀(`account-wide-home-browser.cjs`·`life-sync-browser.cjs`), 숨김 → 표시 복귀 시 즉시 받기 확인.

### 7. 비로그인 정적 안내 즉시 표시

- **근거:** 비로그인 첫 그림은 1.7초인데, HTML에 이미 있는 안내가 스크립트 144개 실행 뒤 8.2초에 보인다(모바일 모사). 데스크톱도 1.1초다.
- **방향:**
  - 저장된 세션 키(`caeyeon_life_platform_session`)가 없을 때만 HTML에서 바로 안내를 보인다. 세션 키가 있으면 지금처럼 서버 확인 뒤 판단한다.
  - 소유자는 대부분 로그인 상태라 이 후보의 효과는 비로그인 방문에 한정된다. 그래서 순위를 낮게 두었다.
- **파일:** `index.html`(`#lifeWelcome`의 `hidden`), 작은 인라인 판단 또는 `assets/life/shell.js`.
- **UI·디자인 파일:** **건드린다**(`index.html`). 디자인 세션 이후로 잡는다.
- **데이터 안전:** 공개 안내만 보이고 개인 저장소는 열지 않는다. 로그인 사용자에게 안내가 깜빡이지 않게 세션 키가 있으면 숨김을 유지한다.
- **검증:** `unified-home-browser.cjs`의 비로그인 홈 검사, 로그인 → 로그아웃 → 재진입, 3폭 시각 확인.

### 8. 홈에 쓰지 않는 기능 스크립트 지연 로드 (보류 권고)

- **근거:**
  - 홈에서 5% 미만 실행한 모듈이 37개 1.12 MB, 전체 흐름 뒤에도 5% 미만이 28개 0.53 MB다.
  - 그러나 시간 비중은 작다. 재방문에서 이 모듈들의 평가 시간은 12~30 ms이고, HTML 해석이 254~440 ms다.
  - 상한 실험에서 스크립트 28개를 빼도 홈 표시·DOMContentLoaded·평가 시간에 측정 가능한 차이가 없었다. 변형 페이지 1회는 홈이 준비되지 않았다.
  - **측정상 이득이 보이지 않으므로 보류를 권한다.** 같은 시간을 CSS 분리(후보 5)에 쓰는 편이 낫다. 실제 iPhone에서 HTML 해석·서비스워커 요청 수의 비용이 크게 나오면 다시 검토한다.
- **방향:**
  - 네이버 가져오기·9칸·자료로 글쓰기·전체 백업 화면·블로그 관리·공개 표지·연재·보존·Obsidian처럼 홈에서 쓰지 않는 화면 묶음을, 화면 진입 시 `<script>`를 붙여 로드한다.
  - 공용 계층(`storage.js`·`core.js`·sync 엔진)은 그대로 둔다.
  - Quill은 지연하지 않는다. 재방문 평가가 12 ms뿐이고, 지연하면 글쓰기 진입(현재 0.5초)이 늘어난다.
- **파일:** `index.html`·`life.html`의 `<script>` 목록, `assets/life/ui.js`의 화면 진입부, 해당 `*-ui.js`, `sw.js`.
- **UI·디자인 파일:** HTML과 화면 진입 코드를 건드린다. 디자인 세션 이후로 잡는다.
- **데이터 안전:**
  - 모듈은 사용할 때 `HaedoLife.X`를 찾는 구조라 순서 의존은 작다. 다만 평가 시점에 다른 모듈을 참조하는 파일(예: Quill·fflate를 즉시 참조하는 모듈)은 하나씩 확인해야 한다.
  - 로드 실패나 오프라인 첫 진입 때 입력 중인 편집 내용이 사라지지 않게 실패 표시와 재시도를 둔다.
- **검증:**
  - 각 화면의 브라우저 회귀(관련 `*-browser.cjs`), 오프라인 첫 진입, `npm run check`의 로컬 리소스 검사.
  - 지연 로드가 서비스워커 캐시를 쓰는지 확인한다.
  - 재방문 DOMContentLoaded와 HTML 해석 시간을 재측정한다.

### 평가했으나 후보에서 뺀 것

- **사전 캐시 목록 줄이기:** 다른 화면 전용 파일은 gzip 0.23 MB(7%)이고 연표·작업공간의 오프라인 실행에 쓰인다. 효과는 후보 2의 증분 갱신이 대신한다.
- **벤더 분할·지연:** 재방문에서 벤더 평가 합계는 약 55 ms(`markdown-it` 13.5, `quill` 12.1, `dompurify` 10.7, `js-yaml` 9.7, `fflate` 9.5)다. 첫 열기의 Quill 평가 159~201 ms는 후보 2·3이 다루는 첫 설치 경로의 비용이다. Quill 지연은 글쓰기 진입을 늦춘다.
- **숨김 상태의 폴링 간격:** 이미 분당 2요청이다.
- **화면 전환 최적화:** 모두 모사 조건에서 1초 안쪽이다. 뉴스 첫 진입(0.57~0.94초)의 공개 피드 103 KB 정도가 남는다.

## 측정 한계

- **실제 기기가 아니다.** CPU 4배 감속은 데스크톱 CPU 기준의 근사다. 최근 iPhone은 이보다 빠를 수 있고, Safari/WebKit의 스크립트 캐시·스타일 엔진·서비스워커 구현은 Chromium과 다르다. iPad Chrome도 WebKit 엔진이다. 실제 iPhone·iPad·Mac 확인은 사용자가 해야 한다.
- **네트워크 모사:**
  - 정적 파일은 압축 없이 보냈다(gzip은 추정치).
  - 개인 HTTP는 고정 165 ms를 더한 가짜 응답이다. 운영 Supabase의 지역·처리 시간·TLS 연결 비용은 반영하지 않았다.
  - 서비스워커 요청은 CDP 네트워크 감속을 받지 않아 설치·갱신 시간은 무감속 값이다.
- **HTTP 캐시:** Playwright 요청 가로채기가 HTTP 캐시를 끈다. 서비스워커 없는 재방문은 상한이며, GitHub Pages의 `max-age`·재검증 동작은 재현하지 않았다.
- **자료 규모:** 글 6편(사진 없음)·원문 60개·자료공간 1개다. 소유자의 실제 글·사진 수와 자료공간 수가 많으면 직렬 사슬과 대기 요청 수가 늘 수 있다(자료공간별 주기). 사진 원본 수신은 측정하지 않았다.
- **장비 부하:** 공용 4코어 장비라 다른 세션의 검사가 일부 표본과 겹쳤다. 표의 첫 열기 시간은 부하 2.5 이하에서 시작한 재측정값이고 범위를 함께 적었다. 화면 전환·상한 실험의 수백 ms 차이는 표본 변동과 비슷한 크기다.
- **Coverage:** 함수·블록 단위 실행 여부다. 실행하지 않은 코드가 곧 지연 로드 가능한 코드라는 뜻은 아니다. CSS는 15개 파일(71 KB)이 사용 기록을 남기지 않았다.
- **iOS 저장소 정책:** Safari 탭(홈 화면에 추가하지 않은 경우)은 오래 쓰지 않은 사이트의 저장소를 지울 수 있다. 그러면 "새 기기 첫 열기" 경로를 더 자주 탈 수 있다. 실제 빈도는 확인하지 않았다.
