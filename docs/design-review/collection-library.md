# 컬렉션 실제 보관 흐름

2026-10-12. 목표: 등록 → 큰 분류/세부 종류·주제·문자 검색 → 수정 → 새로고침 후 재열기 → 전용 백업 다운로드 → 기존 항목을 보존한 사본 복구.

## 기준과 범위

시작 기준은 원격 `main`의 `29a325b`다. PR #65의 컬렉션 디자인·분류를 참고하되 시안의 가상 데이터·메모리 저장 코드를 앱 저장으로 옮기지 않았다. 독립 브랜치 `codex/collection-library`이며 PR #65를 먼저 병합할 필요는 없다. Local의 미푸시 작업 폴더는 접근하지 못하므로 원격 상태와 같다고 가정하지 않는다.

원격 조회에서 홈·탐색 PR #59/#60/#61, 회고 PR #64가 열려 있었다. 특히 #61은 `assets/life/ui.js`, 디자인 문서와 CI를 수정하므로 Local이 병합 순서에 맞춰 메뉴·관리 진입 및 서비스워커 번호를 대조해야 한다. 이 변경은 해당 PR을 임의 병합하지 않았다.

실제 앱 `index.html?section=records&view=collection` 및 `life.html?view=collection`에서 공용 인증을 거쳐 사용한다. 기록의 컬렉션 버튼, 관리의 컬렉션 백업·복구로 진입한다. 음악·책·영화·영상·글·예술 작품·도구·인물·장소·기타를 지원한다. 인물의 활동 분야를 작가로 기록하지 않는다. URL은 출처 링크이며 본문 확보를 뜻하지 않는다.

## 설계 결정

- 기존 동봉 idb, IndexedDB DB v1의 `meta` 저장소, 계정 소유권 검사와 원자 트랜잭션을 재사용한다. DB 버전·운영 SQL·인증 방식은 변경하지 않는다.
- `collection:<workspaceId>`에 독립 `life-collection-v1`을 저장한다. 읽기/쓰기는 고정된 로그인 계정과 작업공간 소유권을 요구한다. 이 데이터는 원문 bundle과 workbench 구성, 기존 동기화 업로드·백업·공개 사본에 들어가지 않는다.
- 새 자동 동기화/공개를 막으면서 전용 백업을 명확히 제공하는 선택이다. 향후 서버 동기화·내 페이지 연결에는 별도 계약이 필요하다. 장기적으로 통합 백업이 필요해지면 버전이 명시된 상위 형식으로 확장하고 기존 백업 의미를 바꾸지 않는다.
- 한 작업공간 최대 1,000개, 전체 UTF-8 2 MiB, 제목 500자, 메모 10,000자, 주제 12개. 용량·형식 오류는 기존 자료를 보존하며 거절한다. 미확인 연도는 자유 텍스트로 남긴다. 저장 허용 용량은 백업 파일의 외곽 형식까지 포함해 계산하므로 가득 채운 자료도 내보낼 수 있다.
- 이름/제목이 같아도 자동 합치지 않는다. 수정은 명시 저장이다. 저장 중 중복 제출을 막고, 실패 시 입력을 유지한다. 저장하지 않은 입력은 앱 이동·로그아웃을 막고 저장/취소로 돌아가게 한다. 새로고침 경고는 브라우저가 보장하지 않으며 초안의 자동 영속 보관 기능은 아니다.
- 독립 revision의 비교 후 쓰기로 낡은 탭의 덮어쓰기를 막는다. 충돌 시 최신 항목과 현재 입력을 비교하고 현재 입력을 새 사본으로 보관할 수 있다. 최신 변경도 그대로 유지한다. BroadcastChannel 알림은 개인 내용을 보내지 않는다.
- 보관은 목록 숨김이며 삭제가 아니다. 보관 목록에서 다시 표시할 수 있고 백업에도 포함된다. 영구 삭제 UI는 이번에 추가하지 않았다.
- 전용 `life-collection-backup-v1`은 항목·비공개 메모·보관 상태를 포함하며 계정/작업공간 연결·원문·발췌·다른 백업을 포함하지 않는다. 복구 전 개수와 제목을 검토하고 새 ID의 사본으로 추가한다. 기존 항목은 덮어쓰지 않으며 반복 복구는 사본을 추가한다. 검증과 한 번의 원자 저장 사이 revision이 달라지면 재확인을 요구한다.
- 조회가 늦어도 다른 화면으로 이동할 수 있다. 늦은 결과는 화면/작업공간 세대가 다르면 버린다. 조회 실패를 빈 보관함으로 표시하지 않는다.

## 화면과 시각 검수

PR #65의 검색 우선·가로 분류·자료 형태 구분을 기존 앱 프레임에 연결했다. 기존 공통 아이콘과 44px 조작을 재사용하고 새로고침은 구름 아이콘 대신 실제 동작에 맞는 도형을 사용했다. 한글 제목을 단어 단위로 줄바꿈하고 표지 안 요약은 말줄임하되 아래의 실제 제목을 보존한다. 40개씩 더 보기는 렌더링만 제한하며 검색은 전체 저장 항목을 대상으로 한다.

## 검증

[컬렉션 브라우저 결과](evidence/collection-library/report.json): 12개 사용 시나리오 통과. 실제 앱·동봉 SDK·실제 IndexedDB를 사용하며 Auth HTTP만 익명 모사한다. 등록/편집/재열기, 두 탭 충돌과 사본 보관, 트랜잭션 중단, 입력 보존·이동 차단, 보관·재표시, 다운로드·새 ID 복구, 잘못된/초과 용량 백업, 동일 프로젝트의 다른 계정 거절, 다른 작업공간 분리, 느린 조회의 화면 복귀 방지, 조회 재시도, 한글 composition 이벤트와 터치 모사를 확인했다. 원문 bundle과 workbench는 컬렉션 작업 전후 완전히 같았다.

1440·820·390px에서 14개 화면 상태의 조작 크기·입력 글자 크기·이름·대비·페이지 가로 넘침을 점검하고 별도로 스크린샷을 직접 검토했다. 로딩 화면 3개도 캡처했다. 측정한 텍스트 최소 대비 5.846:1. 컬렉션 페이지/콘솔 오류 및 예상 밖 외부 요청 0.

- Node 회귀: 404/404 통과, 신규 컬렉션 모델 검사 6개 포함.
- 홈·인증·공통 탐색: 13/13, 의도한 인증 실패 응답 1개 외 예기치 않은 오류 0.
- 기존 핵심 흐름: 5/5, 시각 상태 6개, 콘솔/페이지 오류 0.
- 기존 동기화: 14/14, 의도한 연결/스키마 오류 7개 외 예기치 않은 오류 0. 실제 운영 HTTP 검사가 아니다.
- 공개 산출물·PWA: 9/9. 오프라인의 열린 인증 세션에서 컬렉션 저장 후 온라인 재확인으로 재열기, v90 → v91 업데이트와 새 컬렉션 파일의 캐시 해시 일치를 확인했다. 의도한 연결/콜백 오류 3개 외 예기치 않은 오류 0. [로그](evidence/collection-library/platform-regression.log).
- 정적 검사: HTML 18 / JS 61 / 로컬 참조 280 / PWA 통과.

실제 Mac/iPad/iPhone, native IME, VoiceOver, Files와 개인 자료는 미검증이다. 가상 viewport와 합성 composition 이벤트를 실기 검증으로 표시하지 않는다. Cloud에서 운영 계정·SQL·실제 원격 자료에 접근하지 않았다.

## Local 실행 순서

1. `codex/collection-library`와 Local의 최신 코드를 비교한다. #59~#61을 먼저 병합했다면 컬렉션 메뉴·관리 진입·이동 보호를 유지하며 충돌을 해결한다. 서비스워커는 이 브랜치 v91이므로 이미 더 큰 번호가 배포되었다면 새 번호로 올린다.
2. `npm run check`, `npm test`; `python3 scripts/dev-server.py --port 4184` 뒤 `BASE_URL=http://127.0.0.1:4184 node tests/collection-library-browser.cjs`와 기존 공통 탐색 검사를 실행한다. Playwright는 `tests/browser-ci`의 고정 버전 또는 `PW_MODULE_PATH`를 사용한다.
3. 같은 컴퓨터에서 `/index.html?section=records&view=collection`을 열어 항목 추가·수정·새로고침·보관/복귀·백업·사본 복구를 체험한다. 컬렉션은 브라우저/계정/작업공간별이며 기기 간 이동은 이번 전용 파일로 한다.
4. SQL 설치·키 추가는 필요 없다. 병합·공개 배포는 Local에서만 수행한다. 배포 후 로그인 복귀, 새 캐시 파일, 기존 저장 자료와 컬렉션 재열기를 확인한다. 문서·시안·검증 샘플은 공개 산출물에 포함하지 않는다.
