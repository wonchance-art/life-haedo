# 자료 첫 표시와 동기화 속도 개선

2026-10-24 KST. 기준은 main `cef8e8b0f12d0fde733f4f718b459a977c159531`이다. 사용자가 자료를 불러오는 지연을 지적하고 전체 흐름의 속도 개선을 요청했다. 같은 합성 조건의 3회 중앙값에서 첫 자료 조작까지 **새 기기 14.76→6.02초, 같은 계정 재방문 8.21→0.78초**로 줄었다. 여러 공간의 전체 동기화 완료 확인은 더 늦어졌으므로 첫 사용 대기 감소와 구분한다. 이 문서는 초기 실행 계약, 최종 구현의 전후 측정·단위·브라우저·3폭 시각·PWA 보존 검수와 남은 측정 경계를 기록한다.

## 목표와 범위

**같은 계정으로 진입 → 자료 목록을 먼저 읽고 조작 → 최신 자료 수신 → 선택 원문·편집·다른 화면 왕복**을 빠르게 한다. 서버가 자료의 기준이고 IndexedDB는 계정별 캐시·영속 전송 대기·복구층이라는 [계정 자료실 계약](account-library.md)을 유지한다. 브라우저별 독립 보관 방식으로 돌아가지 않는다.

범위는 개인 홈·자료실의 첫 진입, 재방문, 여러 자료공간 수신, 자료 목록/검색, 관련 화면 전환의 실제 대기다. 인증·자료 초기화의 네트워크 순서와 정적 자산·DOM 구성 비용을 따로 측정한 뒤 확인된 병목을 고친다. 완성된 공개 글의 기존 익명 읽기 경로는 개인 저장소 초기화를 요구하지 않는 계약을 보존한다. 새 서버 렌더링 체계·프레임워크·자료 스키마·복제 엔진·분석 전송을 추가하는 작업은 아니다.

기준 코드의 `Shell.start()`는 계정을 확인하고, `build()`는 `AccountLibrary.bootstrap()`과 `UI.mount()` 뒤에 개인 화면을 드러낸다. `bootstrap()`은 계정 기능·기본 공간 확인과 카탈로그 수신, 여러 공간의 자료 및 구성/메타 동기화를 기다린다. 이 순서는 첫 화면에 필요하지 않은 대기도 앞에 놓을 수 있다. 코드 경로의 관찰이며, 실제 지연 시간과 가장 큰 병목은 별도 측정으로 판단한다.

## 화면·저장 보존

- 확인되지 않은 계정에서는 개인 DOM/저장소를 드러내지 않는다. 로그아웃·계정/세대 교체 뒤 늦은 조회·다운로드·인증 결과는 이전 내용을 다시 설치하거나 노출할 수 없다.
- 서버의 기본 공간이 없거나 카탈로그 일부가 실패했을 때 새 빈 자료실이나 삭제 성공으로 대체하지 않는다. 소유자 없는 자료·다른 계정 자료·복구 사본의 자동 편입 제외를 유지한다. 최초 전체 카탈로그 확인이 실패한 뒤, 카탈로그를 재조회하지 않은 부분 작업만 성공했다고 최초 대기/오류를 지우지 않는다.
- 원문 수신 뒤 정확한 참조를 검증한 구성/메타를 적용한다. 별도 CAS 영역 전체가 동시에 최신이라는 보장은 새로 만들지 않는다. 미완료·충돌·실패와 확인된 저장을 구분한다.
- 캐시 우선 표시 중에도 원문/불변 판·BOM/개행·해시·UTF-16 구간·폴더/묶음·영속 outbox·응답 유실의 같은 operation ID·양쪽 충돌 복구를 보존한다.
- 배경 결과가 들어와도 작성 중 값·한글 조합·선택 영역·초점·검색·폴더·읽던 위치·명시한 이전 판을 덮지 않는다. 배경 수신은 사용자가 고른 활성 공간을 옮기지 않는다. 캐시 표시 후 사용자가 같은 계정의 복구 사본으로 이동했다면 뒤늦은 초기화 완료가 기본 공간으로 되돌리지 않는다.
- 원본 ZIP은 기존 목록/열 때 바이트 수신과 무결성 검사를 유지한다. 속도를 이유로 원본을 재압축하거나 개인 데이터를 공개 캐시에 넣지 않는다.

기존 최소 상태 영역과 재시도 조작을 재사용한다. 오래된 캐시를 보여주는 동안 새 큰 안내 패널을 추가하거나, 실제 완료 전에 ‘동기화 완료’를 표시하지 않는다. 초기 안내/빈 화면의 표시 시간과 자료를 실제로 사용할 수 있는 시간은 별개다.

## 공식 근거와 기존 구현 재사용

다음 공식 문서는 2026-10-24에 확인했다. 문서의 일반 원칙을 현재 앱에 적용하는 판단과 실제 개선 측정은 구분한다.

- [MDN Performance API](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API): 관측 가능한 timing과 사용자 정의 구간을 함께 기록할 수 있다. 앱의 첫 자료 조작 시점은 문서 로드 완료와 별도 지표로 둔다.
- [MDN Navigation Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming): 문서 탐색의 구간 관측에 사용한다. 단일 탐색 timing을 SPA 내부의 모든 사용 흐름으로 확대하지 않는다.
- [MDN Long Task Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming): UI 스레드를 50ms 이상 차지한 작업을 관측할 수 있지만 지원 범위에 제한이 있다. 미지원 환경의 관측값 없음은 long task0을 뜻하지 않는다.
- [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control#stale-while-revalidate): 기존 내용을 보여주며 재검증하는 원칙을 참고한다. 이번 앱의 계정별 IndexedDB와 동기화 조정은 HTTP 캐시 지시어 자체가 아니며, 개인 응답을 공용 CDN/서비스워커 캐시에 넣는 근거로 쓰지 않는다.
- [Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser), [getSession](https://supabase.com/docs/reference/javascript/auth-getsession), [getClaims](https://supabase.com/docs/reference/javascript/auth-getclaims), [공식 변경 목록](https://supabase.com/changelog.md): 서버의 현재 사용자 확인·저장 세션 조회·JWT 서명 검증을 구분한다. 인증 담당의 현재 문서 확인과 실제 동봉 SDK 검토를 함께 따른다.

기존 [Supabase JS 2.117.2](../../vendor/supabase/README.md)(MIT)와 [idb 8.0.3](../../vendor/idb/README.md)(ISC), 기존 CAS·outbox·공개 읽기·native Performance API를 재사용한다. 이 버전 표기는 저장소에 고정된 배포본이며 최신 버전 주장이나 SDK 업그레이드 결정이 아니다. 이번에 필요한 것은 현재 초기화/조회 순서의 개선이므로 별도 상태 관리·캐시·복제 라이브러리를 추가하면 이전·계정 격리·오프라인 검수 부담이 커진다. 새 의존성 도입보다 기존 검증된 모델의 작은 순서 변경을 먼저 측정한다.

첫 자료 조작 가능 시점은 실제 DOM을 읽기 전용 `requestAnimationFrame` 관측으로 확인한 값이다. 요청 수의 집계 경계는 Node가 첫 표시를 확인한 시점이므로 polling 확인의 관측 지연이 포함될 수 있으며, 정확한 rAF 시점 이전 요청 수와 같다고 간주하지 않는다. 전체 동기화 확인 시점은 앞선 검색·복귀·CDP snapshot을 마친 뒤 Node에서 세 공간의 상태를 확인한 시점이며, 서버 완료 순간을 연속 측정한 값이 아니다.

**개선한 것은 첫 자료를 읽고 사용할 때까지의 대기다.** 두 조건 모두 세 공간의 동기화 완료 확인은 뒤로 늦어졌다. 선택 공간 준비 후 전체 재확인이 이어지고 화면 사용과 겹치지만, 그 각각의 지연 기여를 분해해 측정하지는 않았다. 전체 동기화가 빨라졌다고 주장하거나 위 관측을 그 개선율로 바꾸지 않는다. 마지막 원문 검색도 새 기기에서는 줄고 재방문에서는 늘었으므로 전체 검색 성능이 좋아졌다고 일반화하지 않는다.

이 수치는 합성 지연 조건의 실험값이며 실제 사용자·기기·회선의 성능 보장이 아니다. Playwright의 요청 라우팅은 HTTP 캐시를 끄므로 **warm은 계정 자료 IDB 재사용만 뜻하고 정적 파일 HTTP 캐시의 재사용은 뜻하지 않는다.** 각각 여섯 탐색에서 정적 응답 999건·고유 자원 165개를 관측했다. 고유 응답의 압축 해제 후 바이트는 5,914,475→5,924,015로 소폭 늘었으므로 파일/전송량 감소로 보고하지 않는다. 최종 검사에서는 long task 관측 지원을 명시적으로 확인했으며, 미지원/관측 없음의 0값을 만들어내지 않는다. CDP의 원시 CPU 계수는 검색 이후 읽은 누적 snapshot이므로 해당 탐색만의 CPU 비용 전후 비교로 사용하지 않는다.

### 인증의 겹친 요청 공유

동일 epoch·uid·정확한 access token에 대해 아직 진행 중인 `getUser()`만 공유하도록 구현했다. 성공·실패가 종료되거나 계정 확인 범위가 바뀌면 공유 상태를 폐기한다. 각 호출자의 세션 전후 확인과 epoch/uid guard, 새로운 호출의 서버 검증은 유지한다(2026-11-02 W4 예외: 한 작업 범위 안의 다음 호출은 끝난 확인을 다시 쓴다. 아래 W4 절). 이 변경의 `platform-auth` 30개와 `platform-life-remote` 13개 검사는 통과했고 독립 검토도 완료했다. 집중 검사는 전체 회귀와 합산하지 않는다.

고정 기준 Auth와 후보 Auth를 같은 동봉 SDK·격리된 Node VM·합성 세션/HTTP에서 대조했다. 동시에 겹친 `verify()` 3회의 `/auth/v1/user` 요청은 **3회 → 1회**였고, 그 검증이 끝난 뒤 다음 호출은 기준·후보 모두 서버에 **새 요청 1회**를 보냈다. 실제 SDK의 요청 수를 비교한 결과이며 실브라우저·전체 시작 시간·운영 지연의 결과가 아니다. 순차 shell/bootstrap/remote 검증은 유지하며 SDK의 내부 세션 잠금으로 늦게 들어온 호출까지 공유된다고 주장하지 않는다.

근거는 `.local/startup-performance-20261024/auth/sdk-comparison.json`(SHA-256 `197bb17e576ee959b3bde98225cfe8890aaa9f3d315beb904525ce578267c1f5`)과 같은 폴더의 `implementation-receipt.json`, `.local/startup-performance-20261024/review/auth-independent-review.json`이다. 해당 Auth SHA-256은 `d68a701895ca99ad5703369a489876dc6868dc011ed01811036aff722d8050b8`이며 최종 통합 소스의 시작 성능과 보존 검수 결과는 위 전후 측정 및 아래 브라우저 기록으로 구분한다.

### 작업 범위의 계정 확인 (W4, 2026-11-02 소유자 승인)

[기능별 작업 계약](../agents/feature-contracts.md)의 2026-10-24 결정("완료된 검증 결과를 재사용하지 않는다")을 한 작업 범위 안에서만 바꾼다. 근거는 성능 점검 W4다. 새 기기 첫 열기에서 화면 전 개인 요청의 대부분이 `/auth/v1/user`였고, 그 대부분은 `sync.js` 한 주기의 확인 3회(주기 시작, `head` 자체 확인, `head` 뒤 확인)였다.

- `HaedoAuth.verificationScope()`는 범위 하나를 연다. 그 범위 안에서 끝난 서버 확인을 다시 쓰는 조건은 다음과 같다.
  - 연 epoch과 같다.
  - 그 뒤 SDK Auth 이벤트(종류 무관), 취소·계정 전환, pagehide/pageshow, 다른 탭의 세션·로그아웃 저장소 변경이 없다.
  - 저장 세션의 사용자와 access token이 확인 때와 같다.
  - 로그아웃 표시가 없고 bfcache에 머문 상태가 아니다.
- 그 밖의 경우는 기존 `verify()`를 그대로 실행한다. 범위가 끝났을 때, 확인이 실패했거나 null일 때, `fresh: true`일 때도 같다. 오류·재시도·늦은 응답 보호는 바뀌지 않는다.
- 시간 기준 재사용은 없다. 범위는 `sync.js`의 한 작업(주기·연결·내려받기·기존 공간 채택)이며 작업이 끝나면 버린다.
- 서버 쪽 세션 철회는 작업 단위로 감지한다. 한 작업 안의 읽기는 철회 뒤에도 그 작업이 끝날 때까지 이어질 수 있다. 다음 작업의 첫 확인에서 멈춘다.
- `life_sync_put`(서버 스냅샷 덮어쓰기)과 충돌 선택(`resolve`)은 범위 안에서도 서버에서 확인한다. 블로그·공개·삭제·자료실·구성·원본 어댑터의 호출마다 확인은 바꾸지 않았다.

격리 Chromium 모바일 모사(390폭·CPU 4배·Fast 4G·개인 HTTP 165 ms)에서 가짜 서버로 측정했다. 원문 60개 공간 1개와 글 6편을 쓰고 새 기기로 열었다. 실제 기기나 운영 Supabase 값이 아니다.

### 페이지 열기의 계정 확인과 글 받기 (2026-11-03)

소유자 지시("딜레이 줄이는 최적화 작업 우선")로 위의 남은 비용 가운데 두 가지를 줄였다.

- **페이지 열기 범위:** `HaedoAuth.beginStartup()`이 shell 확인 → 계정 자료 우선 초기화 → 첫 mount를 한 작업 범위로 묶는다.
  - 화면을 보이거나 열기에 실패하면 shell이 범위를 끝낸다.
  - 시간 상한은 `STARTUP_LIMIT_MS`(10초, 첫 화면 목표 수준)다. 초기화나 mount가 멈춰도 그 뒤의 호출은 서버에서 확인한다.
  - 범위의 끝난 확인을 다시 쓰는 곳은 다음뿐이다:
    - shell 확인: `verify({ startup: true })`, `requireUser({ startup: true })`
    - AccountLibrary의 작업 시작 확인(우선 초기화, 그리고 범위 안에 시작된 `reconcile`)
    - 빌린 클라이언트의 `getStartupUser()`: 자료실 기능·카탈로그·메타 읽기, 구성 읽기, 원문 계정 읽기
    - W4 범위의 첫 확인
  - 조건은 W4와 같다(같은 epoch, Auth 이벤트·취소·pagehide 없음, 같은 사용자·access token, 로그아웃 표시 없음, bfcache 아님).
  - 예외는 문서의 첫 `pageshow`(bfcache 복귀가 아님) 하나다. 숨은 기간이 없어서, 그 전에 끝낸 확인을 범위 안에서 유지한다. W4 범위의 결과는 그대로 버린다.
  - **겹친 호출:** 같은 epoch·세대에서 시작해 아직 진행 중인 확인 하나를 기다린다.
    - 그 답은 진행 중인 `getUser()` 공유(2026-10-24)와 같이 쓴다. 기다리는 동안 계정·세대가 바뀌지 않았다면, 범위가 그 사이 끝났어도 쓴다.
    - 계정 전환 뒤의 호출은 이전 계정의 진행 중 확인을 기다리지 않는다.
  - **계속 서버에서 확인하는 것:**
    - 쓰기(구성·메타 저장, 블로그 저장·공개·삭제, `life_sync_put`·`resolve`)
    - `life_library_open`(첫 자료실을 만들 수 있다)
    - BlogSync 주기(받기와 올리기 모두), `fresh` 확인, 옵션 없는 `verify()`
- **글 받기:** BlogSync 수신은 저장한 글 먼저, 그 안에서 작성 시각이 최신인 글부터 4개씩 받는다.
  - 사진 원본과 HEIC 보기용 JPEG는 모든 글이 함께 쓰는 6개 전송 한도 안에서 동시에 받는다.
  - 받는 중인 글의 사진 바이트 합(원본+보기용)이 160 MB를 넘으면 다음 글은 기다린다. 이 상한보다 큰 글 하나는 혼자 받는다.
    - 이 예산으로 iPhone의 최악 보유량을 묶는다. 글 하나에 사진 20장, 256 MB까지 담길 수 있다.
    - 글의 전송은 모두 끝난 뒤에야 실패로 처리하므로, 예산을 일찍 돌려주지 않는다.
  - 받은 파일의 형식·크기·digest 확인(`Blog.hydrate`)과 원본·보기용 보관 규칙은 바꾸지 않았다.
  - 올리기 동시성(2)은 그대로다.

### 원문 head 중복·공간 순차 수신·글 목록 (2026-11-04)

소유자가 연 최적화 전용 세션이 총괄 지시서(범위 1)에 따라 위의 남은 비용을 줄였다. 동기화 계약(CAS·정확 원문·영수증·복구 사본·늦은 응답·계정 전환)은 바꾸지 않았다.

- **원문 head(`composition-sync.js`, 구성·자료 메타 공통 엔진):** 동기화 한 번(`run`, enable에서 이어진 경우 포함)은 원문 head를 한 번 확인한다.
  - 같은 동기화의 뒤 확인(행의 `source_revision`)은 저장된 원문 상태가 `synced`이고 필요한 판 이상이면 서버를 다시 부르지 않는다. 아니면 이전처럼 head를 확인한다. 더 새 서버 원문까지 요구하지 않고, 행이 요구하는 판 이상만 요구한다.
  - 저장된 원문 상태는 늦을 수 있다. 자료 기기 이동 설치가 bundle 판을 올리면서 `sync:` 상태를 고치지 않는다(독립 검수 M1). 이때 storage가 `composition_source_pending`으로 거절하면 head를 한 번 더 확인하고 다시 시도한다. 두 번째 거절은 이전처럼 오류로 남는다.
  - compare·resolve 자체의 확인은 매번 서버에 묻는다. storage(`checkCompositionRow`·첫 채택 검사)와 서버 RPC의 `source_revision` 검사는 그대로다.
  - 엔진마다 원문 head는 enable(첫 연결) 경로에서 3회 → 1회, 이미 켜진 동기화에서 2회 → 1회로 줄었다. 자료실 자신의 head 1회는 그대로다. 두 엔진의 head는 원문 엔진에서 차례로 돈다.
- **공간 수신(`account-library.js` `receiveAndSend`):** 카탈로그 내려받기와 공간별 동기화를 2개까지 동시에 한다.
  - 공간마다 원문 → 구성·메타 순서는 그대로다. 엔진 잠금은 공간별이고, 내려받기는 `activate:false`라 활성 공간을 바꾸지 않는다.
  - 첫 실패 뒤에는 새 공간을 시작하지 않는다. 시작한 공간이 끝난 뒤 첫 오류를 낸다.
  - 상한 2는 iPhone 메모리를 고려한 값이다. 공간 묶음 전체가 메모리에 올라온다.
- **글 목록(`blog-sync.js` `cycle`):** 주기의 서버 글 목록(`life_blog_sync_list`)을 계정 확인과 함께 요청한다.
  - 확인이 통과한 뒤에만 읽는다. 그 주기에 서버로 보낸 것(삭제·중복 정리·올리기·복구 사본)이 있으면 이전 자리에서 다시 요청한다.
  - 목록 행은 힌트일 뿐이다. 설치·적용·사라짐 판단은 각자 정확한 서버 행을 다시 읽는다.
  - 주기의 계정 확인은 계속 서버에 묻는다(PR183 검수 결정 유지). BlogSync를 mount 전에 시작하는 순서 변경은 하지 않았다.
- **대기 전송:** 자리를 기다리던 사진 전송은 dispose·계정 전환 뒤 시작하지 않는다. 이미 시작한 전송(최대 6개)은 끝까지 받고 버린다. 진행 중 전송을 끊는 AbortController는 SDK 내려받기 신호 지원을 확인한 뒤의 후속으로 남긴다.
- **W4와 10초 상한:** 상한은 열기 범위에만 걸린다. 열기 안에서 시작한 W4 범위가 첫 확인으로 열기의 답을 받았다면, 그 범위는 자기 작업이 끝날 때까지 W4 조건으로 그 답을 계속 쓴다.

### CPU 시간 귀속과 상위 비용 (2026-11-04)

PR185 뒤에도 CPU 4배 조건의 20행 시간은 줄지 않았다. 원인을 추측하지 않고 먼저 쟀다(총괄 지시서 제안 1).

- **측정 방법:** `HOME_PERF_PROFILE=1`(기본·CI 꺼짐)
  - cold 측정 동안 Chromium 트레이스와 V8 CPU 샘플을 받는다.
  - 메인 스레드 시간을 셸 전, 셸→20행 구간으로 나눈다.
  - `HOME_PERF_PROFILE_SAVE=1`이면 원본 트레이스(gzip)를 남긴다.
  - 프로파일러 자체 부하로 절대 시간은 늘어난다. 그래서 비율만 보고, 시간 비교는 프로파일 없는 실행으로 한다.
- **메인 스레드는 거의 포화 상태다(CPU 4배, `884a84b`).**
  - 셸 전: 15.8초 중 14.2초(90%)
  - 셸→20행: 22.8초 중 22.4초(98%)
  - 50ms를 넘는 long task는 그중 일부(약 25%)다. 나머지는 짧은 작업이 이어진 것이다.
  - 트레이스로 보면 IndexedDB·fetch 응답(IPC) 처리 안의 JS가 가장 크다.

V8 샘플의 구간별 비중이다(셸 전 / 셸→20행).

**수정**

- **`core.js` `utf8Length`**
  - `validateText`는 본문마다 `new TextEncoder().encode(text)`로 전체 바이트를 만들어 길이만 봤다.
  - 이제 대리 문자 검사 반복 안에서 UTF-8 바이트 수를 센다. 짝 없는 대리 문자는 이전처럼 거절한다.
  - 다음 조건에서 `TextEncoder`와 같은지 검사로 고정했다.
    - 고정 시드 무작위 문자열 2만 건
    - 0x7F/0x7FF/0xFFFF 경계, 대리 문자 쌍, 빈 문자열
    - 실제 상수 기준 1 MiB ±1바이트(1·2·3·4바이트 문자와 혼합 본문)
- **`home.js` `HomeUI.dateLabels`**
  - 글 한 줄마다 만들던 `Intl.DateTimeFormat` 2개를 재사용한다.
  - 서울·UTC·LA·오클랜드 시간대에서 날짜·연도 경계를 포함해 이전 문자열과 같은지 검사한다.
- **측정 도구:** `getAnimations()`를 목록 준비 뒤에만 부른다(`motionEnd`에 필요한 구간).
  - 매 프레임 호출이 CPU 4배에서 셸→20행 메인 스레드의 약 12%를 써서, 측정하는 대상을 늦췄다.
  - 아래 전후 비교는 수정 전과 수정 후 모두 이 판으로 다시 쟀다. 이전 표(PR183·185)의 숫자와 섞지 않는다.
  - 보고서의 `animationsSeen`도 의미가 바뀌었다. 지금은 목록 준비 뒤에 동시에 돈 애니메이션 수의 최댓값이다. 이전에는 셸이 뜬 뒤부터 쟀으므로 PR183·185의 값과 비교할 수 없다.
- **진행 중 사진 전송 중단(`blog-remote.js`):** 계정 전환이나 dispose 때 `cancel()`이 진행 중 내려받기도 abort한다.

### 저장소 상태 읽기 축소 시도 (2026-11-04, 대부분 채택하지 않음)

### 계정 자료 초기화의 경계

초기화는 새 `bootstrap({ foreground: true })` 선택 경로로 분리하고, 인자를 생략한 기존 `bootstrap()`의 전체 수신 장벽은 유지했다. shell이 이 선택 경로를 호출하고 실제 화면을 mount/reveal한 뒤 명시적으로 `reconcile()`을 시작한다.

- **재방문:** 새 서버 계정 검증 후 scoped storage의 적격한 활성 공간을 읽는다. source와 LibraryMeta의 project/user/remoteId 연결 및 양의 안전한 원격 revision을 확인한 경우에만 캐시를 먼저 제시한다. 이때 현재 서버 최신성은 확인되지 않았으므로 `catalogPending`을 유지한다.
- **새 기기:** 기능 지원·동기화 계정·실제 기본 공간을 확인하고 선택한 한 공간의 원문→구성/메타 준비를 우선한다. 전체 카탈로그·다른 공간·원본 목록의 준비는 화면 표시 후 재개한다. 도중 storage/focus/timer 이벤트가 첫 표시 전에 이 배경 작업을 시작하지 않게 한다.
- **실패·변경:** 전체 카탈로그 실패 뒤에는 부분 동기화 요청도 카탈로그를 다시 확인한다. 캐시 표시 후 같은 소유자의 복구 사본으로 옮긴 선택을 유지하고 해당 사본을 자동 등록하지 않는다. 이미 계정 캐시를 제시한 뒤 capability1이 capability0으로 바뀌면 로컬 전용으로 조용히 전환하지 않고 확인 실패를 남긴다. 인증 실패 전에 개인 캐시를 먼저 읽지 않는다.

기존 계정 브라우저 회귀의 첫 실행에서 원본 ZIP 검사 1개가 실패했다. 빨라진 첫 화면에서 원본 메뉴를 열면 공유 원본 서비스가 준비되기 전에 별도 fallback 객체가 만들어지는 경합이었다. 테스트의 기존 assertion을 바꾸거나 기다림을 덧붙이지 않고 제품 초기화 순서를 보완했다. 서버 계정 검증과 적격 캐시 또는 capability1 확인 뒤 공유 서비스 객체를 먼저 생성·구독한다. 이 준비 자체는 HTTP/IDB 작업을 시작하지 않는다. 사용자가 원본 메뉴를 열거나 배경 수신이 끝날 때 같은 서비스에서 실제 작업을 시작하며, 시작 실패 뒤 재시도에도 객체 identity를 유지한다. 실패한 구독의 부분 객체는 정리한다.

최종 초기화 단위 **24개**, source/storage/remote/composition/meta 관련 회귀 **113개**와 독립 검토를 통과했다. 처음 발견한 카탈로그 대기·복구 사본 선택 문제와 원본 서비스 경합은 각각 회귀로 검증했다. 근거는 `.local/startup-performance-20261024/library/originals-unit-attempt1.log`, `originals-domain-regression.log`, `originals-correction-receipt.json` 및 `review/originals-foreground-independent-review.json`(SHA-256 `bc2211f95c141b43ac504202576d4025f9a929a22a4814331b1ce14d9cbfc896`)이다. 최종 `account-library.js` SHA-256은 `c39bfc46493725ba58bc54b1b10950a393de315d578ee3fd2197d045822f663b`다. 이전 후보의 20/109 검사·검토·실패 보고서도 보존하며 최종 결과와 합산하지 않는다.

### 화면 표시·목록 갱신 통합

shell만 우선 표시 옵션을 사용하고, mount/reveal 뒤에도 현재 인스턴스·세대·계정 coordinator를 확인한 후 배경 수신을 시작하도록 연결했다. 자동 자료 갱신은 입력 세대·편집/dirty 상태·현재 공간·화면·표시 상태·초점을 확인한 뒤 bundle/stage를 상태에 대입한다. 처음 검토에서 상태를 대입한 뒤 확인하던 경로를 교정했으며, 명시 저장·이동의 기존 `flush` 계약은 유지한다.

배경에서 받은 다른 자료공간은 현재 native select를 교체하지 않고 옵션을 갱신한다. 선택값을 유지하고 조작에 초점이 있으면 blur 뒤에 옵션을 반영한다. 화면을 연 뒤 자료공간 목록을 쓰는 경로들은 요청 순서와 마지막으로 수용한 순서를 공유해, 오래된 자동 조회나 복원 조회가 더 새 목록을 되돌리지 않게 했다. 거부된 자동 조회가 유효한 다른 목록 결과를 무효화하지 않도록 구분한다.

빈 검색의 카드 발췌 목록은 같은 갱신에서 이미 계산한 결과를 재사용한다. 폴더 필터는 필요한 폴더 메타데이터만 가져오고, 필터가 전체인 경우 불필요한 전체 snapshot 복사를 생략한다. 기존의 전체 `getSnapshot()` 계약·원문·검색 의미는 유지한다. 서비스워커 등록은 중복을 억제하고 첫 진입 결과를 표시할 기회 이후로 미뤘으며, 셸 버전은 161→162로 올렸다.

이 shell/UI/PWA 변경과 신규 단계별 브라우저 검사 소스는 독립 검토를 통과했다. 근거는 `.local/startup-performance-20261024/review/shell-ui-independent-review.json`과 원본 서비스 보완 검토다. 최종 고정 소스의 전체 단위 **1,498개**, 정적 **22 HTML·169 JS·714참조**는 모두 통과했다. 근거는 `unit-final.log`, `check-final2.log`다. 집중 검사 수와 이전 후보의 검사 수를 여기에 합산하지 않는다.

### 첫 표시·배경 수신의 브라우저 보존 검수

최종 검사기 SHA-256 `4e32a4d8869f211fb1f438d828a06d18cb5b7bf6b0369a953b49bfb22678bbc1`로 실제 SDK·계정별 IDB·명시적으로 멈추고 해제하는 익명 HTTP를 사용한 **5개** 흐름을 통과했다. 구조 검사의 고정 HTTP 지연은 0ms이며, 성능 측정의 요청당 100ms 조건과 구분한다.

3. 최신 판이 배경에서 도착해도 사용자가 읽던 정확한 이전 판을 유지한다.
4. 배경 조회 실패 때 기존 자료를 유지하고, 명시 재시도 뒤 계정 상태를 확인할 수 있다.

### 출시 기록과 남은 측정

최종 전후 성능과 보존 검수는 위 결과로 확정했다. PR/main CI와 실제 배포 산출물·공개 응답 확인은 이번 변경 PR 본문에 완료한 근거로 기록한다. 이전 릴리스의 검사 수나 배포 성공을 이번 변경의 결과로 합산하지 않는다.

남은 성능 과제는 전체 배경 동기화 완료까지의 중복 조회와 스케줄 비용을 따로 측정하고, 큰 자료 검색의 조건별 편차를 좁히는 것이다. 실제 기기·회선의 계정 재방문과 변경 자료 수신도 별도 검수가 필요하다. 이번의 첫 사용 개선 수치를 전체 동기화·모든 검색·현장 성능의 완료로 확대하지 않는다.
