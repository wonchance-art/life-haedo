# 네이버 원문 판과 사진의 기기 간 복구

2026-10-29 KST. 같은 계정의 A에서 보관한 원문의 정확한 판과 사진을 B에서 이어 읽는다. 같은 본문이어도 사진이 다르면 서로 다른 판이며 본문 해시·제목·최신 수집 결과로 사진을 추정하지 않는다.

## 실행 범위와 보존

- 계정별 `(workspaceId, sourceId, sourceVersionId)`에서 `(captureId, captureHash)`로 가는 불변 연결을 별도로 보관한다. 기존 자료·구성·분류 metadata v1과 capabilities 응답은 바꾸지 않는다.
- A의 원문·사진 sidecar·연결 전송 대기는 같은 IndexedDB 트랜잭션에 보관한다. 기존 원문 동기화의 서버 ACK 이후에만 연결을 등록한다. 등록 응답 유실은 같은 불변 값으로 재시도하며 구기기의 기존 원문 저장은 연결을 삭제하지 않는다.
- 서버는 소유자·정확 원문 판·네이버 글 식별자·본문과 해시·형식·확보 범위·수집 해시를 검증한다. 다른 연결로 덮어쓰기와 다른 계정 접근은 거절한다.
- B는 현재 연 정확 원문 판의 연결만 조회하고 사진을 지연 다운로드한다. 실제 바이트·SHA·디코딩된 픽셀을 기존 NaverMedia로 검증하고 사진 sidecar와 확인된 연결만 원자 설치한다. 원문 revision·과거 인용·UTF-16 범위를 바꾸거나 새 Core 판을 생성하지 않는다.
- 로컬의 검증된 사진은 먼저 표시한다. 서버 연결 확인과 재시도는 본문 읽기·선택·검색 복귀를 막지 않는다. 미확인·오프라인/통신 실패·무결성 오류를 구분하며 최신 사진으로 대체하지 않는다.
- 기존 sidecar는 원래 소유자·서버 판과 해시를 재확인한 뒤 등록한다. 영수증이 없는 본문만으로 새 연결을 생성하지 않는다. `localOnly` ZIP은 새 식별자의 독립 사본이며 서버 연결을 승계하거나 업로드하지 않는다.
- 전용 원문·사진 ZIP, 선택 사진 글쓰기와 일반 JSON/근거 ZIP의 기존 포함 범위를 유지한다. 실제 네이버 수집·예약 실행·HEIC 지원은 이 작업의 완료로 간주하지 않는다.

## 검수와 출시

같은 본문·다른 사진의 두 원문 판을 독립 A/B 저장소에서 각각 복구하고 원문·옛 인용·사진 바이트/픽셀·순서를 비교한다. 원문/연결 선후 도착, 유실 ACK, 중복·동시 수신, 부분 다운로드·손상, 계정/공간/화면 전환 중 늦은 응답, 로컬 ZIP 복원과 파일 재보관을 검수한다. 정상 경로만 통과해 출시하지 않으며 정확한 소스·실패·교정·CI/배포 결과를 연결 PR에 기록한다. 실제 Apple 기기·소유자 브라우저·네이버 공개 응답의 관찰은 합성 SDK/IDB·격리 SQL 검수와 구분한다.

최종 로컬 코드에서 Node22 단위 1,572개·정적22 HTML/173 JS/726참조, 독립 A/B Chromium 8개 여정, 기존 Obsidian 연결/정확 복귀6개와 사진 상태 회귀, 실제 PostgreSQL17 21개 및 동시 두 세션을 통과했다. 실제 v164→v165 준비 사이트 PWA9개에서 기존 자료·설정·오프라인 편집과 계정 격리를 확인했고 입력197개 SHA가 전후 동일했다. 390/1440px의 정상/사진 다운로드 오류/연결 등록 오류6장을 직접 확인했다.

회귀 검수에서 비동기 사진 준비 뒤 원래 버튼으로 초점이 복귀하지 않는 제품 결함과 두 오류 상태의 버튼 겹침을 발견해 교정했다. 기존 selector·단언·20초 제한을 유지했고 오류 버튼 간격8px 이상·포인터 도달, 사용자의 키보드/포인터/스크롤 뒤 지연 응답이 초점을 빼앗지 않는지 확인했다. 검사 도구의 read 요청 sourceId 가정·새 계정 준비 대기·존재하지 않는 계측 함수도 원래 실패와 구분해 교정했다. 백그라운드 영수증 확인은 사진 Blob/문서를 모두 물질화하지 않고 해당 키만 조회한다.

정확한 PR/main CI·공개 사이트 반영은 연결 PR의 출시 기록으로 확정한다. 로컬 자동 검사와 실제 소유자 기기의 사진·네이버 upstream 성공은 별개다.
