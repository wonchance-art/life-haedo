# 같은 작성기의 첨부·보관·사진 읽기와 파일 재사용

2026-10-15 KST. `codex/blog-editor-flow`의 `4e7e474` 위 후속. 사용자 장면은 “여행 문장을 쓰면서 사진·읽은 책·다녀온 장소를 붙이고, 미완성 글을 따로 두었다가 다시 읽고 파일로 보관하기”다. [대표 편집기 비교](blog-editor-comparison.md)와 [기본 작성 흐름](blog-editor-flow.md)을 이어간다. 새 서버·SQL·라이브러리·자동 전송은 추가하지 않았다.

## 이번 범위와 선택

본문/사진 편집기를 유지하고 기존 CollectionPicker·PagePosts의 첨부 검증/투영·PagePostsView의 카드를 연결했다. 여러 작성기 사이에서 새 글을 옮기거나 컬렉션에 먼저 등록할 필요가 없다. 대상은 본문 뒤 카드이며 자유 배치 블록은 아니다. 엔진 교체보다 현재 저장본과 실패 복구를 유지하는 작은 어댑터가 이 장면에 적합하다. [재사용 근거](../life-tools-design/open-source-review.md).

- **같은 글에 대상 첨부.** `음악·책·대상 붙이기`에서 기존 컬렉션·명시적 외부 검색·직접 입력을 사용한다. 종류·제목·창작자·출처만 최대 12개 복사한다. 개인 메모·태그는 가져오지 않는다. 직접 입력/외부 후보는 확인 후 반영하고, 카드 수정·위/아래·빼기는 이 글의 사본에만 적용한다. 미반영 입력이나 한글 조합이 있으면 저장/이동/내보내기를 막고 같은 폼/본문을 보존한다. 이미 반영된 본문은 로컬 자동 저장을 계속할 수 있다.
- **초안과 보관함.** 공통 피드에는 저장한 활성 글만 놓고 `초안 N · 보관함 N` 안에서 미완성/보관 글을 구분한다. 완전히 빈 활성 초안은 새 글을 시작할 때 재사용한다. 보관·복원은 삭제가 아닌 명시적 상태 변경이고, 원본 파일과 문서는 200개 한도에 계속 포함된다. 보관 글은 일반 피드와 통합 검색에서 빠지며 목록으로 복원할 수 있다. `사본으로 이어 쓰기`는 새 ID의 독립 초안을 만든다.
- **연속 원본 보기.** 읽기의 사진을 열면 문서 순서대로 이전/다음·위치·해상도·현재 사진 원본 다운로드를 제공한다. 맞춤 보기에서는 좌우 방향키로 이동하고 원본 크기에서는 사진 스크롤을 유지한다. 원본 크기 설정은 다음 사진에도 이어진다. Escape/닫기 후 마지막으로 본 사진에 초점을 돌리고 이미지 교체/닫기 때 해당 Object URL을 해제한다.
- **원본 포함 HTML 읽기 파일.** `더 보기 → HTML 읽기 파일 받기`는 본문·설명·대체 텍스트·출처 카드와 원본 이미지 바이트를 단일 UTF-8 HTML에 담는다. 별도 사진 폴더나 앱 로그인 없이 읽는다. 이미지를 재인코딩하지 않고 data URL로 담으며 스크립트/앱 버튼/blob URL을 넣지 않는다. CSP·no-referrer와 검증한 링크를 사용하고 외부 이미지/미디어를 자동 요청하지 않는다. 원출처 링크는 사용자가 직접 연다. HTML은 읽기용이고 다시 편집할 복원은 ZIP을 사용한다.

좁은 읽기 화면에서 `더 보기`의 우측 정렬 팝업이 왼쪽 화면 밖으로 밀리는 실제 클릭 실패를 발견했다. 읽기 메뉴는 문서 흐름 안에서 펼치도록 고쳤다. 편집기의 상단 저장 도구와 본문은 그대로 유지한다.

## 형식·보존·복구 계약

`life-photo-post-v2`는 기존 제한 Delta/원본 Blob에 검증된 `attachments`와 boolean `archived`를 더한다. v1 문서는 읽기만으로 저장/변환하지 않는다. 편집·사본·보관 같은 명시 동작 시 메모리에서 승격한다. 저장소는 v2를 v1로 덮어쓰는 구형 클라이언트를 차단한다. 본문·첨부·상태의 문서와 검색 요약은 같은 계정/작업공간 CAS 트랜잭션에서 저장한다. 보관 실패는 읽기 DOM/기존 문서/요약을 그대로 남기고 재시도할 수 있다. 다른 탭이 원본을 보관한 뒤 예전 수정본으로 저장하면 revision 충돌이 나고 새 글로 보존할 수 있다.

ZIP v1은 기존 manifest로 계속 내보내고 읽는다. ZIP v2는 첨부를 추가하며 기존 원본 바이트/해시/경로/크기 검증을 유지한다. 어느 ZIP이든 복원 전 제목·사진/첨부 수·카드를 확인하고 **새 ID의 비공개 미보관 초안**으로 설치한다. 문서/사진 ID를 재매핑하고 원본을 덮어쓰거나 보관 상태를 자동 재현하지 않는다. 일반 JSON 백업·기존 `page.posts`·일반 원천 글쓰기·구성 동기화·공개 사본은 이 형식을 자동 포함/변환하지 않는다.

HTML/ZIP 생성 중에는 조작과 이동을 보호하고, 완료 직전에 현재 계정/작업공간/문서 수명을 다시 확인한다. IDB 저장 실패가 있더라도 유효한 현재 입력은 파일로 보관할 수 있다. 첨부 검토가 미반영이면 먼저 반영/취소해야 한다. 최대 사진/파일 크기 등 기존 제한은 바꾸지 않았다.

## 한계와 다음 판단

Mac/iPad/iPhone 실기의 한글 키보드·Photos/Files·VoiceOver·소프트 키보드·회전·분할 화면은 미검증이다. 화면 폭 모사는 Apple 실사용을 증명하지 않는다. JPEG/PNG/WebP는 OS에서 전달받은 파일 바이트를 보존한다. HEIC 자동 변환·클라우드 사진 저장·기기 간 자동 동기화·공개 게시·나란히 사진 배치는 구현하지 않았다.

단일 HTML은 이미지 base64 때문에 원본보다 파일이 커지며 전체 256MiB 한도를 채운 모바일 메모리는 측정하지 않았다. 사용자의 소량 첨부 장면에서 먼저 체험하고, 실제 Files 저장/재열기 부담이나 큰 파일 메모리 문제가 확인되면 별도 사진 폴더를 포함한 읽기 ZIP/출력 한도 안내를 비교한다. 실제 Apple 검증은 Local에서 익명 사진 2장과 한글 설명으로 작성→Files ZIP/HTML 저장→재열기→복원을 확인할 때 진행한다. 엔진 교체는 IME/history/블록 배치에서 반복 재현되는 실패와 대체 엔진 실험의 개선이 확인될 때 다시 판단한다.

## 직접 확인과 Local 인계

`npm run dev` 후 `http://127.0.0.1:4173/index.html?section=records&view=page`에서 로그인한 내 페이지를 연다. 개발 서버는 Ctrl+C로 종료한다. `글쓰기 → 문장/사진 → 음악·책·대상 붙이기 → 첨부 검토 → 글 저장`을 따라가면 같은 읽기 글에 원본 사진과 대상 카드가 함께 나타난다. 사진을 열어 다음/이전·원본 다운로드를 확인하고 `더 보기`에서 HTML 읽기 파일/ZIP을 따로 받는다. 보관함으로 옮긴 뒤 접힌 목록에서 열어 복원하고, ZIP은 확인 화면을 거쳐 새 초안으로 복원한다.

이 작업은 #91 위의 후속 브랜치이며 운영 배포가 아니다. Local은 선행 PR 순서와 실제 Apple 체험을 확인한 뒤 병합·배포를 진행한다. 새 SQL 설치나 인증 변경은 없다. 자동 공개/원격 업로드를 추가하지 않았고, 실행 중인 실제 사용자 저장소를 샘플로 바꾸지 않았다.
