# 내 페이지에서 작성 → 첨부 → 저장 → 같은 피드

2026-10-12. 사용자의 정정에 따라 **컬렉션 선등록 또는 저장한 글을 다시 페이지에 추가하는 단계를 기본 흐름에서 제거**했다. 기존 원문·묶음으로 페이지를 구성하는 기능은 보존했다. 디자인·구현 책임자는 Codex 한 명이다.

## 체험

`npm run dev` 후 로그인된 테스트 환경에서 `index.html?section=records&view=page`를 연다. 글쓰기 아이콘 → 본문 → `+` → 컬렉션 선택 또는 직접 입력 → 저장. 저장한 글에 초점이 돌아오고 같은 피드에 나타난다. `life.html?view=page`도 같은 UI를 사용한다. 운영 사이트에 배포됐다는 뜻은 아니다.

음악·책·영화·영상·글·작품·도구·인물·장소 등을 붙일 수 있다. 제목·창작자·출처 링크만 복사하는 구조화된 첨부다. 컬렉션의 ID·비공개 메모·태그·세부 정보는 따라오지 않는다. 컬렉션이 없어도 직접 입력하거나 지원하는 YouTube/GitHub 링크를 확인해서 붙인다. 컬렉션을 나중에 바꿔도 이미 저장한 첨부는 바뀌지 않는다. 현재 첨부 카드는 유형별 도형이며 실제 앨범 이미지나 자동 임베드가 아니다. 링크는 새 탭에서 연다.

## 저장과 공개 계약

- 저장한 글은 선택 필드 `workbench.page.posts`에 저장한다. 기존 `life-workbench-v1`의 원문·버전 참조·페이지 entries·책·정본·회고는 그대로다. 글 본문과 첨부는 서로 다른 필드다. 글 200개, 글당 첨부 12개·본문 20,000 UTF-16 단위; 구성 전체 2 MiB 한도를 유지한다.
- 작성/수정 초안은 계정·작업공간 소유권을 확인하는 별도 로컬 `page-drafts` 메타데이터다. **구성 이어쓰기와 공개 사본에 들어가지 않는다.** 초안 보관함에는 별도 CAS revision과 2 MiB 한도가 있다. 같은 브라우저에서 이어 쓰며 초안 파일로 새 사본을 옮길 수 있다.
- `저장`은 초안을 먼저 보관하고 현재 구성 revision과 수정 대상의 `updatedAt`을 확인한다. 저장한 글의 교체·초안 정리·기존 구성 동기화 대기 상태 갱신을 하나의 IndexedDB 트랜잭션으로 처리한다. 실패하면 기존 글과 초안이 남는다. 같은 시각에 수정해도 기준 시각은 증가한다. 가득 찬 200개 피드에서도 기존 글을 수정할 수 있다.
- 다른 탭이 먼저 저장한 경우 페이지를 다시 읽고 초안을 이어 열 수 있다. 수정 기준이 달라졌으면 새 글로 저장할 수 있고 기존 글은 유지된다. 로컬 초안 CAS 충돌은 입력을 유지하며 초안 파일을 받아 다시 불러올 수 있다. 초안 삭제는 확인 후 로컬 초안만 제거한다.
- `비공개`가 기본이다. `공개 후보`는 방문자 미리보기와 공개 사본 검토에 포함시키는 선택이며 즉시 공개하지 않는다. 기존 명시적 게시/갱신/철회가 필요하다. 이미 공개한 글을 비공개로 바꿔도 기존 공개 사본은 자동 철회되지 않는다.
- 기존에 구성 이어쓰기를 연결한 작업공간에서는 **저장한 글**이 같은 계정으로 이어진다. 새로운 자동 연결을 만들지 않는다. 로컬 작성 초안은 포함하지 않는다.
- 자료·구성 백업에는 저장한 글과 첨부가 포함되며 새 사본 복원에서 글 ID를 재매핑한다. 원문은 합치거나 새 버전으로 바꾸지 않는다. 작성 중인 초안은 화면의 별도 `초안 파일`로 받는다. 불러오기는 기존 초안을 덮지 않고 비공개 새 초안으로 만들며 수정 대상 연결을 끊는다. 잘못된 UTF-8은 거부한다.
- 공개 `life-share-v1` entry에 선택 필드 `attachments`를 허용한다. 공개 entry에는 개인 ID·초안·수정 기준이 없다. 첨부가 있는 entry는 기존 원문 parts를 동시에 담지 못한다. 전체 첨부+원문 수 200개, 100 entry, 1 MiB 한도를 유지한다.

저장 범위의 반대 검토 결과, 작성 초안을 기존 구성에 그대로 넣으면 이미 연결한 작업공간에서 자동 전송될 수 있었다. 이를 피하려고 기존 저장 계층의 소유권 확인·트랜잭션·CAS를 재사용하는 로컬 보관함으로 분리했다. 별도 서버 테이블이나 동기화 엔진은 추가하지 않았다.

## 화면과 재사용 판단

작성창이 주 행동이고 페이지 설정/기존 원문 추가는 접힌 보조 영역이다. 본문 16–17px, 충분한 행간, 얕은 구분선과 첨부 색만 사용한다. 책은 세로형, 음악은 정사각형, 영화는 포스터형, 인물은 원형, 도구는 둥근 사각형이다. 새 아이콘도 기존 24px viewBox·2px 둥근 선을 따른다. 입력 16px 이상, 조작 44px 이상을 유지했다. 새 프레임워크나 앱 의존성은 없다.

2026-10-12 공식 npm의 `@radix-ui/react-dialog` **1.3.1 / MIT**, 공식 [라이선스](https://github.com/radix-ui/primitives/blob/main/LICENSE), [최근 Dialog 변경](https://github.com/radix-ui/primitives/commit/925c88b773bb32aecf1b52a296a1a21ba7a720b9)을 재확인했다. React 런타임·빌드 비용 없이 가능한 이번 작업에는 선행 #69의 native dialog와 선택/조회 어댑터를 재사용했다. 본문은 plain textarea, 카드는 allowlist된 텍스트 DOM으로 구현해 편집기·HTML sanitizer 의존성을 늘리지 않았다. 새 공급자나 이미지 자동 요청도 없다. 별도 패키지 보안 감사 통과를 주장하지 않는다.

## Local 실행 순서

1. #66 → #67 → #68 → #69가 선행이다. **#70 `codex/collection-insert`는 이 방향에서 제외한다.** 이 브랜치는 #69 `06f47c8`에서 시작했고 #70의 텍스트 삽입을 포함하지 않는다. Local 미커밋 작업은 보존하고 별도 비교한다. Cloud는 병합·배포하지 않는다.
2. 기존 자료·구성 백업을 유지한다. 해도 전용 운영 Supabase에 `supabase/migrations/20261012010000_life_page_posts.sql`을 설치한다. composition/public-page 선행 SQL이 필요하다. 기존 두 validator와 새 비공개 첨부 validator만 변경하며 기존 테이블·RPC·권한·Auth는 변경하지 않는다. 과거 동기화/게시 SQL이나 합성 자료 생성 검사는 운영에서 다시 실행하지 않는다.
3. `supabase/tests/life-page-posts-installation.sql`을 실행해 **8조건 모두 passed=true**를 확인한다. 개인 행을 읽지 않는 상수/메타데이터 검사다. SQL 설치 전 앱을 배포하지 않는다.
4. `npm test`, `npm run check`, 브라우저 체험과 Local 변경의 충돌을 검토한 뒤 병합·배포한다. 공개 산출물의 새 JS/CSS 네 파일과 SW v96(다른 Local 변경과 합치면 새 번호)을 확인한다. 계정 설정/신규 Secret은 필요 없다.
5. 실제 기기에서 글 작성 → 대상 첨부 → 비공개 저장 → 새로고침 → 수정/초안 복구를 확인한다. 연결된 테스트 작업공간으로만 저장한 글의 구성 이어쓰기, 초안 비전송을 확인한다. 공개 확인은 합성 글에 대한 별도 명시적 게시로 수행하고 검증 후 철회한다. 사용자 글을 자동 게시하지 않는다.
6. 새 필드가 있는 자료를 옛 strict client로 되돌리면 읽기 거부가 발생한다. 새 데이터를 삭제해 맞추지 않는다. 앱의 수정 배포를 우선하고 백업과 새 client를 함께 보존한다. SQL 허용 필드는 호환성을 유지하는 방향으로 남긴다.

다음 우선순위: 실제 페이지 작성 사용성/Apple 확인 → 출처별 선택적 표지·미디어 보기 → 한국어 음악·책·장소 이름 검색 제공자의 품질/요금/사용 조건 비교. 수집 경로를 늘리기 전에 현재 작성 흐름의 체험 결과를 받는다.
