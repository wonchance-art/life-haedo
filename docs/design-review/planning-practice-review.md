# 계획·실행·기간 회고의 연결 명세

2026-10-29. [생활 시스템 계약](../life-tools-design/life-system-contract.md)의 구현 인계용 상세 설계다. main `30e94f0`·[PR140 계획 인계](https://github.com/wonchance-art/life-haedo/blob/dc1bef8f65b995fe72d472f0cccbaa83938287d3/docs/handoff/planning-execution.md)를 대조해 P0에서 미정이던 범위·날짜·관계·회고·파일 결정을 구체화한다. 아래 새 저장 형식/API 역할은 설계이며 현재 존재하는 구현으로 인용하지 않는다.

## 클릭 가능한 설계 시연

[단일 HTML 시연](../prototypes/planning-practice-review.html)은 합성 2026년10월 자료로 연결 → 요일 변경/과거 체크 정정 → 기간 확인 → 회고 저장 → 현재 계획/진척 수정 → 저장 회고 비교를 직접 눌러 볼 수 있다. 이 탭의 메모리만 사용하며 새로고침하면 초기화된다. 계정·동기화·운영 자료는 사용하지 않는다. 제품 UI나 서버 구현의 완료를 뜻하지 않는다.

로컬 확인은 저장소에서 `python3 -m http.server 8768 --bind 127.0.0.1 --directory docs/prototypes`를 실행한 뒤 `http://127.0.0.1:8768/planning-practice-review.html`을 연다. 이미 사용 중인 포트면 빈 포트를 고른다. 시연은 추가 네트워크 요청을 필요로 하지 않는다. 원격 실패/파일 복원은 이 시연에서 모사하지 않으며 아래 구현 검수의 대상이다.

시연 검수는 [결과·환경·파일 해시](evidence/planning-system/prototype-check.json)에 기록했다. 합성 자료로 16개 동작과 390/820/1440px의 초기·기간 확인·저장/현재 비교 화면을 확인했다. 경계 날짜, 빈 요일 거절과 입력 유지, 요일 변경 후 과거 중복 체크 정정, 당시 회고 불변, 판단 공란 저장, 무저장 종료·재시작을 검수했다. 추가 네트워크 요청·저장소 접근·콘솔/실행 오류는 없었다. [390px](evidence/planning-system/prototype-390.png) · [820px](evidence/planning-system/prototype-820.png) · [1440px](evidence/planning-system/prototype-1440.png)를 직접 읽고 잘림·겹침을 확인했다. Linux Chromium의 화면 폭 검수이며 실제 Apple 기기·제품 계정 저장·백엔드·배포 검수를 대신하지 않는다.

## 대표 결과와 범위

**A에서 월 방향/선택한 의도를 기존 습관 또는 목표에 연결 → B에서 같은 대상 실행·체크 → 선택 기간의 확인 가능한 기록과 내 판단 → 필요한 계획 수정 → A에서 재개·정확 근거 확인 → 선택 파일 복원**을 한 묶음으로 끝낸다.

읽은 문장이나 월 계획 없이 기존 습관을 체크해도 된다. 자료에서 바로 기존 목표로 연결할 때는 별도 작성 준비를 요구하지 않는다. 월 계획·목표·습관을 모두 만드는 사슬을 만들지 않는다. 새 목표 생성은 기존 도구에서 할 수 있지만 첫 연결 경로는 **기존 대상 선택**을 우선한다. 자동 일정·알림·외부 캘린더·AI 실행은 포함하지 않는다.

## 2. 화면과 문맥 이동

| 진입 | 필요한 화면 | 명시 결과와 복귀 |
| --- | --- | --- |
| 자료/읽기 메모의 선택 문장 | 기존 더보기의 `계획에 연결` → 의도 문구와 기존 목표/습관 선택 | 확인한 문구·선택 근거만 관계에 보관. 메모 전체/새 목표/마감일 자동 생성 없음 |

| 연결된 목표/습관 | 기존 목표/습관 화면의 정확 항목 | 기존 진척/체크 조작. 항목별 접힌 근거·월 계획 복귀 |
| 선택 기간 확인 | 계획 내부의 한 열 화면: 계획/확인한 기록/내 판단 | 범위·대상 변경, 저장 없이 닫기 또는 회고 저장 |
| 저장 회고 | 당시 자료와 판단을 읽는 화면 | 정확 근거, 현재 내용 확인, 수정한 회고의 새 판, 명시 다음 계획 편집 |
| 설정·파일 | 기존 계획 파일 그룹 | v1 계획 파일과 새 연결 파일의 포함 범위를 구분해 검토·복원 |

기본 표·본문 위에 통계 카드·진행 마법사·매일 평가를 추가하지 않는다. 관계와 회고의 대표 위치는 계획 메뉴이며, 다른 메뉴는 정확 대상에 문맥 진입한다. 44px 조작·16px 입력·키보드 초점·표 내부 가로 스크롤과 본문 읽기를 유지한다.

복귀 키는 계정/프로젝트·공간·원래 화면·정확 월 항목/대상·선택 구간·초점이다. 자료 근거는 source/version/hash·필요 구절 범위를 포함한다. 같은 세션에서만 위치를 복원하고 다른 기기에는 현재 존재하는 대상부터 연다. 계정 변경·미확보 대상에서는 이전 제목/메모를 새 계정 화면에 표시하지 않는다.

## 3. 날짜와 역사적 사실

| 값 | 의미·보존 규칙 |
| --- | --- |
| monthEntry.date | 실제 달력 날짜로 저장한 배치 기준. 생일/연도 표시 전환에도 ID/date/text 불변 |
| goal.target | 사용자가 정한 선택 마감일. 월 시작일로 자동 설정하지 않음 |
| habit.checks의 날짜 | 사용자가 체크해 현재 저장된 달력 날짜. 실제 활동 관찰·체크 입력 시각은 아님 |
| observedAt / recordedAt | 시스템에서 읽은 시각 / 저장한 시각(UTC). 수행 날짜로 사용하지 않음 |
| 회고 구간 | 명시 `[start,endExclusive)` 날짜 + 달력/생일 구간 선택 당시 라벨/기준 |
| 계획 snapshot | 연결 때 또는 회고 저장 때 확인한 문장·revision·시각. 기간 시작 전 계획이라는 보장은 없음 |

‘오늘’은 목표·습관·계획의 새 연결 흐름에서 하나의 **계정 계획 시간대**로 정한다. 처음 날짜/오늘 판단이 필요한 조작에서 현재 기기 IANA 시간대를 제안하고 사용자가 확인한 값을 계정에 보관한다. 단순 의도·대상 연결에는 시간대 설정을 선행하지 않는다. 이후 기기 이동·여행으로 자동 변경하지 않는다. 기존 날짜 문자열은 변환하지 않는다. 과거 시간대는 미확인이다. 기존 도구의 현지 날짜와 연간 계획 초기 한국 날짜 차이는 실행 시 이 공통 설정으로 연결하되, 기존 날짜·연간 행을 소급 재작성하지 않는다. 서버 설정 미확인 오프라인에서는 검증된 캐시만 사용하고 첫 설정 없이 미래/오늘 수행 여부를 확정하지 않는다.

저장 회고는 시작/끝을 실제 날짜로 고정한다. 생일 변경·평년 2/29 보정·다음 해 전환 뒤에도 과거 구간을 다시 계산하지 않는다. 월말·연말·DST·한국/해외 기기·1900/2199를 검수한다. 끝 경계는 마지막 유효 날짜 다음 날까지 표현할 수 있어야 하지만 범위 밖 새 계획을 허용하지 않는다.

계정 시간대 설정도 독립 revision/CAS를 사용한다. 두 기기의 최초 설정이 다르면 서버에서 먼저 확정한 값을 읽어 비교하고 기기 시각으로 덮지 않는다. 변경은 명시 선택이며 앞으로의 ‘오늘’에만 적용한다. 날짜 조작을 시작할 때의 timeZone/revision을 고정하고 확인 중 설정이 바뀌면 저장 전 날짜를 다시 확인한다. 이미 저장한 체크 날짜·회고 기간은 이동하지 않는다.

목표 progress는 `현재 80% · 확인 시각`처럼 표시한다. 과거 월에 속한 성과로 계산하지 않는다. 습관은 기간 안의 유효한 고유 체크 날짜만 세며 같은 목표/습관을 여러 월·공간에 연결한 횟수로 수행을 중복 합산하지 않는다. 체크 없음은 미확인이다. 현재 days를 과거 분모로 사용하지 않으며 요일 변경으로 남은 과거 체크를 삭제하지 않는다.

가져온 중복 체크는 원본 배열을 보존하고 읽기 투영에서 날짜 한 번만 센다. 미래·잘못된 날짜는 합산에서 제외하고 확인 필요로 표시한다. 현재 요일과 다른 과거 체크도 유효 날짜이면 ‘체크한 날’로 보여 주며 당시 반복 규칙은 미확인으로 둔다.

**과거 체크 정정은 이번 실행 묶음에 포함한다.** 기간 확인에서 이미 저장된 정확 날짜의 체크를 명시 제거할 수 있어야 하며 현재 요일에 포함되는지로 제거를 막지 않는다. 제거는 그 날짜의 중복 값 전체를 제거하는 의도를 먼저 보여 주고 다른 날짜는 보존한다. 새 체크는 현재 규칙·선택 날짜·미래 금지 조건을 따른다. 같은 날짜의 동시 체크/취소를 최신 시각으로 임의 병합하지 않고 기존 충돌 해결과 양쪽 변경 보존을 보강한다. 습관 전체의 과거 요일 편집기·진척 그래프는 필요가 확인된 뒤의 확장이다.

## 4. 선택 관계와 정체성

새 관계 저장의 최소 의미는 다음과 같다. 필드명은 실행 때 검증기를 확정할 논리 계약이며 기존 v1에 넣을 필드가 아니다.

```text
owner = project + authenticatedUser
scope = owner + workspaceId
link = id, revision, deleted,
       confirmedIntent {text, selectedAt, origin?},
       monthRef? {annualGeneration, entryId, entrySnapshot, planRevision, observedAt},
       target {kind: goal|habit, itemId},
       targetAtSelection {title, stamp, observedAt}
origin? = 정확 원문 참조 또는 선택 메모의 명시 사본과 원래 대상 키
```

메모 origin은 planId/materialId/source/version/hash와 선택 당시 메모 사본을 구분한다. 가변 메모의 과거 revision이 다시 열릴 수 있다고 약속하지 않는다. 원문을 확보하지 않았으면 URL/확보 범위만 보존하고 구절을 생성하지 않는다. 의도 사본은 선택·확인한 짧은 문구만 담으며 계획은 원래 메모가 다른 기기에 없어도 읽고 실행할 수 있다. 원문이 미수신인 상태와 의도 보관 완료는 따로 표시한다.

동일 관계의 중복 기준은 scope + annualGeneration/entryId(있을 때) + target kind/ID + 같은 명시 작업 ID다. 다른 의도·다른 월을 사용자가 고르면 별도 관계가 가능하다. 대상 이름으로 병합하지 않는다. 단순 연결은 목표의 제목/마감/진척·습관의 요일/체크를 수정하지 않는다. 원래 메모나 계획 문장이 바뀌면 현재 값과 선택 당시 사본의 차이를 보여 주고 사용자가 관계의 의도를 갱신할 때만 새 revision으로 저장한다.

관계 해제는 관계 tombstone만 바꾼다. 원문·목표·습관·체크·저장 회고를 삭제하지 않는다. 대상 삭제/권한 거부/통신 실패/미수신을 구분하며 같은 제목의 대체 항목에 연결하지 않는다. 관계 삭제 전후를 옛 기기의 전체 업로드가 뒤집지 않도록 remote revision/operation/세대를 확인한다.

월 항목 연결은 `annualGeneration + entryId`로 고정한다. 일반 편집·표시 기준 변경은 generation을 유지하고 v1 파일의 전체 교체는 새 generation을 만든다. 기존 월 관계는 옛 generation의 보관 관계로 남고 새 파일에 자동 적용하지 않는다. ID가 같아도 사용자가 매핑을 확인해야 한다. 현재 세션 되돌리기가 있다면 계획과 generation/관계를 같은 CAS 트랜잭션에서 되돌리며 후속 입력 뒤 무조건 복원하지 않는다. 연간 행은 안정 ID가 없으므로 첫 버전에서 행 자체를 생존 관계로 연결하지 않고 확인한 연간 문장을 설명 snapshot으로만 쓴다.

## 5. 계정 보관·실패·도메인 간 경계

연간 계획은 기존 account+workspace 범위로 서버 기본 보관을 추가한다. 계획 원본과 그 교체 generation/월 관계는 함께 검증·커밋한다. 저장 데이터는 기존 AnnualPlan v1을 담는 별도 외곽과 관계 sidecar로 분리하며 원문 bundle/LibraryMeta에 추가하지 않는다. 큰 저장 회고는 별도 ID·revision의 레코드로 보관하고 목록에는 요약만 읽는다. 기존 계획 2 MiB 한도를 유지하며 연결 한도/회고 한도는 별도 검증·용량 초과 안내를 둔다. 입력을 자르거나 숨겨진 삭제로 맞추지 않는다.

로컬에는 원자 CAS·영속 작업 영수증·전송 대기, 원격에는 owner 검증·expected revision·동일 operation 재시도 결과를 둔다. 세대·개인 공간을 검증한 서버가 기준이며 브라우저는 표시/미전송/복구 캐시다. 처음 빈 서버/빈 로컬/양쪽 기존/삭제 tombstone을 구별한다. 기존 로컬 계획을 전송하기 전 소유 범위를 확인하고 양쪽 자료가 다르면 사본을 보존해 명시 선택한다. 현재 계획을 보기 위해 무관한 전체 원문 수신을 기다리지 않는다.

CompositionSync/LibraryMetaSync의 내구 작업·CAS·계정 세대 패턴은 재사용하되 sourceSync 전체 완료 의존성은 그대로 복제하지 않는다. 필요한 정확 근거만 별도 수신하고 일반 계획 편집을 계속할 수 있게 한다. 서버 RPC 이름·테이블 정의는 실행 시 Supabase 공식 문서/설치 상태·기존 계약에 맞춰 확정한다. 익명/다른 owner 거부, 제한된 권한, 기존 RPC 정의/권한 보존, 동시 CAS를 격리 검수한다. 운영 개인 계획을 검수 데이터로 쓰지 않는다.

목표/습관 저장은 여전히 다른 도메인이다. `store.change()`는 로컬 대기를 만든 결과이며 `flush()` 호출 반환만으로 서버 성공을 합산하지 않는다. 해당 ID의 현재 상태·정확 데이터·syncedAt/ACK를 확인한다. 동일 계정의 변경 중·충돌·삭제 대상을 관계 확정 대상으로 조용히 채택하지 않는다. pending 항목은 후보로 표시할 수 있으나 관계의 서버 확인은 대상 확인 후 끝낸다.

새 목표를 만들고 관계를 잇거나 파일에서 새 대상을 복원할 때는 다음 재개 가능한 절차를 사용한다.

1. owner/공간·명시 입력·operationId·선택 대상 또는 미리 할당한 새 target ID를 영속 기록한다.
2. 기존 저장 경로에 같은 target ID로 생성/확인한다. 같은 ID에 다른 내용이 있으면 중단한다.
3. 목표/습관 서버 ACK를 확인한 뒤 정확 관계를 저장한다.
4. 관계 ACK 뒤 완료 영수증을 남긴다. 중간 실패는 생성된 대상과 미완료 관계를 유지해 같은 ID로 재시도한다.

2의 성공 후 3이 실패했다고 대상을 지우거나 새 목표를 만들지 않는다. 취소는 아직 시작하지 않은 단계만 멈추고 이미 보관한 대상은 알려 준다. 여러 HTTP/IDB/localStorage 작업을 하나의 원자 저장으로 표시하지 않는다. 기존 플랫폼 충돌 처리에 양쪽 자동 복구가 있다고 가정하지 않고 연결 여정에서 필요한 사본 보존을 구현·검수한다.

## 6. 기간 확인과 불변 회고

기간 확인은 조회만으로 저장하지 않는다. 화면에는 다음 세 덩어리만 둔다.

- **계획:** 선택 당시 문장·확인 시각과 현재 문장. 당시 자료가 없으면 현재 계획이라고 표시한다.
- **기록:** 현재 목표 상태, 기간 안의 고유 체크 날짜, 미확인/오류 범위. 실제 활동의 객관적 증명이라고 표현하지 않는다.
- **내 판단:** 선택적 자유문. 점수·감정·성과 평가·다음 달 계획은 필수 입력이 아니다.

회고 저장의 최소 모델:

```text
reviewId, revision, previousRevision?, deleted,
scope, period {start, endExclusive, basisLabel, timeZone, timeZoneRevision},
capturedAt, planSnapshots[], itemSnapshots[], linkSnapshots[],
sourceReferences[], coverage {confirmed, pending, missing, excluded},
note, manifestHash, operationId
```

snapshot에는 선택한 계획 ID/generation/revision/문장과 목표·습관의 실제 읽은 stamp/필드·조회 시각을 넣는다. 습관 snapshot은 선택 기간에 필요한 날짜와 당시 현재 규칙만 보관한다. 현재 규칙을 과거 규칙이라고 표시하지 않는다. 원문 참조는 기존 SourceReference의 정확 판·검증 규칙을 따른다. 회고의 서술은 사용자 입력이고 자동 사실 해석으로 섞지 않는다.

저장 직전 표시한 snapshot/manifest와 로컬 입력·owner/공간·계획 revision·대상 stamp를 재대조한다. 바뀌면 원래 입력을 유지하고 다시 확인한다. 원격 확인이 실패하면 확인 시점·미확인 범위를 남긴 로컬 초안으로 보관할 수 있지만 모든 대상의 최신 상태를 확인한 회고로 표시하지 않는다. 이 데이터는 여러 대상의 **각 확인 시점**을 가진 snapshot이며 전체 서비스의 같은 순간을 원자 촬영한 것으로 주장하지 않는다.

확정된 회고 판은 이후 원문·목표·계획 수정/삭제로 바뀌지 않는다. `현재 내용 확인`은 별도 읽기 비교, 수정 저장은 이전 판을 유지하는 새 revision이다. 회고 삭제는 명시 tombstone이며 비공개 원본 보존 정책과 파일 안내를 따른다. 자료실의 기존 reflection.note를 덮지 않고 계획 기간 회고 전용 목록/정확 판을 제공한다. 회고에서 글쓰기를 선택하면 검토한 문장만 기존 PhotoPost에 채택하고 개인 체크·생년월일·미선택 근거는 자동 공개하지 않는다.

다음 계획 조정은 회고에서 **그대로 두기 / 현재 계획 수정 / 선택 문장을 다음 구간에 추가 / 연결 해제** 중 사용자가 고르는 편집이다. 다음 달 자동 이월·목표일 이동·완료 되돌리기를 하지 않는다. 회고는 당시 판을 계속 보존한다.

## 7. 파일·복원 결정

기존 `haedo-annual-plan` v1은 계속 계획만 내보내고 현재 공간에 교체한다. 연결/수행/회고를 임의 추가하지 않는다. 새 형식은 **별도 `haedo-planning-package` v1 외곽 JSON**으로 선택한다. 기존 strict v1을 바꾸는 안보다 구버전 호환·포함 범위가 명확하기 때문이다. 명칭·파서는 새 구현이며 현재 지원 파일로 안내하지 않는다.

새 파일은 선택 계획(v1 payload), 관계, 선택 목표/습관의 확인 사본, 선택 회고 판, 필요한 정확 원문 참조와 명시 포함한 원문 closure를 담는다. 생년월일·체크 날짜·내 판단·원문 전체 포함 여부를 내보내기 전에 확인한다. 계정 ID/토큰·서버 연결·미선택 목표·전체 초안·뉴스 반응은 포함하지 않는다. 사진 원본은 기존 전용 파일 범위를 사용하며 이 JSON에 있다고 표시하지 않는다. 회고 snapshot과 살아 있는 원본 대상 사본은 형식에서 구분한다.

압축 없는 총 16 MiB를 초기 검증 상한으로 설계하고 기존 plan 2 MiB 및 원문/항목 검증기를 함께 적용한다. 실행자는 근접 용량·손상/알 수 없는 키·동일 ID 충돌·순환/누락 관계·잘못된 hash를 검수한 후 상한을 확정한다. 초과하면 선택 범위를 줄이게 하며 조용히 잘라내지 않는다.

복원은 명시 계정의 **새 공간·새 계획 generation·새 대상/관계/회고 ID**로 만든다. 파일 내부 ID→새 ID 매핑을 먼저 영속 기록한다. 리뷰 내부의 당시 사실은 과거 snapshot으로 보존하고 살아 있는 참조만 새 사본으로 매핑한다. 목표 이름으로 기존 항목과 합치지 않는다. 원문 미포함/사진 미확보는 별도로 남긴다.

복원 전 파일의 원래 manifestHash와 정확 구절을 검증한다. 새 ID/소유 범위로 매핑한 뒤 같은 정규 직렬화 규칙으로 새 manifestHash를 계산·검증하고 이전 hash는 가져오기 출처로만 보존한다. 새 소유 범위의 자료와 구절이 검증되지 않았는데 원래 hash를 복사해 검증 완료로 표시하지 않는다. 회고에만 있는 삭제된 대상은 역사 snapshot으로 남기며 살아 있는 목표로 부활시키지 않는다. 선택한 원본 대상 사본만 명시 복원 대상이다.

내보내기는 허용한 portable 필드/파일 내부 별칭만 남기며 원래 계정 ID·인증 scope·서버 연결은 출처 정보에도 넣지 않는다. 원문 열기에 쓰는 sourceReferences는 새 workspace/source/version 매핑과 정확 hash·구절 검증을 거쳐 다시 만든다. 원래 파일의 별칭/식별자를 수신 계정의 기존 자료 조회 키로 쓰지 않는다. 수신 계정에 같은 raw ID가 이미 있어도 결합하지 않는 반례를 검수하고, 원문 미포함은 미확보로 남긴다. 저장 회고의 당시 문장·체크 사실과 실행용 새 scope를 구분한다.

실제 순서는 파일 검증·포함 범위 검토 → 복원 의도/매핑 보관 → 새 공간의 계획/정확 자료 사본 설치 → 같은 ID의 목표·습관 사본 생성/ACK → 관계/회고 설치 → 완료다. 부분 설치는 복구 중인 사본으로 표시한다. 실패 뒤 같은 operation/매핑으로 재개하고 기존 공간·기존 목표를 건드리지 않는다. 기존 플랫폼 가져오기의 반복 `change(null,...)`를 그대로 호출해 중복을 만들지 않는다. 회고와 원본이 일부만 복원된 상태를 완전 복원으로 표시하지 않는다.
