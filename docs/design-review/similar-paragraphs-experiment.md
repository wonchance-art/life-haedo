# 기기 안 비슷한 문단 실험(묶음 C)

2026-11-02 KST. **판정: 기각.** 기존 임베딩 워커로 문단을 색인해 "비슷한 문단" 후보를 내는 방식은, 근거 없는 후보를 채우지 않도록 임계값을 둔 상태에서 평가 세트 Hit@3가 0.229였다. 기존 재발견 규칙을 문단에 적용한 기반선과 같은 값이다. 실제 글 길이(약 275자) 문단 200개의 색인도 CPU 4배 감속에서 243초가 걸려 60초 한도를 넘었다. 제품 코드·저장 형식·PWA 셸·분석 정책은 바꾸지 않았고 `PRODUCT.md`도 고치지 않았다.

근거: [글쓰기·메모 AI 적용 검토](../life-tools-design/writing-ai-review.md) §5(3순위)·§6 묶음 C. 참고 사례는 Obsidian Smart Connections다. 로컬 임베딩으로 비슷한 노트를 점수와 함께 후보로만 보여 주고, 연결은 사용자가 만든다.

## 질문

기존 브라우저 안 임베딩 워커로 자료·내 글의 문단을 색인해 "비슷한 문단" 후보를 내는 것이 기존 재발견 규칙보다 유의미하게 나은가? iPhone·iPad에서 감당할 비용인가?

- 워커: `interest-model-worker.js`·`interest-model-loader.js`, Transformers.js 4.3.1, `Xenova/paraphrase-multilingual-MiniLM-L12-v2` 고정 revision, q8, WASM 1스레드, 384차원.
- 재발견 규칙: `rediscovery.js`. 같은 주제·같은 묶음·실제 공통어 2개 이상.

## 사전등록과 봉인

[사전등록](evidence/similar-paragraphs/preregistration.md)의 판정 기준은 총괄이 작업 지시서에서 정한 값을 그대로 옮긴 것이다. 실행 뒤에는 고치지 않았다.

| 1. 모델 실행 전: 사전등록·말뭉치·gold·생성기 | `seal.json` | `5f453484dbda279fc598c260c4c7f8dfb6e61fde942e3d18aaececdadd7738b2` | `ba4f4a0` |

첫 동결은 평가 세트를 한 번도 실행하기 전에 대체했다. 세션의 명령 검사기가 실행 모드 인자 `eval`을 셸 `eval`로 보고 막았기 때문이다. 바꾼 것은 CLI 이름(`heldout`)뿐이고 매개변수 TP·τ=0.61, 후보, gold, 말뭉치는 같다.

평가 세트는 `eval-output.json`이 없을 때만 실행되며, 한 번 성공 실행했다. 실패한 시도는 없다.

### 동결 전 구현 메모

개발 데이터로 평가 경로를 미리 돌렸을 때 한 가지를 확인했다. q8 모델은 활성값을 배치 단위로 동적 양자화하므로, 배치 구성이 다르면 같은 문장도 벡터가 조금 다르다. 최대 절대 차는 0.025, 최소 코사인은 0.987이었다.

그래서 사전등록의 "같은 입력에서 두 경로 벡터 동일" 검사를 **같은 배치 입력** 비교로 구현했다. 품질 경로의 첫 32개 입력을 iframe 경로로 다시 임베딩해 비교한다. 이 수정은 평가 실행 전에 이뤄졌다. 배치 구성 차이는 사실로 따로 보고한다.

## 자료

- **합성·익명 한국어**만 썼다([생성기](evidence/similar-paragraphs/build-corpus.py)). 실제 사람·계정·개인 기록·실제 기사가 아니며 외부로 보내지 않았다.
- **개발 세트:** 14문서·70문단. 관련 기준 16개(gold 쌍 18), 무관 기준 10개.
- **평가 세트:** 새로 쓴 독립 세트 30문서·150문단. 개발 세트와 주제가 겹치지 않는다. 관련 기준 35개(gold 쌍 39), 무관 기준 16개. 유형은 질문 3, 경험 23, 주제 9다.
- MODEL-03 heldout은 재사용하지 않았다. 문서 단위 주제·질문 gold라 문단 쌍 과제와 맞지 않고, 이미 본 자료이기 때문이다.
- **gold 정의:** 기준 문단과 다른 문서에 있으면서, 같은 질문·같은 종류의 경험·같은 구체 주제(중심 논점)를 다른 표현으로 다룬 문단이다. 같은 넓은 분야에 속하거나 단어만 겹치는 문단은 관련이 아니다.
- **일부러 넣은 문단:** 단어는 겹치지만 논점이 다른 문단, 같은 문서 안의 비슷한 문단, 다른 문서로 그대로 옮긴 인용 복제(`E10:4` = `E11:4`).
- **한계:** 말뭉치와 gold를 구현 작업자 1인이 썼다(독립 표시자 없음).
  - 문단이 짧다(평균 약 55자, 한 문단에 논점 하나).
  - 후보 풀이 150문단으로 작다.
  - gold 쌍 중 공통어 규칙이 성립하는 비율은 39쌍 중 8쌍(0.205)이다. 표현을 바꿔 쓴 쌍이 대부분이라 기반선에 불리한 자료다. 그런데도 임베딩이 기반선을 넘지 못했다.

## 방법

- **후보** [`candidate.js`](evidence/similar-paragraphs/candidate.js): 빈 줄로 나눈 문단을 쓴다. 400자를 넘으면 문장 경계에서 나누며 무음 절단은 없다.
  - 같은 문서와 정규화 복제를 빼고, 코사인 점수가 τ 이상인 문단을 최대 3개 낸다. τ 미만이면 결과를 채우지 않는다.
  - 입력 변형 세 가지(P 문단, TP 제목+문단, W2 두 문장 창)와 τ는 **개발 세트에서만** 정했다. 개발 오탐 ≤ 0.10에서 Hit@3가 가장 높은 값을 골랐다.
  - 결과는 **TP, τ = 0.61**이다(개발 Hit@3 0.3125, 오탐 0.10).
- **기반선**: 제품 `rediscovery.js`의 `related()`를 수정 없이 문단 단위로 호출했다. 같은 문서·복제는 제품의 `discovery.excludedPairs`로 뺐다.
  - B1: 소스 제목을 비웠다.
  - B2: 소스 제목에 문서 제목을 넣었다.
  - 판정에는 B1·B2 중 높은 쪽을 쓴다.
  - B3: 현재 제품처럼 문서 단위로 찾은 참고값이다. 판정에는 쓰지 않는다.
- **실행:** Chromium 153.0.8010.12(Playwright, Linux headless), 390×844·DSF 3·모바일 모사.
  - 품질 벡터는 제품 경로(로더 → 전용 모듈 워커)에서 감속 없이 만들었다.
  - CDP `Emulation.setCPUThrottlingRate`는 Chromium 153에서 전용 워커에 적용되지 않는다(`Operation is only supported for pages, not workers`, 사전 확인). 그래서 비용은 **제품 워커 소스 바이트를 그대로**(SHA 대조) 같은 출처 iframe 주 스레드에서 실행해 4배 감속으로 쟀다.
  - 실측 감속비는 4.12였다.

### 사후 서술(평가 정답을 본 뒤, 판정을 바꾸지 않음)

[`posthoc.json`](evidence/similar-paragraphs/posthoc.json):

- **임계값 없이 순위만 쓸 때:** Hit@3 0.743. 관련 기준 35개 중 26개는 가장 가까운 gold가 3위 안이고, 14개는 1위다.
- **그 대신:** 무관 기준 16개 모두 후보를 낸다(오탐 1.0).
- **평가 정답을 보고 오탐 ≤ 0.20인 최적 임계값을 고르면:** τ = 0.55에서 Hit@3 0.40이다. 이는 성능 추정치가 아니라 상한이다.

점수 분포가 겹친다. gold 최고 점수는 0.185~0.717(중앙값 0.514), 무관 기준의 최고 후보 점수는 0.388~0.573(중앙값 0.497)이다. 이 모델의 코사인 점수 하나로는 "관련 있음"과 "근거 없음"을 가를 수 없다.

## 판정과 근거

**기각.** 근거는 다음과 같다.

1. "근거 없는 결과를 채우지 않는다"는 제품 규칙을 지키는 임계값에서는 적중률이 기존 규칙과 같다(0.229 대 0.229). 정답을 보고 고른 최적 임계값으로도 0.40이다. 순위 신호(순위만 0.743)는 있지만, 후보를 낼지 말지를 정하는 신호가 없다.
2. 기존 재발견에는 재발견 화면의 정확한 공통어라는 설명 가능한 근거가 있다. 임베딩 점수는 근거를 보여 주지 못한다. 두 문단 나란히 보기로 보완하더라도, 같은 적중률에 모델 118MB와 준비 시간을 더할 이유가 없다.
3. 실제 글에 가까운 길이에서 200문단 색인이 4배 감속 4분이다. 보관함 전체(수천 문단)를 색인하면 기기에서 수십 분이 걸린다.

## 바꿀 조건

아래 중 하나가 새 근거로 확인되면 같은 규약(새 독립 평가 세트, 사전등록·봉인, 한 번 실행)으로 다시 실험한다. 이 결과를 본 같은 자료에 임계값을 맞춘 것은 새 검증이 아니다.

- 비슷한 문장 쌍 판별용으로 보정된 다국어 모델이 같은 크기 한도(약 120MB 이하) 안에서 공식 고정 revision으로 제공된다. 예: 교차 인코더 재순위, 또는 한국어 문장 유사도 학습 모델. 그리고 개발 세트에서 무관 오탐 ≤ 0.20일 때 Hit@3 ≥ 0.70을 먼저 보인다.
- 제품 요구가 "후보를 낼지 판정"이 아니라 "사용자가 고른 문단 둘의 비교"나 "점수 없이 순위만 보여 주는 탐색"으로 바뀐다. 그래도 근거 없는 결과 금지 규칙과의 관계를 소유자가 먼저 정해야 한다.
- 색인 비용: 기기 안 WebGPU 경로나 더 작은 모델로 4배 감속 기준 275자 문단 200개를 60초 안에 색인한다.

기존 재발견(같은 주제·같은 묶음·실제 공통어)은 그대로 유지한다. 같은 의미의 다른 표현을 놓친다는 한계는 [재발견 설계](rediscovery.md)에 이미 적혀 있다.

## 채택했다면 붙였을 최소 설계(기록용, 구현하지 않음)

재발견 화면에 기본 꺼짐의 "비슷한 문단" 후보를 둔다.

- **준비:** 명시 준비 버튼과 모델 다운로드 안내(약 141MB, 셀룰러 주의, 기기 저장 공간)를 둔다.
- **표시:** 후보는 두 문단 나란히 보기와 함께 낸다. 의미·동의를 단정하지 않는다.
- **연결:** 연결·묶음 담기는 사용자가 한다.
- **실패 시:** 색인을 끊어도 기존 재발견에는 영향이 없다.

이번 판정으로 착수하지 않는다.
