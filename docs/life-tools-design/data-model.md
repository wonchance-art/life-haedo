# 데이터·권한 설계

2026-10-05 후속: 최신 제품 방향은 [활동 통합·내 페이지](lifestyle-blog.md)다. SNS는 가져오기 전용이며 아래의 외부 실행·수신자 권한 계약은 원본 SNS 게시·수정·삭제 권한을 뜻하지 않는다. 다음 운영 단위는 보관한 자료의 선택 편집·방문자 미리보기다. 직접 글쓰기·추천·보고서·공개 블로그는 후속이며 원문·작성자·근거·개인/공개 사본 계약을 유지한다.

기준: 2026-10-03 당시의 방향을 반영한 설계 제안. R1은 이미 기록한 것을 가져와 원문·출처를 보존하고, 발췌·검토·통합한 뒤 다시 열고 내보내는 개인 로컬 도구다. 직접 입력은 빠진 맥락을 보완하는 수단이다. R1에서 실제 구현한 최소 모델·저장과 검증은 [구현 기록](r1-implementation.md)을 따른다. 후속 원격 권한·AI·삭제 전파 등은 설계로 남는다.

## 확인된 기반과 보호 범위

후속 활동 묶음은 원문·버전·발췌를 가리키는 해제 가능한 연결이다. 같은 자료가 여러 모음에 속해도 원문을 복제·합치거나 공개 권한을 합산하지 않는다. 원천별 기본값·모음·항목 예외는 선택 초안의 구성을 돕고, 새 자료를 자동 공개하는 허용으로 사용하지 않는다. 공개 초안 제외, 페이지 배치 숨김, 이미 게시된 해도 사본의 열람 철회는 각각 다른 변경이다. SNS 원본의 수정·삭제는 해도가 실행하지 않으며 수집 중지나 원천 접근 실패로 보관본을 조용히 삭제하지 않는다. 이는 새 저장 필드·DB 마이그레이션을 이번에 적용했다는 뜻이 아니다.

- 기존 `assets/app.js`의 `caeyeon_life_registry`, `caeyeon_life_doc_<id>`, 과거 `caeyeon_life_v2` 및 다른 `caeyeon_life_*` 키·JSON 형식을 유지한다. DB 사용자의 원격 `charts`와 로컬 사본을 함께 보존한다.
- `assets/sync.js`의 문서별 직렬화·`updated_at` 조건부 쓰기·원격 삭제 부활 방지는 기존 연표의 계약이다. 신규 원문 버전·가져오기·병합·권한까지 검증됐다는 뜻이 아니다.
- `assets/data.js`의 가져오기는 새 ID를 만드는 연표 사본 복원이다. 새 원천 가져오기와 다른 입구다. 중첩 `kind`, `t`, `fut` 등을 제거하는 `canonical()`과 연표 전용 `sanitize`·`migrateScale`은 신규 모델에 적용하지 않는다.
- 기존 회귀 22개·실제 Supabase 검사 28개 통과는 전달받은 기존 charts 검증 결과다. 이번 문서 수정에서 재실행하지 않았고 신규 R1의 검증으로 승계하지 않는다.
- 실제 개인 원문·계정 정보·로그인 세션을 이 저장소·로그·스크린샷에 복사하지 않는다. 설계와 검증은 익명 샘플을 사용하며 이 작업은 외부 DB·계정·스키마를 변경하지 않는다.

## R1의 원천과 입력 범위

첫 원천은 Apple 메모, Obsidian, 네이버 블로그, 인스타그램으로 확정됐다. 공통 입력은 사용자가 선택·제공한 본문, 텍스트, Markdown, 링크다. 네 서비스의 자동 연동·크롤링·API나 모든 내보내기 형식 지원을 확정한 것은 아니다. 실제 파일 선택·공유·내보내기 가능 경로는 [기술 설계](architecture.md)에서 조사·검증한다.

| 원천 | 보존할 구분 | 입력의 한계 |
| --- | --- | --- |
| Apple 메모 | 메모 식별 정보가 있으면 보존, 제목·본문·작성 시각의 출처 표시 | 체크리스트·표·첨부·손글씨가 텍스트에 포함됐다고 추정하지 않음 |
| Obsidian | 노트 경로·Markdown 본문·제공된 속성·링크 | 원본 경로는 비공개, 내부 링크 대상·이미지가 함께 제공됐는지 따로 기록 |
| 네이버 블로그 | 게시물 URL·저자·제공된 본문·원 게시 시각 | URL만으로 본문·댓글·이미지에 접근할 수 있다고 표시하지 않음 |
| 인스타그램 | 게시물 URL·작성자·제공된 캡션·인용/저장 관계 | 캡션과 이미지·영상·댓글을 구분; 사진 속 글/OCR은 제공되지 않으면 없음 |

URL만 받으면 `coverage.status=link_only`, `contentText=null`, `contentHash=null`로 보관한다. 본문 미확보와 실제 빈 문자열을 구분한다. 텍스트를 붙여넣었다면 “서비스 원본 전체”가 아니라 실제 받은 문자열을 보존한다. 일부 제공·누락·미상 범위를 표시하며, 접근 실패나 링크 삭제를 원문 내용으로 추론하지 않는다.

## 최소 논리 모델

R1의 중심은 Source·SourceVersion과 선택한 발췌/생각의 연결이다. 아래 개념은 논리 구분이며 모두 독립 테이블·화면·필수 입력을 만들지 않는다. 자료만 보관하거나 두 발췌를 주제로 묶어도 완결된다. Activity·Plan·Object를 먼저 만들게 하지 않는다.

| 개념 | 최소 내용과 책임 | 필수성·연결 |
| --- | --- | --- |
| Source | `id`, `origin`, 제목/식별 설명, `sourceKey?`, `url?` | 원천 문서의 정체성; 확실하지 않은 동일성은 미확인 유지 |
| SourceVersion | `id`, `sourceId`, 받은 원문, 형식·확보 범위·원출처 메타데이터 | 불변 스냅샷; 같은 Source의 이전 버전을 덮지 않음 |
| 검토 후보 | 제안 내용, `sourceRefs`, 추출 방법, 검토 상태 | staging에 둠; 실제 통합 전에는 저장된 사실·계획·활동으로 취급하지 않음 |
| Record | `id`, 발췌/관찰/정리 종류, 본문, `sourceRefs` | 선택한 발췌·통합 내용을 담고 원문 근거를 보존 |
| Thought | `id`, 질문/해석/판단 본문, `sourceRefs?` | 사용자 생각과 원문 인용·AI 해석을 구별 |
| Object | `id`, `type`, `title`, 자료 참조·개인 속성 | 책·장소·작품·프로젝트가 필요할 때 연결 |
| Activity | `id`, 실제 수행 내용·시점, `active/interrupted/completed` | 수행을 확인해 구조화하기로 선택했을 때만 생성 |
| Plan | `id`, 예정 내용·시점, `planned/postponed/cancelled/fulfilled` | 계획을 관리하기로 선택했을 때만 생성; 수행함은 사용자 확인 |

공통 항목은 `id`, `revision`, `createdAt`, `updatedAt`, `provenance`, `deletedAt?`를 갖는다. `provenance.kind=user/imported/ai`는 생성 경로이며 원문의 발화자 역할과 별개다. AI 제안을 확인해 저장해도 AI 기원을 사용자 직접 작성으로 바꾸지 않는다.

작업공간은 `workspaceId`, `ownerLocalId`, `accountBinding?`, `schemaVersion`, `revision`을 갖는다. 항목은 작업공간의 개인 보관 권한을 상속한다. 보관자의 ID가 타인 원문의 저작자·공개 권한을 뜻하지 않는다. 로컬 ID는 인증·암호화 수단이 아니며 초기 공동 편집자는 없다.

UUID를 사용하고 제목·URL·ISBN·날짜·배열 위치를 내부 ID로 쓰지 않는다. 일반 연결 `entityRefs`는 `{entityType,entityId,revision?}`이고 원문 참조 `sourceRefs`는 `{sourceId,sourceVersionId,locator}`다. 원문 발췌는 항상 특정 SourceVersion을 참조한다. 링크는 다른 항목의 접근 권한을 전달하지 않는다.

## 원문·출처·발화·시간 계약

SourceVersion의 최소 예시는 다음과 같다. 실제 서비스 자료가 아닌 익명 형식 예시다.

```json
{
  "id": "sv-example", "sourceId": "s-example", "format": "text/plain",
  "contentText": "다음에 이 질문을 다시 읽어 보기.", "contentHash": "example-hash",
  "originalAuthor": {"label": "작성자 미상", "relation": "unknown"},
  "originalCreatedAt": null, "originalUpdatedAt": null,
  "importedAt": "2026-10-03T00:00:00Z",
  "coverage": {"status": "partial", "omissions": ["앞뒤 문맥", "이미지"]},
  "segments": [{"speakerRole": "unknown", "locator": {"start": 0, "end": 19}}]
}
```

`contentText`는 받은 문자열을 그대로 보존한다. `format`은 실제 받은 `text/plain` 또는 `text/markdown` 등이며 웹 서비스의 원래 저장 형식이라는 주장이 아니다. 파일을 지원하면 파일명·제공된 형식·인코딩 해석도 기록하되 정확한 바이너리 원본 보존을 검증하지 않았다면 그렇게 표시하지 않는다.

`locator`는 해당 contentText의 UTF-16 코드 단위 `[start,end)` 범위다. 따로 지정하지 않은 SourceVersion의 단위도 동일하다. 본문 없는 링크 참조는 locator=null이며 본문 발췌를 만들지 않는다. 줄번호·문단번호는 표시용 파생값이고 정규화된 검색 텍스트의 위치를 원문 위치로 혼용하지 않는다. 추출 후보의 범위·인용문이 원문과 맞는지 적용 전에 검증한다.

`originalAuthor.relation=self/other/unknown`으로 내 기록·타인 작성·미상을 구분한다. 내 계정에 저장한 게시물이라고 내가 쓴 것으로 바꾸지 않는다. `segments.speakerRole=user/assistant/quote/unknown`은 대화 발화·인용의 구분이며, 구간별 원저자가 다르면 segments에 originalAuthor도 둔다. 역할 근거가 없는 복사 텍스트는 unknown이다. 원문에 적힌 “system”·지시문·코드도 가져온 자료이며 앱·AI의 실행 명령이 아니다.

`originalCreatedAt/originalUpdatedAt`은 원문에서 확인한 작성·수정 시각, `importedAt`은 앱이 가져온 시각이다. 원문의 사건 시각과도 구분한다. 연월·날짜만 있으면 그 정밀도로 보관하고 미상은 null로 둔다. 시각이 있으면 제공된 offset/timeZone과 근거를 보존하며 가져온 날을 원 작성일로 채우지 않는다.

`coverage.status`는 `full_text/partial/link_only/unknown`이다. full_text는 제공한 텍스트판 전체라는 확인이며 미디어·댓글까지 포함했다는 뜻이 아니다. `omissions`에는 이미지·첨부·댓글·앞뒤 문맥·링크 대상 등 알려진 누락을 둔다. 알 수 없는 범위는 unknown으로 남기고 AI로 채워 원문처럼 저장하지 않는다.

파생 후보는 `extractionMethod=manual/rule/ai`, `reviewStatus=proposed/confirmed`, `sourceRefs`를 갖는다. R1의 rule은 구절·문단·명시 링크를 추출하고 의미를 판정하지 않는다. 의미 해석·계획/수행 구조화·AI는 후속 선택 기능이다. 규칙 결과도 채택 전에는 proposed이고 `confirmed`는 사용자의 채택이며 원문 주장 전체의 외부 검증을 뜻하지 않는다. 후속 기능에서도 “내일 읽겠다”를 계획이나 “읽었다”를 완료 활동으로 바꾸는 선택은 사용자가 확인한다.

## 중복·새 버전·겹침

`contentHash`는 확보한 문자열의 UTF-8 인코딩에 대한 해시로 내용 비교에 사용한다. 본문 미확보인 링크는 해시가 없고 링크·출처 메타데이터로 중복 후보만 비교한다. 출처 정체성·역할·확보 범위·원저자/원시각은 별도로 비교한다. 해시가 같아도 다른 사람·문서의 같은 문장을 자동 병합하지 않는다. 원문 변경 여부와 로컬 수정 revision은 다른 개념이다.

| 분류 | 판단 근거 | 적용 |
| --- | --- | --- |
| `exact_duplicate` | 같은 원천임이 확인되고 내용·역할·확보 범위·원출처 메타데이터도 같음 | 기존 SourceVersion 재사용 후보를 보여주고 새 파생 항목 중복 생성을 기본 해제 |
| `new_revision` | 같은 원천임이 확인됐지만 본문 또는 출처 메타데이터가 달라짐 | 새 SourceVersion 추가, 이전 버전·기존 발췌 유지; 최신 선택은 검토 후 변경 |
| `overlap` | 부분 인용·거의 같은 본문·원천 정체성 미확인 | 비교 후 별개 보관/같은 원천 연결/건너뛰기 선택; 자동 원문 합치기 금지 |
| 서로 모순됨 | 날짜·발화자·사실 주장 등이 다름 | 양쪽 원문과 후보 보존, 충돌 표시; 최신 시각만으로 승자 선정 금지 |

원천 ID가 없으면 URL·파일 경로·사용자 확인을 동일성의 단서로 삼는다. URL 정규화나 파일명만으로 동일성을 확정하지 않는다. 반복 가져온 사실은 import session의 이력으로 남기며 중복 원문을 매번 새로 만들 필요는 없다. 본문이 없던 링크에 본문을 제공하면 검토를 거친 새 SourceVersion으로 추가할 수 있다.

## 가져오기 staging과 원자 적용

R1 흐름은 선택·제공 → 원문 사본과 범위 보관 → 결정적 추출/수동 발췌 → 중복·추론 검토 → 통합 → 원문 추적 → 재열기·내보내기/사본 복원이다. 분류를 확정하지 않고 원문만 보관하는 선택도 유효하다.

1. `ImportSession`의 `stageId` 아래 받은 입력·범위·원천 후보를 staging에 저장한다. 제목/본문/URL 이외 필드는 확보된 것만 채운다. 저장 실패면 검토 초안이 영속 보관됐다고 표시하지 않는다.
2. 선택한 원문 범위에서 수동 발췌 또는 구절·문단·명시 링크 규칙으로 후보를 만든다. 원문 스냅샷은 수정하지 않는다. 사용자가 새로 쓴 제목·설명은 별도 후보이며 R1에서 의미 요약·날짜 해석을 자동 생성하지 않는다. 외부 AI 없이 이 과정을 완료한다.
3. 사용자가 포함/건너뛰기, 기존 자료 연결/별개 보관, 항목 종류·주제 연결을 검토한다. 후보를 고치면 수정 내용과 근거를 분리하며 Activity·Plan 자동 생성은 하지 않는다.
4. 적용 시 원문 해시·locator·선택 결과·현재 workspace revision·검토한 stageRevision을 다시 확인한다. 기존 `Storage.commitLocal`로 선택한 Source/SourceVersion·파생 항목·링크·재개 정보와 성공 영수증을 함께 반영하고 staging을 applied로 바꾼다. 다른 탭이 검토 선택을 바꿨다면 이전 선택으로 적용하지 않는다.
5. 취소·용량 오류·충돌에서는 해당 미적용 작업이 본 작업공간에 일부만 합쳐지지 않는다. staging은 재검토용으로 유지하거나 사용자가 폐기한다. 닫기 후에는 원문/검토 단계와 선택 상태로 재개하며 적용된 stage는 자동으로 재적용하지 않는다.

“자료만 보관”을 선택하면 원문 Source/SourceVersion만 먼저 commitLocal로 확정한다. 이후 발췌·모음 연결은 이미 보관한 버전을 참조하는 새 commitLocal로 저장한다. 원문과 발췌를 한꺼번에 선택한 경우에만 함께 원자 적용한다. 검토 취소는 미적용 ImportSession만 취소하며 이미 성공적으로 보관한 원문을 자동 삭제하지 않는다. staging은 “검토 중 보관됨”, 성공한 원문 저장과 통합 적용은 각각 완료 범위를 표시한다.

R1의 가져오기는 외부 자료를 현재 작업공간에 검토해 합치는 행위다. `life-tools-backup-v1` 복원은 검증된 앱 스냅샷을 새 작업공간 사본으로 만드는 별도 경로이며 추출·중복 병합을 다시 실행하지 않는다.

## 초기 저장 단위와 쓰기 계약

| 대안 | 이점 | 문제·선택 |
| --- | --- | --- |
| 기존 연표 JSON에 원문 추가 | 기존 경로 재사용 | 정규화·charts·백업과 결합하므로 채택하지 않음 |
| 신규 localStorage JSON | 시작 코드가 짧음 | 긴 원문 동기식 직렬화·다중 키 원자성 때문에 채택하지 않음 |
| IndexedDB의 bundle·staging | 검토와 적용 경계, 원자 커밋, 기존 저장소 분리 | 초기 가설로 선택; 실제 iPad 성능·실패 복구 검증 필요 |
| 원문별 저장소·서버 테이블 | 부분 조회·큰 자료 처리 | 작은 사용 단위 검증 후 필요한 분할만 도입 |

예시 `life-tools-v1` DB의 `bundles`, `operations`, `recovery`에 `staging`을 추가하는 설계다. bundle에는 `sources`, `sourceVersions`, `records`, `thoughts`, `links`, `resumeHints`, `tombstones`와 필요한 선택 모듈만 둔다. 논리 개념마다 원격 테이블을 만들지 않는다. 실제 R1은 bundles/operations/staging/meta/recovery 저장소와 최소 컬렉션을 구현하며 thoughts 및 후속 도메인 컬렉션은 아직 만들지 않았다. 정확한 런타임 형태는 [구현 계약](implementation-contract.md)을 따른다.

[오픈소스 검토](open-source-review.md)의 idb·Dexie 후보를 비교하고 원자 커밋·중단·업그레이드·두 탭 경합을 샘플로 확인한 뒤 adapter를 선택한다. SourceVersion의 의미·가져오기 검토·복원 계약은 앱 규칙이며 라이브러리 선택과 분리한다.

대형 이미지·음성·영상·책 전체·OCR은 R1 범위에 넣지 않는다. 텍스트도 실제 iPad에서 처리 가능한 건별/묶음 크기를 측정해 명시하고 초과 입력은 원문을 자르지 말고 적용 전 거절·분할 안내한다. bundle 5 MiB/항목 10,000개·저장 p95 100ms는 분할 검토 가설이며 지원 상한·성능 보장이 아니다. 원문이 커지면 SourceVersion을 별도 객체 저장소로 옮기되 트랜잭션·백업 계약을 유지한다.

`Storage.commitLocal({operationId,workspaceId,baseRevision,changes})`는 한 사용자 적용을 저장한다. `stored`이면 새 revision과 영수증, `conflict`이면 currentRevision·conflictRefs, `rejected`이면 error.code를 반환한다. 가져오기에서는 원문·선택 파생 항목·링크·stage 상태·operations를 같은 readwrite 트랜잭션에 넣는다. 직접 기록을 보완할 때도 이 계약을 사용한다.

성공한 stored 영수증만 영속화한다. 같은 operationId·내용 재시도는 영수증을 반환하고 같은 커밋 ID에 다른 내용을 붙이면 거절한다. rejected·트랜잭션 중단은 작업 기록도 중단하므로 원인 해소 후 같은 ID·내용으로 재시도한다. 충돌 해결로 기준 revision이나 내용이 달라지면 새 operationId를 만든다.

`baseRevision`은 로컬 workspace revision, 수정 항목의 `expectedRevision`은 항목 revision, 후속 원격 `remoteRevision`은 서버 비교값이다. SourceVersion ID는 원문 버전을 고정하는 별도 식별자다. 첫 구현은 workspace revision 불일치 시 양쪽과 staging을 보존해 재검토하며 자동 덮어쓰지 않는다. BroadcastChannel은 갱신 알림일 뿐 잠금이 아니다.

동기화는 `not_configured/pending/syncing/synced/conflict/error`로 별도 표시한다. stored+not_configured는 “이 브라우저에 저장됨”, stored+error는 “이 브라우저에 저장됨 · 동기화 실패”다. 인증 만료는 `error.code=auth_required`; 로컬 적용을 취소하지 않는다. IDB 열기 실패·quota·앱 종료 전 미커밋 상태는 초안을 유지하고 내보내기를 안내한다.

`resumeHint`는 `{sourceId?,sourceVersionId?,stageId?,entityRef?,locator?,note?,revision}`로 원문·검토·통합 결과의 다시 열 위치를 담는다. 후속 활동 모듈의 activityId/objectId도 선택 확장으로 허용한다. 탐색 cursor는 기기 UI 상태이며 저장된 원문·수행 사실을 변경하지 않는다. 실행 취소는 새 작업으로 처리하고 성공 영수증·revision을 과거로 되감지 않는다.

stored는 현재 브라우저 프로필·origin의 트랜잭션 완료다. 다른 브라우저/프로필·홈 화면 실행과의 공유나 사이트 데이터 제거·축출·기기 분실 뒤 보존을 보장하지 않는다. 같은 IDB의 recovery도 독립 백업이 아니다. R1은 개인 브라우저 프로필을 전제로 하며 저장소 지속성 권한은 백업 보장이 아니다.

## 원문 수정·삭제와 파생 항목

새 원문을 가져오면 새 SourceVersion을 추가한다. 기존 발췌의 locator·인용은 예전 버전에 고정하고 “새 원문 있음”을 표시한다. 같은 문장이 새 버전에서도 보인다고 참조를 자동 이동하지 않는다. 다시 연결할 때 원문 범위·사용자 수정·누락 범위를 검토한다.

외부 게시물 삭제·접근 불가는 앱에 보관한 원문 사본 삭제와 다르다. 외부 접근 상태를 알게 되면 표시하되 기존 스냅샷을 조용히 지우거나 링크만으로 최신 내용을 안다고 판단하지 않는다. 반대로 앱 사본 삭제가 외부 게시물을 삭제하지 않는다.

앱 원문 삭제는 Source/SourceVersion tombstone·검색/AI 선택 제외·파생물 무효화를 같은 로컬 작업으로 기록한다. 연결 발췌·요약은 근거 없음/재검토 상태로 기본 숨기고, 독립적인 사용자 생각은 유지하면서 `source_missing`을 표시한다. 연결 해제만 하면 원문·독립 항목은 삭제하지 않는다.

영구 삭제 전 원문을 복제한 인용·요약·첨부·공유본의 포함 범위를 보여주고 제거 대상을 정한다. 지우지 않은 독립 내용까지 삭제됐다고 표시하지 않는다. 이미 내려받은 백업·외부 사본은 현재 앱 삭제로 회수되지 않는다. 휴지통 복구와 영구 삭제를 구분하며 내용 없는 최소 tombstone으로 오래된 기기의 부활을 막는다.

## 자기완결 백업·내보내기·사본 복원

`life-tools-backup-v1`에는 schemaVersion, 내보낸 시점, 작업공간 스냅샷, 보관 중인 SourceVersion의 contentText·메타데이터·coverage, 파생 내용·sourceRefs, 삭제 표식, 파일 목록·해시를 넣는다. 기본 백업은 확정된 작업공간 전체이며 미적용 staging은 포함 여부를 사용자가 선택하고 manifest에 표시한다. 토큰·접속 키·로그인 세션은 제외한다.

자기완결은 “이 앱이 보관한 텍스트와 연결을 외부 사이트에 접속하지 않고 다시 여는 것”이다. 링크만 제공한 자료·미제공 이미지·첨부까지 복원된다는 뜻은 아니다. 포함한 본문·미디어와 링크만 있는 항목·누락 범위를 manifest와 내보내기 화면에 표시한다. 링크 목록만 내보낸 파일을 원문 포함 백업이라고 부르지 않는다.

앱 전용 JSON 백업과 별도로 선택 원문/통합 내용을 UTF-8 텍스트·Markdown으로 내보내는 경로를 둔다. 출처 설명·버전·인용 범위를 함께 내보내 재사용할 수 있게 한다. 후속 첨부 기능은 실제 바이트·해시·용량·누락 목록을 포함하는 별도 계약이 필요하다. 해시는 손상 탐지이며 암호화·저자 인증은 아니다.

기존 `haedo-backup-v1` 읽기/쓰기는 유지하며 신규 자료 포함 여부를 명시한다. 통합 백업에서는 연표 원문을 별도 구획에 보존하고 연결 대응표를 둔다. 사용자 데이터의 이전·복원 구현 전 실제 보존 대상과 백업 상태를 먼저 확인한다.

복원은 형식·버전·개수·해시·참조·locator를 검사한 뒤 새 workspace/entity/source/sourceVersion/operation ID와 내부 참조를 대응시켜 원자 설치한다. 복원하면서 텍스트를 재추출하거나 원문 내용을 정규화하지 않는다. 계정·remoteRevision·활성 공유권한·미완료 외부 실행은 자동 승계하지 않는다. 원래 ID는 출처 메타데이터로만 남긴다.

선택해 포함한 staging은 미적용 상태로 복원하고 자동 통합하지 않는다. 알 수 없는 상위 schemaVersion은 쓰기를 막고 원문 내보내기를 허용한다. 손상 항목은 원문을 보존해 격리하고 누락 개수를 보고하며 조용히 버리지 않는다. 마이그레이션은 이전 사본→변환·검증→포인터 전환으로 실패 시 기존 사본을 유지한다.

다운로드 요청 성공과 사용자의 실제 파일 보관을 구분한다. R1 검증은 격리 샘플의 사이트 저장소를 제거한 뒤 별도 보관한 백업을 오프라인 복원하고, 실제 iPad Chrome에서 파일 저장·재선택도 확인한다. 기기 분실 복구에는 해당 기기 밖에서 접근할 수 있는 사본이 필요하다.

## 후속 원격 동기화·충돌·공유

R1은 개인 로컬 가져오기·통합·재열기·백업으로 완결한다. 새 원격 동기화·특정인 공유·공개는 후속 단계이며 기존 charts 큐와 분리한다. 서버가 소유권·remoteRevision·operationId를 원자 검증하도록 별도 구현·검증해야 한다.

동시에 받은 서로 다른 원문 버전·독립 항목은 보존하고 같은 항목 수정은 기준/로컬/원격 사본으로 비교한다. 삭제와 오프라인 수정이 만나면 삭제 표식 유지·수정 복구 사본을 제안하며 자동 부활시키지 않는다. 미확인 전송은 같은 operationId로 결과를 대조한다. 기기 시각으로 덮어쓰기 우선순위를 정하지 않는다.

작업공간·staging·큐·캐시는 ownerLocalId+accountBinding+originScope 범위로 나눈다. 계정/연결 변경 중인 작업은 중지하고 이전 계정 응답을 현재 공간에 적용하지 않는다. 로컬 자료·미전송 작업을 새 계정에 자동 올리지 않는다. 원격 tombstone을 압축하면 오래된 기기는 전체 재동기화하도록 별도 epoch 정책이 필요하다.

비공개 원본과 공유본은 별도다. ShareSnapshot은 `shareId`, 고정 `entityRefs`, 필요한 원문 범위의 `sourceRefs`, `fieldAllowlist`, `contentSnapshot`, `audience`, `approvalRevision`, `status`, `revokedAt?`를 가진다. sourceRefs는 원문 참조 전용이며 공유 원본 전체를 받는 권한이 아니다. 원문 작성자가 사용자라고 공개 권한을 자동 추정하지 않는다.

개인→특정인은 선택 필드·수신자·고정 버전을 확인하고 승인한다. 특정인→공개는 새 미리보기·승인이 필요하며 원문 전체·대화·댓글·수신자 목록·개인 경로가 따라가지 않는다. 원본 수정은 공유본을 자동 갱신하지 않는다. 공개→특정인/개인은 공개 접근 철회 후 허용된 사본만 제공한다.

특정인 공유는 수신자 인증·서버 권한 검사가 필요하다. 철회는 즉시 로컬 추가 게시를 막고 `pending_revocation`, 서버 접근 차단 확인 후 `revoked`로 표시한다. 원본 삭제도 관련 공유본 철회 대상으로 올리고 검색·캐시·파생물을 추적한다. 늦은 응답은 approvalRevision/권한 epoch로 걸러 재활성화하지 않는다. 이미 받은 파일·화면 캡처·외부 사본의 회수는 보장할 수 없다.

## 선택 모듈과 기존 연표 연결

책·교재 구조화는 가져온 자료를 이용하는 선택 모듈이다. 공용 서지·판본 사실은 개인 보유·진도·생각과 분리하고 정보 출처를 보존한다. 범용 원문 수집을 위해 먼저 공용 카탈로그를 만들지 않는다. 원문의 “읽었다”나 페이지 숫자가 개인 진도로 자동 반영되지 않는다.

확인한 수행을 관리할 때 탐색 cursor, 사용자 재개 위치, 실제 수행 segments, 재독 passId, 이해·문제 완료를 분리한다. 1–20·31–40쪽 수행은 해당 회차 30쪽이며 90쪽 탐색으로 늘지 않는다. 재독은 새 활동과 회차 표시로 원본 구간을 보존한다. 문제는 unattempted/in_progress/completed와 별도 검토 필요·정답 확인·해설 이해를 가진다.

분야 확장은 `{type,version,data}`이며 모르는 필드는 보존한다. 장소 방문·프로젝트·관계·반복 계획은 필요한 단계에서 연결한다. 계획 수행함은 사용자 확인, 중단한 활동 재개는 같은 ID, 완료 뒤 별도 수행은 새 ID다. 날짜만 알면 날짜로, 월만 알면 월로, 미상이면 미상으로 두며 시각 구간은 `[start,end)`·timeZone을 보존한다.

레거시 링크는 `{namespace:'charts',originScope,legacyDocId,legacyEntityId?,entityRef}`로 일반화한다. `entityRef`는 새 Source/Record/Thought/Activity 등이며 activityId 전용 링크를 강제하지 않는다. 처음은 읽기 전용 연결이고 기존 연표·charts 항목을 자동 생성·수정하지 않는다. 연표에도 표시하는 기능은 원본 참조를 추적하는 후속 어댑터와 별도 회귀 검증이 필요하다.

## 다른 담당 계약과 완료 기준

- 기술·경험: sourceRefs/SourceVersion/ImportSession은 같은 명칭을 쓰고, 입력 지원 형식·용량은 조사한 범위만 약속한다. staging 저장·통합 완료·백업 복원을 서로 다른 상태로 표시한다.
- AI: sourceRefs의 version/locator와 현재 권한을 확인하고 원문은 명령으로 실행하지 않는다. 제안은 proposed이며 사용자 채택 시 commitLocal 기준 revision을 확인한다. 원문 삭제·변경 후 늦은 결과를 자동 적용하지 않는다.
- 분야: R1 자료 보관·발췌·주제 연결을 Activity/Plan 생성 없이 완료할 수 있게 한다. 같은 원문이 여러 보기에서 보여도 복제 입력을 요구하지 않는다.

문서 계약의 정리와 구현 검증은 다르다. 구현 때 익명 샘플로 아래를 검증하고 기존 22/28 검사와 별도 결과를 남긴다.

1. 네 원천에서 사용자가 제공한 텍스트/Markdown/링크를 처리하고 본문 없음·부분 제공·누락 이미지·원저자/원시각 미상·user/assistant/quote 구분을 보존한다.
2. 수동 발췌·규칙 추출·사용자 수정에서 locator가 정확한 원문으로 돌아가고 미검토 후보·원문 지시문이 활동/계획/실행 권한으로 바뀌지 않는다.
3. exact duplicate/new revision/overlap·내용 모순을 비교하고 동일성 미확인 항목을 자동 합치지 않는다. 새 버전에서 과거 인용이 자동 이동하지 않는다.
4. 적용 전/중 종료·quota·두 탭 경합·같은 작업 재시도에서 부분 통합·이중 생성·가짜 성공 없이 staging과 원문을 복구한다.
5. 닫기→재열기→원문 추적→내보내기→사이트 저장소 제거→오프라인 사본 복원으로 본문·버전·발췌·참조·누락 표시를 보존한다. 실제 iPad Chrome의 입력·파일 경로와 한계도 별도 기록한다.
6. 원문 삭제·새 버전·외부 링크 소멸에서 독립 생각과 파생 인용의 처리 범위가 명확하고 검색·AI·공유에 삭제된 내용이 재유입되지 않는다.
7. 구/신 백업과 레거시 연결에서 기존 caeyeon_life_*·charts가 변경되지 않는다. 복원이 계정·공유·미완료 전송을 부활시키지 않는다.
8. 후속 동기화·공유 구현 시 계정 전환·응답 유실·삭제 충돌·권한 철회·늦은 응답과 승인 필드 범위를 따로 검증한다.
