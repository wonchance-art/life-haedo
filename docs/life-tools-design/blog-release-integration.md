2026-10-18 KST. **#94의 최종 홈·작성기 변경 + #95의 블로그·자료실 + #96의 선택 근거 파일**을 한 후보에서 검수하고, 배포·되돌림과 실제 기기 체험을 준비하는 기록이다. 이번 실행 범위는 **통합 후 검수와 배포 준비까지**이며, main 병합·Pages 배포·새 개인 자료의 외부 전송·공개는 실행하지 않는다.

## 통합 후보의 출시 검수

1. **한 후보 확정.** #94·#95·#96의 포함 관계와 최종 커밋을 확인한다. 이미 포함된 변경을 다시 순차 적용하지 않는다. 홈·작성기·공통 탐색은 #94의 최종 동작을 존중하며 자료실·글 관리·공개·보관 파일 진입을 연결한다. 통합 후 바뀐 파일과 보존할 저장 형식·계정 경계를 기록한다.
2. **현재 후보 검사.** README의 `npm run check`·`npm test`와 `.github/workflows/pages.yml`의 `check`·기존 `browser` 집계·`blog`를 같은 후보에서 확인한다. 실제 생성 사이트는 `scripts/prepare-site.mjs`의 허용 목록·공개 설정·SHELL 전체 해시를 대조한다. 코드 변경 뒤 필요한 검수는 다시 하되 이미 통과한 같은 후보의 검사를 근거 없이 반복하지 않는다.
3. **이전 배포에서 업데이트.** `scripts/verify-prepared-site.mjs`는 실제 이전 커밋의 사이트를 보존해 생성 사이트와 서비스워커 업데이트를 확인한다. `PREVIOUS_RELEASE`는 당시 실제 배포된 커밋으로 정하고, 통합 중간 커밋을 운영 직전 버전이라고 추정하지 않는다. 기존 브라우저의 글·초안·원본 사진을 남긴 채 업데이트하고 새 모듈·따뜻한 오프라인 재열기를 확인한다. 공개 본문·RPC·원본 사진 응답은 캐시에 남지 않아야 한다.
4. **대표 사용자 흐름.** 로그인 전 안내 → 합성 인증으로 계정 진입 → 홈에서 여행 글 작성 → 비공개 저장 → 홈/글 관리에서 같은 글 재열기 → 원본 확대·파일 복원 → 원문 인용/9칸 정확 근거 왕복을 확인한다. 새 작성기와 기존 일반 글 경로를 구분하고 저장 실패·뒤로가기·다른 탭·계정 변경에서 입력과 원본을 보존한다. 공개 흐름은 합성 RPC 또는 격리 SQL 검수로 연결하고 운영 개인 글을 시험 게시하지 않는다.
5. **독립 화면 검토.** 1440·820·390px에서 긴 한글 제목·본문·사진 설명·빈 목록·부분 실패·저장 오류를 확인한다. 확정 `DESIGN.md`의 글꼴·공통 색·44px 조작·초점·가로 넘침·실제 대비와 글을 쓰고 찾는 부담을 각각 판단한다. 익명 읽기의 실제 자체 호스팅 글꼴 로드와 CSP 오류도 확인한다. 화면 폭 모사는 Mac/iPad/iPhone 체험과 구분한다.

새 통합에 SQL/Edge 변경이 없다면 기존 설치를 유지한다. 추가 스키마나 버킷 변경이 정말 필요해지면 이번 정적 릴리스 준비와 분리해 근거와 보존 계획을 먼저 확정한다. 현재 검사 실패를 해소하려고 운영 권한을 넓히거나 개인 자료를 변경하지 않는다.

## 운영에서 필요한 읽기 전용 확인

설치 상태는 `supabase/tests/blog-installation.sql`의 메타데이터 조건, 실제 migration 이력과 파일 SHA, Edge 배포 버전·함수 이름을 대조한다. 공개 RPC의 익명 권한과 개인 RPC/미디어 위치 조회의 익명 거절, 존재하지 않는 공개 사진의 404·`no-store`·`nosniff`를 확인한다. 공개 키만 사용하는 익명 요청으로 확인할 수 있는 범위와 관리자 메타데이터 조회를 구분한다. 키·계정 식별자·개인 본문을 로그나 캡처에 남기지 않는다.

이 확인은 기존 자료의 본문 조회·실사용자 로그인 세션 복사·개인 글 업로드·사진 게시·삭제·소유권 변경을 요구하지 않는다. 빈 토큰 응답과 거절이 정상이어도 실제 로그인·관리형 Storage 업로드·유효한 게시 사진 읽기까지 통과한 것은 아니다. 해당 경로의 실제 사용은 아래 별도 체험 단계에서 다룬다.

이번 통합 준비에서 총괄이 운영 설치 조건 **11/11**, migration `20261017144744`, `haedo-blog-media` Edge v1 ACTIVE를 읽기 전용으로 재확인했다. 익명 공개 읽기는 200의 빈 결과, 개인 RPC와 미디어 위치 RPC는 401, 없는 공개 사진의 Edge는 404와 `no-store`·`nosniff`를 반환했다. 별도 라이브 바이트 대조에서 현재 `index.html`·`sw.js`는 실제 main `29a325b8e90702eb0f56e64732440cbe2e8c616e`와 일치하고 캐시는 v90이었다. 이는 이번 후보가 배포됐다는 증거가 아니라 **기존 라이브가 그대로 유지된다는 새 확인**이다.

## 배포 준비와 실제 실행의 경계

현재 workflow는 **main push와 `workflow_dispatch` 모두** `build`·`deploy`를 실행할 수 있다. 수동 workflow 실행을 읽기 전용 검수나 배포 없는 CI로 사용하지 않는다. 현재 범위에서는 PR과 로컬 통합 후보를 검수하고 배포용 산출물·절차만 준비한다.

실제 배포를 진행할 때는 검수한 후보 SHA, 직전 배포 SHA·캐시 이름·사이트 주소, 실행할 workflow와 되돌림 후보를 먼저 고정한다. 개인 파일·Git 이력·SQL fixture·서버 키·Edge 소스가 Pages 산출물에 들어가지 않는지 확인한다. 로그인 콜백 주소와 공개 설정은 실제 배포 origin을 기준으로 대조하며 인증 키를 문서에 복사하지 않는다.

배포 성공의 증거는 workflow의 성공 표시만이 아니다. 실제 Pages 주소에서 제공되는 문서·스크립트·서비스워커가 같은 후보인지 확인하고, 기존 캐시 사용 세션과 새 세션에서 로그인 전 화면·개인 저장소 비노출·공통 탐색·공개 읽기를 확인한다. 기존 서비스워커를 삭제해 업데이트 경로를 우회하지 않는다. 라이브 확인 전에는 “배포 완료”로 표시하지 않는다. 실제 Google 로그인이나 개인 글 게시를 하지 않았다면 그 한계도 함께 남긴다.

## 되돌림과 데이터 보존

되돌림 대상은 우선 정적 앱 배포다. 서버 테이블·버킷·원본·공개 사본을 지우거나 migration down을 실행하는 절차가 아니다. 브라우저 데이터·IndexedDB·파일·서비스워커 전체 삭제를 복구 수단으로 요구하지 않는다.

출시 전에 **새 데이터 형식을 보존하며 읽을 수 있는 호환 후보**를 준비한다. 기존 main이 오래된 버전이라면 그 코드를 그대로 다시 제공해도 새 글·근거 파일·계정 경계를 사용할 수 있다고 가정하지 않는다. 문제가 좁으면 확인된 안정 동작을 포함한 수정 후보를 만들고 새 캐시 버전으로 검수하는 편이 낫다. 되돌린 정적 코드가 이미 공개한 글을 자동 철회하거나 서버 데이터를 과거 상태로 복구한다고 표시하지 않는다.

되돌림을 실제 실행할 때도 해당 실행 권한과 후보·영향 범위를 확인하고, 그 후보의 정적 산출물·저장 형식 호환·이전 캐시 업데이트를 검증한다. 실행 뒤 라이브 코드·캐시·기존 글·초안·사진 보존과 공개 관리 경로를 다시 확인한다. 검증된 호환 후보가 없으면 안전하게 되돌릴 수 있다고 약속하지 않고 입력·원본 보존과 수정 경로를 먼저 정한다.

## 여행 글 한 편의 실제 Google·Apple 체험

이 절은 **미실행 체험 절차**다. 실제 배포 주소와 Mac·iPad Chrome·iPhone 접근, 사용자가 선택한 시험 범위가 있어야 한다. 실제 Google 인증은 소유자가 직접 수행하고 에이전트가 개인 프로필·기존 Auth 토큰을 복사하지 않는다. 새 개인 자료의 외부 전송·공개는 현재 준비 작업의 권한에 포함되지 않는다. 합성 사진이라도 운영 서버 업로드·게시를 이 문서만으로 자동 실행하지 않는다.

소유자가 “저장하면 누가 보는가”, “전체 원본 서버 보관과 선택 사진 공개는 어떻게 다른가”, “다른 기기에 근거까지 옮기는 파일은 무엇인가”를 직접 구분하는지 확인한다. 사용자가 멈춘 위치·설명이 필요했던 문구·복구 부담을 기록해 가장 가까운 개선으로 연결한다. 자동 검사 통과를 이 이해도 체험으로 대체하지 않는다.
