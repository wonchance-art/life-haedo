# 블로그 글의 비공개 보관과 선택 공개

## 글 저장 시 비공개 서버 보관 기본 — 2026-10-20 사용자 결정

기본 작성기의 **글 저장**은 본문과 모든 원본 사진을 내 계정 서버에 비공개로 보관하는 것을 기본으로 한다. 저장 앞에는 이 범위를 짧게 안내한다. 이번 사용자 요청이 이 기본 보관을 허용하며, 매번 별도 보관 동의를 다시 요구하지 않는다. 공개할 내용·사진 선택과 게시 동의는 그대로 별도다. 아래 이전 기록의 “서버 보관을 별도로 시작”하는 절차는 기본 작성기에 대해 이 계약으로 갱신한다.

- 대상은 `PhotoPostUI.finish()`와 `saveIndependent('saved')`의 명시 저장이다. 기존 저장 글을 수정한 경우도 사용자가 명시적으로 저장할 때 해당 글만 처리한다.
- 입력·초안 자동 저장·사진/대상 첨부·ZIP 복원·9칸 초안 생성·앱 부팅·기존 글 재열기만으로 전송하지 않는다. 과거 저장 글이나 다른 초안을 한꺼번에 서버로 올리지 않는다.
- 기존 로컬 저장을 먼저 완료하고 기존 BlogSync의 `saveDefault` 경로로 그 글의 비공개 서버 보관을 시도한다. 원격 전송 실패를 로컬 저장 실패로 바꾸거나 저장한 글을 없애지 않는다.
- 화면은 로컬 저장 성공과 서버 보관 중·성공·실패·충돌을 구분한다. 실패하면 로컬 글과 원본 사진을 유지하고 재시도할 수 있게 한다. 영속 작업 영수증·원격 CAS를 유지해 응답 유실 후 같은 보관 요청의 재시도가 중복 글을 만들지 않게 한다.
- 사용자가 명시적으로 서버 보관을 중지한 글은 다시 저장해도 자동으로 재개하지 않는다. 수정 저장으로 로컬 글 ID가 바뀌는 경우에도 이 선택을 유지해야 하며 해당 계승 경계는 구현·검수 대상이다.
- 원본 사진의 바이트·해상도·설명·대체 텍스트와 파일 안 메타데이터를 비공개로 보관한다. 재압축·축소·메타데이터 제거를 새로 수행하지 않는다.
- 공개 사진 선택의 기본값은 0개다. 비공개 서버 보관 성공이 공개본 생성·갱신·철회나 공개 사진 선택을 대신하지 않는다.
- 구조화 인용 근거 sidecar·다른 원문·개인 메모·작성 준비를 새로 전송하지 않는다. 기존 전용 근거 파일과 별도 자료 이동 계약은 유지한다.

구현과 독립 코드 검토를 완료했다. 정적 검사·단위 1,110/1,110, 실제 SDK/IndexedDB의 기본 서버 보관 8개 흐름과 3폭 9개 화면, v143→v144 업데이트·기존 데이터 보존 9/9를 통과했다. 새 브라우저 검수의 첫 진입 선택자와 계정 전환의 서버 확인 누락은 합성 fixture를 기존 실제 진입·검증 계약에 맞춰 수정하고 첫 증거를 보존했다. 9칸 기존 검수는 앞선 5개 통과 후 새 fixture 첫 로딩 시간 초과가 있었으며, 코드·제한 변경 없이 남은 3개를 집중 검수해 통과했다. 전체 CI·SQL 연계 회귀·최종 배포는 아직 미완료다. 실제 사용자 데이터 전송과 Google·Apple 체험을 이 합성 검수로 대신하지 않는다. 아래 과거 검수 수치는 이번 정책의 완료 증거가 아니다.

## 원문 근거의 로컬 범위

인용 글은 선택 구절·출처 제목/URL·내 생각을 작성기 본문에 넣고, 정확한 원문 ID/버전·범위·해시는 계정/작업공간별 별도 근거 sidecar로 보관한다. 새 초안과 근거를 함께 저장하므로 실패하면 어느 쪽도 부분 설치하지 않고 구절과 입력을 유지한다. 원문이 달라지거나 없으면 최신 버전을 대신 열지 않는다.

사진 글 ZIP·HTML·글별 서버 보관에는 본문에 명시적으로 넣은 인용/출처 문자열은 남지만 이 sidecar는 따라가지 않는다. 다른 기기나 ZIP으로 받은 사본에서 구조화된 근거까지 복원됐다고 표시하지 않는다. 9칸 v2 파일은 고른 항목의 근거 스냅샷을 보존하지만, 원래 작업공간의 자료가 없거나 저장 글 revision이 달라졌다면 정확한 재열기는 불가능하다고 알린다. 저장 글과 원문 자체의 이동은 별도 경로다.

## 원본 문서와 공개 사본

`assets/life/blog.js`는 저장소나 네트워크를 열지 않는 모델이다. `pack(doc)`는 기존 PhotoPost v1/v2의 형식·ID·수정 기준·본문 Delta·사진 메타데이터를 유지하고 Blob만 분리한다. `validateManifest()`는 엄격한 필드·본문·사진 선언을 검증하고 `hydrate(manifest, photos)`는 누락/중복·형식·크기·파일 서명·SHA-256을 확인해 원본 문서를 복원한다. 브라우저의 이미지 디코더가 있으면 실제 픽셀 크기도 대조한다. Node 검사에서 이미지 디코딩까지 수행했다고 해석하지 않는다. 수신 후 새 사본 ID를 만드는 일과 원래 글의 보존은 저장·동기화 계층이 담당한다.

공개 모델 `life-blog-public-v1`의 필드는 `format`, `title`, 제한 Delta `ops`, 검토한 `attachments`, `photos`, 직접 고른 `author.name/intro`뿐이다. 계정·작업공간·원래 글/사진 ID·파일명·초안·수정 대상·원문 참조 sidecar·개인 메모를 포함하지 않는다. `publicSnapshot(doc, {photoIds, author})`에서 사진 선택의 기본값은 빈 배열이다. 선택하지 않은 사진은 사진 메타데이터뿐 아니라 본문의 사진 삽입·설명·대체 텍스트에서도 빠진다. 선택한 사진에는 새 공개 식별자를 부여하고 원본 문서를 바꾸지 않는다. 사진 없는 기본 작성기 글도 같은 공개 모델을 사용한다.

미리보기와 익명 읽기는 `BlogPublicUI.render()`의 동일한 제한 Delta 렌더러를 사용한다. 본문 문자열을 HTML로 실행하지 않고, 지원하는 문단·제목·인용·목록·정렬·강조·안전한 링크만 DOM으로 만든다. 원격 이미지 URL이나 임의 embed를 본문에 넣지 않는다. 글의 첨부에는 이미 검토한 종류·제목·창작자·출처만 사용한다.

## 선택·확정·읽기의 경계

개인 화면은 공개 내용 검토에서 이름·소개·공개할 사진을 직접 고르고 미리보기를 갱신한다. 미선택 사진이 본문에서 제외되는 사실을 설명하며, 선택을 바꾸면 앞선 미리보기와 동의를 무효화한다. 계정 서버에 이 글 전체와 모든 사진 원본을 비공개로 보관하는 범위와, 그중 선택 사진을 공개하는 범위는 별도 동의다. 원본 파일을 공개하면 파일에 포함된 촬영·위치 등 메타데이터도 노출될 수 있으므로 이를 명시 확인한다. 이 문서는 메타데이터 제거 또는 원본 다운로드 차단을 구현했다고 주장하지 않는다.

서버는 소유자가 보관한 정확한 비공개 글과 명시 선택한 사진 ID·이름/소개를 기준으로 공개 사본을 생성한다. 비공개 글 revision과 공개본 revision을 함께 비교하고 작업 ID 영수증을 유지한다. 클라이언트의 미리보기용 공개 사진 UUID를 서버의 저장 식별자로 신뢰하지 않는다. 공개 글과 블로그 주소는 개인 ID를 사용하는 대신 공개용 토큰을 사용한다.

방문자는 `blog.html?blog=AUTHOR_TOKEN`에서 공개 글 목록을 읽고 `blog.html?post=POST_TOKEN`으로 이동한다. 제목·순서·본문을 갱신해도 공개 유지 중에는 같은 글 주소를 사용한다. 목록은 `(updatedAt, token)` 복합 커서로 더 읽으며 같은 시각의 여러 글을 건너뛰지 않는다. 이름·소개는 명시 공개한 값만 사용하며 계정 이메일을 자동 복사하지 않는다. 공개 글이 없으면 빈 블로그를 표시한다.

`blog-public.js`는 공용 공개 키로 익명 RPC만 호출한다. 인증 SDK·세션·개인 IndexedDB·localStorage를 열지 않고 쿠키를 전송하지 않는다. 요청은 `no-store`, `credentials: omit`, 리퍼러 없음으로 제한하고 응답의 필드·토큰·공개 모델·크기를 확인한다. 공개 사진은 `/functions/v1/haedo-blog-media?token=…&photo=…`의 공개 상태 확인 경로로만 읽는다. 비공개 버킷 주소·서명된 장기 파일 URL을 방문자에게 제공하지 않는다. 사진은 전달된 원본 크기로 확대할 수 있고, 로드 실패 때에도 본문과 복구 안내가 남는다.

글 철회 후에는 목록·글 주소·사진의 새 접근을 함께 차단해야 한다. 브라우저는 새 상태를 확인해 철회된 본문과 사진을 제거하며, 페이지가 숨겨지거나 오프라인으로 바뀌면 기존 표시를 비운다. 접속 중인 페이지는 30초마다 상태를 재확인하므로 다른 화면에서 수행한 철회가 현재 화면에서 즉시 사라진다고 약속하지 않는다. 이미 읽거나 외부로 복사한 파일의 회수도 약속하지 않는다. 실제 Edge 설치·빈 endpoint의 캐시 헤더·관리형 서버 권한 확인은 [설치 기록](blog-installation.md)의 범위이며, 유효한 개인 사진의 운영 게시/읽기를 시험한 결과로 확대하지 않는다.

## 기존 구현과 오픈소스 선택

새 편집기·CMS·익명용 Supabase SDK를 추가하지 않았다. 제한 Delta·원본 Blob·기존 Quill 편집기, PhotoPost 검증·ZIP과 공용 인증을 재사용한다. 새 코드의 유지 범위는 비공개 전송 모델·명시 공개 투영·익명 렌더러·원본 자산 접근 경계다. [대표 블로그 편집기 비교](../design-review/blog-editor-comparison.md)의 Ghost/SmartEditor ONE 사용 흐름과 Quill 유지·Tiptap 비교 조건, [기존 Supabase/CMS 비교](open-source-review.md#선택한-사본의-공개-게시--기존-supabase와-별도-cms-비교)를 따른다. 현재 제약을 피하려고 저장된 Delta 전체를 다른 엔진 형식으로 자동 이관하지 않는다.

- Quill의 제한 Delta·custom blot 근거는 [공식 Delta 문서](https://quilljs.com/docs/delta)와 [커스터마이징](https://quilljs.com/docs/customization)이다. 기존 비교는 Quill 2.0.3·BSD-3-Clause와 유지보수 간격을 기록한다. 이번 GitHub 최신 릴리스 재조회는 HTTP 401로 확인되지 않아 이를 최신판 재검증 성공으로 표시하지 않는다. 새 vendor를 도입하거나 교체하지 않았다.
- Supabase의 [공식 API 경로·키 안내](https://supabase.com/docs/guides/api/creating-routes)를 이번 MCP 문서 검색으로 확인했다. 기존 REST/RPC와 공개 `apikey`로 읽으며 익명 페이지에 공용 인증 SDK를 복제하지 않는 근거다. 공식 GitHub 최신 릴리스 API는 [supabase-js 2.118.0](https://github.com/supabase/supabase-js/releases/tag/v2.118.0), 2026-10-15 12:55:27 UTC를 반환했다. 이는 현재 동봉 SDK를 업그레이드했거나 해당 버전으로 앱을 검증했다는 뜻이 아니다. 기존 공용 인증과 MIT vendor 라이선스를 유지한다.
- Supabase changelog 원문 요청은 환경 프록시의 HTTP 403으로 받지 못했다. 이를 우회하지 않고 공식 MCP 문서 검색으로 관련 API 경로를 확인했다. 새 SQL·버킷·Edge의 실제 적용 여부는 이 조사 결과 대신 [설치 기록](blog-installation.md)으로 확인한다.

## 이번 모델·방문자 검사

`node --test tests/blog-model.test.cjs tests/blog-public.test.cjs`의 9개 검사는 v1/v2 원본 왕복·사진 바이트·오염된 파일 거부·기본 미선택·공개 화이트리스트·사진 없는 새 글·익명 전송 옵션·잘못된 커서·취소·제한된 응답 읽기를 확인한다.

`BASE_URL=http://127.0.0.1:4173 node tests/blog-public-browser.cjs`는 실제 로컬 `blog.html`과 익명 합성 RPC/사진 응답을 사용한다. 모델 테스트와 달리 실제 Chromium 이미지 디코딩으로 1600×1200 PNG의 표시·원본 확대를 확인한다. 개인 IndexedDB/localStorage/sessionStorage 접근은 예외를 던지도록 막고도 목록→글→목록·같은 주소 갱신·철회·빈 블로그를 검증한다. 깨진 이미지의 안내, 오프라인 전환 후 표시 제거, 잘못된/중복 주소의 무요청 상태도 포함한다. 1440·820·390px의 가로 넘침·44px 조작·접근 가능한 이름·대비를 검사하고 캡처를 직접 읽었다. 증거는 `.local/blog-public/report.json`과 `post-*.png`다. 의도한 오프라인 전송 오류는 수집한 콘솔에서 정확한 오류 문구로 별도 집계하고 다른 오류를 허용하지 않는다.

공개 모델·목업 읽기의 통과는 실제 게시 RPC·RLS·Edge 권한 검증을 대신하지 않는다. 실제 Google 로그인·Apple Photos/Files·모바일 메모리 상한·운영 SQL 설치·배포는 이번 방문자 검사 범위에 없다. HEIC·전체 사진 라이브러리·자동 외부 게시·댓글·추천망도 추가하지 않았다. 현재 글·사진의 기본 작성·보관·개인 활용은 공개 기능의 성공에 의존하지 않는다.

통합 CI에서 드러난 연결 문제도 보완했다. 글 관리에서 연 글을 닫으면 같은 항목에 초점을 복원한다. 책과 회고의 자체 고정 도구막대에 공통 헤더의 스크롤 여백이 중복 적용되던 문제를 제거해 장 선택과 읽던 위치를 보존한다. 홈 자료실은 펼침 알림이 늦게 도착하더라도 화면을 떠날 때 실제 펼침 상태를 기억해 키보드로 다음 메뉴에 접근할 수 있다. 기존 검사는 새 홈의 실제 메뉴를 따라가도록 갱신하고, 비동기 목록·작업공간 전환·로그아웃 문서 전환의 완료를 기다린다. 원문·해시·선택 범위·계정 분리 단언은 유지했으며, 기존 브라우저 73단계의 명령을 네 CI 묶음에 각각 한 번씩 보존했다. 서버 검사도 임시 초기화용 소켓 대신 최종 TCP 서버의 준비를 확인한 뒤 시작한다.

운영에는 `20261017144744_life_blog_originals` 이력과 Edge 버전 1을 설치했다. 읽기 전용 11개 설치 조건과 익명 거절 경로를 확인했고 기존 작업공간 3개·원문 전송 영수증 1개는 유지됐다. 새 블로그 문서·자산·게시 사본은 0개다. 이 결과는 **개인 자료 없이 설치·기본 접근 경계를 확인한 상태**이며, 실제 사용자의 글/사진을 올려 게시한 상태가 아니다. 상세 migration 파일과 해시·버킷·응답 상태는 [운영 설치 기록](blog-installation.md)을 따른다. 프런트 배포와 실제 기기 검수는 별도 완료 조건으로 남긴다.
