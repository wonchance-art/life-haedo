# 블로그 플랫폼 방향 검토

2026-10-17 후속: 사용자 지시에 따라 [SNS형 UX·UI](../design-review/sns-blog-experience.md)를 전체 공통 화면에 적용했다. 피드·프로필·작성·읽기의 실제 동작을 연결했고, 공개·서버 전송 범위를 넓히지 않았다. 아래 공개 플랫폼 후속은 별도다.

2026-10-17 KST. 사용자의 “메인에서 무엇을 하는 곳인지 모르겠다”는 피드백과 “블로그 플랫폼의 형태로 진행하자”는 지시에 대한 제품 검토다. 이 문서는 방향과 적용 범위를 제안하며 운영 구현 완료를 뜻하지 않는다.

## 판단

**해도를 개인 블로그를 중심으로 구성하는 방향은 적합하다.** 사용자가 처음 이해할 대상은 글과 그 글을 쓴 사람이고, 첫 행동은 읽기 또는 글쓰기다. 흩어진 기록·취향·회고는 글을 쓰고 자신을 표현하는 데 필요한 개인 자료로 연결한다.

이는 기존 목적의 복원이다. [제품 기준](../../PRODUCT.md#목적과-사용자)은 이미 “라이프스타일 블로그인 내 페이지 뒤에 수집·관리·추천·자기 이해”를 둔다. [기존 설계](lifestyle-blog.md)는 방문자가 블로그를 보고, 소유자가 그 뒤의 개인 기능을 이용하는 구조를 설명한다. [두 순환 로드맵](roadmap.md#현재-실행-기준--두-순환--2026-10-14-kst)의 개인 활용·선택 공개도 이 구조와 양립한다.

목표로 하는 제품을 설명하는 문장은 **“내 생각과 일상을 글로 쓰고, 원하는 글을 공개하는 블로그”**로 제안한다. 현재 모든 형식의 글을 공개할 수 있다는 설명은 아니다. 기록 수집·자기 이해·책 만들기를 한 문장에 모두 넣어 첫 화면을 다시 추상화하지 않는다. 블로그를 쓰기 위해 자료 가져오기·컬렉션 등록·프로필 완성이 먼저 필요하지 않아야 한다.

## 어떤 블로그인가

글을 직접 쓰고 읽을 수 있는 개인 블로그를 중심으로, 비공개 집필과 선택 공개를 제공한다. 가져온 자료는 출처를 보존한 개인 자료실에 남고, 사용자가 선택한 내용만 별도 공개 사본으로 전달한다. 비공개로 쓰고 끝내는 것도 정상적인 사용이다.

| 필요한 역할 | 핵심 대상과 행동 | 별도로 유지할 것 |
| --- | --- | --- |
| 개인 블로그 | 내 글의 제목·본문·사진을 읽고 새 글 쓰기·수정하기 | 내 글의 비공개 저장과 공개 상태 |
| 비공개 집필 | 쓰던 글 이어쓰기·저장·재열기 | 이 브라우저 보관과 기기 간 동기화 범위 |
| 개인 자료실 | 가져온 기록·인용·책·음악 등을 글쓰기 맥락에서 찾기 | 원문·정확 버전·원저자와 내 생각 |
| 방문자 블로그 | 소개·대표 글·공개 글 읽기 | 개인 자료실·초안·관리 화면 |

여러 작가의 추천 글을 모으는 포털은 현재 사용 목적에서 도출되지 않는다. 작가 탐색·팔로우·댓글·알림·구독 결제·광고·랭킹은 독립된 사용자 필요와 운영 비용을 가진다. 이 기능들을 갖춰야 블로그라고 부를 수 있는 것은 아니다. 지금은 독자가 글을 읽고 작성자가 글을 완성하는 경험을 먼저 검증한다.

## 메인의 세 역할

아래 표는 목표로 하는 역할 구분이다. 현재 개인 홈의 실제 적용 범위와 후속 공개 블로그 구현을 구분하며, 홈에 별도 초안 이어쓰기 행이 구현됐다는 뜻은 아니다.

| 화면 | 처음 보여줄 내용 | 첫 행동 | 사용자가 이해해야 할 것 |
| --- | --- | --- | --- |
| 로그인 전 서비스 홈 | 해도가 블로그임을 알리는 한 문장, 실제 글 형태의 예시 | 시작하기, 예시 글 읽기 | 어떤 글을 쓰고 읽는 곳인가 |
| 로그인 후 개인 홈 | 내 블로그 제목·소개, 글쓰기, 쓰던 글, 최근 내 글 | 글쓰기·계속 쓰기·내 글 읽기 | 내 글은 어디 있으며 무엇을 이어 할 수 있는가 |
| 공개 블로그 홈 | 작성자 소개, 대표 글, 공개된 글 목록 | 글 읽기 | 누구의 어떤 글을 읽을 수 있는가 |

로그인 전 예시는 가상 자료임을 밝히며 사용자 보관함에 넣지 않는다. 실제 공개 블로그 목록을 조회할 기반이 없다면 예시를 인기 글·실시간 피드처럼 표시하지 않는다.

개인 홈에는 기록 수·동기화 정보·빈 도구 타일보다 실제 내 글을 먼저 둔다. 가져오기·기록·컬렉션·회고·연표는 계속 접근할 수 있어야 하지만 내 블로그를 쓰는 데 거쳐야 하는 관문으로 만들지 않는다. 프로필이나 글이 비어 있으면 제목·소개 입력을 강요하지 않고 **글쓰기**로 시작한다.

방문자 홈은 별도 공개 데이터만 읽는다. 개인 홈의 목록을 화면에서 일부 숨겨 방문자 화면으로 사용하는 방식은 공개 범위 검증을 대신할 수 없다. 소유자가 개인 홈과 방문자 관점을 전환할 때는 “내 블로그”와 “방문자 미리보기”를 구분하며, 미리보기를 공개 완료로 표현하지 않는다.

## 이번 적용 단위와 후속

이번 단위는 **메인 → 글쓰기 → 비공개 저장 → 같은 글 읽기 → 홈에서 다시 열기**다. 이 흐름을 이미 있는 작성기와 저장 모델로 연결하고, 메인에서 블로그라는 정체와 첫 행동을 드러낸다.

- 로그인 전에는 짧은 블로그 설명과 글 예시, 시작 진입을 둔다.
- 개인 홈은 내 글 중심으로 읽히게 하고 글쓰기·저장한 글 다시 열기를 앞세운다. 사진 글과 기존 글을 기존 저장 범위에 맞게 읽고 연다. 초안 이어쓰기는 기존 작성기의 초안 관리에서 이용하며 이번 홈의 별도 행으로 추가하지 않는다.
- 글마다 실제 상태를 표시한다. 저장한 글을 일괄 “발행 글”로 바꾸지 않는다.
- 가져온 기록과 기존 도구는 보존하며 보조 진입에서 계속 연다. 기존 URL·계정 격리·복구·백업 경계를 유지한다.

이 단위의 완료를 공개 블로그 플랫폼 전체 완성으로 보고하지 않는다. [사진 글 구현 기록](../design-review/blog-writing-completion.md#한계와-다음-판단)에 따르면 현재 사진·리치 글은 이 브라우저의 별도 저장 범위를 사용하고 공개 게시·기기 간 자동 동기화를 지원하지 않는다. [현행 공개 게시](../design-review/page-publication.md)는 선택 사본의 개별 공개 주소를 제공하며, 익명 작성자별 글 목록을 제공하는 블로그 인덱스와는 범위가 다르다.

다음 완결 단위는 **기존 공개 가능 글 한 편 선택 → 방문자 미리보기 → 명시적 게시 → 익명으로 글·작성자 블로그에서 다시 찾기 → 갱신·철회**다. 작성자별 공개 목록·고정 글 주소·실제 게시 상태·빈 블로그를 함께 설계해야 한다. 사진 게시를 연결하려면 공개할 사진 범위·원본과 공개본의 관계·저장/용량·철회·백업을 별도 완료 조건으로 정한다. 정체를 분명하게 만들기 위해 사진 공개가 이미 가능한 것처럼 보여주지 않는다.

기존 메뉴 명칭·주소를 전부 동시에 바꾸거나 CMS·프레임워크를 교체할 이유는 아직 없다. 먼저 메인과 글쓰기의 연결이 사용 이해를 높이는지 확인한다. 댓글·팔로우·작가 추천·수익화·자동 외부 게시·AI 보고서는 이 흐름의 선행 조건이 아니다.

### 이번 로컬 구현과 확인 범위

2026-10-17 로컬 구현은 로그인 전 블로그 안내, 개인 홈의 글쓰기·글 관리, 여러 기존 저장 형식의 최근 글 최대 5개, 자료실과 도구 진입을 연결했다. 최근 글에는 새 글·기존 첨부 글·기록으로 저장한 내 글이 포함된다. `글 관리`는 기존 내 페이지 화면이며 모든 형식의 내 글 전체 목록은 아니다. 별도 홈 초안 이어쓰기 행과 공개 블로그 목록·글별 공개 주소·신형 글/사진 공개는 이번 구현에 추가하지 않았다.

독립 QA 담당은 최신 Obsidian ZIP 변경과의 rebase 통합 전 브랜치에서 신규 블로그 홈 검사 **6/6**과 로그인 전·빈 홈·저장 후·조회 오류의 1440·820·390px **12상태**를 확인했다. 이 메인 검사에서 콘솔 오류·페이지 오류·예상 밖 외부 요청·원격 쓰기·공개 쓰기는 모두 0건이다. 실제 로컬 앱·공용 SDK·IndexedDB를 사용하고 인증/공개 RPC는 익명 합성 응답으로 검증한 Linux Chromium 화면 폭 모사다. 실제 OAuth·운영 DB·Apple 실기·배포·사용자 이해도 평가는 확인 범위가 아니다. 이 수치는 통합 HEAD의 재검 결과와 구분하며 기존 모든 회귀 검사나 공개 플랫폼 완료로 확대하지 않는다. 최종 통합 검증과 시각 검토 기록은 [메인 구현 검토](../design-review/blog-platform-home.md)에 별도로 남긴다.

최신 [Obsidian ZIP 복원과 지정 계정 반영](../design-review/obsidian-package.md)은 비공개 자료실을 채우는 별도 작업이다. 서버 계정에 자료를 보관한 결과와 사용자 브라우저의 자료 받기·실기·코드 배포는 구분한다. 가져온 원문은 블로그 글이나 공개 사본에 자동 편입되지 않고 자료실에서 찾아 활용한다. 이 메인 검사의 원격 쓰기 0건은 앞선 명시적 계정 반영 작업이 없었다는 뜻이 아니다.

### 첫 공개 단위의 최소 연결

**기존 공개 형식으로 표현할 수 있는 글 한 편을 공개 블로그에서 읽고, 같은 주소에서 갱신을 확인하고, 철회 후 목록과 직접 주소에서 접근할 수 없게 만드는 흐름**을 먼저 완결한다. 사진 글 전체 지원을 선행 조건으로 두지 않는다. 아래의 ‘일반 글’은 기존 일반·첨부 글과 선택한 기록을 뜻한다. 기본 작성기의 신형 글은 사진이 없어도 이 범위에 자동 포함되지 않으며, 신형·사진 글의 공개는 지원되지 않는다는 상태를 작성기와 검토에서 분명히 한다. 사진을 조용히 빼고 게시 성공으로 표시하지 않는다.

기존 공개 저장소는 계정·작업공간당 공개 사본 하나를 저장한다. 이 사본의 `title`·`intro`와 공개된 `entries`를 각각 블로그 소개와 글 목록으로 활용하는 것이 가장 작은 대안이다. 별도 전체 작가 목록이나 소셜 그래프가 없어도 개인 블로그는 성립한다.

다만 현행 `life-share-v1`의 `entries`에는 안정적인 공개 글 식별자와 글별 발행 시각이 없다. 현재 사본에 글이 여러 개 있다고 글별 주소·게시 상태가 구현된 것은 아니다. 새 공개 모델을 검토할 때 기존 사본의 엄격한 검증·읽기 호환성을 유지하면서 이 최소 정보만 확장한다. 기존 DB 테이블을 재사용할지 별도 공개 모델을 둘지는 구현 착수 시 현재 운영 제약과 비교하며, 이 문서로 스키마 변경을 확정하지 않는다.

| 순서 | 최소 연결 | 완료 기준 |
| --- | --- | --- |
| 1. 일반 글 한 편의 공개 검토 | 사용자가 고른 저장 글 한 편과 공개할 제목·본문·출처·첨부 범위만 고정해 미리 본다. 블로그 제목·소개에는 직접 고른 값이나 기본 제목을 사용한다 | 다른 저장 글·초안·자료실이 들어가지 않고, 검토와 익명 읽기가 같은 공개 데이터와 렌더러를 사용한다. 개인 저장은 그대로 비공개다 |
| 2. 블로그 주소와 글 주소 | 기존 공개 사본 주소를 블로그 진입으로 활용하고 글마다 별도 공개 식별자로 상세 주소를 만든다. 주소 모양은 기존 정적 호스팅 안에서 정한다 | 제목·순서·본문을 바꿔도 공개를 유지하는 동안 해당 글 주소가 바뀌지 않는다. 배열 번호·제목·원문 내부 ID로 글을 대신 식별하지 않는다 |
| 3. 소개·목록과 상세의 왕복 | 동일한 공개 사본에서 블로그 제목·선택 소개·공개 글 목록을 읽고, 글 상세에서 같은 블로그로 돌아간다 | 새 비로그인 브라우저에서 블로그 → 글 → 블로그를 사용할 수 있다. 목록에 보이는 것은 공개한 글뿐이며, 계정 이름·이메일을 소개로 자동 복사하지 않는다. 글이 없으면 빈 블로그 상태를 보여준다 |
| 4. 갱신·글 철회·블로그 철회 | 기존 revision 비교와 작업 ID 영수증을 재사용한다. 글 갱신/철회와 공개 목록의 변경은 같은 공개 revision에서 반영한다 | 비공개 편집은 게시본을 바꾸지 않는다. 명시 갱신 뒤 같은 주소에 새 본문이 보인다. 글 철회 뒤 목록과 직접 글 주소에서 읽히지 않고 다른 공개 글은 남는다. 블로그 전체 철회 뒤 그 블로그와 모든 글 경로가 닫힌다 |
| 5. 실패와 다른 기기에서 관리 | 응답 유실·충돌·브라우저 사본 부재에도 서버의 최신 게시 상태를 확인하고 기존 사본을 관리한다 | 같은 요청 재시도가 중복 글이나 옛 글 부활을 만들지 않는다. 오래된 검토로 다른 공개 글을 덮어쓰지 않는다. 원래 브라우저가 없어도 최소한 공개 글/블로그의 철회가 가능하다 |

글 상세는 공개 블로그의 한 항목을 읽는 경로로 시작할 수 있다. 블로그 사본이 이미 모두 공개할 내용으로 구성돼 있으므로 별도 글 테이블이 반드시 필요한 것은 아니다. 이 경우 글 철회는 공개 사본에서 해당 공개 글을 제거하는 변경이며, 목록만 숨기고 본문을 남기는 작업으로 구현하지 않는다. 첫 사본에 여러 글을 한 번에 넣지 않고 한 글의 게시·갱신·철회를 먼저 검증한 뒤 두 글에서 한 글만 철회하는 경계를 확인한다.

주소의 유지 범위는 **공개 유지 중 갱신까지**다. 기존 정책대로 블로그 철회 후 재게시하면 새 공개 주소를 발급한다. 새 글 공개 식별자도 철회된 글의 옛 직접 주소를 다시 살리지 않게 설계한다. 공개 주소와 개인 글 사이의 연결은 소유자 내부에서 관리하고 익명 응답에 개인 계정·작업공간·원문 ID를 섞지 않는다. 첫 발행 시각과 글 갱신 시각을 구분하며, 블로그 전체 갱신 시각을 각 글의 작성일로 표시하지 않는다.

현행 공개 읽기 화면의 인증·개인 IndexedDB 비의존, `no-store`, 공개 상태 재확인, 철회 후 표시 제거는 재사용할 계약이다. `noindex`가 있다고 비공개인 것은 아니고, 블로그에 글별 주소가 있다고 검색엔진 노출까지 완료된 것도 아니다. 첫 단위는 링크를 받은 독자가 실제로 읽는 공개 블로그를 완결한다.

### 사진 공개는 그다음 한 단위

일반 글 공개 왕복을 확인한 뒤 **사진 한 장을 포함한 글 한 편**으로 공개 자산 보관을 연결한다. 원본을 보존하는 기존 로컬 저장·ZIP과 공개용 자산은 별도 범위다. 로컬 Blob URL·브라우저 파일·일반 사본의 1 MiB JSON에 사진 base64를 붙여 방문자에게 전달하지 않는다.

연결 순서는 **공개할 사진과 본문 선택 → 비공개 업로드 준비 → 파일·참조 확인 → 공개 본문과 자산 참조의 게시 확정 → 익명 읽기 → 갱신·철회**다. 준비 중인 자산은 게시 전 익명으로 읽히지 않아야 한다. 모든 참조가 준비된 뒤 공개 사본을 확정하고, 업로드 중 실패하면 기존 게시본과 로컬 원본을 유지한다. 새 사진은 기존 공개 파일을 제자리 덮어쓰지 않고 새 자산으로 준비해 새 revision에서 참조한다.

완료 기준은 다음과 같다.

- 새 브라우저에서도 사진 순서·설명·대체 텍스트가 본문과 함께 읽히고 업로드 성공과 게시 성공이 구분된다.
- 공개할 파일의 해상도·원본 내려받기 허용·메타데이터 포함 범위를 정하고 방문자 미리보기와 실제 게시가 일치한다. 개인 원본의 보존을 공개 원본 다운로드 허용으로 간주하지 않는다.
- 사진을 뺀 공개 갱신·글 철회·블로그 철회 뒤에는 옛 자산 직접 주소에서도 새 접근이 차단된다. 화면에서 사진만 빼거나 공개 파일 저장소에 그대로 둔 상태를 철회 완료로 부르지 않는다.
- 자산 읽기가 현재 게시본의 참조·공개 상태를 확인하도록 설계한다. 만료 URL을 선택한다면 잔여 접근 가능 시간을 제품 계약에 명시하고 즉시 회수로 표현하지 않는다. 이미 외부로 복사된 사진의 회수는 약속하지 않는다.
- 게시 응답 유실·파일 하나 실패·계정 전환·철회와 업로드 경합에서도 미완료 자산이 공개되지 않고, 현재 게시본과 로컬 원본이 보존된다. 사용되지 않는 준비 파일의 정리는 게시 성공 판정과 분리한다.

이 단위에는 전체 사진 라이브러리·앨범·지도·자동 기기 동기화를 추가하지 않는다. 공개 자산 보관을 사용한다는 사실만으로 기존 로컬 사진 글 전체가 동기화되거나 공개되지는 않는다.

대안인 자료 보관함 중심 홈은 가져오기와 검색을 잘 설명하지만, 이번 피드백의 핵심인 서비스 정체와 글쓰기 목적을 충분히 해결하지 못한다. 개인 작업 대시보드 중심 홈도 기능 복귀에는 유리하지만 “어떤 결과물을 만드는가”를 사용자가 추론하게 한다. 그래서 블로그를 전면에 두는 편을 채택한다.

방향을 바꿀 조건은 실제 사용에서 블로그라는 설명이 지속적으로 목적을 왜곡하는 경우다. 예를 들어 사용자는 가져온 자료를 읽고 끝내려는데 계속 글을 완성하거나 공개하라는 압박을 느끼고 자료실도 찾지 못한다면, 홈에서 개인 블로그와 자료실로 가는 두 경로의 비중을 비교한다. 이때도 미리 모든 기능을 동등하게 나열하는 화면으로 되돌리지는 않는다.

## 이해도와 완료 기준

구현 검수와 사용자 체험은 별도 증거다. 설명 없이 처음 본 사람에게 “무슨 서비스인가”, “첫 글은 어디서 쓰는가”, “저장하면 다른 사람이 보는가”를 물어 목적·진입·공개 경계를 확인한다. 재방문자는 쓰던 글을 찾고 이어 쓰며, 저장 후 홈에서 같은 글을 다시 열 수 있어야 한다.

구현 담당은 이번 개인 흐름을 익명 합성 자료로 데스크톱·태블릿·모바일 폭에서 확인한다. 저장 실패의 입력 보존, 계정 변경의 격리, 기존 글·사진 원본·백업의 보존을 관련 회귀로 확인한다. 제품 검토 담당은 실제 사용자 체험에서 설명을 덧붙여야 했던 단어와 첫 클릭을 기록한다. 브라우저 자동 검사가 통과했다는 사실을 사용자 이해도 검증으로 대체하지 않는다.
