# 행복도 입력 — 쓰는 곳을 하나로 (설계안, 2026-11-04)

총괄 지시(11-04): 행복도를 일정과 연표 편집기 양쪽에서 입력하되, 저장소에 쓰는 곳은 하나로 한다. 구현 전 설계 문서다. 기준 main은 `c403d1f`(#187 병합, haedo-v187)다.

## 왜 다시 설계하나

#187은 처음에 일정에서도 행복도를 연표 문서(`haedo_documents`)에 직접 썼다. 쓰는 곳이 둘(일정 스토어, 연표 편집기)이 되자 네 차례 검수마다 새 손실 경로가 나왔다. 결국 소유자 결정 "습관·목표 먼저"로 일정은 행복도를 보기만 하게 줄였다. 재현된 실패 8가지는 [되돌림 기록](../design-review/timeline-latest-wins.md)에 있다. 요약하면 다음과 같다.

- 연표 문서는 **문서 하나 전체**를 조건부 PATCH(`updated_at`)로 쓴다. 하루 값 하나를 바꿔도 문서 전체가 경쟁한다.
- 연표 편집기는 문서를 **메모리(`DATA`)에 들고** 편집한다. 저장 시 그 판을 통째로 쓴다. 다른 곳이 디스크나 서버에 쓴 값은 편집기 메모리 판과 경쟁한다(편집기 열림, 되돌리기, Esc, 끌기 중).
- 탭의 localStorage 보기는 다른 탭의 쓰기보다 늦게 맞춰진다. 목록·본문을 통째로 되쓰면 다른 탭의 미전송 상태를 덮는다.

그래서 기준은 다음과 같다.

1. 같은 저장 단위에 쓰는 코드 경로(엔진)는 하나다.
2. 그 단위는 행복도 하루 값만큼 작아야 한다.
3. 편집기 메모리의 큰 문서와 같은 단위를 공유하지 않는다.

## 현재 사실 (확인한 것)

- **연표 문서**
  - `happiness: [{date, v}]`에 하루 점(`YYYY-MM-DD`)과 월 점(`YYYY-MM`)이 섞여 있다. 곡선은 이 점들에 사건·기간의 `happiness`를 더해 그린다(`app.js` 474–508).
  - v는 signed1(−1~+1)이고, 옛 0–10·signed10 문서는 `HaedoData.toSignedScale`로 바꾼다.
- **`haedo_items`**
  - `kind in ('goal','habit')` 검사 제약이 있다.
  - `id text primary key`는 **사용자별이 아니라 전역**이다.
  - 스토어(`platform-store.js`)에 항목별 최신 채택·복구 사본·재시도·깨우기가 이미 있다. 이 스토어는 `timeline.html`과 일정 둘 다에서 싣는다.
- **`life_account_documents`**
  - 문서별 조건부 쓰기(revision)·영수증·4 MB 상한이 있다.
  - 엔진은 `storage.js`(IDB) + `account-docs-sync.js`다. `LISTS`로 항목별 3-way 병합(key·time)을 한다. 같은 항목이 양쪽에서 바뀌면 늦은 쪽을 채택하고, `recovery: true`면 진 쪽을 남긴다.
  - 전체 백업의 `accountDocuments`에 이미 포함된다. 새 표·마이그레이션 없이 문서 종류를 더할 수 있다(스키마 번호만 올림).
  - `timeline.html`은 이 엔진(storage.js·IDB·AccountDocsSync)을 싣지 않는다. 일정(`index.html`·`life.html`)은 셸이 싣는다.

## 후보

### (a) 연표 편집기가 유일한 쓰는 곳 — 일정은 편집기에 요청

| 변형 | 내용 | 평가 |
|---|---|---|
| a1 지금 방식 | 일정은 보기 + `연표에서 기록` 링크 | 손실 위험 없음. 일정에서 입력하지 못함(목표 미달) |
| a2 요청함 | 일정이 요청을 기기 요청함(localStorage)에 넣고, 편집기가 열릴 때 반영·전송 | 편집기를 열기 전까지 계정에 올라가지 않는다. iPhone에서 일정만 쓰면 영영 동기화되지 않아 11-01 "모든 데이터 자동 동기화"를 어긴다. 요청함을 계정 문서로 올리면 사실상 (b)가 된다 |
| a3 편집기 쓰기 경로를 모듈로 분리 | 편집기의 저장·전송·충돌 정리를 한 모듈로 빼고, 일정도 그 모듈을 부름 | "코드는 하나"지만 저장 단위는 여전히 문서 전체다. 두 탭·두 화면이 같은 문서를 쓰는 구조라 되돌림 기록의 실패 1–8이 그대로 남는다. `app.js`의 메모리 편집 모델을 크게 바꿔야 한다 |

- **손실 위험:** a1 없음, a2 동기화 누락, a3 높음(검수에서 이미 확인)
- **형식 변경:** 없음
- **판단:** a1은 지금 상태로 두는 기준선이다. a2·a3는 목표를 못 이루거나 위험이 크다.

### (b) 하루 행복도를 계정 문서로 분리 — 권장

하루 행복도(`YYYY-MM-DD`)를 연표 문서에서 꺼내, 기존 `life_account_documents`의 새 문서 종류로 둔다.

- **문서:** `happinessDays:<계정>:days` → `{ revision, entries: [{ date, v, at }] }`
  - `v`: signed1(−1~+1), 둘째 자리. 지우기는 `v: null`(삭제 표시)로 두어, 다른 기기의 늦은 삭제도 병합된다.
  - `at`: 누른 시각(기기)이다. 같은 날짜가 양쪽에서 바뀌면 늦은 `at`이 이긴다.
- **병합:** `LISTS.happinessDays = [{ path: 'entries', key: 'date', time: 'at', sort: byDate('date') }]`, `recovery: true`
  - 진 날짜 값은 엔진의 복구 사본으로 남는다.
  - 서로 다른 날짜는 언제나 둘 다 남는다.
- **쓰는 곳은 하나다.** 엔진은 `storage.js`의 계정 문서 트랜잭션 + `AccountDocsSync`다.
  - 일정: 셸이 이미 싣는 엔진으로 쓴다.
  - 연표 편집기: 하루 점을 고칠 때만 같은 엔진을 늦게 싣는다(`storage.js`, `account-docs-sync.js`, `account-docs-remote.js`). 편집기의 연표 문서 저장 경로와는 섞지 않는다.
  - 두 화면이 같은 기기에서 동시에 써도, 엔진의 IDB 트랜잭션과 문서별 revision CAS가 한 번에 하나씩 받는다. 다른 기기와는 항목(날짜)별 3-way 병합이다.
- **연표 문서에 남는 것:** 월 점(`YYYY-MM`)과 사건·기간의 `happiness`. 이것들은 계속 연표 편집기만 쓴다.
- **곡선 표시:** 편집기·일정은 연표 문서의 점에 계정 문서의 하루 값을 더해 그린다. 같은 날짜가 둘 다 있으면 계정 문서가 우선한다(이행 뒤 남은 옛 점).
- **손실 위험:** 낮다.
  - 저장 단위가 하루 값이라 편집기 메모리 문서와 경쟁하지 않는다.
  - 같은 날짜 경쟁은 늦은 쪽을 채택하고 진 쪽은 복구 사본으로 남는다(11-01 규칙).
  - 엔진은 뉴스 판단·연간 계획 등에서 이미 쓰는 경로다.
- **형식 변경:** 있다. 하루 행복도의 정본이 연표 문서에서 계정 문서로 옮겨 간다. 11-03 결정("저장 형식 그대로")을 바꾸므로 **소유자 결정이 필요하다.**
- **서버 변경:** 없다(새 표·RLS·마이그레이션 없음). 문서 종류가 늘어 `ACCOUNT_DOC_SCHEMA`를 4로 올린다. 이전 판 기기는 변경 목록을 한 번 처음부터 다시 읽는다(기존 규칙).

## (b)의 이행 계획

1. **소유자 결정 받기:** 하루 행복도의 정본을 계정 문서로 옮길지, 공유 보기(아래 열린 문제) 처리 방식.
2. **문서 종류 추가**(storage.js, account-docs-sync.js)
   - 검증기: date `YYYY-MM-DD`, v는 −1~+1 또는 null, at은 문자열, 한 날짜에 한 항목, 상한
   - `LISTS`·`TRIGGERS`를 등록하고 `ACCOUNT_DOC_SCHEMA` 4로 올린다(S0 고정값·종류 표 갱신).
3. **첫 이행:** 계정마다 한 번, 복사만 한다.
   - 보여 줄 연표(현 `baseDocument`)의 하루 점을 계정 문서로 복사한다. `at`은 연표 문서의 `syncedAt`으로 한다(가장 오래된 편집으로 취급).
   - 연표 문서의 하루 점은 지우지 않는다. 표시할 때 계정 문서가 우선한다.
   - 복사는 엔진의 일반 쓰기라서, 여러 기기가 동시에 이행해도 날짜별 병합으로 수렴한다. 같은 값은 같은 내용이라 진 쪽 사본도 생기지 않는다.
4. **일정**
   - 하루 칸에 0–10 입력을 되살린다. 쓰기는 계정 문서 엔진만 쓴다. 상태는 엔진의 동기화 상태를 두 단계 문구로 보인다.
   - 지우기는 `v: null`이다.
5. **연표 편집기**
   - 곡선의 하루 점을 고치거나 더할 때 엔진을 늦게 싣고 계정 문서에 쓴다. 메모리 `DATA`의 연표 문서에는 쓰지 않는다.
   - 월 점·사건·기간은 지금처럼 연표 문서에 쓴다.
   - 엔진을 싣지 못하면 하루 점 편집을 막고 이유를 보인다(입력 보존).
6. **곡선 합치기:** 공용 함수 하나로 한다(`platform-data.js`, 예: `curvePoints(doc, days)`). 편집기·일정·공유 보기가 함께 쓴다.
7. **백업·복원:** 계정 문서는 이미 전체 백업에 들어간다. 연표 단독 백업(`haedo-platform-backup-v1`)에는 `happinessDays`를 덧붙일지 정한다(복원은 덧붙이기만 한다).

## 검사 계획

- **단위(storage·account-docs-sync)**
  - 검증기 경계(날짜 형식, v 범위·null, 중복 날짜)
  - 두 기기가 다른 날짜를 동시에 넣으면 둘 다 남는다.
  - 같은 날짜를 동시에 바꾸면 늦은 `at`이 이기고 진 값은 복구 사본이 된다.
  - 삭제(`v: null`)와 값 넣기가 겹칠 때의 규칙
  - 이행은 반복해도 같은 결과다. 이행과 다른 기기의 새 값이 겹치면 새 값이 이긴다.
  - 스키마 4 되읽기
- **단위(곡선 합치기):** 계정 문서 우선, 월 점·사건·기간 보존, 척도 변환
- **브라우저**(실제 앱·IDB·소유자별 가짜 서버). 되돌림 기록의 실패 1–8을 각각 시나리오로 둔다.
  - 일정 입력과 편집기 입력을 번갈아 하면 둘 다 남고 연표 문서 PATCH는 0이다(하루 값 변경은 연표 문서를 건드리지 않음).
  - 편집기를 연 채(항목 편집기 열림·끌기 중·Esc) 일정에서 입력해도 편집기 메모리 판과 경쟁하지 않는다. 손실 0.
  - 오프라인 입력 → 다시 열기·온라인 → 전송. 탭 닫힘·늦은 localStorage 보기에서도 손실 0.
  - 계정 전환 중 늦은 응답은 무시한다.
  - 390·1440 화면, 한글 입력 없음(숫자 선택), 키보드 조작
- **변이:** 병합 규칙 제거, 계정 문서 우선 제거, 이행 반복 시 중복, 편집기가 하루 점을 연표 문서에 쓰는 경로. 각각 해당 검사가 실패해야 한다.
- **CI:** 새 브라우저 검사 등록은 총괄이 한다.

## 열린 문제 (소유자·총괄 결정)

1. **형식 변경 승인:** 하루 행복도의 정본을 계정 문서로 옮기는가. 11-03 "저장 형식 그대로"를 바꾼다.
2. **공유 보기(`VIEW_ONLY`)·공개 사본:** 공유 보기는 연표 문서만 읽는다. 이행 뒤 하루 값을 공유 보기에 넣으려면 공유를 만들 때 하루 값을 사본에 함께 담아야 한다. 담을지, 공유에서는 월 점만 보일지 정한다. 공유는 명시적 선택이므로 자동으로 담지 않는 것을 기본안으로 둔다.
3. **연표가 여러 개일 때:** 하루 행복도는 계정에 하나(연표와 독립)로 둔다. 모든 연표 곡선에 같이 보일지, 보여 줄 연표 하나에만 보일지 정한다. 기본안은 "모든 연표에 같이"다. 하루 행복도는 사람의 하루에 대한 값이지 연표 하나의 값이 아니기 때문이다.
4. **옛 하루 점 정리:** 이행 뒤 연표 문서의 하루 점을 영영 두는가(표시 때 가려짐), 아니면 다음 편집기 저장 때 빼는가. 기본안은 두기다. 지우지 않으므로 손실이 없다.
5. **(c1)로 갈 경우:** 운영 DB 승인(`haedo_items` 제약 변경)과 받기 쿼리 분리가 필요하다.

## 선택을 바꿀 조건

- 편집기에 계정 문서 엔진을 싣는 비용(첫 하루 점 편집까지의 지연)이 크면 (c1)로 바꾼다. (c1)은 편집기가 이미 싣는 스토어로 해결한다.
- 하루 행복도를 연표와 떼는 것을 소유자가 원하지 않으면 a1(지금)을 유지한다. 그러면 일정에서의 입력은 하지 않는다. (a3)·(c2)는 되돌림 기록의 실패가 남으므로 택하지 않는다.
