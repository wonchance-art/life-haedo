## 지연 추가 단축 — PR185, 최적화 전용 세션, 병합 전 (2026-11-04 KST)

소유자가 최적화 전용 세션을 열었다(11-04). 총괄 지시서의 범위 1(남은 병목 3곳과 PR183 재검수 마이너)이다. 상세는 [startup-performance.md](../design-review/startup-performance.md#원문-head-중복공간-순차-수신글-목록-2026-11-04)에 있다.

- **구성·자료 메타 엔진:** 동기화 한 번에 원문 head를 한 번만 확인한다.
  - 로컬 원문이 깨끗하고 필요한 판 이상이면 다시 묻지 않는다.
  - 저장 상태가 늦어 storage가 거절하면 한 번 더 확인하고 다시 시도한다.
  - compare·resolve는 매번 확인한다.
- **계정 자료실 배경 수신:** 자료공간 2개를 동시에 받는다. 첫 실패 뒤에는 새 공간을 시작하지 않는다.
- **BlogSync**
  - 글 목록을 계정 확인과 함께 요청하고, 확인을 통과한 뒤에만 쓴다. 그 주기에 서버로 보낸 것이 있으면 목록을 다시 받는다.
  - 자리를 기다리던 사진 전송은 dispose 뒤 시작하지 않는다.
- **수치**(합성, 3회 중앙값)
  - cold 셸 / 첫 행 / 20행: 5.63 / 7.25 / 10.04초 → 4.61 / 5.74 / 8.51초. 셸 전 단계 14 → 12.
  - CPU 4배 cold: 측정 중.
  - warm은 변화 없음(편차 안).
- **검수·CI**
  - 내부 독립 검수: 블로커·메이저 0, 마이너 2(늦은 원문 상태, 첫 채택 경로 검사 공백). 둘 다 반영했다.
  - 새 검사 13건. 변이 시험으로 각 보호를 빼면 실패하는 것을 확인했다.
  - `b047c5c` CI 전부 녹색.
  - 총괄이 붙이는 독립 검수와 병합 시 캐시 판올림은 총괄 몫이다.
- **미검증:** 실제 기기·실제 Supabase 지연, iPhone 메모리에서의 동시 2공간.
- **후속 후보**
  - 진행 중 사진 전송 AbortController: SDK의 내려받기 신호 지원 확인이 먼저다.
  - 자료 기기 이동 설치가 `sync:` 상태를 갱신하지 않는 storage 문제: 지금은 엔진 재시도로 막는다.
  - BlogSync를 mount 전에 시작하기: 시작 순서 계약 변경이다.
  - 범위 2: S2b(blog-sync 수명 주기를 sync-lifecycle로 옮기기).

## 시작 지연 최적화 — PR183 병합·배포, 캐시 `haedo-v182` (2026-11-03 KST)

소유자 지시(11-03): "딜레이 줄이는 최적화 작업 우선".

- **열기 중 계정 확인 공유**
  - 무엇을: 페이지를 여는 동안 고른 읽기(AccountLibrary, 자료실 읽기 3종, 구성 읽기, 원문 계정 읽기)는 서버 계정 확인 하나를 함께 쓴다(`platform-auth.js`).
  - 다시 쓰지 않는 경우: epoch·세대·사용자·access token이 다를 때, 로그아웃 표시가 있을 때, bfcache 복귀일 때. 열기 범위는 최대 10초다.
  - 모든 쓰기와 BlogSync 주기는 지금처럼 서버에서 확인한다.
- **블로그 수신**
  - 저장 글부터, 최신 글부터 받는다.
  - 글은 4편, 전송은 6개까지 동시에 하고, 받는 바이트는 160MB 예산 안에서 쓴다.
  - 둘 곳 없는 글은 0.5초부터 두 배씩 간격을 늘려 다시 본다.
- **수치**(합성 데이터, 비공개 요청 150–300ms·정적 요청 40ms 지연, 3회 중앙값)
  - cold 셸 / 20행: 7.91 / 16.13초 → 4.84 / 9.12초. 셸 전 auth 요청은 16회 → 2회.
  - cold CPU 4배 셸: 11.11 → 8.12초.
  - warm 목록 준비: 1.22 → 1.04초. CPU 4배: 2.56 → 2.10초.
- **검수·CI**
  - 독립 검수에서 블로커 0, 메이저 2(회귀 검사 공백)가 나와 보강했다. 같은 검수자가 컨테이너 재시작으로 사라진 뒤 새 검수자가 재검수해 블로커·메이저 0을 확인했다.
  - CI 회귀 2건은 재현 → 원인 → 수정했다.
    - blog-completion: 새 기기의 첫 주기가 자료실보다 먼저 돌아 30초를 건너뛰었다.
    - life-discovery-automation: bfcache 복귀 때 auth가 2회 나갔다.
  - 현재 head CI는 전부 녹색이고, 병합은 `bc820ed`다.
- **라이브**: `haedo-v182`. 셸 파일 11개가 main과 같고, 1440·390 콘솔 오류는 0, 스크립트 150개 요청이 0.2초 안에 시작한다.
- **미해결로 기록**: life PWA 오프라인 검사 서비스워커 대기 1회(재현 안 됨, 기존과 같은 종류).
- **미검증**: 실제 기기·실제 Supabase 지연·Safari pageshow 순서, iPhone 메모리에서의 160MB 예산.
- **후속 후보(재검수 마이너)**
  - 이벤트 없이 사용자만 바뀌는 순서(M2)를 잡는 검사를 추가한다.
  - 계정 전환이나 dispose 뒤에도 이미 시작한 다운로드(최대 6개)가 끝까지 받아진 뒤 버려진다. AbortController가 필요하다.
  - W4 범위가 10초 상한을 넘어 열기 확인을 계속 쓰는 경우를 문서에 적는다.
  - 이름 가림, 검사 주석.
- **남은 병목**
  - 구성·자료 메타 엔진의 원문 head 확인이 반복된다(약 1.5–2초).
  - BlogSync가 mount 뒤에 시작한다(첫 행 약 1.1초).
  - `receiveAndSend`가 자료공간을 하나씩 받는다.

## 로그인 뒤 첫 화면 지연 회귀 수정 — PR181 병합·배포, 캐시 `haedo-v181` (2026-11-03 KST)

소유자가 "첫 화면 로그인 후 자료 불러오는데 너무 오랜 시간 걸림"을 보고했다(11-03).

- **원인(v180 회귀):** PR179가 `index.html`·`life.html`의 `<head>`에 CSP `frame-src` meta를 넣었다. 그 뒤로 Chromium 미리 받기가 스크립트 약 180개를 미리 받지 못하고 차례로 받았다. 데이터 읽기·동기화·사진은 원인이 아니었다. 셸이 뜬 뒤 목록이 준비될 때까지는 두 판 모두 약 80ms였다.
- **수정:** HTML의 meta를 지우고 `shell.js` 맨 앞에서 같은 정책을 `head`에 넣는다. 정책의 효과는 같다. 허용 밖 틀, 틀이 스스로 하는 허용 밖 이동, `data:` 틀이 막힌다. `page-preload.test.cjs`가 meta가 HTML로 돌아오면 실패한다.
- **수치(합성 데이터, 비공개 요청 150–300ms 지연, 중앙값)**
  - 일정 목록 warm 목록 준비: v179 1142ms → v180 1744ms → 수정 1148ms.
  - 같은 조건에 CPU 4배를 걸면: 2425 → 3741 → 2126ms.
  - 정적 요청마다 40ms 지연을 넣은 DOMContentLoaded(독립 검수 실측): 0.55 → 7.66 → 0.69초.
- **검수·출시**
  - 독립 검수: 블로커 0, 메이저 1(캐시 판올림, 반영함), 마이너 4는 아래 후속 후보에 넣었다.
  - CI는 현재 head에서 전부 녹색이고, 12:25 UTC에 병합했다(`67ccf67`).
  - 라이브: `haedo-v181`, 셸 파일 8개가 main과 같다. HTML에 CSP meta는 0개이고 실행 뒤 `HEAD`에 1개가 들어간다. 스크립트 150개 요청이 모두 0.2–0.3초 안에 시작됐다.
- **미검증**
  - Safari/WebKit에서 동적 meta가 적용되는지. 실기기가 없어 WebKit 소스와 HTML 명세를 근거로만 판단했다.
  - 실제 기기·실제 망에서의 체감 시간.
- **후속 후보**
  - 정책 적용을 브라우저에서 단언하는 검사.
  - `page-preload` 정규식이 서식에 묶여 있는 문제.
  - 계측 스크립트의 cold 지표.
  - 이전부터 있던 cold 첫 로그인 약 8초. 셸 전에 `/auth/v1/user` 요청 약 14회와 자료공간별 읽기가 차례로 나간다. 인증·동기화 경로라 독립 검수가 필요하다.
  - warm에서도 셸 전에 `/auth/v1/user` 2–3회가 차례로 나간다.

## 내 데이터 한 번에 지키기 — 공개 배포 완료, 실기기 확인 전 (2026-11-01 KST)
