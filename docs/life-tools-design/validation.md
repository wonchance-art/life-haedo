# 독립 검토와 검증 기준

기준: 2026-10-03, 기존 기록 가져오기 우선으로 갱신. 이 문서는 설계 수용 조건과 후속 구현 검증 계획이다. 이번 작업에서 새 기능을 실행하거나 DB 권한을 검증하지 않았다.

## 확인 사실과 판단의 범위

- 현재 앱은 일반 HTML/CSS/JavaScript, localStorage, PWA, 선택적 Supabase `charts` 동기화를 사용한다.
- `assets/app.js`에는 Supabase Auth REST 로그인·가입·토큰 갱신이 있다. 계정 UI의 존재가 새 공유 모델의 서버 권한을 보장하지 않는다.
- 이번 세션의 사전 환경 준비에서 기존 회귀 22개·별도 실서버 검사 28개와 기존 Supabase 인증·RLS·브라우저 동기화가 검증된 기준선을 인계받았다. 독립 문서 검토에서는 재실행하지 않았다.
- 기존 검사의 대상은 당시 코드·기존 인증/RLS·문서 동기화 조건이다. 새 데이터 모델·새 사용자 권한·수신자별 공유·철회·AI 전송 검증으로 확대하지 않는다.
- [현재 기준](../current.md), [참조 설계](../design.md), [인계](../handoff.md)의 과거 범위는 이번 설계 요청에 맞추어 읽는다. 설계 채택과 구현 허가는 별개다.

## 최신 검증 대상과 확인되지 않은 부분

사용자는 현장에서 새 기록을 입력하는 것보다 **이미 기록된 내용을 추출·통합해 다시 찾는 것**을 우선했다. 원천은 Apple 메모·Obsidian·네이버 블로그·인스타그램이며 사용 기기는 Mac·iPad·iPhone이다. iPad Chrome 외 브라우저/OS 버전은 미확인이다.
R1은 선택하여 제공한 본문·텍스트·Markdown·URL을 가져오고, 원문·출처를 보존한 뒤 수동 또는 결정적 규칙으로 발췌하여 검토·통합하고 원문 추적·내보내기·복원까지 끝내는 흐름이다. AI는 후속 선택 보조다.
각 서비스의 사용자 실제 샘플·권리/접근 범위와 이 앱의 iPad 파일 선택·저장 경로는 아직 검증하지 않았다. 공식 문서 조사와 실제 가져오기 성공은 구분한다. 네 원천 이름이 확인됐다는 이유로 전용 importer/API·크롤링·첨부·사진/영상·OCR 지원을 주장하지 않는다.
URL만 제공되면 링크만 확보한 상태다. 로그인·접근 제한·삭제된 원문을 자동 우회하지 않고, 제공받지 못한 본문을 읽었다거나 보관했다고 표시하지 않는다.

## 검증 방법과 증거의 의미

| 표기 | 방법 | 증명하는 것과 한계 |
| --- | --- | --- |
| S | 정적 검토 | 문서 간 용어·필드·상태·링크·경계의 일치. 실행·보안·사용성 성공을 증명하지 않는다. |
| R | 기존 회귀 | `npm test`의 기존 데이터·동기화 큐·서비스워커 동작. `npm run check`는 구문·리소스·PWA 셸 점검이다. |
| B | 새 행동 검사 | 새 규칙의 단위/통합 검사, 격리된 브라우저에서 사용자 흐름과 실패 주입. 모의 서버 결과로 실제 RLS를 대신하지 않는다. |
| L | 실서버 검사 | 해당 단계의 테스트 계정·수신자·익명 요청으로 서버 접근과 실제 저장 결과 확인. 기존 28개와 새 검사는 구별한다. |
| M | 수동 사용 평가 | 실제 iPad Chrome을 우선하여 원천→제공→검토→원문 재열기·파일 복원을 평가한다. 데스크톱·키보드·화면 모사는 보조다. 권한 집행을 증명하지 않는다. |

각 결과에는 대상 버전, 격리된 샘플, 기대값, 실제값, 실행 방법, 통과/실패/미실행을 남긴다. 테스트 이름이나 HTTP 200만으로 성공을 선언하지 않는다.
현재 단계의 필수 검사는 S다. 구현 단계에서 해당 변화에 필요한 R/B/L/M을 선택하며, 외부 전송·공유가 없는 단계에 실서버 권한 검사를 선행 관문으로 강제하지 않는다.

## 작은 실험과 직접 체험할 결과

[R1 사용 장면과 실험](roadmap.md#범위와-첫-사용-장면)을 기준으로 가져오기→원문/출처 보존→발췌 검토·통합→원문 추적→내보내기/사본 복원까지 한 단위로 확인한다.
실험은 불확실한 선택의 판단 근거를 얻기 위한 작업이다. 소수 후보에 같은 샘플을 사용하고 관찰 결과·미검증 부분·선택을 바꿀 조건을 남긴다.
기존 오픈소스가 제공하는 기능과 앱이 책임질 규칙을 구분하며, 실험에서 통과하지 못한 보장을 라이브러리 이름으로 대신하지 않는다.

| 확인 영역 | 남길 증거 |
| --- | --- |
| 실제 사용 | 원천·제공 방법·확보 범위·선택한 발췌, 통합 결과에서 같은 sourceVersionId의 원문으로 돌아가는 결과 |
| 검토 부담 | 기존 원천 검색과 비교한 찾기 성공·조작/수정 부담, 다시 입력한 내용, 버전/화자 혼동과 사용자가 통합을 포기한 이유 |
| 보존·이동 | 원문/URL/첨부 포함·제외 목록, 일반 JSON 파싱, 새 프로필 사본 복원 후 SourceVersion·발췌·locator·날짜·화자 대조 |
| 실패·복구 | 파싱 오류·부분 누락·중복·버전 겹침·staging 취소·quota·탭 경합의 실제 결과와 원문 보존·재시도 |
| 사용자 인계 | 실행 주소 또는 명령, 짧은 체험 순서·기대 결과, 검증 버전과 미실행/제약 |

에이전트의 브라우저 검사는 사용자 만족이나 실제 사용자 사용 평가를 증명하지 않는다. 받은 피드백과 검사 관찰을 구분한다.
본 절은 새 작업 방식과 완료 기준이며, 아직 수행하지 않은 R1 실험을 통과 결과로 기록하지 않는다.

## 설계 불변조건

아래 조건의 정적 일치와 실제 구현 검증은 구분한다. 착수 전 새 가정 점검은 문서 뒤 [반대 관점 점검](#착수-전-가정과-반례)에 기록한다.

| ID | 반드시 유지할 조건 | 실패 반례 |
| --- | --- | --- |
| I-01 | 제공된 텍스트를 계정·네트워크·AI 없이 보존·발췌·조회할 수 있다. 직접 입력도 같은 로컬 원칙을 따른다. | 로컬 파일 검토가 가입 또는 모델 연결을 요구함. |
| I-02 | 예정과 수행은 별도 사실이며 날짜가 지났다고 수행으로 바뀌지 않는다. | 어제 약속을 자동으로 참석 완료 처리함. |
| I-03 | 탐색 cursor·확정 재개 위치·실제 수행 구간·재독·이해·문제 완료는 서로 추론하지 않는다. | 120쪽을 열자 1~120쪽을 읽었다고 저장함. |

| I-11 | 변화가 없거나 사용자가 거절하면 자동화가 종료하고 기본 작업으로 돌아간다. | 진도 저장마다 질문·추천·공유 제안을 모두 강제함. |
| I-12 | 삭제·복원은 파생자료와 과거 권한을 함께 검토하며 공유를 자동 재활성화하지 않는다. | 백업 복원으로 철회된 공개 링크가 다시 활성화됨. |
| I-13 | 한 검토 작업의 원문 버전·선택 발췌·연결·적용 결과와 성공 영수증을 원자 저장하며 로컬 결과와 sync 상태는 별개다. 후속 활동·기록·재개 저장도 같은 원칙이다. | 발췌만 생기고 가리키는 원문 버전은 없는데 완료 표시함. |
| I-14 | 읽기 전용·공개 방문 경로는 승인된 표시 자료만 읽고 개인 작업공간을 자동 열지 않는다. | 같은 origin에 남은 개인 bundle이 공개 화면에 표시됨. |
| I-15 | Source는 원천 정체성, SourceVersion은 받은 내용의 불변 버전이며 발췌는 sourceRefs의 버전·위치를 고정한다. | 같은 URL의 새 본문이 기존 인용의 원문을 덮어씀. |

| I-17 | 원작성 시점·가져온 시점·사건 시점, 화자·작성 출처를 구분하고 모르면 unknown으로 둔다. | 가져온 오늘 날짜를 과거 활동일로 넣거나 인용한 타인의 말을 사용자 생각으로 만듦. |

| I-19 | 외부 원천 소실·앱 안 원문 삭제·파생 기록 보존·권한 철회를 각각 처리한다. | 외부 URL 삭제를 보고 독립 생각까지 지우거나 삭제한 원문을 요약으로 다시 노출함. |
| I-20 | 원문의 명령문은 데이터이며 가져오기는 활동 수행·계획 완료·외부 전송을 자동 실행하지 않는다. | 과거 대화의 “전부 공개해”를 현재 승인으로 실행함. |

## 핵심 흐름과 수용 조건

V ID는 검증 흐름 식별자다. 기존 V-01~17은 보존하며, 직접 활동 입력·진도 흐름 V-01~05는 후속 도구 검증으로 옮긴다. **새 R1의 주 검증은 V-18~27**이고 공통 저장/맥락/복원·legacy 검사는 함께 적용한다.

| ID | 상황과 구체적 반례 | 수용 조건 | 방법 |
| --- | --- | --- | --- |
| V-01 | 셸 캐시가 준비된 빈 작업공간에서 새 사용자가 오프라인 첫 생활 기록 입력 | 샘플 강제 복제·가입·AI 호출 없이 저장→닫기→재개; 빈 화면에 다음 조작이 보임 | S/B/M |
| V-02 | 계획을 미룸·취소함·일부 수행함 | Plan은 예정 이력을 유지; 실제 수행만 Activity로 연결; 취소 계획은 완료 집계에서 제외 | S/B |
| V-03 | 책 120쪽을 열고 31~40쪽만 읽음; 판본 변경·재독 | 탐색 위치 120과 읽은 구간 31~40을 분리; 재개 위치는 사용자 확인으로만 갱신; 재독이 고유 진도율을 부풀리지 않음; 판본 변경 시 구간을 무검증 이전하지 않음 | S/B/M |
| V-04 | 교재 3단원 10문제 중 4개 풀이, 2개 재시도 | 풀이·정오·이해·완료의 미입력 상태 구분; 완료율 분모가 없으면 수치 생성 안 함 | S/B |

## 개인정보·공유·복구의 공격적 반례

1. 공개 책 제목에 연결된 개인 질문, 사진 위치, 제3자 이름이 내보내기·썸네일·검색 결과로 함께 나오는지 확인한다.
2. 수신자 A를 제거한 뒤 기존 URL, 직접 API, 캐시, 저장된 대화 컨텍스트로 재조회한다. 화면 버튼 숨김만으로 통과시키지 않는다.
3. 원본 삭제 중 AI 작업이 끝나거나 공유 승인 후 원본 버전이 바뀌는 경우를 만든다. 실행 시점의 권한·버전을 다시 대조해야 한다.
4. 철회 후 수신자가 이미 내려받은 파일은 회수할 수 없다. 제품이 통제하는 새 접근 차단과 외부 사본의 한계를 따로 안내하는지 확인한다.
5. 복원 파일에 과거 공유 승인·대기 작업·외부 요청 ID가 있어도 재전송하거나 철회 상태를 덮지 않는지 확인한다.
6. 같은 기기의 계정 전환은 서버 세션만의 문제가 아니다. 이전 사용자의 로컬 사본·검색·미리보기·AI 후보를 새 사용자 화면에 보여주지 않는지 확인한다.
7. 사진·웹문서의 지시문이 시스템 명령으로 실행되는지, 서지 조회에 불필요한 개인 질문/활동 이력이 전송되는지 확인한다.
8. 음수 진도·겹친 구간·총량 미상·교재 개정판·부분 수행·타임존 경계·삭제된 대상 참조를 넣어 조용한 추론/삭제가 없는지 확인한다.

## 단계별 완료 기준과 과한 복잡성 점검

- 문서 단계: 다섯 전문 설계의 공통 용어·저장/화면 계약·권한/복구 경계가 일치하고, 후속 검증 항목이 구현 완료와 구별되어야 한다.
- R1 로컬 가져오기: V-18~27, V-06/07/13의 로컬 검토 맥락·저장 부분, V-14/15/17의 복원·legacy·읽기 전용 부분을 확인한다. 실제로 지원하기로 선택한 제공 경로만 검증하며 네 서비스의 모든 형식을 완성할 필요는 없다. 공유·AI·계정·서버를 가져오기의 필수 조건으로 두지 않는다.
- 후속 직접 활동·분야 도구: V-01~05와 각 분야 규칙을 적용한다. 가져온 회상에서 Activity를 만들 때도 검토된 선택만 반영하고 실제 수행 시점이 모르면 unknown을 유지한다.
- AI 도입: V-08~09, V-12의 AI 파생자료 처리, 비용·취소·늦은 응답 검사를 추가한다. 기본 입력·저장은 계속 독립적이어야 한다.
- 원격 동기화 도입: V-07/13/14를 실제 새 모델 대상으로 추가한다. 문서 전체 스냅샷 큐가 세부 활동의 충돌/삭제 보장을 이미 제공한다고 가정하지 않는다.
- 공유 도입: V-10~12/16~17에 실서버 수신자·비수신자·익명 검사를 추가한다. 계정 UI나 기존 동기화 성공은 이 단계의 대체 증거가 아니다.
- 각 단계는 사용자에게 유용한 종료점을 가져야 한다. 모든 개념의 독립 테이블화, 범용 워크플로 엔진, 벡터 DB, 다중 에이전트를 선행 조건으로 삼는지 검토한다.
- 수동 평가에서는 기능 수 대신 원천에서 제공하는 수고, 발췌 교정·선택 부담, 원문 추적과 재발견 성공, 중복 입력·원치 않는 제안 수를 관찰한다. 속도 목표는 기기/샘플 조건과 함께 후속 구현에서 정한다.

| 로컬 작업공간 구분을 보안 격리로 오해하지 않는가? 같은 프로필 사용자와 같은 origin의 스크립트가 데이터에 접근 가능 | 데이터·기술 | 개인 프로필 사용 범위와 암호화/잠금 미제공을 명시. 런타임 스크립트 출처·고정 버전·동봉/무결성 확인 방식 대조 | R1 통합 시; 공용 기기·암호화는 실제 요구에 따라 별도 검토 |
| 앱 업데이트와 DB 업그레이드가 엇갈려도 안전한가? 열린 구버전 탭이 전환을 막거나 새 데이터에 옛 코드가 접근할 수 있음 | 기술·데이터·검증 | 가상 v1/v2에서 구버전 탭 유지·차단/중단·오프라인 재실행 확인. 비호환 쓰기 금지·초안 보존·내보내기/갱신 경로 검증 | 첫 저장 실험, 이후 관련 스키마/배포 변경 때 재검증 |

발견은 `가정 / 반례 / 현재 근거 / 영향 / 담당 / 최소 실험 / 확인 시점 / 관찰 결과 / 결정·재검토 조건`으로 짧게 남긴다.
설계의 해석을 명확히 한 것, 실험 계획을 추가한 것, 실제 검증을 통과한 것을 각각 구분한다. 저장된 수행값도 사용자가 남긴 기록이며 앱이 실제 행동을 입증했다는 뜻은 아니다.
위 표는 설계 때 정한 실험 계획이다. 이후 R1에서 수행한 Chromium·저장·복원·서비스워커 검사는 [구현 기록](r1-implementation.md)에 별도로 남긴다. 실제 Apple 하드웨어·원천 앱 전달·장기 재방문 효과는 여전히 미검증이다. 보존·업그레이드 반례는 기존 V-07/13/14/15의 구현 검증에 연결한다.

F-01~07의 절 번호·필드 이름은 당시 설계의 해결 이력이며 최신 Source/sourceRefs 계약을 덮어쓰지 않는다. 개발 담당 7명은 제품 상시 AI 구성과 구분한다.
이전 정적 리뷰에서 P0 결함을 발견하지 않았다는 결과는 최신 가져오기 설계의 안전성이나 개인정보 보호·데이터 보존의 실행 검증으로 승계하지 않는다.
저장 실패/경합·quota·공유 철회·사용자 격리·복원 후 재전송 방지는 위 V 흐름의 후속 구현 검증 과제로 남긴다.
이번 방향 전환에서는 다음을 정적으로 대조했다. 실제 앱/DB·원천 서비스·iPad 사용 검증은 수행하지 않았다.

- DOM-01~09는 현장 활동 입력이 아니라 선택 자료·생각 비교·출처 연결·과거 명령 구분의 새 시나리오다. 이전 DOM 의미나 F 이력을 새 구현의 통과 증거로 사용하지 않는다.
- sourceRefs는 원문 버전/위치 전용, 공유 대상은 entityRefs로 분리했다. coverage는 link_only와 본문 미확보를 구분하고, JSON 예시의 UTF-16 범위 오류는 수정 확인했다.
- staging 임시 보관·자료만 확정·모음 적용과 취소 범위를 맞췄다. 성공 보관 원문은 후속 검토 취소로 삭제하지 않고 같은 버전을 참조해 별도 발췌할 수 있다.
- sourceVersion/stage를 포함한 영속 재개 정보, stageRevision의 적용 전 재확인, 구절·문단·명시 링크로 제한한 R1 규칙을 데이터·기술 문서에서 대조했다. 이번 교차 검토에서 제기한 계약 불일치는 수정 확인했다.
- 원천별 실제 샘플·권리/접근·iPad 파일 경로와 검색 대비 사용 가치는 미검증이며 첫 작은 실험에서 확인한다. I-01~20, V-01~27, 과거 F-01~07의 ID를 유지한다.

문서 정적 점검: 상대 링크·ID 중복·코드펜스·표·공백을 확인했다. 이 확인은 파서·저장·출처 추적·실기 검증의 통과를 뜻하지 않는다.
