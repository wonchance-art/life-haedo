# 네이버 블로그·Instagram 반복 가져오기: 다음 입력 단위

조사일 **2026-10-07 UTC / 2026-10-08 KST**. [현재 로드맵](roadmap.md)의 원천 연결 조사다. [기존 소셜 입력](../design-review/social-import.md), [이전 공식 경로 검토](open-source-review.md#네이버-블로그instagram-글과-출처-입력-개선), [제품 기준](../../PRODUCT.md)을 바탕으로 한다. 이 문서는 비교·권고 기록이다. 후속 [네이버 기존 원문 재가져오기 구현](../design-review/source-reimport.md)은 별도로 진행했으며 자동 계정 연결·운영 설정은 바꾸지 않았다.

**다음 작은 구현으로 네이버 블로그의 ‘보관한 글에 본문 추가·다시 가져오기’를 권고한다.** 이미 확인한 원천·URL·작성자 정보를 다시 입력하는 부담을 줄이고, 새로 제공한 본문만 기존 검토·새 버전 저장으로 연결한다. 현재 근거로는 특정 블로그의 최신 글 전체를 자동 수집하거나 Instagram 저장 목록 전체를 가져온다고 약속할 수 없다. 반복 입력 개선과 자동 계정 연결은 별개다.

## 이번에 새로 확인한 근거

### 네이버 검색 API: 본문 수집과 다른 용도

네이버 공식 [`naver-openapi-guide`의 블로그 검색 가이드](https://github.com/naver/naver-openapi-guide/blob/c135ae76afb59cb8c1f82d6016cb92f180558463/ko/service-apis/search/blog/blog.md)를 읽었다. 확인한 저장소 HEAD는 `c135ae76afb59cb8c1f82d6016cb92f180558463`이며, [해당 문서의 최근 변경](https://github.com/naver/naver-openapi-guide/commit/d3ae6097739aa89a0203fae0193bb7e467bd9720)은 **2024-01-25**다. 최근 저장소 변경을 API 문서의 최신 개정이나 운영 응답 검사로 대신하지 않는다.

- 문서는 **네이버 검색의 블로그 검색 결과**를 JSON/XML로 반환한다고 설명한다. `query`가 필수이며 정렬은 정확도순/날짜순이다. 특정 소유자의 전체 기록·비공개 글·수정 이력을 반환하는 계약이 아니다.
- `title`, `link`, `description`, `bloggername`, `bloggerlink`, `postdate`를 명시한다. `description`은 **내용을 요약한 패시지**이며 제목·패시지에 검색어 강조 `<b>`가 포함될 수 있다. 전체 본문·이미지 바이트 필드는 명시하지 않는다. 검색 요약을 원문 전체나 사용자의 정확한 발췌로 보관해서는 안 된다.
- 비로그인 API지만 개발자 애플리케이션 등록과 **클라이언트 ID·시크릿**이 필요하다. 최종 이용자의 블로그 로그인 없이 검색한다는 뜻이지 인증값이 없다는 뜻은 아니다. 문서상의 한도는 하루 25,000회, 결과당 `display` 최대 100, `start` 최대 1,000이다. 운영 한도·현재 계정 권한은 호출하지 않아 미확인이다.
- XML 응답에 `rss/channel`이 있어도 **검색 결과의 RSS 컨테이너**다. 이것을 특정 블로그의 새 글 구독 RSS나 전체 내보내기 지원 근거로 쓰지 않는다.
- 공식 [Node 예제](https://github.com/naver/naver-openapi-guide/blob/c135ae76afb59cb8c1f82d6016cb92f180558463/sample/nodejs/APIExamSearchBlog.js)는 서버에서 인증 헤더를 붙인다. 해도 정적 코드에 시크릿을 넣을 수 없으므로 이 API를 도입한다면 서버 경계·사용량 관리가 필요하다. 예제의 과거 의존성이나 다른 언어 예제의 TLS 검증 해제 코드는 재사용하지 않는다.

**판단:** 외부 자료 발견의 제목·링크 후보 공급에는 검토할 수 있지만, 지금의 ‘내 블로그 글을 반복해서 보관’하는 흐름을 해결하는 첫 어댑터로는 맞지 않는다.

### Instagram: 임베드와 원문 보관을 구분

Meta 공식 [`facebook/meta-embeds-for-wordpress`](https://github.com/facebook/meta-embeds-for-wordpress/blob/948c1a0807f4dca37d8c58ec729df06ecb6dfcca/README.md)를 읽었다. 공식 최신 릴리스 조회는 **[v1.2.2, 2026-06-12](https://github.com/facebook/meta-embeds-for-wordpress/releases/tag/v1.2.2)**다. README는 **GPL-2.0-or-later**, [태그 LICENSE](https://github.com/facebook/meta-embeds-for-wordpress/blob/v1.2.2/LICENSE)는 GPL v2 전문을 제공한다. [공개 보안 권고 조회](https://api.github.com/repos/facebook/meta-embeds-for-wordpress/security-advisories)는 이번 조회에서 0건이었으며 전체 의존성 감사·무취약성 보증은 아니다. 플러그인을 설치·실행하지 않았다.

- README는 Instagram 게시물·Reel·프로필 등의 **tokenless oEmbed**를 설명한다. 따라서 예전 기억만으로 모든 Instagram oEmbed가 토큰 필수라고 단정하지 않는다.
- 실제 설명은 **WordPress 서버가 임베드 HTML을 받고, 방문자 브라우저가 Instagram 외부 스크립트를 로드해 표시**하는 구조다. WordPress 5.9+·PHP 7.4+ 요구가 명시돼 있다.
- URL에서 풍부한 표시를 만드는 기능이며 계정의 새 게시물 목록·저장한 타인 글 전체·불변 평문·미디어 파일을 내 저장소로 반출하는 계약이 아니다. 외부 표시가 성공해도 해도의 본문·출처 버전·오프라인 백업을 확보했다는 뜻이 아니다.
- 이 공식 코드와 설명을 확인했을 뿐, 임베드 엔드포인트·실제 게시물 응답·브라우저 CORS·계정별 공개 범위는 호출하지 않았다. **도입하지 않고 구분의 근거로만 참고한다.**

Meta 공식 Python Business SDK의 [`IGUser.get_media`](https://github.com/facebook/facebook-python-business-sdk/blob/efd8423a2e595ea8d4c04eb824ce113f2f1d68cd/facebook_business/adobjects/iguser.py)와 [`IGMedia`](https://github.com/facebook/facebook-python-business-sdk/blob/efd8423a2e595ea8d4c04eb824ce113f2f1d68cd/facebook_business/adobjects/igmedia.py)도 읽었다. 고정한 HEAD의 날짜는 **2026-09-17**이다. 미디어 목록 요청과 `id`, `caption`, `media_type`, `media_url`, `permalink`, `timestamp`, `children` 관련 코드가 존재한다는 것까지 확인했다. **필드 정의는 임의 계정에서 그 값을 받을 권한의 증거가 아니다.** 미디어 URL만 받아도 실제 파일을 백업한 것은 아니다.

공식 [Original Coast Clothing 예제](https://github.com/fbsamples/original-coast-clothing-ig/blob/d68684226a2db3d4830e0a0771a1abd5c0dc635b/README.md)는 Business 계정·연결된 Facebook Page·개발자 계정·앱·서버를 요구하는 **메시징 예제**다. 이를 모든 현행 Instagram Login 경로의 공통 요구 조건으로 확대하지 않는다. 개인/프로페셔널 계정별 읽기 허용 범위, 현행 권한 이름·심사·토큰 수명·내 저장 목록 지원은 아직 미확인이다. SDK도 도입하지 않는다.

### 전달 경로: 붙여넣기와 웹 공유 수신은 다름

[MDN `paste` 원본](https://github.com/mdn/content/blob/main/files/en-us/web/api/element/paste_event/index.md)은 사용자가 시작한 붙여넣기에서 `clipboardData`를 읽을 수 있고, textarea의 기본 동작이 커서 위치에 내용을 넣는 것임을 설명한다. 기존 평문 입력·파일 선택은 외부 본문을 자동 요청하지 않고 받은 범위를 그대로 검토할 수 있다. 원천 앱이 복사·공유에 본문까지 넣어 주는지는 별도 사실이다.

[MDN `share_target` 원본](https://github.com/mdn/content/blob/main/files/en-us/web/progressive_web_apps/manifest/reference/share_target/index.md)은 **설치한 PWA가 OS 공유 대상이 되는 수신 기능**을 설명한다. `navigator.share()`의 보내기 기능과 다르다. [이번 브라우저 호환 데이터](https://github.com/mdn/browser-compat-data/blob/ef3eb098c3fea5291e31dc40ed9f8e47de2978bd/manifests/webapp/share_target.json)는 Chrome/Android 일부 지원과 Safari 미지원, Safari iOS의 해당 결과 상속을 기록한다. 이 데이터에 사용자 iPad Chrome의 실제 실행 결과는 없다. **iPad·iPhone 공통 기본 입구로 Web Share Target을 확정하지 않는다.**

공유 수신을 구현하는 경우에도 링크·제목·본문·파일이 실제로 각각 왔는지 확인해야 한다. URL만 받은 공유를 본문 확보로 표시하지 않는다. 문서는 POST와 서비스워커 처리를 설명하지만 현재 지원하지 않는 기기에 지원을 추가해 주는 방법은 아니다. 로그인 복귀·취소·중복 전달·임시 저장의 수명도 추가 검증이 필요하다.

[MDN CORS 원본](https://github.com/mdn/content/blob/main/files/en-us/web/http/guides/cors/index.md)을 재확인했다. 공개 URL을 브라우저에서 열 수 있다는 사실과 해도 origin의 스크립트가 응답을 읽을 수 있다는 사실은 다르다. Readability·서비스워커·RSS 파서가 서버의 CORS 권한을 대신하지 않는다. 이번에는 실제 네이버/Instagram 응답 헤더를 검사하지 않았다.

| --- | --- | --- |
| 현재 수동 전달 | 앱의 `Source.id`를 유지하고 `SourceVersion`을 고정한다. 원형 URL·작성자·포함 범위·본문 해시를 비교하되, 같은 URL이나 본문이라는 이유만으로 자동 병합하지 않음 | 기존 staging의 미적용 초안·명시 저장·재개를 사용. 실패 시 입력을 유지하고 이미 적용한 영수증을 다시 적용하지 않음 |

## 권고하는 첫 구현 계약

### 네이버 블로그 기존 글에서 새 본문 받기

**사용 장면:** 처음에는 블로그 링크만 보관했거나, 나중에 같은 글의 더 넓은 본문/수정된 내용을 복사해 왔다. 현재도 일반 가져오기로 새 버전을 보관할 수 있다. 다만 기존 정보를 그대로 유지하려면 원천·URL·제목·작성자 정보를 다시 제공하고, 검토에서 같은 자료임을 선택해야 한다. 이를 **보관한 원문 → 본문 추가·다시 가져오기 → 비교 → 저장 결과 열기**로 줄인다. 제목·작성자 입력이 필수라는 뜻은 아니다. Instagram에도 적용 가능한 기반이지만 첫 UX·샘플 검증 원천은 네이버 한 곳으로 제한한다.

1. 기존 원문 화면에서 사용자가 선택한 `Source.id`와 기준 `SourceVersion.id`로 시작한다. 원문 URL·원천·제목·확인한 작성자 관계를 새 검토 초안에 제안한다. 원문을 바꾸거나 새 버전을 만들기 전에 입력 화면을 연다.
2. 새 본문을 붙여넣거나 현재 지원하는 UTF-8 TXT/MD를 선택한다. 새로 받은 본문의 범위는 다시 확인한다. 이전 `full_text`나 `link_only`를 새 본문에 기계적으로 승계하지 않는다. 없던 작성자·날짜·이미지·댓글을 추정하지 않는다.
3. 원문 URL 원형을 유지하고 `existingSourceId`로 기존 자료 연결 의도를 전달한다. 다른 URL을 입력했다면 기존 strict identity 검사를 우회하지 않고 별개 자료로 보관하거나 기존 입력으로 돌아간다. 모바일/데스크톱/단축 URL을 새 정규화 규칙으로 자동 합치지 않는다.
4. 기존 `Core.prepareImport`의 `exact_duplicate`/`new_revision`과 현재 검토 UI를 재사용한다. 동일한 본문·범위·출처라면 같은 버전 재사용, 달라졌다면 새 불변 버전 추가를 명시적으로 적용한다. 기존 발췌·묶음·내 페이지·공개 사본의 참조는 옛 버전에 남긴다.
5. 저장 후 실제 적용한 원문 버전으로 돌아간다. 이전 버전과 기준 출처를 다시 열 수 있어야 한다. 취소·두 탭 경합·용량/계정 오류에서는 새 입력을 유지하고, 중단한 검토는 기존 staging에서 재개한다.

### 이미 있는 기능과 추가할 진입점

아래 함수는 이번에 현재 코드를 직접 대조했다. **새 버전 저장이나 중복 판정 기능을 다시 만들자는 제안이 아니다.**

| 현재 코드 | 이미 가능한 일 | 이번 권고에서 필요한 차이 |
| --- | --- | --- |
| [`ui.js`](../../assets/life/ui.js)의 `renderImport()` → `prepareStage()` → `renderPrepared()` | 일반 입력을 초안으로 보관하고, 겹침 후보에 ‘같은 자료로 확인 · 버전 비교’를 선택하면 `existingSourceId`를 넣어 다시 검토함 | 보관한 블로그 글에서 출발할 때 기존 메타데이터와 사용자가 고른 원문 ID를 검토 초안에 제안. 기존 정보를 다시 찾고 입력하는 작업을 줄임 |
| `ui.js`의 `renderPrepared()` 내부 `apply()`와 [`core.js`](../../assets/life/core.js)의 `prepareImport()`·`buildImportChanges()` | 적용 직전 재검증, 동일 버전 재사용, 새 버전 추가, 옛 버전 불변성 확인. 자료만 보관하면 실제 저장한 원문 버전으로 복귀 | 그대로 재사용. 중복 판정·버전 생성·저장 후 복귀를 별도 엔진이나 새 기능으로 추가하지 않음 |
| `ui.js`의 `renderSource()` 및 [`writing-ui.js`](../../assets/life/writing-ui.js)의 `open()` | 해도에서 직접 쓴 글의 최신 버전에 ‘내 글 수정’ 제공. 가져온 글은 작성자 관계가 `self`여도 직접 글쓰기 편집 대상이 아님 | 블로그 원문에는 별도의 ‘본문 추가·다시 가져오기’ 진입점을 제공. 원본 SNS를 수정하거나 직접 쓴 글로 전환하지 않음 |
| `ui.js`의 `persistDrafts()` | 읽는 중인 발췌·주제·메모를 보존할 때 기존 원문 ID·메타데이터를 포함한 검토 초안을 만듦 | 초안 구성·보존 패턴을 참고하되, 이 함수는 새 외부 본문을 받는 사용자 진입점이 아님. 읽기 메모 보존을 중복 구현하지 않음 |

**연결만 넣으면 끝나는 수정은 아니다.** 현재 `renderImport()`의 입력 이벤트는 본문·제목 변경에도 `existingSourceId`를 지운다. 따라서 새 진입점이 초안을 미리 채워도 사용자가 본문을 붙이면 일반 겹침 확인으로 돌아간다. 작은 구현 안에서 원천·URL이 같은 동안 명시적으로 고른 연결 의도를 유지하고, 정체성을 바꾸는 입력에는 연결 재확인을 요구하도록 이 경계를 다뤄야 한다. `prepareImport()`의 원천·URL·파일 키 검사와 적용 직전 재검증은 유지한다. 제목·범위·작성자 변경이 실제로 새 버전으로 반영되는지도 기존 경로로 검사한다.

줄이는 것은 **알고 있는 출처 정보의 재입력과 뒤늦은 동일 자료 선택**이다. 원천 앱에서 본문을 복사하는 일, 새 본문의 범위 확인, 내용 검토, 명시 저장은 남는다. 새 게시물 여러 개의 수집·분류 시간까지 줄였다고 평가하지 않는다. 새 외부 API·스크래퍼·스키마·파서 도입은 이 단위에 필요하지 않으며, UI 수정은 현재 진행 중인 화면 담당과 분리해 조정한다.

### 완료 판단과 선택을 바꿀 조건

- 링크만 보관 → 일부 본문 제공 → 같은 본문 재시도 → 더 넓은 본문 새 버전의 네 경우에서 원문 수·버전 수·정확한 발췌 위치·저장 결과가 맞아야 한다. 가져오기 취소만으로 버전이 늘어나면 실패다.
- 서로 다른 글의 같은 구절, 같은 글의 다른 URL 표현, 이전 버전에서 시작한 검토, 작성자/날짜 미상, 일부 본문, CRLF·emoji를 포함한다. 제목·출처 입력을 다시 하게 하는 횟수와 검토 단계 수를 기존 흐름과 비교한다.
- JSON 사본 복원·원문 선택 동기화·계정 전환에서도 기존 참조를 보존하고, 수신을 SNS 쓰기·공개 사본 갱신으로 연결하지 않는다.
- **실제 Mac·iPad·iPhone에서 본문을 복사해 전달하는 비용은 미검증이다.** 작은 브라우저 구현 검사는 실기 성공을 뜻하지 않는다. 실제 전달이 막히거나 주된 불편이 ‘여러 새 글을 한 번에 가져오기’라면 이 개선의 우선순위를 내리고 공식 내보내기/RSS의 익명 파일 한 건을 먼저 비교한다.
- RSS/계정 API 도입 판단은 같은 글의 재전달·수정·본문 누락·페이지 경계·중지 후 재개를 확인할 수 있는 공식 계약과 작은 샘플이 확보됐을 때 한다. 현재 정적 앱의 원문 검토로 충분하면 새 연결 서비스를 만들지 않는다.

## 이번 결과와 남은 범위

이번에 한 일은 공식 공개 문서·코드 읽기, 현재 입력/버전 코드 대조와 이 문서 작성이다. **새 라이브러리 선정·도입, 계정/토큰 발급, 서비스 API 실행, RSS 수신, 실제 반출 파일 해석, 원격 게시물/개인 기록 수집, Apple 실기 검증은 하지 않았다.** 이전 2026-10-05의 브라우저 검사 수치를 이번 조사 결과로 합산하지 않는다. Meta 직접 도움말과 네이버 반출/RSS의 미확인은 남아 있지만 현재 UI 품질 작업을 막지 않는다.
