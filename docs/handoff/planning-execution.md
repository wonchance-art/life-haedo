# 실행 인계: 계획의 계정 연속성과 실행·회고 연결

2026-10-29 KST. 확인한 배포 기준은 main `ab6aef594a2d6d0cabbaf89864e7994ce22a6fec`(PR139)다. 이 문서는 **다음 실행 세션의 설계·작업 명세**이며 아래 후속 기능의 구현·설치·출시 완료 기록이 아니다. 시작할 때 최신 main, 관련 PR, 다른 세션의 연간 계획 작업을 다시 대조하고 이미 반영된 기능은 재구현하지 않는다.

## 1. 사용자 결과와 범위

**A에서 연간·월 계획 작성 → B에서 같은 계획을 이어 열기 → 선택한 월 항목/자료를 기존 목표·습관과 연결 → 실제 수행 확인 → 기간 회고 → 다음 계획 조정 → A에서 반영 확인**을 하나의 목표로 삼는다.

계획만 쓰고 끝내기, 기존 목표·습관만 사용하기도 계속 지원한다. 자료나 월 계획을 읽었다고 목표·습관을 자동 생성하지 않는다. 이번 인계의 기본 사용 장면은 ‘독서/외국어 학습 계획의 한 월 항목을 기존 목표 또는 습관에 연결하고, 실제 수행을 확인해 다음 달 계획을 조정’하는 흐름이다. 검수에는 익명 자료를 사용한다.

범위는 연간 계획의 계정 보관, 선택 연결, 수행 사실을 구분한 회고, 실패/충돌/파일 복구다. 기존 다섯 메뉴 재개편·범용 캘린더·자동 일정 배정·AI 계획 생성·외부 캘린더 쓰기·실제 사용자 일정 이관은 포함하지 않는다.

## 3. 구현 전에 확정할 계약과 권장 선택

아래는 권장 설계다. 새 테이블명·RPC명·파일 스키마·메서드가 이미 존재한다고 가정하지 않는다. 실행 세션이 최신 코드와 작은 격리 검증으로 확정하고, 변경 이유를 인계/PR에 기록한다. 통상적인 구현 선택 때문에 사용자에게 재승인을 반복 요청하지 않는다.

### 3.1 소유 범위와 계정 보관

권장 기본은 **연간 계획의 기존 account + workspace 정체성을 유지한 채 같은 공간의 계획을 다른 기기로 전달**하는 것이다. 계정 전체의 모든 계획을 하나로 합치면 동일 연도·동일 날짜의 독립 계획이 섞일 수 있다. 한 계정의 기본 자료공간을 열면 그 공간의 계획이 이어지는 경험을 제공한다. 계정 공통 계획이 별도로 필요하면 공간별 사본을 덮지 않는 명시적 승격/이동 설계로 다룬다.

목표·습관은 현재 account 범위이므로 연결은 ‘계획의 workspace/항목 → 같은 owner의 goal/habit ID’를 명시한다. 다른 계정의 항목, 다른 프로젝트의 같은 ID, 삭제된 공간을 제목으로 추정해 연결하지 않는다. 같은 목표에 여러 계획 항목이 연결될 수 있지만 연결 건수를 서로 다른 목표의 수행 실적으로 중복 합산하지 않는다.

개인 생년월일·계획은 비공개 계획 도메인에만 포함한다. 원문 Core·LibraryMeta의 고정 형식·뉴스 설정·공개 사본에 끼워 넣지 않는다. 공개 권한은 계정 보관과 별개다.

### 3.2 전송과 충돌

독립 계획 모델 + 로컬 CAS/영속 outbox + 원격 비교 교환 + 실제 서버 반영 확인을 기본으로 설계한다. 기존 adapter를 재사용하되 먼저 CompositionSync의 source dependency가 정말 필요한지 확인한다. 본문 참조가 없는 계획을 열기 위해 전체 원문 동기화를 강제하는 것은 피한다. 원문 참조가 있는 연결에는 필요한 정확 판의 도착 조건을 별도로 둔다.

| 상황 | 요구 결과 |
| --- | --- |
| 로컬 빈 계획, 서버 계획 있음 | 서버 계획을 먼저 수신. 빈 기본값으로 덮지 않음 |
| 기존 로컬 계획, 서버 없음 | 현재 계정/공간 소유 확인 후 이관. 동일 작업의 재시도로 중복 계획을 만들지 않음 |
| 로컬·서버가 모두 존재하고 다름 | 두 사본 보존 및 명시 해결. 기기 시각의 최신순으로 자동 덮지 않음 |
| 서버는 저장했으나 응답 유실 | 같은 operation의 결과를 확인해 중복 전송·중복 행 없이 완료 |
| 입력 중 새 원격 판 수신 | 입력/커서 유지, 비교 또는 안전한 재적용. 다른 기기의 판으로 화면을 즉시 교체하지 않음 |
| 계정·공간 전환 후 늦은 응답 | 원래 요청의 owner/space/generation 재확인, 새 범위에 쓰기·성공 표시 0 |
| 삭제 후 옛 기기 재접속 | 삭제 revision/tombstone과 미확인 변경을 대조. 오래된 전체 문서 업로드로 조용히 부활시키지 않음 |

로컬 저장과 원격 완료는 다른 상태다. UI는 공통 보관 상태를 재사용하되 계획의 실제 ACK를 근거로 표시한다. 큰 계획/원문 수신 때문에 기존 첫 화면 표시·오프라인 복구를 지연시키지 않는다.

### 3.3 날짜와 연결 정체성

- 기존 월 항목의 `date`는 화면에서 추가한 구간의 시작일이다. 사용자가 정한 실제 마감일이라고 추정하지 않는다. 연결 시 월 방향과 목표 마감일을 구분하고, 목표일은 비워 두거나 사용자가 직접 고른다.
- 생일/연도 기준 전환은 기존 `id/date/text`를 바꾸지 않는 투영이다. 2월29일·월말·연말·1900/2199 경계를 유지한다.
- 첫 완주 대상은 안정 ID가 있는 월 항목이다. 연간 행은 현재 `year`만 있으므로 삭제 후 같은 연도 재생성까지 같은 실체로 취급하지 않는다. 연간 문장 자체의 연결을 추가하려면 v2 안정 ID/세대 또는 명시 스냅샷 계약을 먼저 정한다.
- 정확 원문 연결은 source ID뿐 아니라 version ID·필요한 구절 범위/해시를 보존한다. 원문 제목 변경·새 판 도착 시 연결을 최신 판으로 교체하지 않는다.
- 목표/습관은 현재의 가변 항목 ID로 연결하되, 저장한 회고에는 당시 확인한 값과 확인 시점을 남긴다. 목표명이 바뀌어도 기존 회고 문장과 당시 사실을 소급 수정하지 않는다.

### 3.4 연결 수명주기와 중간 실패

연결은 계획이나 목표 자체와 구분되는 해제 가능한 관계로 둔다. 기존 목표/습관을 선택하는 경로를 먼저 제공한다. 새 목표 생성도 제공한다면 ‘대상 생성 → 연결 보관’이 두 저장 체계를 지나므로, 중간 실패 시 실제 생성된 대상 ID와 미완료 연결 의도를 영속 보관해 같은 대상에 재시도해야 한다. 두 HTTP 쓰기가 하나의 원자 작업이라고 표시하지 않는다.

계획 항목 삭제/복원, 목표·습관 tombstone, 원문 미도착은 각각 구분한다. 연결을 해제해도 원문·계획·목표·수행 체크를 삭제하지 않는다. 대상이 없으면 미확인/삭제 상태와 정확 복구 경로를 제공하며 같은 제목의 다른 항목에 자동 연결하지 않는다. 다른 공간의 목표 사용을 이유로 그 공간의 전체 계획·원문을 함께 노출하지 않는다.

## 4. 실행·회고의 사실 범위

현재 목표의 진행률은 특정 날짜의 수행 이력이 아니다. `updated_at`을 목표 완료일로 사용하지 않는다. 습관의 체크 날짜는 실제 저장된 날짜별 체크지만, 과거 계획의 의도나 삭제 이전의 수정 이력까지 증명하지는 않는다.

첫 회고는 사용자가 선택한 기간·연결된 항목을 대상으로 ‘계획 내용 / 확인 가능한 수행 / 직접 쓴 판단’을 나눠 보여 준다. 현재 목표 상태는 **현재 확인한 상태**로, 날짜가 있는 습관 체크는 해당 기간의 체크로, 과거 수행일이 없는 목표는 **수행일 미확인**으로 표시한다. 기간 실적에 목표 진행 변화를 포함하려면 이후의 명시 수행 기록/변경 사건을 보관하는 추가 모델과 이관 기준이 필요하다. 기존 과거 사실을 만들어 채우지 않는다.

읽기 전용 회고 미리보기는 원본을 수정하지 않는다. 사용자가 회고를 저장하면 선택한 사실·정확 원문 참조·수행 범위·확인 시점·내 판단을 저장하고, 이후 원본 변경으로 저장한 회고가 바뀌지 않도록 한다. 자료 기반 Reflection의 작성연도 분류에 수행 날짜를 섞지 않고 별도 입력 투영을 연결한다.

## 5. 파일과 이관

현재 `haedo-annual-plan` v1은 계획 내용/표시 설정만 담으며 account/workspace/revision을 제외한다. 기존 파일은 계속 검토·복원할 수 있어야 한다. 현재 백업 함수의 엄격한 키와 2 MiB 한도를 깨지 않는다.

연결·실적을 포함한 완전 왕복에는 새로운 버전 또는 별도 전용 외곽 형식이 필요하다. 실행 전에 둘을 비교해 하나를 고르고 포함 범위를 명시한다. ‘기존 v1 계획 파일’과 ‘연결된 결과까지 포함하는 파일’을 같은 복구 수준으로 안내하지 않는다. 새 형식은 선택한 계획/연결/필요한 대상 사본·회고만 포함하고, 원문 포함 여부와 개인 정보 범위를 생성 전에 보여 준다.

복원은 새 사본 ID와 명시 계정 범위를 사용하고 관계를 새 ID로 재매핑한다. 기존 목표를 이름으로 병합하거나 가져온 완료 기록을 사용자 원본에 자동 합치지 않는다. 누락된 정확 원문은 미확보로 유지한다. 새 파일이 기존 연표·목표·습관 전체 백업을 대체한다고 표시하지 않는다. 기존 로컬 계획의 이관은 먼저 읽기 전용 스냅샷/복구 사본을 확보하고 전송 완료 뒤에도 명시 보존 정책에 따라 유지한다.

| P0 계약 고정 | 최신 구현/미출시 작업 대조, 소유 범위·날짜 의미·이관·파일 형식·불변조건 결정표 | 총괄: 이 명세·설계/로드맵 |
| P1 계정 연속성 | owner/workspace·CAS·영속 작업·서버 수신/충돌/삭제/이관. 기존 계획 UI와 A/B 왕복 | 저장 담당: 연간 저장 API와 새 동기화/원격 모듈, 필요한 서버 migration/SQL 검수 |
| P2 선택 연결 | 안정 월항목↔기존 goal/habit, 정확 원문 근거, 수명주기·중간 실패 재개 | 모델 담당: 순수 관계 검증/이관/전용 파일. 플랫폼 담당: 기존 목표/습관의 안전한 선택·반환 경계 |
| P3 실행·회고 | 현재 상태와 실제 날짜를 구분한 기간 투영, 명시 저장·근거 왕복 | 회고 담당: 순수 투영·기존 Reflection 연결. UI 담당: 연간/목표/습관 문맥 조작·복귀 |
| P4 통합/출시 판정 | 전체 여정·기존 날짜/파일/계정/읽기 보존·시각·정확 배포 결과 | 독립 QA/리뷰, 총괄: 공통 ui.js/storage.js·셸/allowlist·CI·문서·출시 |

공통 `storage.js`·`ui.js`·`platform-store.js`를 여러 담당자가 동시에 편집하지 않는다. 새 API/이벤트/오류 계약을 먼저 고정하고 독립 모델·저장·UI·검수만 병렬로 진행한다. P1을 끝낸 뒤 매 화면마다 사용자에게 ‘다음’을 요구하지 않고 같은 승인 목표 안의 P2–P4를 이어간다. 미정 서버 계약을 SQL 파일 존재만으로 설치 완료라고 보고하지 않는다.

서버 구현이 필요할 때는 설치된 Supabase 환경·공식 변경 사항·현재 권한을 실행 시점에 확인한다. 기존 플랫폼/원문/구성 RPC의 정의와 권한을 보존하고, 새 계획 API의 owner 검사·RLS·동시 CAS·operation 재시도·다른 owner/익명 거절을 격리 DB에서 검증한다. 실제 사용자 계정/개인 계획을 시험 데이터로 쓰지 않는다.

## 7. 검수와 완료 관문

기존 검사부터 재사용한다. 아래 명령은 현행 회귀의 시작점이며 새 계정/연결/실적 경계를 검증하는 새 의미 있는 사례를 추가해야 한다. 이 인계 작성 중 검사를 실행한 것은 아니다.

```sh
npm run check
node --test tests/life-annual-plan.test.cjs tests/life-annual-plan-storage.test.cjs tests/platform-store.test.cjs tests/platform.test.cjs tests/life-reflection.test.cjs
```

실제 로컬 서버와 동봉 SDK/격리 IndexedDB에서는 `tests/life-annual-plan-browser.cjs`, `tests/feature-flow-browser.cjs`, 필요한 `tests/purpose-workflow-browser.cjs`·회고 브라우저 검사를 사용한다. 각 runner의 `BASE_URL`/출력 경로 지원을 확인하고 기존 실패 증거를 덮지 않는다. 기존 테스트의 단언·제한시간을 느슨하게 해 통과시키지 않는다.

| 관문 | 반드시 확인할 결과 |
| --- | --- |
| 날짜/표시 보존 | 생일·연도 기준, 윤년·월말·범위 끝에서 기존 ID/date/text 유지. 월 방향의 날짜가 자동 마감일로 바뀌지 않음 |
| A/B 완주 | 독립 A에서 계획 저장→실제 서버 반영→B 같은 계획/ID 수신→연결·체크/회고→A 반영. 단순 localStorage 복사로 기기 이동을 흉내 내지 않음 |
| 이관/충돌 | 최초 빈 서버·빈 로컬·양쪽 기존 자료·동시 변경·유실 ACK·구버전 재전송에서 양쪽 내용과 삭제 의미 보존 |
| 원자성/늦은 응답 | 실제 IDB 중단, 원격 저장 실패, 연결 중 목표 생성만 성공, 계정/공간/화면 전환. 부분 성공 표시·다른 계정 쓰기·중복 목표 0 |
| 입력/탐색 | 한글 조합 Enter·Shift+Enter·연속 입력·저장 실패 이동·새 원격판 도착에서 입력/커서/초점 유지. 기존 tools 주소·로그인 복귀 유지 |
| 수행/회고 | 목표 현재 진행률을 과거 실적으로 추정하지 않음. 습관 기간 체크·중복 연결·삭제·실행일 미확인 구분. 저장 회고가 후속 수정으로 변하지 않음 |
| 연결/파일 | 명시 연결→원문/목표 왕복→해제→삭제/복원→새 사본 파일 복원. 정확 판·항목 재매핑, 기존 원본/타계정/미선택 자료 보존 |
| 화면 | 실제 내용으로 1440/820/390px·44px 조작·16px 입력·키보드/터치 도달·표 내부 스크롤·문서 넘침 확인. 설명·상시 패널 증식 억제 |
| 출시 | 최종 변경 범위의 회귀, 이전 실제 PWA→새 캐시·기존 계획 보존, 정확 PR/main CI·필요한 설치·공개 산출물 확인. 실제 Apple 기기·사용 효용은 별도 기록 |

핵심 여정이 미통과하거나 실제 계획/근거가 손실되면 완료·출시로 판정하지 않는다. 첫 실패와 수정 근거를 보존하고 다음 실행자가 원인을 재현할 수 있게 로그·소스 SHA·검증 범위를 남긴다.

## 8. 실행 세션의 첫 산출물

1. 최신 코드/관련 작업과 이 명세의 차이표: 기존 완료 기능, 충돌 파일, 이번에 필요한 경계만 확정한다.
2. P0 결정표: 계획 소유 범위, 로컬 이관, CompositionSync 재사용 적합성, 월항목/연간행 정체성, 목표 실적 사실 범위, 파일 포함/복원 계약.
3. 변경·검수 지도: 위 P1–P4의 실제 파일 책임과 의존성, 격리 검수 명령, 되돌릴 수 있는 이전/새 형식 공존 방식.

그 뒤 목표 여정을 구현·독립 검수하고 결과를 [최신 로드맵](../life-tools-design/roadmap.md)에 반영한다. 기능 수나 검사 개수 대신 같은 계획의 재입력·재선택 감소, 기기 간 작업 재개, 실패 후 복구, 실제 수행 사실과 근거의 보존으로 평가한다.
