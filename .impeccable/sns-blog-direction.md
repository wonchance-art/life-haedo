# SNS형 블로그 전면 개편 계약

2026-10-17 KST. 사용자가 UX·UI 전체를 트렌디하고 깔끔한 SNS형 블로그로 바꾸도록 지시했다. 기존 메인의 문구·우선순위 조정 범위를 넘어 공통 시각 체계와 사용 화면을 교체한다. 사용자 지시가 이전 라벤더·민트·떠 있는 탐색띠를 보존하던 지침보다 우선한다. 설치된 Impeccable은 지침 배포본이며 엔진·컨텍스트 로딩·컨셉 추첨·자동 검사는 실행하지 않는다. 명시된 SNS 방향을 코드로 구현한다.

## 제품의 기제와 사용 장면

내 생각과 사진을 글로 쓰고, 다시 읽고 고치며, 원문과 취향 자료를 비공개로 연결한다. 사용자는 Mac·iPad·iPhone에서 짧게 기록하거나 긴 글을 읽는다. 첫 화면에서 실제 글과 작성 행동을 발견해야 한다. 피드와 프로필의 익숙한 SNS 구성을 제품의 명확성을 위해 적용한다.

## 첫 화면과 이동

- 로그인 전: 블로그 목적·시작 행동과 명시적으로 가상 표시한 글 예시. 인증 전 개인 데이터 조회 금지.
- 개인 홈: 실제 블로그 제목·소개·이니셜 → 짧은 작성 진입 → 실제 글의 작성 맥락·본문·사진을 가진 피드 → 자료실·도구. 첫 화면을 설명문·기능 타일·큰 수치로 채우지 않는다.
- 프로필: 제목·소개·실제 개인 글 피드·명시적 프로필 편집. 공개 사본과 비공개 글의 상태를 구분한다.
- 작성: 제목·본문·사진을 중심에 두고 닫기·비공개 저장·필요한 서식을 일관된 곳에 배치한다. 기존 초안·IME·실패 복구를 유지한다.
- 읽기: 본문과 사진이 주체이며 원래 목록·정확한 버전·초점·읽기 위치로 복귀한다.
- 자료실·검색·컬렉션·도구·설정·로그인·연표 목록도 같은 활자·조작·구분선·상태 언어를 사용한다. 연표 그래프의 데이터 의미는 바꾸지 않는다.

## 토큰과 구조

- 바탕 `#f7f7f8`, 읽기 표면 `#ffffff`, 본문 `#18181b`, 보조 `#66666f`, 구분선 `#ececee`.
- 주요 행동은 차콜 `#18181b`와 흰 글자. 링크·키보드 초점 `#3156d3`. 오류는 기존 의미를 유지하는 짙은 빨강. 라벤더·민트색을 구조의 기본 배경으로 쓰지 않는다.
- 기존 한국어 산세리프를 유지한다. 본문 16px 이상, 긴 글 17–19px, 입력 16px 이상. 명확한 제목·본문·메타 위계와 한글 줄바꿈을 제공한다.
- 글 피드·읽기 본문은 680–720px 중심 열. 일반 앱은 최대 800px 안에서 도구에 필요한 폭을 사용한다. 글 항목은 얇은 구분선과 여백으로 나누며 상시 큰 카드·색 면을 쌓지 않는다.
- 데스크톱 공통 예약 폭 `--haedo-nav-width:216px`, 761–1100px `88px`, 760px 이하는 `0px`. 데스크톱 탐색은 아이콘+라벨, 모바일은 화면 끝에 붙는 하단 탐색이며 떠 있는 둥근 도크를 폐기한다. 주요 조작 최소 44px.
- 표준 제어 반경 12px, 작은 주요 버튼은 pill 허용, 미디어 반경 16px. 그림자는 팝업 등 깊이를 구별해야 할 때만 사용한다.

## 상호작용과 자산

의미 있는 반응은 150–200ms의 선택·누름·저장 상태다. 본문 등장 애니메이션은 없다. reduced-motion을 지원한다. 피드 → 글 읽기 → 원래 항목으로 돌아오기와 작성 → 명시 저장 → 피드 재열기를 실제 동작으로 완결한다.

이미지는 실제 보관한 사진만 조회하며 썸네일 URL은 화면 이탈·계정 전환·재렌더 시 폐기한다. 아바타는 실제 제목의 이니셜을 사용한다. 가짜 좋아요·댓글·팔로워·방문 수·동작 없는 아이콘은 넣지 않는다. 테스트 자료는 익명 가상 자료로 표시한다.

## 보존과 판단 기준

새 글·사진은 현재 브라우저 비공개 저장 범위이며 기존 선택 내용의 공개 사본과 같지 않다. 공개된 블로그 플랫폼·타인 추천 피드가 완성됐다고 표시하지 않는다. 저장 구조·원문·불변 버전·계정/공간·원본 사진·ZIP/JSON·명시 공개 경계는 유지한다.

동일한 익명 자료로 기존/새 화면의 로그인 전·피드·프로필·읽기·작성·자료실·도구·설정을 1440/820/390px에서 비교한다. 기능 검사와 실제 렌더 품질을 구분한다. 통합 첫 렌더를 묶어 확인하고 문제를 한 번에 수정한 뒤 최종 확인한다. 마지막은 새 대화 문맥을 상속하지 않은 독립 리뷰어가 요청·이 계약·실제 캡처를 기준으로 판단한다. 디자인 문서는 실제 완성된 토큰과 구현 범위를 기록한다.
